시각·상호작용 기준 · SPEC 후 구체화

초록 추가·교체 제안빨강 삭제·교체 대상CLAUDE: 파란 상자 · CODEX: 보라 상자

검토자 필터는 코멘트·부록만 바꿉니다. ‘인라인 제안 미리보기’는 코멘트의 대안까지 합친 최종본이 아닙니다. 보기 전환은 MD 수정·수락·승인을 하지 않습니다.

문서 역할: 기능을 사람이 어떻게 보고 조작하는지 정의한다. 제품 범위는 PRD.md, 동작의 세부 의미는 SPEC.md, 실제 기술과 구현 작업은 IMPLEMENTATION_PLAN.md에서 정한다.제품 범위는 docs/PRD.md, 동작의 세부 의미는 SPEC(docs/specs/), 실제 기술과 구현 작업은 PLAN(docs/plans/PLAN.md)에서 정한다.
적용 상태: 시각 원칙과 기본 상호작용 기준. SPEC의 기능·상태가 구체화되면 화면별 상태·문구·행동을 대조해 확정한다. 완성된 기능 명세나 구현 완료 화면이 아니다.

claudeR-01중간 확정된 폴더 구조에는 SPEC.md·IMPLEMENTATION_PLAN.md 파일이 없고(docs/specs/ 세트, docs/plans/PLAN.md) PRD도 docs/ 아래로 이동함. 문서 첫 줄의 역할 선언이 없는 파일명을 가리키면 에이전트가 파일을 못 찾거나 루트에 새로 만들 수 있으므로 실제 경로로 맞출 것.

codexR-17중간 동의 · Claude R-01 재검토. 실제 경로로 바꾸는 제안은 타당하다. SPEC은 docs/specs/ 묶음, 마스터 구현계획은 docs/plans/PLAN.md라는 점을 문서와 복사용 요청문에서 동일하게 사용해야 한다. 현재는 사용자 검토를 위해 원문과 제안을 함께 유지한다.

사용자는 코드를 해독하지 않고 대상을 가리키고 그리며, 실제 중간 결과를 보면서 작업의 방향을 바꿀 수 있어야 한다.

01 / 화면이 답해야 하는 질문

어느 프로젝트·호스트·문서·대안을 보고 있는가? 무엇을 바꾸고 무엇을 유지하는가? 지금 보이는 것은 원본인가 후보인가? 새 지시는 접수만 되었는가 실제 반영되었는가? 결과가 적용·저장되었는가? 지금 어떤 행동을 할 수 있는가?

모델·도면·스케치·데이터가 판단의 중심이다. 채팅은 유일한 입력 수단이 아니고, 터미널은 기본 조작 경로가 아니다. AI의 긴 독백이나 가상의 진행률보다 실제 대상·변경·조건·마지막 결과를 보여준다.

화면을 예쁘게 만드는 일과 기능을 지원하는 일은 다르다. 연결하지 않은 호스트, 생성하지 않은 후보, 동작하지 않는 전송을 완료처럼 표시하지 않는다.

02 / 시각 언어와 토큰

시각 기준은 제공된 임대료_공개공지_분석.html의 흰 바탕·얇은 경계·큰 한국어 제목·작은 영문 표제·절제된 코랄 강조다. 자료의 분석 수치·법규·사이트 내용은 제품 데이터로 가져오지 않는다. 글꼴 파일을 동봉하지 않고 운영체제에서 사용할 수 있는 글꼴로 대체한다.

claudeR-02중간 시각 기준의 근거 파일이 저장소에 없어 SPEC·목업 작성자가 '흰 바탕·얇은 경계·큰 한국어 제목'의 실제 모습을 확인할 수 없다. 이 파일은 사이트·법규 분석 자료라 PRD §17의 '공유 파일에 비밀·개인 자료' 위험에 해당하므로 저장소에 넣지 말고(.gitignore가 docs/assets/reference/*.html을 제외함), §02 토큰과 세 HTML 스냅샷(또는 가려낸 캡처 한 장)을 시각 기준의 기록으로 선언하고 이 파일 의존을 지우는 쪽을 권한다. 어느 쪽인지 소유자 결정.

codexR-18중간 부분 동의 · Claude R-02 재검토. 저장소에 없는 참조 파일에 의존하지 않게 해야 한다. 다만 HTML은 MD의 생성물이므로 별도의 동등한 토큰 원본으로 선언해서는 안 된다. 이 절에 스타일 의도·토큰·용도를 기록하고, 필요하다면 비공개 내용을 제거한 캡처를 보조 자료로 둔다. 원래 분석 파일이 없다는 이유만으로 목업을 막을 필요는 없다.

CSS
--ink: #292c2d;
--muted: #777e80;
--line: #e1e3e1;
--soft: #f5f5f1;
--coral: #d97660;
--paper: #ffffff;
--font: "Pretendard", "Noto Sans KR", "Malgun Gothic", Arial, sans-serif;

claudeR-03중간 MD는 #777e80인데 Design.html·PRD.html·DEVELOPMENT_GUIDE.html의 :root는 모두 #626b6e라 토큰 원본이 둘이다. #777e80은 흰 바탕 4.1:1로 WCAG AA 본문 기준(4.5:1) 미달이고 #626b6e는 5.5:1로 통과한다. 렌더러가 MD 토큰으로 HTML을 다시 만들 것이므로 MD를 #626b6e로 맞추고, 이 CSS 블록이 유일한 토큰 원본임을 한 문장으로 명시할 것. 제안 문구: 「--muted: #626b6e;」

codexR-19중간 동의 · Claude R-03 재검토. 흰 배경 기준 계산은 맞다. #777e80은 약 4.13:1, #626b6e는 약 5.46:1이다. 작은 보조 텍스트에도 사용할 기본 muted를 #626b6e로 바꾸는 안에 동의한다. 실제 제품의 각 배경/상태에서는 다시 검증해야 하며, 이 토큰 변경 제안이 현행 HTML 전체의 접근성 통과를 뜻하지는 않는다.

이 토큰은 시각적 출발점이다. muted 색은 작은 필수 텍스트에 무조건 쓰지 않고 배경과 크기에 따라 읽기 가능한 대비를 확인한다. 코랄은 현재 위치·주요 행동·강조에 제한적으로 쓰며, 오류·선택·진행을 같은 색 하나로 구분하지 않는다.

claudeR-04중간 '확인한다'만 있고 기준 수치가 없다. 본문 4.5:1, 큰 글자·아이콘·상태 외곽선 3:1(WCAG AA)을 수치로 적을 것. 현재 토큰으로는 --coral #d97660이 흰 바탕 3.1:1이라 작은 코랄 텍스트는 불가하고, --line #e1e3e1은 1.3:1이라 입력 상자·선택 외곽선처럼 상태를 전달하는 경계에는 쓸 수 없다.

codexR-20중간 부분 동의 · Claude R-04 재검토. 일반 텍스트 4.5:1, 큰 텍스트 3:1, 조작·상태를 식별하는 필수 비텍스트 정보는 인접색 대비 3:1을 기준으로 삼는 안에 동의한다. 그러나 모든 아이콘·장식 구분선에 일률적으로 3:1을 적용하는 것은 과하다. 큰 텍스트의 기준도 18pt 또는 굵은 14pt 이상으로 명시하자. 코랄/흰색은 약 3.13:1이므로 작은 코랄 글자와 코랄 버튼 위 작은 흰 글자 모두 주의 대상이다. W3C 텍스트 대비, 비텍스트 대비.

도면 같은 구분선, 넓은 여백, 작은 모서리 반경, 절제된 그림자, 정렬된 숫자를 사용한다. 보고서 제목은 크게 쓰되 실제 작업 화면에서는 모델 영역을 침범하지 않게 한다. 배지와 미세한 글자에 핵심 상태를 숨기지 않는다.

외부 웹 검토에서는 허용된 자료와 행동만 보여준다. Windows IDE의 모든 제어 기능을 작은 브라우저 화면에 그대로 복제하지 않는다.

04 / 같은 공간 입력기를 여러 진입점에서 사용한다

문장 안 참조

일반 채팅처럼 문장만 입력할 수 있다. 필요한 경우 객체 핀, 스케치, 코멘트, 자료를 문장 안에 넣는다.

**[변경할 객체]**를 **[스케치한 선]**에 맞추고, **[유지할 객체]**는 그대로 둔다. **[관련 결정]**을 참고한다.

대상·변경 방향·유지·참고의 관계를 표현한다. 핀 삽입 순간의 참조를 보존하며 현재 선택을 바꾸어 기존 요청의 대상을 바꾸지 않는다. 핀을 누르면 해당 객체·문서·기준과 참조 상태를 확인한다.

모델 위 코멘트

모델 위 객체·위치를 가리키면 작은 공간 입력기를 연다. 문장과 스케치를 함께 작성할 수 있다. 코멘트 저장과 AI에게 제안 요청을 분리한다. 여러 코멘트를 모아 하나의 요청으로 연결할 수 있게 설계한다.

코멘트와 AI 대화는 입력 UI를 공유하지만 저장된 자료는 구분한다. AI 세션을 바꾸거나 닫아도 코멘트 원본과 작성 맥락은 남아야 한다.

이번 요청의 문맥

이번에 사용할 프로젝트·대안·문서·객체·스케치·주요 조건·자료를 짧게 확인할 수 있다. 필수조건과 참고 의견, 사용자 확정과 AI 추정을 구분한다원본에서 읽음·도구로 계산함·사용자가 확정함·AI가 추정함을 구분한다(PRD §6.3). 매번 수동으로 모든 자료를 고르는 복잡한 준비 과정을 요구하지 않는다.

claudeR-05중간 PRD §6.3은 값·관계의 출처를 '원본에서 읽음·도구로 계산함·사용자가 확정함·AI가 추정함' 4종으로 구분해 남기라고 하고, AC-14는 신뢰 수준·출처 구분을 시험함. Design이 2종만 언급하면 문맥 확인 화면과 §06 작업 카드('참조 자료·가정')가 원본 읽음/도구 계산을 구분 표시하지 않게 설계될 수 있음.

codexR-21중간 동의 · Claude R-05 재검토. 출처 4종을 화면에서도 구분하는 제안에 동의한다. 네 종류를 매 카드에 네 배지로 늘어놓을 필요는 없고, 값·관계의 출처를 확인할 수 있으면 된다. 필수조건/참고 의견은 사용 역할, 원본/계산/확정/추정은 출처이므로 서로 다른 분류로 다뤄야 한다.

05 / 선택·핀·스케치의 공간 기준

객체 선택과 참조는 이름만 아니라 호스트·문서·기준 버전과 연결해 표시한다. 원본 객체와 표시용 형상이 어긋나거나 대응을 확인하지 못하면 이를 드러낸다. 삭제·분할·합침 뒤 가까운 객체로 몰래 재연결하지 않는다.

스케치 작성 중 작업평면, 좌표·단위, 연결 대상, 선의 역할을 확인할 수 있어야 한다. 화면 위 주석, 공간에 등록된 평면 스케치, 미등록 업로드 이미지를 다른 상태로 표시한다. 임의의 화면 선을 깊이가 확정된 3D 기하로 표현하지 않는다.

스케치 해석을 보여줄 때 원본 선을 남기고 해석된 경계를 겹쳐 확인하게 한다. 선이 외곽·이동 방향·비움·유지 중 무엇인지 모호하면 필요한 역할을 확인한다. 사용자의 선을 AI의 정리된 선으로 조용히 덮어쓰지 않는다.

펜·터치와 마우스·키보드는 지원 기기에서 검증한다. 펜은 스케치, 터치는 카메라라는 구분을 기본 실험안으로 사용할 수 있으나 실제 제스처·오입력·취소 동작은 SPEC과 기기 시험에 맞춘다. 펜이 없어도 기본 선택·입력·검토가 가능해야 한다.

06 / 실제 진행을 보여주는 작업 카드

작업 카드에는 목적, 정확한 대상, 기준, 마지막 결과, 적용 조건, 현재 상태, 가능한 다음 행동을 우선한다. 코드·전체 로그·세부 비용·도구 원문은 펼쳐 본다.

claudeR-06낮음 '작업 카드'는 PRD §5 용어표에 없는 새 단위다. PRD는 '검토 가능한 작업 단위'와 'Run·실행 시도'를 구분하고 한 작업 단위에 여러 실행 시도가 있을 수 있다고 한다. §06 첫 문단에 '작업 카드 = 검토 가능한 작업 단위 하나, 실행 시도는 카드 안의 이력'처럼 대응을 한 줄로 명시하면 §12의 화면↔상태 ID 연결이 쉬워진다.

codexR-22낮음 부분 동의 · Claude R-06 재검토. 작업 카드와 PRD의 논리적 작업 단위 대응은 도움이 된다. 다만 카드 하나에 실행 시도 이력을 넣는 배치는 UI 제안으로 두고, 이를 영속 데이터 모델의 고정 구조로 간주하지 않는다. 먼저 작업 단위와 Run의 의미를 SPEC에서 확정하자.

표시 내용 사용자에게 전달할 의미
대상과 유지 영역 무엇을 바꾸고 무엇을 건드리지 않는가
원본·중간 후보·최신 후보 지금 무엇을 보고 있으며 어느 기준인가
변경 치수·속성·관련 지표 실제 무엇이 달라졌는가
참조 자료·가정·검토 범위 왜 그렇게 처리했고 무엇을 아직 확인하지 않았는가
현재 작업·마지막 결과 시점 실행과 표시의 기준이 같은가
수정·중단·분기·반영 지금 사람이 할 수 있는 행동은 무엇인가

AI가 계획한 일을 수행했다고 표시하지 않는다. 수치 완료율은 측정 가능한 기준이 있을 때만 사용한다. 결과가 아직 없으면 이를 알리고, 마지막 후보를 보여줄 때는 그 기준과 새 지시 반영 여부를 함께 표시한다.

불완전한 내부 연산의 매 단계를 중간 결과라고 노출하기보다, 사람이 이해할 수 있는 일관된 후보를 보여준다. 형상 변화가 없는 계산·자료 작업은 포함 자료, 가정, 달라진 수치로 설명한다.

07 / 개입·중단·복구의 표현

codexR-33높음 추가 지적 · 새 지시 반영과 결과 생성. 현재 새 지시 반영됨 행은 적용된 조건과 생성/변경 결과를 요구한다. 하지만 대상을 제외하거나 앞으로의 실행을 멈추라는 개입은 새로운 형상을 만들지 않고도 반영될 수 있다. 지시가 실행 기준에 반영된 상태와 결과 생성/원본 반영 상태를 나누는 안을 제안한다. PRD §9.3의 의미를 먼저 합의하고 이 표와 SPEC을 함께 맞춰야 한다.

아래는 반드시 구분할 의미다. 세부 상태 전이와 허용 행동은 SPEC이 정의하고, Design은 그 상태를 오해하지 않게 표현한다.

상황 기본 표현 방향 피할 표현
추가 지시 접수지시 접수 받은 내용과 대상 확인 이미 새 조건을 반영했다고 표시
새 지시 처리 중반영을 위한 정리 중 이전 실행·현재 후보와 새 지시의 관계 이전 후보를 새 결과처럼 표시
새 지시 반영됨 적용된 조건과 생성/변경 결과 실제 결과 없이 반영 성공
중단 요청·연산 종료 대기 새 작업은 시작하지 않으며 실제 종료 상태를 확인 즉시 원상복구 완료
정지됨 남은 입력·후보·이미 반영된 원본 구분 후보 폐기와 원본 복구를 동일 취급
적용 결과 불명 해당 대상 상태 확인과 필요한 행동 성공·실패 단정 후 자동 재실행
사람의 직접 수정과 충돌 새 기준과 이전 후보 차이·재검토 오래된 결과가 덮어쓰는 것을 숨김

claudeR-07낮음 PRD §9.3의 상태명은 '지시 접수'다. SPEC이 PRD 용어로 상태 ID를 만들 때 목업 문구와 갈리지 않게 맞춘다.

codexR-23낮음 부분 동의 · Claude R-07 재검토. 정식 상태명과 대응시키면 추적이 쉽다. 다만 사용자 화면 문구가 내부 상태명과 글자까지 같아야 하는 것은 아니다. 정식 의미/상태 ID와 화면 라벨을 연결하면 짧고 이해하기 쉬운 표현도 사용할 수 있다.

claudeR-08중간 PRD §9.3의 상태명은 '반영을 위한 정리 중'인데 Design은 '새 지시 처리 중'으로 쓴다. SPEC이 PRD 용어로 상태 ID를 만들면 목업 문구와 상태 ID가 어긋나므로 지금 맞출 것.

codexR-24낮음 부분 동의 · Claude R-08 재검토. PRD 상태와 의미가 대응되어야 한다는 지적에 동의한다. 표시 문구를 일괄 복사하는 것보다 SPEC 상태 ID → 화면 문구 → 가능한 행동의 대응을 만드는 것이 핵심이다. 새 지시 처리 중이라는 문구 자체가 잘못된 상태를 뜻한다고 단정할 수는 없다.

claudeR-09중간 PRD §9.3이 최소 구분으로 요구하는 4개 상태(지시 접수 · 반영을 위한 정리 중 · 새 지시 반영됨 · 적용 불가 또는 추가 결정 필요) 중 마지막 하나가 §07 표에 없음. 이 행의 '적용 결과 불명'은 PRD §11.3의 원본 쓰기 결과가 불명확한 상황이라, 개입 자체를 반영할 수 없어 사용자 결정이 필요한 상태와는 다른 개념임. SPEC이 §9.3 상태에서 전이를 정의할 때 Design 표현이 비게 되므로, '새 지시 반영됨' 다음에 '적용 불가·추가 결정 필요 | 반영하지 못한 이유와 선택지 제시 | 조용히 무시하거나 부분 반영을 반영됨으로 표시' 행을 추가할 것.

codexR-25중간 동의 · Claude R-09 재검토. 적용 불가 또는 추가 결정 필요는 원본 쓰기의 적용 결과 불명과 다르므로 독립 행이 필요하다. 제안한 행을 추가하되 반영하지 못한 범위와 이미 반영된 부분도 구분한다. 결과 불명은 사용자에게 다시 실행하라고 바로 안내하는 상태가 아니다.

모든 중간 결과에 승인 버튼을 강제하지 않는다. 위임 범위 안의 후보 작업은 계속 진행한다. 유지 조건·변경 범위·추가 비용·원본 쓰기·외부 공개의 중요한 결정에 필요한 행동을 제시한다.

보안·권한·대상 오류는 탐색 중에도 지켜야 한다. 단순 전문 검토 미완료나 경험칙 경고는 후보 탐색·입력 저장 전체를 막는 화면으로 만들지 않는다.

08 / 네이티브 결과와 원본·저장 상태

codexR-34중간 추가 지적 · 기준이 바뀐 후보의 반영 UI. 오래된 후보의 기준 문서·시점과 현재 원본의 차이를 보여주고, 다시 비교해야 하는 이유를 설명하는 구체 상태가 필요하다. 반영 버튼에서 후보를 새로 생성하거나 최신 원본에 조용히 재적용하는 흐름을 막아야 한다. 이미 확인된 원본 적용 이후의 저장/캡처 실패는 재실행 대신 각 실패를 복구하는 행동으로 연결한다.

호스트에 반영할 객체 종류, 대상 문서, 변경 내용과 검토 상태를 확인한 뒤 반영한다. 실제 네이티브 결과를 지원하는 경우 그 유형과 후속 편집 범위를 표시한다. 지원 불가·일반 형상 대체는 정상 네이티브 완료와 시각적으로 구분한다.

후보 채택, 원본 적용, 적용 확인, 파일 저장, 저장 후 재열기는 같은 상태가 아니다. 파일 저장을 확인하지 못했다면 적용 상태만 표시한다. 캡처·보고서 생성에 실패했어도 확인된 원본 적용을 다시 실행하는 버튼 흐름을 만들지 않는다.

되돌리기는 호스트별 실제 지원 범위가 있을 때 제공하고, 여러 호스트의 전체 원자적 복구를 암시하지 않는다. 지원하지 않는 동작은 설명 없는 회색 버튼만 남기기보다 필요한 조건을 짧게 알려준다.

09 / 확장과 산출물의 최소 화면

확장은 이름·목적·필요 호스트·입력·권한·실행/비활성 상태를 확인할 수 있게 한다. 등록·실행·진행·결과·실패는 공통 작업 경험으로 이어져야 한다. 초기 UI를 공개 마켓·검색·평가·결제로 확대하지 않는다.

산출물은 제목, 생성 기준·자료, 실제 결과와 검토 범위, 사용 가능한 저장·공유·내보내기를 보여준다. 기본 HTML 열람·전달 화면이 곧 HTML 직접 편집기는 아니다.

즉석 생성·부분 선택 편집 C-01은 채택되지 않은 후보다. 이 문서에는 캔버스·DOM 편집기, 자유 레이아웃, 임의 스크립트 실행을 확정하지 않는다. 향후 채택 시 사용자 편집이 원문·계산 가정·표현 중 무엇을 바꾸는지 SPEC에서 먼저 구분한다.

10 / 진단과 전문가 도구

기본 작업 기록에는 실제 처리·조회·생성·오류·개입·예산 정보를 보여준다. 실패 이유를 코드 덤프만으로 설명하지 않는다. 필요할 때 생성 코드와 상세 로그를 별도로 열 수 있다.

터미널은 기본 입력 경로가 아니라 전문가용 선택 기능이다. 로그를 보는 것과 실제 셸 명령을 실행하는 것은 구분한다. 터미널에서 별도 세션을 열었다고 현재 공간 작업과 자동으로 동일한 상태가 된다고 표시하지 않는다. 실행 엔진 선택과 터미널 제공 깊이는 구현계획에서 정한다.

claudeR-10중간 PRD §1.1은 '터미널 중심 화면을 필수로 정하지 않는다'고만 하고, FR-01~21 어디에도 셸 명령 실행 터미널 제공 요구가 없음. Design이 터미널을 '전문가용 선택 기능'으로 존재 전제하고 '제공 깊이는 구현계획에서 정한다'고 하면 제품 범위 결정이 PLAN으로 넘어가며, 가이드 §01(Design은 기능 지원 범위 임의 확대 금지)과 §04(SPEC이 지원하지 않은 행동을 확정 기능으로 추가 금지)에 어긋남. 오너 결정 필요: 터미널을 PRD에 FR 또는 OQ로 추가할지, 아니면 이 문단을 '생성 코드·상세 로그 열람'(FR-10 범위)으로 한정하고 셸 실행은 미채택 후보로 표기할지.

codexR-26중간 동의 · Claude R-10 재검토. 실제 셸 실행 터미널을 Design이 도입 결정하는 구조는 타당하지 않다. FR-10 범위의 생성 코드·상세 로그 열람은 유지하고, 셸 실행은 별도 제품 채택 없이는 지원 행동으로 확정하지 않는 문구를 제안한다. 필요한 경우 PRD에서 후보로 다룬 뒤 SPEC과 PLAN으로 내려야 한다.

11 / 빈 상태·오류·반응형·접근성

호스트 미연결, 미지원 버전, 대상 없음, 참조 끊김, 스케치 미등록, AI 단절, 저장 실패, 권한 부족, 원본 적용 불명을 각각 표현한다. 전체 화면을 오류로 덮기보다 영향받는 작업·대상을 표시하고 가능한 다른 작업은 유지한다.

좁은 화면에서는 핵심 모델·입력·상태를 우선하고 보조 정보는 펼쳐 본다. 기존 데스크톱 작업과 입력을 잃지 않게 한다. 웹 검토 화면에서 네이티브 원본 쓰기 버튼을 노출하는 것으로 기능을 대신하지 않는다.웹 검토 화면에는 네이티브 원본 쓰기 행동을 노출하지 않으며, 외부 검토자의 제출은 원본 반영과 별개 상태로 표시한다(PRD §1.3·§12.5, AC-19).

claudeR-11중간 현재 문장은 '버튼은 노출하되 기능 대체로 보지 않는다'로도 읽혀, 외부 검토자에게 로컬 원본 쓰기 권한이 없다는 PRD §1.3·§12.5와 어긋날 여지가 있음. 가이드 §04 예시도 '외부 검토자는 읽기/의견 권한만 → 허용하지 않을 원본 변경'을 Design이 명시하라고 함. AC-19의 제출/병합/원본 반영 구분에 맞춰 노출 자체를 금지하는 문장으로 고칠 것.

codexR-27중간 부분 동의 · Claude R-11 재검토. 현재 외부 검토 역할에는 로컬 원본 쓰기 권한이 없으므로 그 행동을 제공하지 않는 방향에 동의한다. 다만 브라우저라는 기술 자체에 영구적으로 쓰기를 금지하는 규칙으로 확대하지 말자. 제안 문구: 현재 외부 검토자 역할에는 원본 반영 행동을 제공하지 않으며, 제출·채택·로컬 반영 상태를 구분한다. 실제 권한 검사는 버튼 숨김과 별도로 실행 경계에서 필요하다.

키보드 포커스, 입력 라벨, 읽을 수 있는 텍스트, 선택/변경을 구분할 외곽선·패턴·문구를 제공한다. 색만으로 원본·후보·오류를 구분하지 않는다. 주요 동작에 드래그 외의 대안을 두고 터치 목표 크기를 실제 장치에서 확인한다.

13 / 목업 검수 기준

claudeR-15중간 §13 문단은 AC-01·02·03(핀·스케치), AC-08·09·11(접수/반영·늦은 후보·중단 대기), AC-24·27(네이티브·미지원), AC-04·22(입력 보존·키보드/터치)를 사실상 다시 쓴 것인데 ID가 없다. 가이드 §01의 '복사하지 말고 참조' 원칙에 어긋나고, 목업 검수 결과를 PRD 수용 시나리오에 되돌려 기록할 고리가 없다. 검수 항목·대응 AC ID·목업만으로 확인 가능/실호스트 필요 열의 표로 바꾸거나 각 문장 끝에 AC ID를 붙일 것.

codexR-31중간 동의 · Claude R-15 재검토. 목업 과제에 AC ID와 검증 가능한 범위를 연결하는 제안에 동의한다. 표현의 이해·입력 유지·키보드 흐름은 목업에서 확인하고, 원본 객체/저장/중복 쓰기 등의 실제 통과는 실호스트 검수로 남겨야 한다. 같은 AC를 인용해도 목업 통과가 AC 전체의 제품 통과가 되는 것은 아니다.

사용자가 정확한 호스트·대상·버전을 찾고 핀을 삽입한 뒤 선택을 바꿔도 대상이 유지되는지 확인한다. 스케치를 다른 시점에서 볼 때 공간 기준을 이해하는지, 원본 선과 해석을 교정할 수 있는지 확인한다.

진행 중 유지 대상을 추가하고 접수와 실제 반영을 구분하는지, 중단 대기를 실제 정지로 오인하지 않는지, 늦은 후보를 최신 결과로 착각하지 않는지 확인한다. 네이티브 적용과 저장, 미지원 결과를 구분할 수 있어야 한다.

코멘트 저장·패널 토글·화면 크기 변화로 입력이 사라지지 않아야 한다. 키보드와 마우스로 기본 흐름을 완료하고 지원하는 터치·펜 환경에서도 같은 의미를 전달해야 한다.

claudeR-16낮음 '키보드와 마우스로'는 둘을 합친 기준이라 키보드만으로 완료 가능한 범위가 검수 항목으로 남지 않는다. 포커스 이동·핀 삽입·카드 행동·코멘트 저장·반영 확인은 키보드 단독 완료, 스케치는 포인터 필수(좌표·치수 입력 대안을 둘지는 SPEC 결정 질문)로 나눠 적을 것.

codexR-32중간 부분 동의 · Claude R-16 재검토. 키보드 단독 검수 범위를 분리하는 데 동의한다. 그러나 스케치는 전부 포인터 필수라고 일괄 예외 처리하면 안 된다. 자유 곡선의 경로 자체가 본질인 입력과, 끝점·좌표·치수로도 표현 가능한 선/이동을 구분하고 후자의 대안을 SPEC에서 정하자. 드래그의 클릭 대안과 키보드 대안은 서로 별도의 검수다. W3C 키보드, 드래그 대안.
