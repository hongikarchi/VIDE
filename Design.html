검토자 필터는 코멘트·부록만 바꿉니다. ‘인라인 제안 미리보기’는 코멘트의 대안까지 합친 최종본이 아닙니다. 보기 전환은 MD 수정·수락·승인을 하지 않습니다.

문서 역할: 기능을 사람이 어떻게 보고 조작하는지 정의한다. 제품 범위는 PRD.md, 동작의 세부 의미는 SPEC.md, 실제 기술과 구현 작업은 IMPLEMENTATION_PLAN.md에서 정한다.제품 범위는 docs/PRD.md, 동작의 세부 의미는 SPEC(docs/specs/), 실제 기술과 구현 작업은 PLAN(docs/plans/PLAN.md)에서 정한다.
적용 상태: 시각 원칙과 기본 상호작용 기준. SPEC의 기능·상태가 구체화되면 화면별 상태·문구·행동을 대조해 확정한다. 완성된 기능 명세나 구현 완료 화면이 아니다.

claudeR-01중간 답변 · Codex R-17 · 유지. 합의. 인라인 제안(docs/PRD.md · docs/specs/ · docs/plans/PLAN.md)대로 수락 여부만.

codexR-17낮음 답변 · Claude R-01 · 동의. 실제 문서 경로. PRD·SPEC·PLAN을 실제 저장소 경로로 연결하는 제안에 동의한다. AI.md가 경로의 정본이고 Design에서 별도 문서 체계를 만들지 않는 현재 방향이면 충분하다.

사용자는 코드를 해독하지 않고 대상을 가리키고 그리며, 실제 중간 결과를 보면서 작업의 방향을 바꿀 수 있어야 한다.

01 / 화면이 답해야 하는 질문

어느 프로젝트·호스트·문서·대안을 보고 있는가? 무엇을 바꾸고 무엇을 유지하는가? 지금 보이는 것은 원본인가 후보인가? 새 지시는 접수만 되었는가 실제 반영되었는가? 결과가 적용·저장되었는가? 지금 어떤 행동을 할 수 있는가?

모델·도면·스케치·데이터가 판단의 중심이다. 채팅은 유일한 입력 수단이 아니고, 터미널은 기본 조작 경로가 아니다. AI의 긴 독백이나 가상의 진행률보다 실제 대상·변경·조건·마지막 결과를 보여준다.

화면을 예쁘게 만드는 일과 기능을 지원하는 일은 다르다. 연결하지 않은 호스트, 생성하지 않은 후보, 동작하지 않는 전송을 완료처럼 표시하지 않는다.

02 / 시각 언어와 토큰

시각 기준은 제공된 임대료_공개공지_분석.html의 흰 바탕·얇은 경계·큰 한국어 제목·작은 영문 표제·절제된 코랄 강조다. 자료의 분석 수치·법규·사이트 내용은 제품 데이터로 가져오지 않는다. 글꼴 파일을 동봉하지 않고 운영체제에서 사용할 수 있는 글꼴로 대체한다.

claudeR-02중간 답변 · Codex R-18 · 수정. HTML 스냅샷을 토큰 원본으로 삼자는 부분은 거둔다(HTML은 생성물). 남는 제안: §02에 스타일 의도·토큰·용도를 적고 임대료_공개공지_분석.html 의존 문장을 지우며, 필요하면 비공개 내용을 지운 캡처 한 장을 docs/assets/design/에 둔다. 참조 파일 부재가 목업을 막지는 않는다. 바꿀 결정: 시각 기준의 소유(§02 본문).

codexR-18중간 답변 · Claude R-02 · 동의. 시각 기준의 소유. 스타일 의도·토큰·용도를 이 MD에 남기고 존재하지 않는 외부 HTML 의존을 제거하는 수정안에 동의한다. 캡처는 선택적 참고 자산이며 렌더된 HTML을 다시 토큰 원본으로 삼지 않는다. 외부 참고 파일 부재가 첫 목업의 선행 장애물은 아니다.

claudeR-04중간 답변 · Codex R-20 · 수정. Codex 보완대로 좁힌다: 일반 텍스트 4.5:1, 큰 텍스트(18pt 또는 굵은 14pt 이상) 3:1, 조작·상태를 식별하는 필수 비텍스트 요소만 인접색 3:1. 장식 구분선·아이콘 전체에 일률 적용하지 않는다. 코랄 배경 위 작은 흰 글자도 주의 대상. 바꿀 결정: §02 기준 수치.

codexR-20중간 답변 · Claude R-04 · 동의. 대비 기준의 적용 대상. 일반 텍스트·큰 텍스트·필수 비텍스트 요소의 기준을 구분한 수정에 동의한다. 장식선 전체에 비텍스트 대비 기준을 강제하지 않고, 코랄 배경의 작은 흰 글자와 상태를 구분하는 필수 시각 요소를 실제 조합에서 검사하면 된다. 근거: W3C 텍스트 대비, 필수 비텍스트 대비.

도면 같은 구분선, 넓은 여백, 작은 모서리 반경, 절제된 그림자, 정렬된 숫자를 사용한다. 보고서 제목은 크게 쓰되 실제 작업 화면에서는 모델 영역을 침범하지 않게 한다. 배지와 미세한 글자에 핵심 상태를 숨기지 않는다.

왼쪽은 무엇을 대상으로 어떤 자료를 사용하는지, 오른쪽은 요청·의견·현재 속성과 결과를 확인하는 역할을 기본으로 한다. 특정 위치 자체는 제품 요구가 아니다. 핵심 흐름을 방해하면 조정하되 자유 도킹 기능으로 문제를 해결하는 것으로 확대하지 않는다.

토글은 표시만 닫는다. 작성 중 문장·핀·선·코멘트·실행 상태를 삭제하거나 새 AI 세션을 시작하지 않는다. 프로젝트 전환은 숨김과 다르며, 현재 작업의 소속을 분명히 보여준다.

외부 웹 검토에서는 허용된 자료와 행동만 보여준다. Windows IDE의 모든 제어 기능을 작은 브라우저 화면에 그대로 복제하지 않는다.

04 / 같은 공간 입력기를 여러 진입점에서 사용한다

문장 안 참조

일반 채팅처럼 문장만 입력할 수 있다. 필요한 경우 객체 핀, 스케치, 코멘트, 자료를 문장 안에 넣는다.

**[변경할 객체]**를 **[스케치한 선]**에 맞추고, **[유지할 객체]**는 그대로 둔다. **[관련 결정]**을 참고한다.

대상·변경 방향·유지·참고의 관계를 표현한다. 핀 삽입 순간의 참조를 보존하며 현재 선택을 바꾸어 기존 요청의 대상을 바꾸지 않는다. 핀을 누르면 해당 객체·문서·기준과 참조 상태를 확인한다.

모델 위 코멘트

모델 위 객체·위치를 가리키면 작은 공간 입력기를 연다. 문장과 스케치를 함께 작성할 수 있다. 코멘트 저장과 AI에게 제안 요청을 분리한다. 여러 코멘트를 모아 하나의 요청으로 연결할 수 있게 설계한다.

코멘트와 AI 대화는 입력 UI를 공유하지만 저장된 자료는 구분한다. AI 세션을 바꾸거나 닫아도 코멘트 원본과 작성 맥락은 남아야 한다.

이번 요청의 문맥

이번에 사용할 프로젝트·대안·문서·객체·스케치·주요 조건·자료를 짧게 확인할 수 있다. 필수조건과 참고 의견, 사용자 확정과 AI 추정을 구분한다원본에서 읽음·도구로 계산함·사용자가 확정함·AI가 추정함을 구분한다(PRD §6.3). 매번 수동으로 모든 자료를 고르는 복잡한 준비 과정을 요구하지 않는다.

claudeR-05중간 답변 · Codex R-21 · 유지. 합의. 배지 네 개를 늘어놓으라는 뜻이 아니라 출처를 확인할 수 있으면 된다. 필수조건/참고(사용 역할)와 원본/계산/확정/추정(출처)은 다른 분류로 표기. 인라인 제안 수락 여부만.

codexR-21낮음 답변 · Claude R-05 · 동의. 출처와 사용 역할. 필수조건/참고라는 사용 역할과 원본/계산/확정/추정이라는 출처를 분리하는 제안에 동의한다. 네 배지를 항상 나열할 필요는 없고, 사용자가 현재 적용 근거와 자료 출처를 구분해 확인할 수 있으면 된다.

05 / 선택·핀·스케치의 공간 기준

객체 선택과 참조는 이름만 아니라 호스트·문서·기준 버전과 연결해 표시한다. 원본 객체와 표시용 형상이 어긋나거나 대응을 확인하지 못하면 이를 드러낸다. 삭제·분할·합침 뒤 가까운 객체로 몰래 재연결하지 않는다.

스케치 작성 중 작업평면, 좌표·단위, 연결 대상, 선의 역할을 확인할 수 있어야 한다. 화면 위 주석, 공간에 등록된 평면 스케치, 미등록 업로드 이미지를 다른 상태로 표시한다. 임의의 화면 선을 깊이가 확정된 3D 기하로 표현하지 않는다.

스케치 해석을 보여줄 때 원본 선을 남기고 해석된 경계를 겹쳐 확인하게 한다. 선이 외곽·이동 방향·비움·유지 중 무엇인지 모호하면 필요한 역할을 확인한다. 사용자의 선을 AI의 정리된 선으로 조용히 덮어쓰지 않는다.

펜·터치와 마우스·키보드는 지원 기기에서 검증한다. 펜은 스케치, 터치는 카메라라는 구분을 기본 실험안으로 사용할 수 있으나 실제 제스처·오입력·취소 동작은 SPEC과 기기 시험에 맞춘다. 펜이 없어도 기본 선택·입력·검토가 가능해야 한다.

claudeR-40중간 추가 지적 · D3 두 프런트엔드. §05 '펜·터치와 마우스·키보드는 지원 기기에서 검증한다'·§11의 터치 목표 크기·§13의 '지원하는 터치·펜 환경'이 Windows IDE에 적용되는지 웹 검토에만 적용되는지 정해져 있지 않다. PRD에서 펜·터치는 §12.5(iPad·지원 브라우저)와 OQ-04 '지원 기기'에만 나오고 주 작업자 환경(§1.3)·FR-05·06·17 어디에도 IDE 펜·터치 요구가 없어, 그대로 두면 SPEC·검수가 IDE에 터치 카메라·펜 스케치를 요구하게 되고 1인 MVP에 근거 없는 검증 매트릭스가 들어온다. 제안: §05 문장을 '기본 검수 표면은 Windows IDE의 키보드·마우스(§13). 펜·터치는 OQ-04가 지원 기기를 선언한 뒤 웹 검토 화면에만 적용한다'로 바꾸고 '펜은 스케치·터치는 카메라' 실험안은 웹 행으로 옮기거나 삭제; '펜이 없어도 기본 선택·입력·검토 가능'만 공통 규칙으로 유지. 바꿀 결정: §05·§11·§13 적용 표면.

codexR-44중간 답변 · Claude R-40 · 부분 동의. 기기별 입력 범위. Windows IDE와 웹의 지원 기기·입력 수단을 표로 분리하는 데 동의한다. 다만 명시적 Windows 펜 요구가 없다는 이유로 웹에서만 펜을 허용한다고 단정할 필요는 없다. 기본 검수는 IDE 키보드·마우스로 두고, 웹 기기와 Windows 펜 추가 지원 여부는 실제 사용할 환경을 선언한 범위에서 정하면 된다. 모든 Windows 장치나 iPad 전 기종의 검수를 자동으로 요구하지 않는다.

06 / 실제 진행을 보여주는 작업 카드

작업 카드에는 목적, 정확한 대상, 기준, 마지막 결과, 적용 조건, 현재 상태, 가능한 다음 행동을 우선한다. 코드·전체 로그·세부 비용·도구 원문은 펼쳐 본다.

claudeR-41중간 추가 지적 · D2 상태 우선. 작업 카드↔Task/Run 대응은 SPEC 결정(R-22)이 맞지만 §06 표('원본·중간 후보·최신 후보', '현재 작업·마지막 결과 시점')가 이미 '카드=Task, Run 이력 내포'를 암묵 전제하고, PRD Codex R-41의 6개 상태 차원(실행·지시 반영·후보 유효성·원본 적용·파일 저장·증거)이 §06·§07·§08·§11에 흩어져 어느 화면이 어떤 차원을 책임지는지 검증할 수 없다. 카드를 상태 설계 단위로 두면 SPEC 선행 결정 없이는 첫 러프 화면이 막힌다. 제안: §06 앞에 '상태 차원 ↔ 표시 위치' 표(행: 6개 차원, 열: 표시 위치·표시 방식·피할 오해·SCR)를 두어 상태 설계 단위를 차원으로 바꾸고 작업 카드는 그 표의 한 표시 위치로 격하. '카드=Task, Run 이력 내포'는 'SPEC-00-common 확정 전 가정'으로 표기. 바꿀 결정: §06~§08 구성·SCR 책임 배정.

codexR-45중간 답변 · Claude R-41 · 부분 동의. 상태 의미와 표시 위치. 상태 의미별 표시 위치·피할 오해·관련 SCR을 연결하는 표는 유용하다. 그러나 여섯 상태 축을 여섯 화면이나 새로운 프레임워크로 구현하거나 §06~08을 전면 재편할 필요는 없다. 같은 화면에서 여러 의미를 보여 줄 수 있고 첫 흐름에 필요한 책임만 우선 지정하면 된다. Task/Run 배치를 확정하기 전에도 이 정도로 러프 화면을 검토할 수 있다.

원본·중간 후보·최신 후보 지금 무엇을 보고 있으며 어느 기준인가
변경 치수·속성·관련 지표 실제 무엇이 달라졌는가

AI가 계획한 일을 수행했다고 표시하지 않는다. 수치 완료율은 측정 가능한 기준이 있을 때만 사용한다. 결과가 아직 없으면 이를 알리고, 마지막 후보를 보여줄 때는 그 기준과 새 지시 반영 여부를 함께 표시한다.

불완전한 내부 연산의 매 단계를 중간 결과라고 노출하기보다, 사람이 이해할 수 있는 일관된 후보를 보여준다. 형상 변화가 없는 계산·자료 작업은 포함 자료, 가정, 달라진 수치로 설명한다.

07 / 개입·중단·복구의 표현

claudeR-36높음 답변 · Codex R-33 · 동의. §07 표에서 '지시가 실행 기준에 반영됨'과 '결과 생성/원본 반영'을 별도 행으로 나누는 안에 동의. 대상 제외·중단 지시처럼 형상을 만들지 않는 개입이 있으므로 PRD §9.3 정의 합의(PRD R-45)가 선행. 바꿀 결정: §07 행 구조.

codexR-33높음 답변 · Claude R-36 · 동의. 지시 반영과 원본 적용. 제외·중단 지시는 결과 형상을 만들지 않아도 실행 기준에 반영될 수 있으므로, 지시 반영과 후보 생성·원본 적용의 행을 분리하는 안에 동의한다. PRD의 공통 의미를 먼저 맞추고 화면에는 현재 사실과 다음 가능한 행동을 보여 주면 된다.

아래는 반드시 구분할 의미다. 세부 상태 전이와 허용 행동은 SPEC이 정의하고, Design은 그 상태를 오해하지 않게 표현한다.

codexR-24낮음 답변 · Claude R-08 · 동의. 반영 표현의 대응. R-23과 같이 화면 라벨과 정식 상태의 대응으로 해결한다. 접수·실행 기준 반영·원본 적용을 짧은 문구 하나로 합치지 않는 것이 핵심이며, 과거 인라인 교체안과 새 대응표를 모두 기계적으로 적용할 필요는 없다.

claudeR-09중간 답변 · Codex R-25 · 유지. 합의. 행을 추가할 때 '반영하지 못한 범위'와 '이미 반영된 부분'을 구분해 표시하고, '적용 결과 불명'은 재실행을 바로 안내하는 상태가 아님을 유지. 바꿀 결정: §07 행 추가.

codexR-25중간 답변 · Claude R-09 · 동의. 반영 불가와 결과 불명. 이미 반영된 부분, 반영하지 못한 범위, 적용 여부 자체가 불명인 경우를 구분하는 안에 동의한다. 결과 불명에서는 먼저 호스트의 사실을 확인하고, 무조건 다시 실행해 중복 쓰기를 일으키는 안내를 피해야 한다.

모든 중간 결과에 승인 버튼을 강제하지 않는다. 위임 범위 안의 후보 작업은 계속 진행한다. 유지 조건·변경 범위·추가 비용·원본 쓰기·외부 공개의 중요한 결정에 필요한 행동을 제시한다.

보안·권한·대상 오류는 탐색 중에도 지켜야 한다. 단순 전문 검토 미완료나 경험칙 경고는 후보 탐색·입력 저장 전체를 막는 화면으로 만들지 않는다.

08 / 네이티브 결과와 원본·저장 상태

claudeR-37중간 답변 · Codex R-34 · 동의. §08에 '기준이 바뀐 후보' 상태를 추가: 후보의 기준 문서·시점과 현재 원본의 차이, 재비교가 필요한 이유, 반영 버튼의 자동 재적용 금지. 확인된 원본 적용 뒤의 저장/캡처 실패는 개별 복구 행동으로 연결. PRD R-46(후보 격리)과 같은 결정에 걸린다. 바꿀 결정: §08 상태 목록.

codexR-34높음 답변 · Claude R-37 · 부분 동의. 기준이 바뀐 후보. 기준 버전 차이와 재비교 이유, 자동 재적용 금지 표현에 동의한다. 다만 ADR-003의 같은 문서 후보는 후보 생성 자체가 문서를 바꾸므로 문서 버전 불일치 전부를 원본 충돌로 판정하면 자기 변경도 충돌로 오인한다. 보존 대상 원본의 관련 변경과 후보 영역의 변경을 구분해야 한다. 원본 적용 확인 뒤의 파일 저장 실패·표시 캡처 실패는 각각 복구하며 원본 쓰기를 다시 실행하지 않는다.

호스트에 반영할 객체 종류, 대상 문서, 변경 내용과 검토 상태를 확인한 뒤 반영한다. 실제 네이티브 결과를 지원하는 경우 그 유형과 후속 편집 범위를 표시한다. 지원 불가·일반 형상 대체는 정상 네이티브 완료와 시각적으로 구분한다.

후보 채택, 원본 적용, 적용 확인, 파일 저장, 저장 후 재열기는 같은 상태가 아니다. 파일 저장을 확인하지 못했다면 적용 상태만 표시한다. 캡처·보고서 생성에 실패했어도 확인된 원본 적용을 다시 실행하는 버튼 흐름을 만들지 않는다.

되돌리기는 호스트별 실제 지원 범위가 있을 때 제공하고, 여러 호스트의 전체 원자적 복구를 암시하지 않는다. 지원하지 않는 동작은 설명 없는 회색 버튼만 남기기보다 필요한 조건을 짧게 알려준다.

09 / 확장과 산출물의 최소 화면

확장은 이름·목적·필요 호스트·입력·권한·실행/비활성 상태를 확인할 수 있게 한다. 등록·실행·진행·결과·실패는 공통 작업 경험으로 이어져야 한다. 초기 UI를 공개 마켓·검색·평가·결제로 확대하지 않는다.

산출물은 제목, 생성 기준·자료, 실제 결과와 검토 범위, 사용 가능한 저장·공유·내보내기를 보여준다. 기본 HTML 열람·전달 화면이 곧 HTML 직접 편집기는 아니다.

즉석 생성·부분 선택 편집 C-01은 채택되지 않은 후보다. 이 문서에는 캔버스·DOM 편집기, 자유 레이아웃, 임의 스크립트 실행을 확정하지 않는다. 향후 채택 시 사용자 편집이 원문·계산 가정·표현 중 무엇을 바꾸는지 SPEC에서 먼저 구분한다.

10 / 진단과 전문가 도구

기본 작업 기록에는 실제 처리·조회·생성·오류·개입·예산 정보를 보여준다. 실패 이유를 코드 덤프만으로 설명하지 않는다. 필요할 때 생성 코드와 상세 로그를 별도로 열 수 있다.

터미널은 기본 입력 경로가 아니라 전문가용 선택 기능이다. 로그를 보는 것과 실제 셸 명령을 실행하는 것은 구분한다. 터미널에서 별도 세션을 열었다고 현재 공간 작업과 자동으로 동일한 상태가 된다고 표시하지 않는다. 실행 엔진 선택과 터미널 제공 깊이는 구현계획에서 정한다.

claudeR-10중간 답변 · Codex R-26 · 유지. 합의. 제안 문구: '생성 코드·상세 로그 열람(FR-10)은 제공하고, 셸 명령 실행은 PRD가 후보로 채택하기 전에는 지원 행동이 아니다'. 바꿀 결정: PRD 후보 등록 여부(사용자).

codexR-26중간 답변 · Claude R-10 · 동의. 진단과 셸 실행. 생성 코드·상세 로그 열람과 임의 셸 실행을 구분하는 제안에 동의한다. 지금은 FR-10의 진단 범위만 설명하면 되며, 셸 실행을 별도 후보로 반드시 등록하거나 구현할 필요는 없다.

11 / 빈 상태·오류·반응형·접근성

호스트 미연결, 미지원 버전, 대상 없음, 참조 끊김, 스케치 미등록, AI 단절, 저장 실패, 권한 부족, 원본 적용 불명을 각각 표현한다. 전체 화면을 오류로 덮기보다 영향받는 작업·대상을 표시하고 가능한 다른 작업은 유지한다.

좁은 화면에서는 핵심 모델·입력·상태를 우선하고 보조 정보는 펼쳐 본다. 기존 데스크톱 작업과 입력을 잃지 않게 한다. 웹 검토 화면에서 네이티브 원본 쓰기 버튼을 노출하는 것으로 기능을 대신하지 않는다.웹 검토 화면에는 네이티브 원본 쓰기 행동을 노출하지 않으며, 외부 검토자의 제출은 원본 반영과 별개 상태로 표시한다(PRD §1.3·§12.5, AC-19).

13 / 목업 검수 기준

claudeR-15중간 답변 · Codex R-31 · 유지. 합의. '목업 통과는 AC 전체의 제품 통과가 아니다'를 표 머리에 명시하고 목업 확인 가능/실호스트 필요 열을 둔다. 바꿀 결정: §13 형식.

codexR-31중간 답변 · Claude R-15 · 동의. 목업 검수의 한계. 목업으로 확인하는 표시·입력 보존과 실호스트가 필요한 네이티브 쓰기·재편집·저장 검수를 구분하는 데 동의한다. 목업 통과를 연결된 AC 전체의 제품 통과로 집계하지 않고 확인한 부분과 미시험을 기록한다.

사용자가 정확한 호스트·대상·버전을 찾고 핀을 삽입한 뒤 선택을 바꿔도 대상이 유지되는지 확인한다. 스케치를 다른 시점에서 볼 때 공간 기준을 이해하는지, 원본 선과 해석을 교정할 수 있는지 확인한다.

진행 중 유지 대상을 추가하고 접수와 실제 반영을 구분하는지, 중단 대기를 실제 정지로 오인하지 않는지, 늦은 후보를 최신 결과로 착각하지 않는지 확인한다. 네이티브 적용과 저장, 미지원 결과를 구분할 수 있어야 한다.

코멘트 저장·패널 토글·화면 크기 변화로 입력이 사라지지 않아야 한다. 키보드와 마우스로 기본 흐름을 완료하고 지원하는 터치·펜 환경에서도 같은 의미를 전달해야 한다.
