00 / 개발의 전체 흐름

이 프로젝트에서는 문서를 제품 기획·설계와 개발 설계·실행으로 구분한다. 정상 진행의 기준 순서는 다음과 같다.

한 번 쓰고 끝내는 일방향 절차는 아니다. 기능 의미가 불명확하면 SPEC으로, 사람이 이해하기 어려우면 Design으로, 기술·작업 순서가 맞지 않으면 구현계획으로 돌아간다. 제품의 약속 자체가 바뀌면 PRD의 결정이 필요하다.

특정 위험을 확인하는 작은 기술 실험은 SPEC의 미정 사항을 풀기 위해 먼저 할 수 있다. 다만 기술 실험이나 러프 화면이 곧 확정된 Stack·기능 명세·제품 구현이 되는 것은 아니다. 핵심 기능과 상태를 정하지 않은 채 전체 Stack과 모든 화면을 확정하지 않는다.

사람과 AI의 역할

사람은 지원 범위, 원하는 결과, 변경·공개 권한과 채택 기준을 결정한다. AI는 모순을 찾고, 기능을 구체화하고, 기술을 비교·실험하고, 정한 범위를 구현·시험한다. 범위 안의 국소 결정을 전부 사람에게 되묻지 않되 제품 범위와 권한의 변경을 숨기지 않게 한다.

제품을 개발하는 AI의 티켓과 완성된 IDE 안에서 설계를 수행하는 AI의 작업은 다르다. 이 안내서는 전자의 개발을 진행하는 방법이며, 후자의 사용자 경험과 보호 규칙은 PRD·SPEC에서 가져온다.

테스트 계획은 구현계획의 한 장과 각 task의 검증 항목으로 시작한다. 커졌을 때만 TEST_PLAN.md로 분리한다. MVP 범위는 PRD 안에, 호스트별 세부 지원은 SPEC 안에, Stack·기술 결정은 구현계획 안에 둔다.

DEVELOPMENT_GUIDE.md는 이 네 문서를 작성·활용하는 안내서다. AI_PROMPTS.md는 같은 가이드의 복사용 요청문이다. 두 파일을 별도의 제품 기준으로 사용하지 않는다.복사용 AI 요청문은 이 가이드 안의 ‘AI 요청문’ 블록이 원본이며 별도 AI_PROMPTS.md는 두지 않는다. 이 가이드를 별도의 제품 기준으로 사용하지 않는다.

claudeR-04중간 AI_PROMPTS.md는 저장소에 없고 만들지 않기로 했으며, 가이드 안의 ‘AI 요청문’ 블록이 유일한 원본이다. L49의 ‘AI 요청문’도 같은 블록을 뜻한다고 읽히게 맞춘다.

현재 읽을 문서와 다음 작성할 문서

이 자료 묶음에는 PRD, Design의 원칙·기본 화면 기준, 개발 가이드, AI 요청문이 있다. SPEC과 실제 IMPLEMENTATION_PLAN은 아직 작성하지 않았다. Design의 상세 화면·상태는 SPEC과 대조하여 구체화해야 하며, 이 가이드의 예시가 확정 명세나 구현 완료 티켓을 뜻하지 않는다.

다음 실제 기획 산출물은 SPEC.md 초안docs/specs/SPEC-00-common.md와 첫 SPEC-NN-<slug>.md 초안이다. PRD의 미정 사항은 해당 기능과 연결해 남기고, 명확한 기능부터 작성한다. 빈 파일을 만들어 ‘명세 완료’로 취급하지 않는다.

claudeR-05낮음 §01의 '다음 산출물' 선언이 단일 SPEC.md를 가리킨다. 어떤 파일을 먼저 채우는지(공통 규칙 → 가장 명확한 기능 하나)를 여기서 정하면 바로 뒤 '빈 파일을 명세 완료로 취급하지 않는다'와 연결된다. 497행도 같이 고칠 것.

문서를 늘리기 전에 확인한다

같은 요구를 복사하지 말고 참조한다. 기능이 복잡해져 SPEC을 나누거나 시험 기록이 커졌을 때만 파일을 분리한다. 새로운 파일을 만들 때는 기존 어느 장을 맡는지 명확히 하여 두 기준이 동시에 생기지 않게 한다.

claudeR-06낮음 SPEC과 시험 기록은 처음부터 기능별·호스트별·날짜별로 나누기로 했다(AI.md §2). 이 문장을 그대로 두면 AI가 분할을 미루거나 파일을 합칠 근거로 삼는다. 'SPEC·시험 기록은 AI.md §2의 분할 단위를 따르고, 그 밖의 문서는 커졌을 때만 분리한다'로 손보고, 이 절의 취지(같은 요구를 두 파일에 복사하지 않는다)는 그대로 둘 것.

02 / PRD — 무엇을 만들 것인지 확인한다

PRD에서 결정할 것은 제품의 약속과 범위다. 작성 도중 새로운 기술을 추천받았다는 이유로 목적을 바꾸지 않는다.

Drawing IDE의 현재 제품 방향은 PRD에 정의된 Windows 설치형의 확장 가능한 플랫폼 MVP다. Rhino·Revit·선정 CAD의 기본 제어와 네이티브 결과, 시각적 진행·개입, 공통 데이터·기억·권한·확장 기반이 중심이다. 전문 법규·구조·평면 자동화는 이후 스킬이다.

이는 가이드가 새로 선택하는 범위가 아니다. 제품을 설명하는 근거는 PRD이고, 이 장은 그 결정에서 다음 명세를 어떻게 도출하는지 설명한다.

사람이 확인할 것

‘기본 제어’가 연결 표시만을 뜻하지 않는지, 네이티브 결과와 편집성의 요구가 있는지, 전문 스킬과 기반 보호가 구분되는지 확인한다. 여러 호스트를 포함한 플랫폼을 한 호스트의 매스 수정 도구로 바꾸지 않는다.

AutoCAD·ZWCAD의 조합, 실제 호스트 버전, 각 호스트의 기본 객체 종류, 웹 참여의 첫 배포 범위는 미정이다. 이 질문을 표시한 채 명확한 기능의 SPEC 작성은 시작할 수 있다. 관련 구현·지원 선언에는 먼저 결정이 필요하다.

호스트 버전은 연결할 원본 프로그램의 제품 버전·에디션·업데이트 수준이다. 실제 설치 정보를 모르면 조사 항목으로 남기며, AI가 임의 버전을 채우지 않게 한다.

단계의 산출물과 종료 조건

산출물은 제품 범위가 읽히는 PRD다. 필요한 경우 PRD 안의 범위표와 결정 항목을 보완한다. 별도 MVP_SCOPE 문서를 만들어 같은 범위를 다시 관리하지 않는다.

후속 전문 스킬이 없어도 사용 가능한 공통 행동, 네이티브 품질, 외부 검토 역할, 미정·제외 기능을 사람이 설명할 수 있으면 핵심 SPEC 작성으로 넘어간다.

03 / SPEC — 기능이 정확히 어떻게 동작해야 하는지 정한다

SPEC은 기능 동작 명세다. 구현할 기술을 먼저 고르기보다, 사용자와 시스템 사이에서 일어날 일과 결과를 명확히 한다.

예를 들어 ‘핀 가능’만으로는 부족하다. 핀한 뒤 선택을 바꾸거나, 대상이 삭제되거나, 프로젝트를 다시 열었을 때 어떻게 보존·표시할지 정해야 한다. 다만 JSON 필드명, DB 인덱스, 정확한 HTTP 경로는 구현계획에서 정해도 된다.

호스트별 지원표를 SPEC에서 구체화한다

지원 호스트·버전, 읽을 대상, 생성·수정할 객체, 필수 속성, 후속 편집, 저장 후 유지, 제한과 미지원 상태를 기록한다. PRD의 ‘Revit 네이티브 객체’는 여기서 실제 어떤 객체와 동작을 뜻하는지 좁혀진다.

형상이 비슷한가만 보지 않는다. 선언한 객체 유형과 필수 의미, 호스트 기본 편집 동작이 무엇인지 수용 기준으로 둔다. 매스에서 출발했는지, 어떤 생성 방법을 택했는지는 최종 결과의 객체 유형과 동작을 대신하지 않는다.

06 / 목업과 핵심 기술 실험은 구현계획과 함께 검토한다

목업은 이해 가능성을, 기술 실험은 구현 가능성을 확인한다. 둘을 같은 성공으로 취급하지 않는다.

작은 기술 실험 정확한 문서·네이티브·중단·설치가 가능한가? API 문서가 있으니 모든 객체 지원
실제 종단 간 기능 화면과 실행·호스트·결과가 연결되는가? 한 번 성공했으니 플랫폼 전체 완료

SPEC·Design의 핵심이 정리된 뒤 구현계획을 세우면서 프런트 목업을 병행한다. 불확실성이 큰 API·설치·네이티브 제어는 이를 기다리지 않고 작은 검증을 먼저 수행할 수도 있다. 기술 실험이 요구를 바꾸면 그 결정을 해당 문서로 되돌린다.

먼저 실험할 가치가 큰 경계

문서 두 개 사이의 정확한 대상 식별, 선언한 네이티브 유형의 생성·재편집·저장, 스케치의 좌표 유지, 새 지시 뒤 늦은 결과 보호, 큰 모델의 관련 정보 조회, 설치 환경·작은 확장 중 구조 선택을 바꿀 수 있는 질문 하나를 고른다.

여러 위험을 한 번의 거대한 데모로 합치지 않는다. 실험마다 질문·방법·환경·예상 결과·실제 결과·한계를 남긴다. 실호스트가 없으면 계약·모의 시험의 범위만 보고한다.

07 / 테스트 계획과 TDD는 역할이 다르다

테스트 계획은 어떤 조건을 어떤 환경에서 검증할지 정하는 계획이다. TDD는 작은 테스트를 먼저 작성하고 실패를 확인한 뒤 구현·리팩터링하는 개발 방식이다. 구현을 모두 끝낸 다음 ‘TDD 단계’를 따로 수행하는 것으로 이해하지 않는다.

COPYABLE TEXT
TDD 대상 로직
  기대 동작 테스트 작성 → 예상 이유로 실패 확인
  → 최소 구현 → 통과 확인 → 리팩터링·회귀 확인

초기에는 구현계획 안에 테스트 전략과 task별 검증을 함께 둔다. 복잡해졌을 때만 TEST_PLAN.md로 분리한다. 제품 수용 기준은 PRD·SPEC에서 가져오고, 시험 편의로 새 제품 요구를 발명하지 않는다.

이 제품에서 구분할 검사

검사 대상과 방법 한계
단위·계약 시험 핀 보존, 단위·참조, 지시 순서, 늦은 결과, 권한·상태 전이 실제 호스트 동작을 대신하지 않음
UI·통합 시험 공간 입력·상태·API 연결·오류·키보드·좁은 화면 시각적 유사함은 네이티브 유형 증거가 아님
실호스트 시험 실제 객체·필수 속성·후속 편집·저장·재열기·복구 시험한 호스트·버전·객체 범위만 검증
설치·운영 시험 지원 PC에서 설치·호스트 발견·설정·제거·자료 보존 개발 PC 성공만으로 배포 판정하지 않음
AI·사용자 평가 고정 사례의 의도·결과 품질·개입·시간·재작업 하나의 스냅샷 일치나 모델 자기평가로 대체하지 않음

결정적인 로직은 TDD 대상으로 정하기 좋다. 실제 CAD 호스트, 설치, 시각적 사용성, 설계 결과에는 별도의 통합·수동·기준 사례 검증도 필요하다. AI 출력의 자연어 문장 전체가 매번 똑같아야 하는 시험을 제품 품질과 혼동하지 않는다.

개발 중의 시험과 사용 중의 하네스도 다르다. 개발 때 오류를 촘촘하게 재현하는 것이 매 사용자 요청에 여러 LLM 검증자를 추가하라는 뜻은 아니다. 제품 실행에서는 필요한 대상·권한·조건·결과 확인을 유지하며 반복 비용을 줄인다.

08 / 작은 실제 기능을 구현하고 호스트를 확장한다

모든 프런트 페이지를 끝낸 뒤 백엔드와 호스트를 붙이는 방식보다, 화면 → 실제 처리 → 호스트 → 결과 표시가 이어지는 작은 기능을 먼저 완결한다.

플랫폼을 확인하는 순서의 예는 다음과 같다. 확정 일정표나 선택된 기술 스택은 아니다.

구현 묶음 확인할 실제 행동 범위의 의미
실행·입력 기반 프로젝트·입력·기록이 열리고 보존됨 AI 없는 작업 경로 포함
첫 호스트의 제한된 제어 정확한 대상 읽기·네이티브 변경·결과·저장 내부 alpha; 플랫폼 MVP 전체는 아님
AI·진행·개입 연결 요청·후보·새 지시·중단·재개가 실제 상태에 연결 데이터·원본 상태와 대화 분리
다른 선언 호스트 같은 공통 역할로 각 네이티브 제어를 제공 동등 깊이나 범용 변환을 약속하지 않음
작은 확장 등록·권한·진행·결과·오류가 공통 계약을 사용 전문 스킬의 품질 검증과 별개
설치·플랫폼 검수 선언한 모든 범위가 지원 환경에서 작동 단일 호스트·개발 PC 결과로 대체 불가

일부는 병행할 수 있다. 설치와 두 번째 호스트의 작은 실험을 마지막까지 미룰 필요는 없다. 순서 조정은 구현계획에서 하며 플랫폼 MVP를 특정 업무 앱으로 바꾸지는 않는다.

09 / 수용 검수·배포·전문 스킬 확장

검수는 구현자의 설명을 반복하는 작업이 아니라 SPEC의 수용 기준과 실제 결과를 대조하는 작업PRD §15 수용 시나리오(AC-01~28)와 SPEC의 수용 기준을 실제 결과와 대조하는 작업이다. 통과·실패·미시험을 구분하고, 정상 사례뿐 아니라 변경·끊김·중단·지연·저장 실패를 포함한다.

claudeR-11중간 수용 검수의 기준표가 PRD §15 AC-01~28인데 §09와 420행 요청문 어디에도 AC ID가 없어 검수가 SPEC 문장 대조로만 흐를 수 있음. PRD가 AC를 '구현과 출시 판단의 시험 기준'으로 정의했으니 검수 산출물(VERIFY)은 AC-NN별 통과/실패/미시험/해당 없음으로 집계하고, 420행 요청문에도 'PRD §15 AC-01~28별로'를 추가.

플랫폼 품질은 정확한 대상, 네이티브 편집성, 입력·조건 보존, 가시성·개입·복구·확장·설치다. 전문 스킬의 법규·구조·도면 품질은 별도다. 기본 벽 생성이 성공했다고 법규에 맞는 평면을 자동 설계할 수 있다고 표시하지 않는다.

사람에게 받을 검수 결과

잘못 선택된 객체를 찾아 제외할 수 있는지, 선을 다시 그리면 현재 작업에 반영되는지, 원본 변경과 후보를 구분하는지, 호스트에서 다시 편집할 수 있는지 확인한다. 코드 독해가 아니라 행동과 실제 결과를 검수한다.

작업 준비·대기·검토·수정·실패를 포함한 총시간과 비용을 기록한다. 데이터 크기는 객체 수뿐 아니라 기하 복잡도·속성·관계를 함께 남긴다. 목표치를 아직 측정하지 않았다면 ‘미정’으로, 측정할 수 없는 비용은 ‘미측정’으로 표시한다.

다음 스킬을 추가할 때

새 업무의 사용자 가치·범위를 PRD에서 채택하고, 기능·입력·도구·권한·근거·중간 결과·실패·완료 기준을 SPEC으로 정의한다. 추가 UI가 있으면 Design에 반영하고, 구현계획과 시험으로 내려간다. 공통 호스트 제어와 데이터·진행·권한을 매번 다시 만들지 않는다.

예정된 법규·사이트·매스 배치·구조·평면·개요·일람표 기능은 이 과정을 반복한다. 공개 마켓이나 복잡한 전문 하네스 전체를 처음부터 만들어야만 스킬을 추가할 수 있는 구조는 피한다.

AI 요청문 · MVP 수용 검수와 출시 판단

11 / 제품의 중요한 결정을 개발에 연결하는 법

이 장은 PRD에 있는 요구를 기술로 옮기는 질문을 설명한다. 새로운 제품 범위를 확정하지 않는다.

claudeR-13낮음 §11의 고유 가치는 주제별로 PRD→SPEC→구현계획 어디서 무엇을 정하는지 나누는 것인데, 각 소절이 PRD 규칙을 다시 씀(481행 방화벽·펜·터치·대형 모델=PRD §12.5, 489행 rule book=PRD §4.3, 493행 캔버스/HTML 미정=PRD §0·§4.4·§12.6). SPEC 작성자가 이 장을 읽으면 PRD와 미묘하게 다른 두 번째 요구 문장을 보게 됨. '주제 | PRD 근거(FR/OQ/C ID) | SPEC이 정할 것 | 구현계획이 정할 것' 표 하나로 바꾸고 재서술 문장은 삭제.

네이티브 객체

PRD에서 결과의 성격을 정하고, SPEC에서 지원 객체·필수 속성·재편집·저장 지속성을 정한다. 구현계획에서 생성 API·실행 문맥·검증 방법을 결정한다. 화면상 유사함이나 카테고리 이름만으로 완료하지 않는다. 모든 네이티브 유형과 이력을 동시에 지원하려고 하지 않는다.

Windows 설치형과 외부 웹

PRD의 주 작업자는 Windows 설치형이고 외부 검토는 웹 참여다. SPEC은 설치·미지원 상태·사용 권한·웹 제출·오프라인의 의미를 정한다. 구현계획은 앱 구성, 로컬 통신, 공유·인증·호스트 애드인·업데이트를 결정한다.

같은 PC 내부 통신, 클라우드 호출, 외부 기기의 작업 PC 접근을 구분해 설계한다. 기업 보안 정책을 우회하거나 방화벽 전체 해제를 전제로 하지 않는다. ‘웹이므로 모든 기기에서 같다’고 가정하지 말고 펜·터치·저장·대형 모델을 실제 지원 환경에서 확인한다.

건축 데이터와 문맥

PRD는 대상·형상·속성·관계·근거·작업의 연결을 요구한다. SPEC은 어떤 관계를 읽고 갱신하는지 정한다. 구현계획은 DB·형상 저장·질의·무효화·AI 입력 구성 방식을 정한다. 전체 프로젝트를 완벽하게 분류하거나 매 요청에 모두 넣는 것을 전제하지 않는다.

기본 하네스와 전문 하네스

대상·권한·단위·상태·개입·중복·직접 수정 보호는 공통 구현이다. 전문 검토 기준과 분야별 사례·계산·평가는 스킬 구현에서 보강한다. rule book의 문장만으로 프로그램이 강제해야 할 규칙을 대신하지 않는다.

후보 기능: HTML 산출물 직접 편집

기본 산출물 표시·HTML 공유와 즉석 생성·부분 선택·수정·재생성은 분리한다. 후자는 PRD의 후보 C-01이며 지금 MVP task로 넣지 않는다. 채택한다면 사용자 시나리오, 부분의 원본 대응, 편집 권한, 근거 보존, 화면 방식과 격리를 작은 실험으로 확인한다. 캔버스와 직접 HTML 방식은 미정이다.
