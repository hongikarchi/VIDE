검토자 필터는 코멘트·부록만 바꿉니다. ‘인라인 제안 미리보기’는 코멘트의 대안까지 합친 최종본이 아닙니다. 보기 전환은 MD 수정·수락·승인을 하지 않습니다.

용도: 제품 기획에서 실제 구현·검수까지, 사람이 무엇을 결정하고 AI에게 무엇을 맡길지 확인하는 안내서다.
제품 결정의 기준: PRD.md. 이 가이드는 별도의 제품 요구사항이나 확정 Stack을 만들지 않는다.

PRD는 제품의 약속, SPEC은 기능의 동작, Design.md는 사람의 경험, 구현계획은 기술·작업·검증의 방법을 정한다.

00 / 개발의 전체 흐름

이 프로젝트에서는 문서를 제품 기획·설계와 개발 설계·실행으로 구분한다. 정상 진행의 기준 순서는 다음과 같다.

claudeR-38높음 추가 지적 · G2 검토 루프. AI.md 0.4 §5는 스레드·철회·부록 교체와 '이견은 사용자 최종 선택'을 정했지만 라운드 상한, 보류→OQ 같은 제3의 해소 결과, SPEC-00-common 착수를 실제로 막는 항목의 구분이 없어 4개 문서 100여 건의 해소가 단일 소유자에게 일괄로 걸리고, Codex R-20·R-29·R-31이 '사용자 확정 먼저'를 조건으로 걸었으므로 SPEC 착수 시점이 정의되지 않는다. 수락·거부·철회 시 코멘트와 부록 행을 지우므로 결정의 근거·버린 대안은 채팅과 git 이력에만 남고, ADR은 OQ·PLAN 장 인용으로 한정돼 검토 단계의 제품 결정(터미널 범위, 워크셰어링, 범위 등급 등)이 갈 곳이 없다. §12의 '메모 위젯' 문장은 위젯 제거(af4389f)로 무효다. 제안: §00 확정 단계에 (1) 문서당 AI 라운드 = 지적+답변 2회 상한, 이후 사용자가 재개한 항목만 (2) 해소 결과에 '보류 → OQ 또는 SPEC 착수 시 확인 목록' 추가 (3) SPEC-00 착수를 막는 항목을 지금 명명(PRD 범위 등급·FR↔AC·상태 모델·후보/원본·뷰 전제·Design 상태표 등 8건 내외)하고 그 외는 review 상태로 SPEC 입력 가능 (4) 검토 라운드당 ADR 1건(항목 | 판단 | 최종 문구 | 근거 | 버린 대안 | 출처 R-ID)을 결정 기록으로 두고 AI.md §7에 '검토 해소 기록' 인용을 허용하는 첨삭 제안. §12 메모 위젯 문장 삭제. 바꿀 결정: §00 종료 규칙·결정 기록 위치·§12.

codexR-43높음 답변 · Claude R-38 · 부분 동의. 검토 종료와 결정 기록. 보류를 영향 OQ·착수 확인 목록으로 옮기고 현재 작업을 막는 쟁점만 우선 결정하자는 제안에 동의한다. 그러나 사용자가 몇 번 더 비교하려는 흐름에 지적+답변 두 회 상한을 강제하지 않는다. 새 근거 없는 반복을 줄이는 권고면 충분하다. 의미 있는 제품 선택은 기존 ADR-001~009에 모으고 작은 문구 해소는 Git 이력·출처 링크로 추적하면 되므로 라운드당 ADR 하나도 필수는 아니다. 제거된 메모 위젯의 설명은 본문 수락 정리 때 삭제할 것을 권한다.

AI.md §8 관문의 PLAN은 '첫 티켓 장만 채운 PLAN'으로 해석. 바꿀 결정: §00 축약 경로·요청문 범위 인자.

codexR-42높음 답변 · Claude R-37 · 부분 동의. 첫 기능에 필요한 문서 양. 요청문에 범위를 명시하고 첫 티켓에 필요한 내용만 쓰자는 제안에 동의한다. 다만 원문도 모든 기능에 완성된 PLAN 9장·SPIKE·ADR 전부를 요구한다고 단정할 수는 없다. 검토와 확정은 다르다. 두 검토자의 의견 일치나 HTML의 인라인 미리보기는 사용자 승인이나 파일 변경이 아니며, 첨삭의 해소는 사용자만 한다(AI.md §5). 재검토 횟수는 사용자 의도에 따르고, 검토 요청 자체는 SPEC·PLAN·제품 코드 작성의 위임이 아니다.

한 번 쓰고 끝내는 일방향 절차는 아니다. 기능 의미가 불명확하면 SPEC으로, 사람이 이해하기 어려우면 Design으로, 기술·작업 순서가 맞지 않으면 구현계획으로 돌아간다. 제품의 약속 자체가 바뀌면 PRD의 결정이 필요하다.

특정 위험을 확인하는 작은 기술 실험은 SPEC의 미정 사항을 풀기 위해 먼저 할 수 있다. 다만 기술 실험이나 러프 화면이 곧 확정된 Stack·기능 명세·제품 구현이 되는 것은 아니다. 핵심 기능과 상태를 정하지 않은 채 전체 Stack과 모든 화면을 확정하지 않는다.

사람과 AI의 역할

사람은 지원 범위, 원하는 결과, 변경·공개 권한과 채택 기준을 결정한다. AI는 모순을 찾고, 기능을 구체화하고, 기술을 비교·실험하고, 정한 범위를 구현·시험한다. 범위 안의 국소 결정을 전부 사람에게 되묻지 않되 제품 범위와 권한의 변경을 숨기지 않게 한다.

제품을 개발하는 AI의 티켓과 완성된 IDE 안에서 설계를 수행하는 AI의 작업은 다르다. 이 안내서는 전자의 개발을 진행하는 방법이며, 후자의 사용자 경험과 보호 규칙은 PRD·SPEC에서 가져온다.

01 / 네 문서의 역할을 고정한다

AI.md는 문서 형식과 산출물 위치를, 이 가이드는 절차를 소유한다. 가이드에 별도 폴더 정본을 복제하지 않는다.

테스트 계획은 구현계획의 한 장과 각 task의 검증 항목으로 시작한다. 커졌을 때만 TEST_PLAN.md로 분리한다. MVP 범위는 PRD 안에, 호스트별 세부 지원은 SPEC 안에, Stack·기술 결정은 구현계획 안에 둔다. 구현계획의 마스터는 docs/plans/PLAN.md 하나이며, 분할 PLAN-NN-<slug>.md는 장이 커지거나 별도 검토가 필요할 때만 만들고 마스터와 분할 파일에 같은 티켓 내용을 복제하지 않는다(작업 ID와 내용은 한 곳에 두고 분할 문서는 링크로 연결한다).

DEVELOPMENT_GUIDE.md는 이 네 문서를 작성·활용하는 안내서다. 복사용 AI 요청문은 이 가이드 안의 ‘AI 요청문’ 블록이 원본이며 별도 AI_PROMPTS.md는 두지 않는다. 이 가이드를 별도의 제품 기준으로 사용하지 않는다.

현재 읽을 문서와 다음 작성할 문서

이 자료 묶음에는 PRD, Design의 원칙·기본 화면 기준, 개발 가이드와 그 안의 ‘AI 요청문’ 블록이 있다. SPEC은 docs/specs/SPEC-00-common.md 초안까지, 구현계획은 docs/plans/PLAN.md의 일부 장 초안까지 있고 기능별 SPEC-NN-<slug>.md와 나머지 장은 아직 없다. Design의 상세 화면·상태는 SPEC과 대조하여 구체화해야 하며, 이 가이드의 예시가 확정 명세나 구현 완료 티켓을 뜻하지 않는다.

다음 실제 기획 산출물은 사용자가 문서 검토를 확정한 뒤 작성하는 docs/specs/SPEC-00-common.md와 첫 기능 SPEC-NN-<slug>.md 초안이다. 지금 단계는 문서 검토·확정이며(§00), 모든 후속 기능의 첨삭을 먼저 해소해야 한다거나 검토 요청만으로 SPEC 작성이 위임된다는 뜻은 아니다. PRD의 미정 사항은 해당 기능과 연결해 남기고, 명확한 기능부터 작성한다. 빈 파일을 만들어 ‘명세 완료’로 취급하지 않는다.

문서를 늘리기 전에 확인한다

같은 요구를 복사하지 말고 참조한다. SPEC·시험 기록은 AI.md §2의 분할 단위를 따르되 실제 내용이 생길 때 파일을 만든다. 그 밖의 문서는 커졌을 때만 분리한다. 첫 작업부터 전체 폴더와 템플릿을 채우지 않는다. 새로운 파일을 만들 때는 기존 어느 장을 맡는지 명확히 하여 두 기준이 동시에 생기지 않게 한다.

02 / PRD — 무엇을 만들 것인지 확인한다

PRD에서 결정할 것은 제품의 약속과 범위다. 작성 도중 새로운 기술을 추천받았다는 이유로 목적을 바꾸지 않는다.

VIDE의 현재 제품 방향은 PRD에 정의된 Windows 설치형 로컬 IDE와 웹 검토 환경을 포함한 확장 가능한 플랫폼 MVP다. Rhino·ZWCAD의 기본 제어와 네이티브 결과, 호스트 간 연계·병렬 실행, 시각적 진행·개입, 기본 조회·집계, 검토본·웹 공유·의견, 작은 확장의 실제 실행, 공통 데이터·기억·권한 기반이 중심이다(PRD §14.1·§14.2). 전문 법규·구조·평면 자동화는 이후 스킬이다.

이는 가이드가 새로 선택하는 범위가 아니다. 제품을 설명하는 근거는 PRD이고, 이 장은 그 결정에서 다음 명세를 어떻게 도출하는지 설명한다.

사람이 확인할 것

‘기본 제어’가 연결 표시만을 뜻하지 않는지, 네이티브 결과와 편집성의 요구가 있는지, 전문 스킬과 기반 보호가 구분되는지 확인한다. 여러 호스트를 포함한 플랫폼을 한 호스트의 매스 수정 도구로 바꾸지 않는다.

첫 출시 호스트는 Rhino·ZWCAD로 확정되었고(PRD §14.1) 웹의 열람·탐색·의견 작성도 MVP에 포함된다(PRD §14.2·§14.4). 실제 호스트 버전·에디션(OQ-02), 각 호스트의 기본 객체 종류(OQ-03), 웹 지원 브라우저·기기·공유/의견 동작(OQ-04)은 남은 결정이다. 이 질문을 표시한 채 명확한 기능의 SPEC 작성은 시작할 수 있다. 관련 구현·지원 선언에는 먼저 결정이 필요하다.

호스트 버전은 연결할 원본 프로그램의 제품 버전·에디션·업데이트 수준이다. 실제 설치 정보를 모르면 조사 항목으로 남기며, AI가 임의 버전을 채우지 않게 한다.

단계의 산출물과 종료 조건

산출물은 제품 범위가 읽히는 PRD다. 필요한 경우 PRD 안의 범위표와 결정 항목을 보완한다. 별도 MVP_SCOPE 문서를 만들어 같은 범위를 다시 관리하지 않는다.

후속 전문 스킬이 없어도 사용 가능한 공통 행동, 네이티브 품질, 외부 검토 역할, 미정·제외 기능을 사람이 설명할 수 있으면 핵심 SPEC 작성으로 넘어간다.

03 / SPEC — 기능이 정확히 어떻게 동작해야 하는지 정한다

SPEC은 기능 동작 명세다. 구현할 기술을 먼저 고르기보다, 사용자와 시스템 사이에서 일어날 일과 결과를 명확히 한다.

예를 들어 ‘핀 가능’만으로는 부족하다. 핀한 뒤 선택을 바꾸거나, 대상이 삭제되거나, 프로젝트를 다시 열었을 때 어떻게 보존·표시할지 정해야 한다. 다만 JSON 필드명, DB 인덱스, 정확한 HTTP 경로는 구현계획에서 정해도 된다.

지원 호스트·버전, 읽을 대상, 생성·수정할 객체, 필수 속성, 후속 편집, 저장 후 유지, 제한과 미지원 상태를 기록한다. PRD §12.1의 네이티브 결과 요구는 여기서 선언한 호스트(첫 출시는 Rhino·ZWCAD)의 실제 객체 종류와 동작으로 좁혀진다. PRD의 Revit 벽 예시는 설명용이며 첫 출시 포함을 뜻하지 않는다.

형상이 비슷한가만 보지 않는다. 선언한 객체 유형과 필수 의미, 호스트 기본 편집 동작이 무엇인지 수용 기준으로 둔다. 매스에서 출발했는지, 어떤 생성 방법을 택했는지는 최종 결과의 객체 유형과 동작을 대신하지 않는다.

04 / Design.md — 기능을 사람이 보고 조작하게 만든다

다음 네 가지가 채워지면 나머지 장은 비워 둔 채 첫 티켓의 구현을 시작한다. AI.md §8은 이 조건을 착수 전제로 참조한다.

  • ③ 관련 구조 위험의 증거(SPIKE 기록) 또는 안전한 대체 경로가 있음

위험 실험 하나가 끝났다는 이유만으로 시작하거나 모든 작업에 같은 실험을 강제하지 않는다. 적용은 티켓별로 판단하며, 호스트가 없는 작업에 실호스트 환경을 요구하거나 이미 허용된 범위를 매번 재승인받는 절차로 만들지 않는다. 먼 기능은 미정으로 둘 수 있고, PLAN의 review 표기만으로 충족했다고 보지 않는다.

먼저 실험할 가치가 큰 경계

문서 두 개 사이의 정확한 대상 식별, 선언한 네이티브 유형의 생성·재편집·저장, 스케치의 좌표 유지, 새 지시 뒤 늦은 결과 보호, 큰 모델의 관련 정보 조회, 설치 환경·작은 확장 중 구조 선택을 바꿀 수 있는 질문 하나를 고른다.

07 / 테스트 계획과 TDD는 역할이 다르다

테스트 계획은 어떤 조건을 어떤 환경에서 검증할지 정하는 계획이다. TDD는 작은 테스트를 먼저 작성하고 실패를 확인한 뒤 구현·리팩터링하는 개발 방식이다. 구현을 모두 끝낸 다음 ‘TDD 단계’를 따로 수행하는 것으로 이해하지 않는다.

TDD 대상 로직
  기대 동작 테스트 작성 → 예상 이유로 실패 확인
  → 최소 구현 → 통과 확인 → 리팩터링·회귀 확인

초기에는 구현계획 안에 테스트 전략과 task별 검증을 함께 둔다. 복잡해졌을 때만 TEST_PLAN.md로 분리한다. 제품 수용 기준은 PRD·SPEC에서 가져오고, 시험 편의로 새 제품 요구를 발명하지 않는다.

결정적인 로직은 TDD 대상으로 정하기 좋다. 실제 CAD 호스트, 설치, 시각적 사용성, 설계 결과에는 별도의 통합·수동·기준 사례 검증도 필요하다. AI 출력의 자연어 문장 전체가 매번 똑같아야 하는 시험을 제품 품질과 혼동하지 않는다.

개발 중의 시험과 사용 중의 하네스도 다르다. 개발 때 오류를 촘촘하게 재현하는 것이 매 사용자 요청에 여러 LLM 검증자를 추가하라는 뜻은 아니다. 제품 실행에서는 필요한 대상·권한·조건·결과 확인을 유지하며 반복 비용을 줄인다.

08 / 작은 실제 기능을 구현하고 호스트를 확장한다

모든 프런트 페이지를 끝낸 뒤 백엔드와 호스트를 붙이는 방식보다, 화면 → 실제 처리 → 호스트 → 결과 표시가 이어지는 작은 기능을 먼저 완결한다.

플랫폼을 확인하는 순서의 예는 다음과 같다. 확정 일정표나 선택된 기술 스택은 아니다.

구현 묶음 확인할 실제 행동 범위의 의미
실행·입력 기반 프로젝트·입력·기록이 열리고 보존됨 AI 없는 작업 경로 포함
첫 호스트의 제한된 제어 정확한 대상 읽기·네이티브 변경·결과·저장 내부 alpha; 플랫폼 MVP 전체는 아님
AI·진행·개입 연결 요청·후보·새 지시·중단·재개가 실제 상태에 연결 데이터·원본 상태와 대화 분리
다른 선언 호스트 같은 공통 역할로 각 네이티브 제어를 제공 동등 깊이나 범용 변환을 약속하지 않음
웹 공유·의견 허용 범위의 최신 상태 공유와 핀·코멘트·스케치 제출·로컬 작업 연결 원격 실행·원본 편집은 제외
작은 확장 등록·권한·진행·결과·오류가 공통 계약을 사용 전문 스킬의 품질 검증과 별개
설치·플랫폼 검수 선언한 모든 범위가 지원 환경에서 작동 단일 호스트·개발 PC 결과로 대체 불가

일부는 병행할 수 있다. 설치와 두 번째 호스트의 작은 실험을 마지막까지 미룰 필요는 없다. 순서 조정은 구현계획에서 하며 플랫폼 MVP를 특정 업무 앱으로 바꾸지는 않는다.

claudeR-40중간 추가 지적 · G1 절차 무게. §08 묶음 표는 alpha→다중 호스트→확장→설치로 이어지지만 1인 개발자가 측정된 소요·검수 결과로 플랫폼 범위(호스트 수·웹 깊이)를 다시 정하는 시점이 없다. 이 문장 자체는 '특정 업무 앱으로 바꾸지 않는다'일 뿐 호스트 수 축소를 금하지 않고, PRD §14.4는 '조용한 축소'만 금지하며 §16.3은 목표 미달 시 범위 조정을 허용하므로 명시적 재결정은 PRD와 충돌하지 않는다 — 다만 Codex R-43(3단계)·R-44(OQ 시점) 어느 쪽도 'alpha 결과를 보고 PRD 범위를 다시 정하는' 사람의 결정 지점을 두지 않아 실패 인식이 늦고 매몰이 커진다. 제안: §08 표 '첫 호스트의 제한된 제어' 행 뒤에 '범위 재결정 체크포인트' 행 — 입력: 첫 호스트 VERIFY·실제 소요·미해결 OQ; 출력: 호스트 수(OQ-01)·둘째 호스트 순서·웹 깊이(OQ-04)의 유지/축소를 ADR로 기록하고 PRD §14.1·§18에 역링크. 이 문장은 '순서 조정은 PLAN, 범위 조정은 이 체크포인트의 PRD 결정'으로 고친다. PRD 쪽 대응 지적(§14.4 alpha 판정 관문)과 한 쌍. 바꿀 결정: §08 표·문장.

09 / 수용 검수·배포·전문 스킬 확장

검수는 구현자의 설명을 반복하는 작업이 아니라 PRD §15 수용 시나리오 중 해당 배포에 적용되는 AC 전체와 SPEC의 수용 기준을 실제 결과와 대조하는 작업이다. 통과·실패·미시험·해당 없음을 실제 AC ID별로 구분하고, 정상 사례뿐 아니라 변경·끊김·중단·지연·저장 실패를 포함한다.

플랫폼 품질은 정확한 대상, 네이티브 편집성, 입력·조건 보존, 가시성·개입·복구·호스트 간 연계·웹 공유·확장·설치다. 전문 스킬의 법규·구조·도면 품질은 별도다. 기본 벽 생성이 성공했다고 법규에 맞는 평면을 자동 설계할 수 있다고 표시하지 않는다.

사람에게 받을 검수 결과

잘못 선택된 객체를 찾아 제외할 수 있는지, 선을 다시 그리면 현재 작업에 반영되는지, 원본 변경과 후보를 구분하는지, 호스트에서 다시 편집할 수 있는지 확인한다. 코드 독해가 아니라 행동과 실제 결과를 검수한다.

작업 준비·대기·검토·수정·실패를 포함한 총시간과 비용을 기록한다. 데이터 크기는 객체 수뿐 아니라 기하 복잡도·속성·관계를 함께 남긴다. 목표치를 아직 측정하지 않았다면 ‘미정’으로, 측정할 수 없는 비용은 ‘미측정’으로 표시한다.

다음 스킬을 추가할 때

새 업무의 사용자 가치·범위를 PRD에서 채택하고, 기능·입력·도구·권한·근거·중간 결과·실패·완료 기준을 SPEC으로 정의한다. 추가 UI가 있으면 Design에 반영하고, 구현계획과 시험으로 내려간다. 공통 호스트 제어와 데이터·진행·권한을 매번 다시 만들지 않는다.

예정된 법규·사이트·매스 배치·구조·평면·개요·일람표 기능은 이 과정을 반복한다. 공개 마켓이나 복잡한 전문 하네스 전체를 처음부터 만들어야만 스킬을 추가할 수 있는 구조는 피한다.

네이티브 객체

PRD에서 결과의 성격을 정하고, SPEC에서 지원 객체·필수 속성·재편집·저장 지속성을 정한다(PRD §12.1·FR-04·OQ-03). 구현계획에서 생성 API·실행 문맥·검증 방법을 결정한다. 화면상 유사함이나 카테고리 이름만으로 완료하지 않는다. 모든 네이티브 유형과 이력을 동시에 지원하려고 하지 않는다.

Windows 설치형과 외부 웹

PRD의 주 작업자는 Windows 설치형 로컬 IDE이고, 웹은 열람·탐색·의견 작성까지를 MVP로 포함한다(PRD §1.3·§12.5·§14.4·FR-17·FR-19·OQ-04). AI 실행 시작·진행 중 개입·원본 반영 승인은 로컬 IDE에서 수행한다. SPEC은 설치·미지원 상태·사용 권한·웹 제출·오프라인의 의미를 정한다. 구현계획은 앱 구성, 로컬 통신, 공유·인증·호스트 애드인·업데이트를 결정한다.

같은 PC 내부 통신, 클라우드 호출, 외부 기기의 작업 PC 접근을 구분해 설계한다. 기업 보안 정책을 우회하거나 방화벽 전체 해제를 전제로 하지 않는다. ‘웹이므로 모든 기기에서 같다’고 가정하지 말고 펜·터치·저장·대형 모델을 실제 지원 환경에서 확인한다.

건축 데이터와 문맥

PRD는 대상·형상·속성·관계·근거·작업의 연결과 기본 조회·필터·그룹·집계·표 갱신을 요구한다(PRD §6·§6.6·§10·FR-09·FR-22). SPEC은 어떤 관계를 읽고 갱신하는지 정한다. 구현계획은 DB·형상 저장·질의·무효화·AI 입력 구성 방식을 정한다. 전체 프로젝트를 완벽하게 분류하거나 매 요청에 모두 넣는 것을 전제하지 않는다.

기본 하네스와 전문 하네스

대상·권한·단위·상태·개입·중복·직접 수정 보호는 공통 구현이다(PRD §4.3·FR-10·FR-11·FR-18·FR-21). 전문 검토 기준과 분야별 사례·계산·평가는 스킬 구현에서 보강한다. rule book의 문장만으로 프로그램이 강제해야 할 규칙을 대신하지 않는다.

후보 기능: HTML 산출물 직접 편집

기본 산출물 표시·HTML 공유와 즉석 생성·부분 선택·수정·재생성은 분리한다(PRD C-01·§4.4·§12.6·OQ-08). 후자는 PRD의 후보 C-01이며 지금 MVP task로 넣지 않는다. 채택한다면 사용자 시나리오, 부분의 원본 대응, 편집 권한, 근거 보존, 화면 방식과 격리를 작은 실험으로 확인한다. 캔버스와 직접 HTML 방식은 미정이다.

12 / 현재의 다음 작업과 개인 검토 기록

다음 산출물은 사용자가 문서 검토를 확정한 뒤 docs/specs/SPEC-00-common.md 초안, 첫 기능 SPEC-NN-<slug>.md(이 가이드의 예시인 핀, FR-05), docs/specs/hosts/<host>.md 초안을 병행해 쓰는 것이다. 공통 SPEC은 첫 기능에 필요한 만큼 구체화하며 후속 호스트 OQ까지 닫는 관문으로 두지 않는다. 호스트 지원표 초안은 확인 사실·후보·미정을 나누어 먼저 쓸 수 있고, 지원 선언은 관련 OQ(OQ-02·03) 결정과 실증 뒤에 한다. 아래 표에서 호스트·어댑터·네이티브 결과 세 행은 PRD §5·§12.1의 요약이며 정식 정의는 PRD가 소유한다. 나머지는 이 가이드의 공정 용어다.

네이티브 결과 지원 객체 유형·의미와 약속한 원본 편집 동작을 갖는 결과

한 요구가 바뀌면 그 의미를 소유하는 문서에서 먼저 수정하고 영향을 받는 문서·코드·시험을 맞춘다. 단순 라이브러리 교체로 PRD를 바꿀 필요는 없지만, 기본 제어 범위나 원본 권한이 달라지면 제품 결정이 필요하다.

이 안내서의 단계·템플릿·예시는 이 프로젝트를 운영하기 위한 기준이다. 특정 프레임워크의 채택, 미래 지원 버전, API의 실제 동작, 전문 스킬의 성능을 검증한 결과가 아니다. 실제 기술을 정할 때는 공식 자료와 목표 환경의 시험을 함께 확인한다.
