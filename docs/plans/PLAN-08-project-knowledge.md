# PLAN-08 — 프로젝트 지식 DB

2026-09-28~29 사용자 요청의 단계 계획이다. 요청 내용은 메일·첨부·회의록을 모아 누가 무엇을 말했는지, 주요 쟁점, 진행 경과를 DB로 정리하고, 질문 답변·도면/모델 크리틱에 쓰며, 여러 팀원이 함께 쌓는 것까지 목표로 한다. 원본은 회사 서버에 있을 가능성이 높다. 파악과 선택 근거는 [RESEARCH-06](../research/RESEARCH-06-project-knowledge.md), 저장·공유 구조의 결정 초안은 [ADR-018](../decisions/ADR-018-project-knowledge-store.md)이 소유한다.

2026-09-29 추가 요청과 판단:

- **경로 하나로 구축:** 사용자가 회사 서버의 프로젝트 폴더 경로만 주면, 규칙·파서·Jev가 먼저 거르고 LLM은 선별된 구간에만 쓴다(RESEARCH-06 §7.5의 ①~⑦ 층). 도면 안의 표기와 “어느 파일이 무엇을 말했나”를 근거 구간 단위로 남긴다(§7.4).
- **위치:** 모든 프로젝트에 들어가는 기본 기능이므로 JIG가 아니라 왼쪽 레일의 “프로젝트 자료”로 둔다(§7.6). JIG는 이 DB를 읽기만 한다.

## 착수 조건

- **제품 결정:** PRD §4.4 C-02(첨삭 R-74)는 2026-09-29 채택됐다(결정 A9, 사용자 "프로젝트 자료 jig도 수정해야 해"). 1차 제품 작업은 아래 K0-T3의 연결을 따른다.
- **구조 결정:** ADR-018의 공동 축적 예외(지식 기록만 여러 PC)와 팀 공용 원본 위치. K5 착수 전까지 정하면 되고, K0~K4는 로컬만으로 진행할 수 있다.
- **RESEARCH-06 §12 결정:** 회사 정책(외부 저장·외부 AI 처리), 역할과 공개 범위, 자료 폴더, 표본 자료.
- **동작 계약:** 채택되면 K0 결과로 새 SPEC(프로젝트 지식, 번호는 작성 시 다음 빈 번호. SPEC-06은 구조 해석, SPEC-07은 jig 플랫폼이 사용)을 먼저 쓴다. 출처·역할·상태 규칙은 SPEC-03.4를 확장한다.
- **진행 중 작업과의 관계:** 현재 우선순위(Rhino·CAD 연결 왕복과 Sync 성능)를 막지 않는다. 아래 T-025~031은 제안 번호이며 채택 뒤 마스터 PLAN에 등록한다.

## 처음부터 지킬 기록 구조

K1부터 아래 규칙을 지키면 K5에서 데이터를 옮기지 않고 공동 축적으로 넓힐 수 있다. 물리 스키마는 ARCH-01에 정한다.

- 모든 기록(자료 등록, 근거 구간, 진술, 확정·기각, 대체, 별칭 합치기, 관측)은 **전역 고유 ID·작성자·기록 시각을 가진 사건**으로 쌓기만 한다. 수정·삭제 대신 새 사건을 남긴다.
- 진술은 유효 시작·끝과 기록 시각의 **두 시간축**을 가진다.
- 원본은 복사하지 않고 **위치 참조(UNC 또는 프로젝트 루트 상대 경로) + 내용 해시**로 등록한다.
- 자료마다 **공개 범위**(팀 / 특정 멤버 / 나만)와 **AI 전송 허용**을 가진다.
- 기하 관측은 모델 Sync/체크포인트 ID와 계산 방법을 함께 저장한다.

## 단계

각 단계는 앞 단계만으로도 쓸모가 있어야 하며, 다음 단계는 앞 단계의 실제 사용 결과를 보고 조정한다.

### K0 · 실제 프로젝트 1건으로 DB 구축(SPIKE) — T-025 제안

2026-09-29 사용자 요청: S-06 프로젝트의 회사 서버 폴더 전체를 실제로 SQLite DB로 만들어 보고, 그 과정을 정리해 VIDE 기능(K1·K2)으로 옮긴다. 이 단계는 제품 코드가 아닌 실험이며, 같은 과정에서 Jev의 효과를 잰다.

**지금까지 확인한 것(RESEARCH-06 §7.3)**

- 서버 폴더 전체 목록은 Jev 없이 파일 시스템만으로 25.6초에 읽혔다. 파일 6,286개, 61.5GB, 문자 정보가 많은 형식 약 450개.
- 메일 백업 EML 97통은 표준 MIME 처리만으로 모두 해독된다.
- Office 메모는 0건이고, PDF 주석은 사각형 도형뿐이다.
- **Jev가 빠르거나 싸다는 것은 아직 측정하지 않았다.** 이 단계가 그 측정이다.

**경계**

| 항목 | 규칙 |
|---|---|
| 원본 | 서버 폴더는 읽기만 한다. 쓰기·이동·이름 변경을 하지 않는다. |
| DWG | ZWCAD로 읽을 파일은 `.vide/knowledge-crawl/dwg/`에 복사한 사본만 연다(AI.md §8). 에이전트가 띄운 ZWCAD는 끝나면 종료한다. |
| DB 파일 | 사용자가 VIDE에 만든 이 프로젝트에 붙인다. VIDE는 프로젝트별 폴더 없이 데이터 폴더(`%LOCALAPPDATA%\VIDE`)의 `vide.sqlite` 하나를 쓰므로, 작업 엔진 DB는 건드리지 않고 `knowledge\<프로젝트 ID>.sqlite`를 따로 만든다. 저장소·회사 서버 공유 폴더에는 두지 않는다(RESEARCH-06 §6). 제품에서 같은 DB에 넣을지 파일을 나눌지는 ARCH-01에서 정한다. |
| 원본 참조 | DB는 원본을 복사하지 않는다. 서버 루트 기준 상대 경로와 해시만 가진다. |
| 제외 | 사용자 결정(2026-09-29): 계약·회계·제안서도 포함한다. 백업·캐시·렌더 자산 같은 자동 생성 파일만 뺀다. DB는 로컬에만 있다. |
| 외부 전송 | 파일 경로·구간 문장은 Jev(TypeSafe)로, 선별된 구간은 Claude(구독 CLI)로 간다. 사용자 허용(2026-09-29). |
| 저장소 기록 | 실험 코드와 SPIKE 문서에는 발주처·사업명을 쓰지 않는다. 경로는 실행 인자로만 받는다. |

**단계**

각 단계의 시간·호출 수·토큰은 DB의 실행 기록 표에 남긴다.

| # | 단계 | 방법 | Jev 효과 측정 |
|---|---|---|---|
| 1 | 목록 | 경로·크기·날짜 수집, 제외 규칙, 같은 문서의 다른 형식 묶기. 해시는 문자 정보가 많은 형식과 메일 첨부만 계산한다(3dm·렌더 자산 28GB+를 네트워크로 해시하지 않음). | — |
| 2 | 이름 해석 | 날짜·상대 기관·자료 종류·판 사슬을 규칙으로 뽑고, 남는 것만 Jev로 분류한다. | 규칙만 / 규칙+Jev / Claude 분류를 무작위 100개 경로에서 비교(맞은 비율·시간·토큰) |
| 3 | 추출 | 형식별 추출기로 근거 구간을 만든다. EML(헤더·본문·첨부 해시), DOCX·PPTX·XLSX(ZIP 안 XML), PDF 텍스트·주석(PyMuPDF), HWP(kordoc, 가능하면), DWG 문자·지시선·구름(ZWCAD, 사본). 3DM은 이번에 제외한다. | — |
| 4 | 연결 | 메일 첨부와 서버 파일을 해시·이름으로 잇고, 스레드를 묶는다. 회의·메일을 Episode로 만든다. | — |
| 5 | 선별 | Jev가 구간마다 “결정·요청·조건·의견이 있는가, 종류는 무엇인가”를 확률과 함께 판정한다. 확신 높음은 그대로 채택, 확신 낮음(중간 구간)만 Claude가 다시 본다. | 확신 구간별 Claude 대조 표본(아래)으로 숨은 오류율, Claude로 넘어간 비율, 시간·토큰 |
| 6 | 진술 추출 | 선별된 구간만 Claude가 진술 JSON을 만든다. 인용 문자열이 원문과 일치하지 않으면 버린다. | 전체 구간을 Claude로 처리할 때와 비교한 환산 비용 |
| 7 | 검증·정리 | 인용-진술 일치(Jev Noul), 주체 별칭 합치기 후보 | Jev 판정과 사람 확인 비교 |
| 8 | 질의 시험 | 사용자 지정 주제: **구조 설계에서 고려해야 할 조건**. 경간·기둥 위치·하중·기존 구조물·브릿지·심의 지적·법규 등 조건을 근거와 함께 목록으로 뽑고, 사용자가 빠짐·오류를 판정한다. | — |

- **확신도 기준 나누기(5단계):** 사용자 제안대로 Jev의 확률로 나눈다. 다만 “확신이 높다”가 “맞다”는 보장은 아니다(T-032에서도 Jev 확률의 순위와 정답이 어긋난 경우가 있었다). 그래서 확신 높음·낮음 판정에서 각 30개 안팎을 뽑아 Claude가 대조한다. 이 표본의 오류율로 경계값을 정하고, “Jev만 믿어도 되는 구간”의 오류율을 숫자로 남긴다. 사람이 미리 표시하는 작업은 하지 않는다.
- **DB 구조(실험용):** 자료(Source), 같은 문서 묶음, Episode, 근거 구간(Excerpt, FTS5 trigram), 메일·첨부 연결, 진술(Statement, AI 추정/확정), 주체·별칭, 실행 기록(단계·호출·토큰·시간)을 둔다. 제품의 물리 스키마는 실험 결과를 보고 ARCH-01에 정한다.
- **다시 실행:** 같은 명령을 다시 돌리면 바뀐 파일만 처리한다. 실험 중에도 이 증분 동작을 한 번 확인한다.

**코드 위치**

`tools/spikes/2026-09-29-knowledge-crawl/`에 둔다.
- Node: 목록·메일·DB·Jev 호출. `tools/locate/jev.mjs`를 재사용한다.
- Python: PDF, PyMuPDF가 설치돼 있다.
- ZWCAD: 기존 헤드리스 읽기 경로를 쓴다.

**산출**

- DB 파일(VIDE 데이터 폴더의 `knowledge\<프로젝트 ID>.sqlite`)
- `docs/tdd/SPIKE-2026-09-29-knowledge-crawl.md`: 단계별 시간·양·비용, Jev 비교표, 형식별 판정표, 질의 시험 결과, 한계
- 제품으로 옮길 목록: 프로젝트 지식 SPEC 초안에 들어갈 동작, ARCH-01 스키마 입력, K1·K2 변경 범위 조정, Design의 “프로젝트 자료” SCR 입력

**완료 기준**

- 5단계의 Jev 대 Claude 비교가 수치로 나온다.
- 두 번째 실행이 바뀐 파일만 처리한다.

**VIDE 기능으로 옮기는 순서(K0 뒤)**

실험 코드는 그대로 옮기지 않고, 측정으로 남긴 단계만 `src/`의 서버 작업으로 다시 작성한다.

**K0 실행 결과(2026-09-29)**

전 단계를 실제로 실행했다. 수치는 [SPIKE-2026-09-29-knowledge-crawl](../tdd/SPIKE-2026-09-29-knowledge-crawl.md)에 있다. K1·K2에 반영할 점은 다음과 같다.

- **해시를 미루기:** 첫 목록에서 문서 전체를 해시하면 네트워크 속도(약 11MB/s) 때문에 9분이 걸렸다. 변경 판단은 크기·수정 시각으로 하고, 해시는 추출할 때 읽는 김에 계산한다.
- **DWG는 ZWCAD 한 번 실행으로 충분:** 도면 156개를 29초에 읽었다. ZWCAD가 없는 PC의 대안은 ODA 변환기로 남긴다.
- **이름 규칙이 먼저:** 폴더 규칙만으로 문서 종류의 95%가 풀렸다. 규칙은 프로젝트마다 다를 수 있으니 규칙표를 설정으로 두고, 남는 것만 Jev로 판정한다.
- **Jev의 역할을 좁히기:**
  - Jev가 확신한 “내용 없음”은 표본에서 놓침이 없었다. 이것만 버리는 필터로 쓴다.
  - 확신한 “내용 있음”은 넓게 잡힌다. 판정을 그대로 믿지 않고 다음 단계로 넘긴다.
  - 한국어 발췌에서 Jev가 확신한 비율은 44%였다. LLM 사용 절감도 판정 단계에서 약 43% 수준이다.
- **같은 문장 합치기:** 같은 문장을 한 번만 판정하면 발췌 약 2만 개가 약 5천 개로 줄었다. 도면 판·중복 파일이 많아서다. 모든 AI 단계에 적용한다.
- **외부 전송 표시:** Jev와 Claude로 간 발췌 수를 실행 기록에 남기고 화면에 표시한다(FR-18).

### K0-T · 보기 JIG 시험판 — 2026-09-29 구현

사용자 결정(2026-09-29): 수집을 앱으로 옮기기 전에, K0에서 만든 DB를 VIDE에서 보고 피드백을 받는다. 수집기는 계획만 둔다(아래 기술 선택). 최종 위치는 왼쪽 레일(RESEARCH-06 §7.6)이며, JIG는 시험용 전달 수단이다.

- **변경 범위:**
  - `src/jigs/knowledge.ts`: 프로젝트의 지식 DB(`<데이터 폴더>/knowledge/<프로젝트 ID>.sqlite`)를 읽기 전용으로 연다. 요약, 분야별 이슈 목록, 이슈 노트와 소속 진술, 검색(내용 일치 우선·최신순), 진술의 원문 구간, 원본 열기를 제공한다.
  - 원본 열기는 DB에 기록된 루트 아래 경로만 기본 프로그램으로 연다.
  - `src/server/server.ts`의 `/api/v1/projects/:id/jigs/knowledge[...]` 경로
  - JIG 목록 `J-DATA 프로젝트 자료 · 시험판`
  - `src/ui/knowledge-jig.tsx`: 분야별 이슈 목록 → 회의록형 노트(현재 결론·조건·미결·경과). 근거는 항목마다 “근거 N”을 눌렀을 때만, 원문은 “원문”을 눌렀을 때만 보인다.
  - 이슈 노트 생성은 K0 실험 스크립트의 `issues` 단계가 한다. 검증된 진술을 분야 11개로 나누고, 분야별로 이슈 제목을 합친 뒤 이슈마다 노트를 쓴다.
- **제외:** 앱 안 수집, 채팅의 DB 사용, 검토 요청 대조, 확정·수정(K2 검토 큐)

  - `tests/server/knowledge-jig.test.mjs`
    - DB가 없으면 `available: false`

### K0-T2 · 세 가지 쓰임에 맞춘 현황 요약 — 2026-09-29

K0-T 피드백(2026-09-29): 이슈 113개 × 항목 약 30개를 같은 무게로 나열해 맥락을 잡을 수 없었다. 사용자에게 필요한 것은 **지금 무엇이 정해졌고, 무엇이 막혀 있고, 최근 무엇이 바뀌었나**이다. 이 정보를 쓰는 방식은 셋이다.

1. **보고서로 읽기:** 위에서 아래로 한 번 읽어 현황을 잡는다.
2. **AI에게 묻기:** 채팅에서 자료에 관해 묻는다(K3).
3. **AI에게 설계 검토 맡기기:** 현재 모델·도면을 정해진 조건과 대조한다(K3 검토 요청, K4).

세 방식은 같은 **현황 요약층**을 쓴다. 진술·이슈 노트는 그대로 두고, 그 위에 요약층을 만든다.

- **현황 요약층(DB 표 `brief`):** 범위(프로젝트 전체 또는 분야)마다 다음을 둔다. 항목마다 이슈 ID와 근거 진술 ID를 단다.
  - 상태 한 줄(분야) 또는 개요(프로젝트)
  - 정해진 것: 설계를 묶는 결정·조건. 수치와 날짜를 그대로 쓴다.
  - 막힌 것: 무엇을 누구에게서 기다리는지, 언제부터인지
  - 바뀐 것: 자료의 마지막 날짜 기준 최근 30일 안의 변경, 날짜순
- **쓰임별 연결:**
  - 보고서: 프로젝트 한 장 → 분야별 현황 → 이슈 노트(지금 화면) → 근거. 처음 열면 프로젝트 한 장이 보인다.
  - 묻기(K3): 채팅 AI에 요약층을 기본 맥락으로 주고, 자세한 내용은 작업 도구(`src/server/agent-tools.ts`의 MCP)에 추가할 읽기 전용 찾기 도구로 가져오게 한다.
  - 검토(K3·K4): "정해진 것" 가운데 수치가 있는 조건을 대조 목록으로 쓴다.
- **이번 변경 범위(보고서만):**
  - K0 실험 스크립트에 `brief` 단계 추가. 분야마다 이슈 노트 전체를 LLM 1회로 요약하고(분야당 항목 5개 이하), 분야 요약들로 프로젝트 한 장을 1회 더 만든다. 근거 ID는 원래 이슈 노트에 있는 것만 남긴다.
  - `src/jigs/knowledge.ts` 요약 응답에 요약층을 싣는다. 요약층이 없는 DB는 지금 화면 그대로다.
  - `src/ui/knowledge-jig.tsx`: 첫 화면을 보고서(프로젝트 한 장 + 분야별 현황)로 바꾸고, 항목을 누르면 해당 이슈 노트로 간다. 이슈 노트의 조건·경과는 접어 둔다.
- **제외:** 채팅 연결(K3), 검토 대조(K3·K4), 이슈 수 줄이기(다음 수집기 설계에서 판단)
- **검증:** 요약층 유무 두 경우의 서버 시험, 웹 빌드, 실제 K0 DB로 만든 요약층을 개발 서버 화면에서 확인
- **결과(2026-09-29):**
  - `brief` 단계를 K0 DB에 실행했다. LLM 12회(분야 11 + 프로젝트 1), 입력 약 21만·출력 약 2.8만 토큰, 66초.

  - 도구 발급과 지시문은 실행 경로마다 따로 있다(`sdk-execution.ts`, `zwcad-sdk-execution.ts`, `linked-execution.ts`). 경로마다 고치는 대신 `server.ts`에서 AI 호출(`provider(connection)`)을 한 번 감싸는 방법을 우선 검토한다. 그 방법은 이미 발급된 범위에 도구를 더하는 기능(`AgentTools`)과 과제의 프로젝트 ID가 필요하다.
- **검증(구현 때):**

  - 자료에 없는 질문에 "자료에 없음"으로 답하는지
  - 다른 프로젝트 DB에 접근할 수 없는지
  - 기존 AI 작업 권한이 넓어지지 않는지
  - 조건과 어긋나게 만든 합성 모델에서 해당 객체·근거를 짚는지, 맞는 모델에서 거짓 지적 비율(K4)

- **선행:** ADR-018 승인(공동 축적 예외, 팀 공용 원본 위치: 사내 팀 서버 / D1 / Supabase), 역할·공개 범위 결정.
- **변경 범위:**
  - 사건 동기화(모르는 사건 가져오기·내 사건 보내기, 재시도 멱등)
  - 팀 공용 원본 서비스(선택한 위치), 멤버십·역할(관리자·편집·열람·외부)과 확정 권한
  - 자료별 공개 범위 적용, 동기화 상태·충돌(나란한 판단) 표시
  - 원본 파일은 업로드하지 않고, 다른 팀원이 원문을 열 때는 회사 서버 경로 사용
- **검증:**
  - 두 PC가 오프라인에서 각자 기록한 뒤 동기화하면 양쪽 결과가 같음
  - 같은 자료를 두 사람이 넣어도 한 번만 저장, 비공개 자료의 진술이 다른 멤버에게 가지 않음
  - 권한 없는 확정 거절, 동기화 중단·재시작에도 중복 없음
  - 호스트 제어는 여전히 한 작업환경만 가능(AC-37)
- **완료 기준:** 2~3명이 같은 프로젝트에 자료를 넣고 확정한 결과를 서로의 VIDE에서 질문·조회한다.

### K6 · (선택) 관계 보기

K2~K5의 표·타임라인·인용으로 부족하다는 실제 근거가 생길 때만 Obsidian 폴더 한 방향 내보내기나 한 쟁점 중심의 국소 그래프를 추가한다. 전체 그래프는 만들지 않는다. — T-031 제안

## 기술 선택(초안)

- **로컬:** 기존 SQLite에 테이블 추가, FTS5 trigram, R*Tree 공간 색인, JSON. 벡터 검색은 부족함이 측정될 때 sqlite-vec(로컬 임베딩 모델 필요).
- **팀 공용 원본:** ADR-018. 동기화 방식은 저장소와 분리해 사내 팀 서버·D1·PostgreSQL 어느 쪽으로도 옮길 수 있게 한다.
- **구현 언어(2026-09-29 사용자 결정):** TypeScript(VIDE Node 서버의 백그라운드 작업)와 C#(ZWCAD·Rhino 플러그인)만 쓴다. K0의 Python 추출기(PyMuPDF·pyhwp는 AGPL)는 제품에 옮기지 않는다.
- **추출기:**
  - PDF: pdf.js
  - DOCX·PPTX·XLSX·HWPX: ZIP 해제 + XML 읽기
  - 메일: K0 파서 이식
  - 3DM: rhino3dm.js
  - DWG: K0의 ZWCAD 명령을 `hosts/zwcad` 빌드에 편입하고, 숨은 ZWCAD 일괄 실행을 유지
  - HWP(옛 형식): 라이선스를 확인한 뒤 결정
  - 스캔 PDF·이미지: AI 판독 선택 기능
  - 새 의존성은 PLAN-03의 추적·검사 규칙을 따른다. pdf.js의 속도·품질은 K0 결과와 비교한다.
- **폴더 구조 파악:** 경로를 코드에 고정하지 않는다.
  - 코드가 폴더마다 날짜·번호 접두·괄호 안 이름 같은 후보를 뽑는다.
  - Jev가 폴더의 역할(보낸 자료·받은 자료·회의록·도면·계약·참고 등)과 상대 후보를 고른다.
  - 결과 규칙 표는 사용자가 확인·수정하고, 같은 사무소의 다음 프로젝트에 재사용한다.
  - LLM은 Jev 확신이 낮은 폴더에만 쓴다.
- **업데이트:** 실시간 감시는 하지 않는다(네트워크 드라이브 변경 감시가 불안정). 프로젝트를 열 때와 “자료 새로 고침”에서 증분 수집한다(K0 재실행 약 30초).
- **Jev(TypeSafe):** 폴더 역할·상대 판정, 빈 구간 버리기, 근거 확인, 별칭 후보, 찾기 순위, 새 진술의 이슈 배정. 개발 중에는 `.env` 키, 제품에서는 서버 중계(PLAN-05 §7). 숫자·날짜 판단에는 쓰지 않는다.
- **AI:** 각자 PC의 구독 CLI. 정리는 도구 없는 JSON 추출, 질의·크리틱은 읽기 전용 MCP 도구. 서버 쪽 AI 실행은 하지 않는다.

## 비목표

JIG로 따로 설치하는 형태, 문서 관리·결재·버전 관리 시스템, 메일 클라이언트, 녹음 전사(STT), 법규 자동 판정, 전체 관계 그래프, 사용자 확정 없는 결정 자동 확정, 원본 파일의 클라우드 업로드, 같은 프로젝트의 호스트 공동 제어.
