초기 1단계 실험에서는 AI 코드 전송 전에 TCP 1999의 리스너가 VIDE가 기동한 테스트 실행본인지 OS 프로세스 ID·시작 시각으로 확인한다. 사용자 실행본이나 식별 불명 리스너가 점유하면 해당 실험을 거절하며 연결을 끊거나 포트를 빼앗지 않는다. 수신 시작/종료 방법은 SPIKE로 확인한다. 연결 뒤에는 AI가 작성하지 않은 고정 조회로 실행본 식별과 VIDE가 만든 합성 문서의 세션/기준을 대조한다. 기존 documentGuard의 프로세스 식별 비교는 재사용 근거이나 기동 소유권 증명 자체는 아니다.

소유 확인 뒤 다른 연결로 재접속하면서 검사를 생략하지 않는다. AI 코드의 컴파일/로드/평가 전에 신뢰된 실행 진입점이 소유 실행본과 대상 문서 기준을 다시 검사해야 한다. AI 코드 앞에 검사 문자열을 붙이는 것만으로 초기화 코드까지 통제했다고 간주하지 않는다. 기존 수신부에서 이 순서를 보장하지 못하면 실제 AI 코드 전달은 보류하고 모의 도구로 공급자 연결을 시험하거나 고정 실행 진입점을 먼저 준비한다. 같은 사용자 권한의 악성 프로세스에 대한 보안 샌드박스를 주장하지 않는다. 이 추가 조건은 새 범용 실험 경로에 적용하며 기존 제한 JSON 경로를 몰래 바꾸지 않는다.

초기 1단계는 당시 설치된 RhinoMCP 실행 기능을 한정된 실험에 활용했다. 이미 확보한 단계별 증거는 마스터 §6.5를 확인하고 다시 시작하지 않는다. 이 단계 통과는 자체 애드인 배포나 임의 코드의 완전 격리 증거가 아니다. 설치 의존 제거는 2·3단계와 T-011의 깨끗한 환경 시험 후 선언한다. ZWCAD COM은 이행 중 기존 과업 지원으로 유지한다.

기존 어댑터의 ‘도구가 있으면 실패’ 시험은 레거시 경로에 유지한다. 새 경로는 허용된 VIDE 도구만 호출 가능·다른 도구/낡은 조건은 거절하는 별도 시험으로 추가한다. 새 경로와 기존 저장·입력·호스트 회귀 통과 뒤 전환하고 기존 어댑터/의존 제거 시 해당 시험도 함께 정리한다. 기존 시험을 삭제해 새 경로를 통과시켰다고 보고하지 않는다.

6.1 현재 구현 묶음 — 기반 통합 이후

2026-09-24 사용자 지시: ① 기반 통합 ② 실행 안정성 ③ Rhino/ZWCAD 작업 완결 ④ 공유 왕복을 수행한다. 논현동 수준의 대표 과업 선정·실무 수용 검수는 이 묶음 완료 후 사용자가 결정한다. 합성 형상·두 문서·두 계정으로 기능 검증은 지금 수행하며, 이를 실무 과업 수용으로 대신하지 않는다. Jev는 별도 조사이며 이 구현의 선행 조건이나 새 의존성으로 넣지 않는다.

순서 기존 티켓·기준 실제 변경 대상과 작업 다음 단계 진입 기준
1. 기반 통합 T-019~024·PLAN-03 별도 브랜치의 7개 커밋을 main에 병합. 동시 연구 문서는 그대로 보존하고 HTML은 MD에서 재생성. 통합 코드에 기존 검사를 실행 타입·포맷·기존 136개 자동 시험·문서 일치. 원격 CI 실행·브랜치 보호는 로컬 통합과 구분
2. 실행 안정성 T-003·004·018, SPEC-02.1·3·4·6 WorkerExecutor와 실행 결과 계약: 컴파일 전/후 정책 검사, 위험 API 접근 거절, 실제 예외 진단 보존, 실행 전 거절과 실행 후 불명확 구분 아래 2절의 정책·예외·재시도 시험과 정상 SDK 생성/수정 회귀 통과
3a. ZWCAD 범용 후보 T-006·018, H-ZWCAD-01~04 자체 SDK 실행 경로를 제품 AI 도구에 연결. 사본 생성/읽기/코드 실행/내보내기·저장/재열기를 연결하고 기존 제한 JSON·COM 생성 경로와 지원 차이를 확인 브라우저 입력→선택 공급자→SDK 생성→후속 수정→실제 DWG 표시/저장/재열기. 원본 해시·Handle/속성 보존과 실패 판정

4a. 로컬 공유 왕복 T-009·017, SPEC-04.7 기존 게시/의견 API와 로컬 내보내기·수신·초안 채택 UI를 연결·검증. 현재 파일 왕복과 온라인 연결의 구현 상태를 구별하고 빠진 연결만 추가 두 계정/두 프로젝트 게시→핀/스케치 의견→로컬 채택→후속 후보→갱신 게시. 권한 회수·중복·오래된 게시 기준·재시작 보존

2. 실행 안정성의 구현·검증 범위

  • 문자열에 위험 단어가 있는지만 검사하지 않는다. Roslyn 의미 분석으로 실제 바인딩된 API를 판별한다. 파일 접근·네트워크·프로세스·리플렉션·네이티브 상호운용·동적 호출·다른 문서/앱 전역 접근을 우선 제한하고, SDK 기하/문서 객체 작업의 정상 사용은 회귀로 확인한다. 클래스/초기화 코드 삽입 등 공급된 메서드 본문을 벗어나는 구조도 검사한다.
  • 이 검사는 실수·명백한 위험 호출을 줄이는 방어다. 같은 OS 권한의 임의 코드에 대한 완전한 샌드박스로 선언하지 않는다. 거절 범위와 잔여 한계는 ARCH의 실행 경계에 기록하고, 외부 코드 패키지/사용자 플러그인을 자동 신뢰하는 경로를 추가하지 않는다.
  • 정책/컴파일 거절은 호스트 변경 전에 반환하여 AI가 수정할 수 있게 한다. 실행이 시작된 뒤 예외는 실제 원인을 로컬 진단에 보존하되 원문 경로·자격 증명을 AI/공유 응답에 흘리지 않는다. 결과에는 제한된 진단 식별자를 연결하고 쓰기 상태는 불명확으로 유지한다.
  • 자동 시험: 한정/전체 이름·별칭/이스케이프를 사용한 위험 API, dynamic/typeof/본문 탈출, 무해한 문자열/일반 기하·LINQ, 컴파일 오류, 실행 후 예외, 같은 operationId 재요청·다른 내용 재사용, 저장/응답 실패를 구분한다. 거절된 코드가 객체/파일을 만들지 않았는지 확인한다.
  • 실호스트 시험: VIDE가 띄운 합성 Rhino에서 정상 생성/조회/수정과 의도적 예외를 한 번씩 확인한다. 기존 사용자 실행본에는 시험 코드를 보내지 않는다. 정책 변경으로 기존 스케치/후속 후보가 막히면 방어를 무작정 해제하지 않고 허용 API의 실제 필요를 확인한다.

3. 호스트 연결의 구현 순서

  1. 기존 ZWCAD SDK 실험과 제품 어댑터를 대조해 재사용 범위를 정한다. 설치본의 런타임/컴파일러·트랜잭션 문맥을 확인하며 Rhino의 .NET 8 구현을 그대로 복사하지 않는다.
  2. 소유 실행본·인증·문서/기준·작업 ID 확인을 유지한 채 query/execute/result 경로를 구현한다. 호출 의미는 공통 규약을 재사용하고 호스트 타입과 물리 필드는 ARCH에서 확정한다. 검증 없는 신규 라이브러리/일반 셸 실행을 기본 경로로 도입하지 않는다.
  3. AI 연결 전 결정적 코드로 새 경계·복사·이동·기존 정점 수정·속성 보존·저장 재열기를 시험한다. 기하 수치와 파일/객체 증거가 통과한 뒤 제품 채팅·핀·스케치에 연결한다. 지원 밖 객체를 일부만 누락한 성공으로 보고하지 않는다.
  4. 자체 SDK 후보 열기와 소유 편집 창 연결을 붙인다. 적용은 AI 재실행이 아니라 검토한 후보의 고정 이식이며, 사용자 원본 적용은 명시된 후보/대상 지시를 요구한다. 기존 외부 실행본 연결과 자체 소유 창을 혼동하지 않는다.
  5. 두 실행본/문서에서 대상 고정·직접 변경·Save As·재시작·A→B 데이터 복사를 검증한다. 한 요청의 선행 결과를 다른 호스트의 입력으로 사용하고, 한쪽 실패가 성공한 쪽의 쓰기를 재실행하지 않는지 확인한다.
  6. 배포 검수에서는 잠금 파일의 Roslyn/System 런타임 DLL과 라이선스 고지를 함께 묶고 설치 호스트 SDK는 제외한다. 새 버전 폴더의 Windows 패키지를 만들어 내장 Node·서버·자체 애드인 경로를 확인한다. 기존 검수 패키지를 덮어쓰지 않으며 별도 PC/서명 검수와 구분한다.
  7. 공급자별 구독 합성 시험은 최초 각 1회, 수정 재시험은 실패 원인이 해소된 경우에만 각 1회 추가한다. 요청당 기존 도구 호출/시간 상한을 유지하고 실제 사용량 미제공은 미확인으로 남긴다. 기능 실패를 이유로 무한 AI 호출을 반복하지 않는다.

3b의 복수 대상 구현 순서

  • ARCH-01의 linkedTargets·하위 요청·범위 제한 도구를 구현하고 잘못된 프로젝트/중복 기준/미확인 좌표를 실행 전에 거절한다. 단일 대상 경로는 유지한다.
  • 입력기의 추가 메뉴에서 두 기준 후보를 지정하고 공통 m 원점/축을 확인한다. 결과는 호스트별 하위 후보와 실패를 보여 주며 기존 보기/적용으로 연결한다. 기본 입력기에 기술 필드나 상시 패널을 추가하지 않는다.
  • 결정적 에이전트 대역과 실제 SDK로 CAD 경계 수정→수정 경계를 사용하는 Rhino 후보를 한 요청에서 검증한다. 같은 호스트 두 문서에서도 대상 오지정 거절·원본 불변을 확인한다. 한쪽 컴파일 실패/실행 후 불명확을 주입하고 다른 쪽 성공·영수증 유지, 재시작 후 자동 중복 쓰기 부재를 확인한다.
  • 의미 검사·두 대상 도구 권한·저장/부분 결과 자동 시험을 먼저 통과시키고 실제 브라우저/호스트 연결을 확인한다. 좌표 확인 없는 추론이나 미지원 관계 평탄화로 통과시키지 않는다.

4. 공유·배포와 검증 조건

  • 4a의 실제 호스트 시험은 tests/sharing/membership.mjs --browser --host로 분리한다. 합성 SDK 도면의 브라우저 게시→다른 댓글 권한 사용자 의견→로컬 초안 채택→명시 실행→실제 ZWCAD 후보 재조회→새 게시본을 연결한다. 이 시험은 결정적 에이전트 대역이 제품 MCP를 호출하며 추가 구독 추론 없이 연결·형상·권한을 검사한다. 양쪽 실제 구독 추론 증거는 기존 SDK 검수와 구분한다. 원본 해시·과거 게시본 불변과 미실행 초안 상태도 확인한다.
  • 기존 로컬 회원/권한·게시·의견 검증을 재사용한다. 새 검증은 의견의 공개 기준→로컬 객체 대응→요청 초안→실제 수정 결과→새 게시본을 하나의 흐름으로 잇는다. 의견의 수신/채택이 원본 적용 권한을 부여하지 않는다.
  • 원격 업로드는 무료 범위 확인 전 UPLOADS_ENABLED=false를 유지한다. 기존 R2 자료 삭제, 요금제 전환, 도메인 구매, 메일 발송은 이 작업에 포함하지 않는다. 비용 조건이 막히면 공유의 독립적인 로컬 연결·권한·복구 검증을 계속한다.
  • 원격 CI 실행에는 코드 push가 필요하다. 현재 지시는 통합/구현을 승인하지만 기존 커밋 위임을 무제한 공개/push 권한으로 넓히지 않는다. 로컬에서 CI와 같은 명령으로 검사하고 원격 실행/필수 검사 적용은 별도 상태로 남긴다.
  • 검증 결과는 실제 착수 시 VERIFY에 남긴다. 티켓 완료마다 마스터 §6.5·관련 호스트 지원표를 갱신하고 MD/HTML을 맞춘다. 기능별 커밋과 다음 준비된 작업을 이어가며 대표 실무 과업을 기다린다는 이유로 위 구현을 중단하지 않는다.

6.2 현재 우선 작업 — UI 이후 로컬 제품 완결

2026-09-24 후속 사용자 지시로 실제 왕복/실패 검증과 복수 문서·개입·편집 범위·수량·큰 모델·복잡한 작업을 먼저 수행한다. 최신 배포 ZIP 갱신, 원격 공유, 대표 논현동 과업 선정은 이 묶음 뒤로 미룬다. 제품 범위는 PRD §14·AC-05~13·16·24·25·29·32~34, 동작은 SPEC-00 개입/상태와 SPEC-01.9·SPEC-02.4·6·8·9·13·14·SPEC-03.5·8을 기준으로 한다.

L3의 첫 검증은 이미 고정 적용이 허용된 독립 Curve/Extrusion/Mesh/Point를 대상으로 한다. 합성 문서의 유형별 후보 이동·속성 수정 후 편집 창에 적용하고 재취득 파일을 독립 실행본으로 재열어 ID·유형·수량·속성을 대조한다. 이는 기존 지원의 증거 보강이며 그룹/재질/자원 변경을 허용하는 구현으로 확대하지 않는다. 기본 호스트 수동 편집과 일반 관계 보존은 별도 검증으로 남긴다.

L4는 실제 기하 일치로 증명된 평행이동에 기존 측정을 재사용한다. 동일/속성 편집/이동/회전/크기 변경/삭제를 한 합성 파일에서 비교하며 이동 뒤에도 변경 집합과 world bounds는 갱신한다. 직접 SDK Transform에서 BeforeTransformObjects를 관측하지 못했으므로 이벤트 기반 접근은 채택하지 않는다. 회전의 재사용은 확인 가능한 근거를 추가 확보하기 전까지 재계산으로 유지한다.

L4 수동 Sync는 같은 프로젝트·문서의 직전 성공 취득본에서 기하 해시가 있는 측정만 재사용한다(ARCH §5). 변경 범위는 Rhino scene/내부 export 캐시 계약, 저장 결과 선택, capture/import 경로다. 계약 시험은 다른 문서·구 버전·해시 없는 자료 배제, 실제 Rhino 시험은 무변경 0개 계산·속성 편집 재사용·한 객체 크기 변경/추가/삭제·다른 단위 정규화의 수량 일치다. 서버 재시작 후 기존 DB 결과 사용도 확인한다. 회전/이동된 수동 편집의 재사용은 해시만으로 단정하지 않고 재계산한다.

L4 Undo 검증은 소유 합성 Rhino 문서에서 객체 크기·속성 변경과 삭제를 각각 Undo/Redo하고 단계별 사본을 저장한다. 각 사본을 직전 취득의 기하 캐시로 다시 읽어 ID·체적·속성·삭제/복원 집합과 계산/재사용 수를 대조한다. 실제 문서 Undo 기록을 사용하며 이전 파일을 복사하는 것으로 Undo 시험을 대체하지 않는다. 사용자 문서나 설정은 변경하지 않는다.

L6 진행 관측값은 양쪽 SDK의 요청 결과와 ACTIVE WORK에 연결한다(SPEC-02.6, ARCH §2). 다음 변경은 요청별 도구 호출·대상별 SDK 실행·AI 응답 시간 상한을 초안에서 조절하고 접수 입력에 고정하는 것이다. 기존 기본값은 단일 대상 30호출·12실행·180초, 연계 요청 60호출이며 최대 100호출·48실행·600초까지 허용한다. 이 값은 검증용 운영 설정이고 성능 보증이 아니다. 저장/복원·개입·후속 요청, 양쪽 실행기·연계 라우터·공급자 시간 제한·표시를 함께 연결한다. 경계값 거절, 상한 초과 시 네이티브 실행 0회, 실제 화면 설정과 복원, 기존 중단/불명확 회귀로 검증한다. 시간 제한은 AI 호출부터 적용하며 이미 실행 중인 네이티브 연산은 기존 종료 대기 규칙을 따른다.

L6 복구 후보 연결은 저장 검증 성공과 목표 완료를 구분하는 recovered 표시, 단일 대상의 원 조건/첨부를 유지한 후속 초안, 핀 대응 검사를 추가한다. 기존 입력 복원 동작을 재사용하며 자동 전송하지 않는다. 정상 대응·누락/변경 ID·권한·다중 대상 거절을 계약 시험하고 실제 Chromium에서 복구 표시와 버튼의 초안/기준 변경, 요청 자동 실행 0회를 검증한다. 양쪽 SDK 복구 결과가 원 문서 식별과 마지막 관측 진행값을 보존하는지도 검사한다. 복구 과정에서 원 문서 연결을 잃거나 재실행으로 관측 횟수를 늘리지 않아야 한다.

L5 AI 초기 문맥은 SDK 경로부터 객체·수량 64 KiB/100개로 제한하고 명시 핀을 우선한다. 전체/포함/생략 수와 재조회 안내를 추가하며 기존 JSON 경로와 핀 보호 규칙을 유지한다. 합성 1만 객체·긴 다국어 이름·대형 정점 배열에서 패킷 크기, 핀 우선순위, 누락 고지, 원본 불변을 계약 검증한다. 이 단계는 네이티브 500개 제한 해제를 의미하지 않으며 조회 페이지화·실호스트 확대는 이어서 검증한다.

L5 객체 목록은 매 입력/선택마다 전체 버튼을 제거하고 만드는 경로를 먼저 없앤다. 동일 ID/이름/순서면 기존 DOM과 키보드 포커스를 유지하고 선택 두 행만 갱신한다. 목록 변경 때는 ID별 노드를 재사용하며 삭제된 항목을 제거한다. 실제 Chromium에서 1만 행의 최초/반복 갱신, 노드 재생성 0개, 선택·이름/순서 변경·삭제·빈 목록 전환을 검증한다. 이 개선은 가상화나 네이티브 가져오기 상한 확대와 별도다.

L5 첫 측정에서 정지 화면도 매 프레임 GPU 렌더링하고 선택/스케치 표시를 입력마다 재구성하는 경로를 확인했다. 카메라·화면 크기·형상·선택·스케치 변경 때만 다시 그리고 동일 표시 입력은 재사용한다. 실제 Chromium에서 1천/1만 객체의 표시·선택, 131,072 삼각형 메시, 모델 교체 후 GPU 버퍼 해제를 변경 전후 비교한다. 호스트의 500개 가져오기 제한과 뷰포트 성능은 별도로 보고한다.

L2 개입 구현은 기존 요청 저장소와 취소/종료 Promise를 재사용한다. 서버 접수 API→원 입력 보존/중복·다른 대상 거절→종료 대기→안전한 원 기준 재실행→UI 접수/대기/보류 연결 순서다. 결정적 공급자 대역으로 실제 종료 전 새 호출 0회, 새 조건 전달, 불명확 시 재실행 0회, 후속 취소, 중복 접수와 재시작 보존을 검사한다. 실제 Rhino 사본에서는 제한 시간 연산의 실행 영수증을 확인한 뒤 취소해, 네이티브 호출 종료 전 작업 수명을 유지하고 늦은 결과를 자동 채택하지 않는지 확인한다. 영수증 복구로만 후보를 확인하며 같은 코드를 재전송하지 않는다. 네이티브 명령 강제 중단 지원을 추가로 약속하지 않는다.

기존 완료 증거를 전부 재실행하지 않고 위 변경과 연결된 회귀를 선택한다. 합성 문서/별도 작업 디렉터리를 쓰며 사용자 원본/다른 세션 실행본을 수정·종료하지 않는다. 네이티브 시험 실행 중에는 독립 코드/문서 분석을 계속한다. 새 API나 저장 계약은 해당 SPEC/ARCH에서 먼저 확정하고 UI 표현은 Design에 반영한다. 지원 확대의 한계가 발견되면 해당 항목을 정확히 남기고 독립 묶음을 이어간다. 완료 증거와 남은 조건은 마스터 §6.5와 실제 착수한 VERIFY에서 관리한다.

연결 후보와 선택 절차

MCP 규약을 쓰는 것과 제3자 RhinoMCP 플러그인을 설치하는 것은 별개다. 제3자 설치 의존성은 자체 애드인 배포로 제거하고, 에이전트와의 MCP 사용 여부는 아래 비교로 정한다. MCP·stdio·HTTP·Named Pipe를 같은 층의 대안으로 나열하지 않는다.

구간·후보 시험 시점·내용 선택/제외 조건
AI–VIDE: MCP Streamable HTTP 1단계 기본안. 기존 Node 서버에 endpoint를 내장하고 양쪽 공식 구독 CLI 연결 검증 실행별 설정/인증, 도구 호출, 개입·취소/복구가 통과하면 유지
AI–VIDE: MCP stdio HTTP가 설치 CLI에서 불가능하거나 재현 가능한 운영 문제가 있을 때만 얇은 어댑터 시험 추가 프로세스 관리 비용을 포함해 문제를 해결할 때 채택
AI–VIDE: MCP 없는 공급자 공식 도구 연결 공식 구독 실행 경로가 사용자 정의 도구의 호출/결과 반환을 지원하는지 먼저 확인 지원 증거와 줄어드는 구성요소가 있을 때만 대안 시험. API 유료 키 경로로 몰래 바꾸지 않음
VIDE–호스트: 기존 RhinoMCP TCP 1단계 대조군/임시 실행기 범용 AI 흐름을 빨리 검증하되 최종 자체 설치 지원으로 간주하지 않음
VIDE–자체 애드인: 인증한 loopback TCP 2단계 기본안. 애드인 등록·복수 실행본·재접속을 검증 접근 제어·대상 식별·복구를 만족하면 유지
VIDE–자체 애드인: Named Pipe 4단계에서 같은 실행기/payload로 비교. 실제 ACL 설정과 서버 방향 포함 접근 제어 또는 운영 복잡도/측정 성능의 실익이 있을 때만 교체

셸에서 HTTP 명령을 호출하는 방식은 MCP 제거만으로 단순하다고 판정하지 않는다. 셸 권한, 인수/출력 해석, 토큰과 공급자별 구현 비용까지 포함한다. 단순화를 위해 일반 셸 권한을 새로 여는 방식은 기본안에서 제외한다. 모든 후보 조합을 구현하지 않으며 공식/설치본 능력 조사 뒤 각 구간의 기본안과 필요한 대안 하나만 비교한다.

비교 조건과 채택 기준

  • 결정적 재생 시험: 같은 저장 파일·코드·실행기·payload로 조회, 짧은 편집, 긴 연산, 큰 결과의 자산 전달을 반복한다. 초기 연결/컴파일과 재사용 실행을 분리하고 후보 순서를 교차한다. 첫 설정은 조건별 30회이며 표본 수와 분포를 함께 남긴다.
  • 실제 AI 시험: 공급자별로 같은 모델/effort·초기 대화·문서·지침·과업을 맞춘다. 조회→생성→수정, 스케치 입력, 잘못된 코드 수정, 복수 문서 대상을 포함하고 SDK/호스트 버전을 고정한다. 후보마다 새 세션/같은 원본 사본으로 시작한다. 공급자가 보고한 사용량만 기록하고 누락을 0으로 계산하지 않는다.
  • 실패 시험: 잘못된 대상, 낡은 기준, 중복 요청, 실행 중 연결 끊김/재시작, 취소 후 결과 불명확, 권한 없는 연결을 합성 문서에서 확인한다. 사용자 문서는 사용하지 않는다.
  • 구독 사용량: 착수 시 실험 기록에 과업 수·반복 수·최대 호출/시간을 먼저 정하고 작은 짝 비교부터 수행한다. 한도/실행 실패도 기록하며 임의로 반복을 늘리지 않는다. 표본이 부족하면 속도 우위를 확정하지 않는다.

채택 순서는 다음과 같다. 임의 가중치 점수로 필수 조건 실패를 상쇄하지 않는다.

  1. 필수 조건: 실제 결과가 과업 기준과 일치하고 대상/권한 격리·중복 쓰기 방지·불명확 복구·양쪽 구독 경로가 검증되어야 한다. 설치/설정은 VIDE가 맡아 사용자가 MCP를 수동 구성할 필요가 없어야 한다. 이 설치 조건은 최종 배포 관문이며 1단계 임시 경로만으로 통과 처리하지 않는다.
  2. 단순성: 필수 조건을 만족한 후보 중 별도 프로세스·외부 의존성·공급자별 코드·설치/업데이트/복구 단계가 적은 구성을 우선한다. 줄 수만으로 판단하지 않는다.
  3. 성능·사용량: 총 완료 시간·성공률·p50/p95·토큰·도구 왕복·재시도·사용자 개입을 비교한다. 작은 전송 시간 차이를 전체 작업 개선으로 주장하지 않는다. 반복 변동을 넘는 개선이나 명확한 운영상 이익이 없으면 기본안을 유지한다.

계획·실험·검수 문서의 역할

비교 방법·통과 기준은 이 PLAN, 대안 조사·선택 근거는 RESEARCH/ADR, 채택한 계약은 ARCH가 소유한다. 실제 시험 착수 때 docs/tdd/SPIKE-YYYY-MM-DD-<slug>.md에 가설, 환경/버전, 실행 코드 위치, 표본/예산, 원시 측정 위치와 결과·한계·채택 결론을 기록한다. 구현 후 사용자 과업의 수용 여부는 관련 VERIFY-*에 기록한다. tdd/는 이 저장소의 검증 문서 위치이며 모든 설계 선택을 테스트 주도 개발로 한다는 뜻이 아니다. 아직 수행하지 않은 실험 결과나 빈 시험 문서를 미리 만들지 않는다. 채택 계약은 ARCH, 작업 순서는 PLAN, 실제 지원은 호스트 지원표에 반영한다.

비교와 검증 근거

같은 모델·과업·입력 범위로 ① 기존 제한 JSON ② 새 VIDE 범용 실행 ③ 같은 CLI+RhinoMCP 직접 연결을 비교한다. PRD §16의 수작업 기준선도 T-012에서 유지한다. 직접 연결은 원본 편집까지, VIDE는 후보 준비까지 측정한 값을 같은 완료 시간으로 비교하지 않는다. 후보 준비와 원본 반영 완료를 따로 보고하며 사용자 검토 대기 시간도 시스템 처리 시간과 분리한다. 성공 결과·총시간·토큰·도구 수·거절/재시도·필요한 사용자 개입과 대상 오인/낡은 기준/중복 쓰기 방지 사례를 함께 기록한다. 오류 주입은 소유 테스트 문서에서만 한다. AI가 고른 코드 차이로 생긴 시간을 순수 전송 비용으로 해석하지 않는다.

순수 TCP/Pipe 비교는 자체 실행기에 동일 코드를 넣을 수 있을 때 수행한다. 제3자 TCP 서버와 새 실행기를 비교하는 측정은 전체 경로 비교다. 측정은 실행본 기동·사본 생성·모델 추론·도구·IPC·컴파일·호스트 실행·결과 재조회·메시/측정·후보 표시·원본 적용으로 나누고 p50/p95와 초기 컴파일을 구분한다. 로컬 결정적 경로 반복 30회는 초기 설정이며 실제 AI 반복은 사용량 예산을 정해 수행한다. 성능 보증이나 실행 증거 없는 우위를 기록하지 않는다.

기능별 구현·실제 검증 뒤 커밋하고 지원표는 증거에 맞춰 갱신한다. 이번 문서 갱신으로 제품 코드·실호스트·공유 서비스의 구현 완료 상태가 바뀌지 않는다.

07 / 공유 실험 순서와 완료 기준

이번에는 Cloudflare의 공유 흐름만 구현·검증한다. AWS 배포나 다중 공급자용 추상화를 만들지 않는다. 한국 접속 환경·게시 파일·과업·동시 사용자 조건을 기록해 재현한다. 같은 회사라는 이유만으로 빠르다고 가정하지 않는다. cold/warm 상태의 로그인/API p50·p95, 최초 모델 표시 시간, 큰 파일 완료 시간, DB 쓰기 경합, 오류/재시도와 실제 청구 사용량을 기록한다. 첫 합성 조건은 10/100/500 MiB 파일과 1/10/50 동시 열람이며 실제 사용자 규모를 의미하지 않는다.

필수 통과 조건은 로그인→초대→게시→열람→의견→권한 회수, PC 종료 후 접근, 중단 업로드 복구, 교차 프로젝트 접근 거절, DB/파일 백업 복원이다. Workers/인증/D1 제약과 D1·R2의 기준 일치, 배포 롤백/백업 복원을 확인하고 실제 복원 시간과 자료 손실 구간을 기록한다. 자동화/알림은 에이전트 세션이 끝난 뒤에도 동작해야 한다.

실험은 아래 단계로 수행한다. 단계 1(로컬 재현)과 단계 2a(무료·메일 없는 원격 배포)는 완료했다. 인증 라이브러리의 Workers/D1 로그인·세션은 확인했고, 메일 발송 자격은 발신 도메인·Workers Paid가 필요해 후속 모드(2c)로 분리했다. 메일 확인이 없다는 이유로 배포를 보류하지 않으며, 대신 메일 의존 기능(비밀번호 복구·이메일 변경)을 서버에서 차단한다. 구현을 시작하면 필요한 세부 스키마·라이브러리 버전·설정값은 해당 단계의 코드/마이그레이션과 함께 고정한다. 이 작업 때문에 전체 계획 문서를 다시 작성하지 않는다.

단계 산출물 완료 조건
1. 로컬 재현 Workers 로컬 환경, D1 마이그레이션, R2 바인딩, 인증 라이브러리 연결, 합성 게시 자료 두 사용자/두 프로젝트의 로그인·멤버십·게시·의견·접근 거절을 자동 검증. 메일 대체 수신함은 로컬에서만 사용하고 실제 발송 완료로 표시하지 않음
2a. 무료·메일 없는 원격 배포 운영과 구분한 staging Worker/D1/R2, AUTH_SECRET 비밀 바인딩, AUTH_MODE=manual-approval, 접속 가능한 페이지 실제 두 브라우저 세션에서 가입→프로젝트→참여 신청→소유자 승인→접근→회수→거절 검증. 현재 완료 여부는 마스터 §6.5를 참조. 모델 업로드는 무료 범위 보장을 위해 차단(UPLOADS_ENABLED=false)
2b. 원격 게시·의견 완결 업로드 차단 해제 조건(R2 사용량·예산) 확인, 합성 모델 게시·의견·과거본 설치 PC 종료 후 열람·의견 유지, 실제 파일 전송, 만료/회수·다른 프로젝트 접근 거절. 사용자 원본 대신 합성/공개 허용 자료 사용
2c. 메일 인증 모드 — 후속 발신 도메인·DNS·요금제 승인 뒤 Email Service 바인딩, 인증/초대 메일, 비밀번호 복구 허용된 시험 계정의 실제 메일 수신·인증·복구. D1의 emailVerified를 강제로 바꿔 통과 처리하지 않음
3. 비용·복구 검증 사용량 기록, D1 백업/반출 및 R2 manifest, 복원/배포 롤백 절차 중단 업로드·실패 배포에서 복구, 복원한 게시본과 의견/권한 일치, ARCH-01 공유 설계의 부하 조건에 따른 시간·오류·월 예상 비용 보고

실험 질문·환경·결과는 T-009에 연결한 SPIKE에, 제품 수용 결과는 VERIFY에 기록한다. 기록은 실제 실험 착수 때 생성한다. 2b·2c 전에 청구 설정·테스트 예산·발신 도메인 등 실제 환경을 확인한다. 메일 자격이 없는 동안 메일 검증을 완료로 올리지 않는다. 확정된 예산 없이 유료 자원을 생성하는 권한으로 이번 문서 확정을 해석하지 않는다.

필수 기능과 권한/복구 시험을 통과하면 실험의 기능 검증은 완료다. 성능·비용은 실측으로 보고하며 아직 합의하지 않은 수치 목표를 달성했다고 표시하지 않는다. 현재 가격표는 비용 가설이고 운영 승격은 실제 사용량·예산·복구 결과로 판단한다.
