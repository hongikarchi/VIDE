# 작업 폴더 · 서버 연결 · CLI 진입점 · 파일 지도

2026-10-15 사용자 결정의 작업 폴더 부분이다(같은 날 두 번째 정정 — 서버에는 스키마를 두지 않고 대화로 정하며, 파일 지도를 더함 — 을 0.2에 반영했다). 생각의 정리와 근거는 [RESEARCH-17](../research/RESEARCH-17-workspace-and-records.md), 선택 이유는 [ADR-042](../decisions/ADR-042-workspace-folders.md), 후보 기능 번호는 PRD §4.4의 C-10이다. 이 계획은 **계획만** 세운 상태이며 구현 착수 조건은 「현재 상태」에 적었다.

## 2026-10-15 결정 요약

사용자가 이렇게 정리했다.

> 회사 서버 경로는 앞으로도 이렇게 될거고, 우리가 디자인하는거는 로컬의 폴더 트리일 것 같아. … rhino는 로컬에서 작업하고, cad는 서버에서 작업하는 것도 오케이.

> 규모검토 트리를 그대로 가져오는거는 좀 위험할까? … 우리가 지금 설계하는 VIDE의 모든 기능을 잘 활용할 수 있는 폴더 트리는 어떻게 될지 모르겠어.

> 회사마다 다를거고 사람마다 다를건데, 이거를 픽스시켜버려서 하드코딩하는게 맞나 싶은 생각이 들어서. 로컬에 우리 작업을 위한(AI가 만들고, 사람이 보는 용도) 폴더는 우리가 규칙을 정하면 되는데, 서버는 좀 고민이 되어서… 어떤 폴더를 연결할지는 기존처럼 미리 설정을 하면 될 것 같고, 서버에서 어떤 작업을 어떻게 할지는 vide 내에서 이야기를 하면서 정할 수 있으면 좋겠는데. … 파일 탐색기도 뭔가 서로 파일들이 연결되고, 영향을 받고 하는데, 그거를 시각적으로 … 구현하면, 요청을 할 때 직관적으로 알 수 있지 않을까?

그래서 이 계획의 방향은 다음과 같다.

- **파일은 폴더, 게시는 사이트, VIDE DB는 캐시.** 사람이 탐색기로 보는 유일한 정본은 작업 폴더다. 사이트(공유·Cloudflare)는 게시본, `%LOCALAPPDATA%\VIDE`는 캐시·개인 것이다. GitHub은 네 번째 장소가 아니라 폴더의 이력이다(원격 연결은 [PLAN-54](PLAN-54-outputs-accounts-proposals.md)).
- **로컬 트리(AI가 만들고 사람이 보는 폴더)는 우리가 규칙을 정한다. 단 하드코딩이 아니다.** 기본 트리는 설정의 템플릿 파일 하나이고, 회사·개인이 이름을 바꾸거나 프로젝트별로 덮어쓸 수 있다. 역할 경로(`project.config.json`의 `paths`)가 정본이고 폴더 이름은 프로젝트마다 달라도 된다. 규모검토(논현동 164·7-3)의 트리는 복사하지 않고 역할로 대응시킨다.
- **서버에는 스키마도 템플릿도 두지 않는다.** 어느 폴더를 연결할지는 지금처럼 설정(SPEC-01.13 프로젝트 폴더)에서 미리 정한다. 그 안에서 무엇을 어디에 둘지는 VIDE 안에서 대화로 정한다: 연결하면 AI가 이미 있는 폴더 구조를 읽어 "도면은 여기, 보고서는 여기로 보입니다"라고 **제안**하고, 사람이 확정·수정하면 그것을 프로젝트가 **기억**한다. VIDE는 서버 폴더를 만들거나 이름을 바꾸지 않는다.
- **파일 지도.** 파일들이 서로 어떻게 이어지고 영향을 주는지(xref, 모델↔도면 Sync 쌍, jig 입력→결과, 데이터→보고서, 체크아웃↔서버 원본)를 그림으로 보여 주고, 요청을 쓸 때 영향받는 파일이 먼저 보이게 한다. 1차 범위는 관계 + 영향 미리보기 + 시간축이다(사용자 결정 2026-10-15).
- **읽기는 서버, 쓰기는 로컬, 서버 반영은 사람.** Rhino 3dm은 로컬 체크아웃, DWG는 서버에서 직접 열되(xref) 보호 장치를 붙인다. 서버에 쓰는 것은 사람이 [서버에 반영]을 누를 때뿐이고 이전 판은 자동으로 보관한다.
- **재현.** `project.config.json`이 있는 폴더를 열면 VIDE가 프로젝트를 다시 만들고 색인을 다시 짓는다.
- **CLI.** 작업 폴더에서 터미널(Claude Code 등)로 VIDE jig와 데이터를 부를 수 있는 최소 진입점을 둔다.

## 착수 조건과 범위

- **제품 결정:** 2026-10-15 사용자가 위 방향을 정했다. 다만 서버·로컬 규칙 중 DWG 처리(서버 직접 vs 로컬 체크아웃)는 "비슷한 맥락으로 고민 중"이라 **OQ-18**로 남긴다. 기본값은 서버 직접 + 보호 장치이고, 로컬 체크아웃은 설정으로 켠다(T-312).
- **기준 문서 선행(T-306):** SPEC-01.13에 폴더 역할·체크아웃·반영·'작업 중' 상태의 의미를 더하고, [ARCH-01](../architecture/ARCH-01-system.md) 「데이터 위치(ADR-037)」 표의 "PC 사용자 폴더 — VIDE는 경로만 기록" 행을 이 계획의 쓰기 규칙으로 바꾼 뒤에 코드에 손댄다. ADR-042가 `review` 이상이어야 한다.
- **범위:** 로컬 트리 생성·열기(템플릿은 설정), `project.config.json` 읽기·쓰기, 연결 폴더 구조 읽기 → 스키마 제안 → 대화 확정 → 기억, 3dm 체크아웃·반영·보관·'작업 중', DWG 보호, VIDE 산출물의 트리 쓰기, 프로젝트 로컬 git 준비, `vide` CLI 최소판, 파일 지도(관계·영향 미리보기·시간축), 검수, 논현동 7-3 매핑.
- **범위 밖:** GitHub·Cloudflare 계정과 원격 푸시·배포(PLAN-54), 검토용/보고용 산출물 등급과 갱신 제안 카드의 rev cloud 표시(PLAN-54), 기록 모델과 결정·근거 기록의 타임라인(PLAN-53 — 파일 지도의 시간축은 파일 사건만 다루고 기록은 뒤에 같은 노드에 붙는다), 규모검토 진행판(7-3 작업 종료 뒤 재검토), 서버 폴더의 이름·구조 변경과 서버용 템플릿(하지 않음), 여러 PC의 같은 모델 동시 편집(PRD §14.2 제외 유지).
- **원칙(AI.md §8):** 시험은 `.vide/` 아래의 합성 폴더와 사본만 쓴다. 회사 서버 원본(`\\Lifethings\…`)과 사용자 원본 파일은 열지 않는다. 호스트가 필요한 시험은 사용자에게 미리 알리고 에이전트가 띄운 호스트는 끝나면 닫는다.

## 로컬 트리와 `project.config.json`

새 프로젝트를 폴더로 만들 때 VIDE가 만드는 기본 트리다. 번호는 정렬용이며 10단위 여백을 두지 않는다(역할은 `paths`가 고정하므로 끼워 넣을 자리가 필요 없다). **하드코딩이 아니다:** 아래 표는 설치본 설정의 템플릿 파일(`workspace-template.json`: 역할 키 → 기본 폴더 이름)이 만드는 기본값이고, 회사·개인은 템플릿의 이름을 바꿀 수 있으며 프로젝트는 `project.config.json`의 `paths`로 템플릿을 덮어쓴다. 코드는 역할 키만 알고 폴더 이름은 모른다.

| 폴더 | 역할 키 | 어느 기능이 쓰나 | 서버·로컬 |
|---|---|---|---|
| `project.config.json` · `README.md` · `AGENTS.md` | — | 역할 경로·정본 위치·서버 기억(VIDE가 읽고 씀). 사람·AI 진입문 — 이 폴더에서 Claude Code를 열어도 `AGENTS.md`를 바로 읽는다. VIDE가 갱신하고 사람이 덧쓴 부분은 지키지 않는다(표시 구간만 VIDE 소유) | 로컬(서버 폴더에는 매핑 때 `project.config.json`만 둘지 OQ-18) |
| `01_운영/` | `ops` | 일지·회의록·할 일 내보내기·일정(SPEC-01.14, SPEC-10). 사이트 사본의 원본 | 로컬, 바로 쓰기 |
| `02_자료/` | `raw` | 원본 자료 — 법규·대장·수치지도·의뢰 문서. 읽기 전용. 지식 수집(PLAN-42)과 수동 자료 카드가 여기로 받는다 | 서버 매핑이 보통, 로컬 사본 가능 |
| `03_모델/` | `rhino` | Rhino 3dm, 모델 구성. 작업 중 파일은 로컬 체크아웃 | 서버 정본 → 로컬 체크아웃 |
| `04_도면/` | `cad` | DWG·xref·CTB(X-PLAN 등 참조 원도면 포함) | 서버에서 직접(기본), 로컬 체크아웃은 설정 |
| `05_검토/<jig>/<회차>/` | `review` | 모든 jig 결과 — 데이터 JSON + 검토용 HTML(규모검토·법규 체크·구조·패널링 전부) | 로컬, VIDE가 씀 |
| `06_산출물/` | `output` | 보고용 HTML·CSV·PDF·내보낸 모델 = 게시 대상 | 로컬, VIDE가 씀 |
| `07_검토본/` | `snapshots` | 검토본 스냅샷(시점 비교, SPEC-02.13) | 로컬 |
| `08_레퍼런스/` | `references` | 이미지·사례(느낌 요청 이미지 포함) | 서버 매핑 또는 로컬 |
| `09_도구/` | `tools` | 프로젝트 jig(README·jig.json, SPEC-07.3)·프로젝트 전용 스크립트. 엔진 코드는 두지 않는다 | 로컬 |
| `10_아카이브/` | `archive` | 이전 판 보관. `서버반영/<날짜>/`(T-311)·`서버백업/<날짜>/`(T-312) 포함 | 로컬 |

`project.config.json`은 논현동의 `architecture-workspace/1` 스키마를 그대로 읽을 수 있게 하고(`project_id`·`title`·`paths`·`authority`·`git`), VIDE가 쓰는 판은 `schema: "vide-workspace/1"`로 다음을 더한다.

- `paths`: 위 역할 키 → 상대 경로. 없는 키는 그 역할이 없는 프로젝트다.
- `server`: `{ root: "\\\\Lifethings\\Lifethings_02\\PROJECTS\\2026 Project\\2601-나진상가 공공기여", paths: { raw: "02 자료", cad: "05 도면", rhino: "04 모델", references: "03 참고" }, targets: { output: "05 보고서\\VIDE", snapshots: null }, checkout: { rhino: "local", cad: "server" }, proposedAt, confirmedBy }` — **규약이 아니라 기억**이다. `paths`는 연결 때 AI가 읽어 제안하고 사람이 확정한 "서버의 실제 이름 → 역할" 대응, `targets`는 [서버에 반영] 때 "이 종류는 여기" 기억(없으면 그때 묻고 기억). 뒤에 대화("앞으로 보고서는 여기에")로 바뀐다. 서버 트리는 바꾸지 않는다.
- `template`: 트리를 만들 때 쓴 템플릿 이름·판. 템플릿을 바꿔도 이미 만든 프로젝트는 `paths`가 정본이라 영향이 없다.
- `authority`: 정본 파일 위치(모델 구성·사실·출처 등). 규모검토가 쓰던 키를 그대로 받는다.
- `vide`: `{ projectId, createdBy, createdAt }` — VIDE 프로젝트 id. 재현(T-308) 때 같은 id로 다시 만든다.

물리 형식(필드 이름·직렬화)은 ARCH-01에 「작업 폴더(PLAN-52)」 절로 적는다(T-306). 이 표는 역할과 위치의 의미만 정한다.

## 서버 연결 규칙

| 단계 | 동작 | AI 신뢰 문제의 처리 |
|---|---|---|
| 서버 폴더 연결 | 어느 폴더를 연결할지는 지금처럼 설정(SPEC-01.13 프로젝트 폴더)에서 미리 정한다. UNC·네트워크 드라이브는 지금 코드(`src/server/project-path.ts`, 2026-10-08 `fe2cdba7`·`df2ab89e`)의 실제 경로 규칙을 그대로 쓴다. 이름·구조를 바꾸지 않는다 | 읽기만 |
| 구조 읽기 → 스키마 제안 → 확정 → 기억 | 연결 직후 AI가 상위 두 단계 폴더와 파일 종류를 읽어 역할 제안을 대화에 올린다(T-309): "`05 도면`에 DWG 41개와 xref — 도면 역할로, `03 참고`는 레퍼런스로 보입니다. 보고서를 둘 곳은 없네요 — 반영할 때 물어볼까요?" 사람이 확정·수정하면 `server.paths`에 기억한다. 뒤의 대화 한 문장("앞으로 보고서는 `05 보고서\VIDE`에")이 `server.targets`를 바꾼다. 제안은 **추정**이며 확정 전에는 어떤 쓰기도 그 추정에 기대지 않는다 | 읽기 + 대화, 쓰기 없음 |
| 3dm 체크아웃 | 서버 `rhino` 역할의 파일을 로컬 `03_모델/`로 복사하고 '작업 중(누가·언제)'을 기록한다. 연결 ID(ADR-030)는 파일 안에 있으므로 사본에도 따라온다. 같은 파일을 다른 사람이 체크아웃 중이면 경고하고 읽기 전용 사본만 준다 | AI는 로컬 사본에만 쓴다 |
| [서버에 반영] | 사람이 누른다. 대상 경로는 `server.targets`의 기억을 제안하고, 기억이 없으면 그때 묻고 기억한다. 반영 전 바뀐 객체 수·Sync 어긋남·마지막 서버 판과의 시각 차이를 보이고, 서버의 이전 판을 로컬 `10_아카이브/서버반영/<날짜-시각>/`에 복사한 뒤 덮어쓴다. 체크아웃을 풀지 말지 묻는다 | 서버에는 사람이 반영한 판만 쌓인다 |
| DWG 서버 직접 | `cad` 역할은 서버 경로를 그대로 열어 xref가 깨지지 않게 한다. 요청 단위 되돌리기(ADR-027)는 그대로이고, 하루 첫 AI 편집 전에 그 DWG를 `10_아카이브/서버백업/<날짜>/`에 복사한다. 갱신 제안 카드의 rev cloud 표시는 PLAN-54 | 되돌리기 + 하루 단위 백업 |
| DWG 로컬 체크아웃(설정) | `server.checkout.cad = "local"`이면 3dm과 같은 규칙으로 로컬 `04_도면/`에 체크아웃하고 xref 경로는 서버를 가리키게 둔다(읽기) | OQ-18 |
| '작업 중' 표시 | 대시보드의 프로젝트 폴더 구역과 사이트의 프로젝트 화면에 "누가 어느 파일을 작업 중"을 보인다. 사이트 D1에 작은 표(`project_checkouts`)를 둔다 | 충돌을 미리 보임 |
| 바로 서버 쓰기 허용 | 신뢰가 쌓이면 역할별로 켠다(예: `ops`·`review`·`output`). 기본은 모두 꺼짐 | 설정, 2차 |

## 파일 지도

탐색기를 목록이 아니라 **관계 지도**로 만든다. 참고는 RESEARCH-17 §2의 아티팩트 ②(모델 + 타임라인 한 커서)·③(행 × 시간, 기록 사이 연결선)이며, 데이터 모양과 상호작용만 가져온다.

| 요소 | 1차 범위 | 출처 |
|---|---|---|
| 노드 | 로컬 트리의 파일 + 연결된 서버 폴더의 파일(역할이 있는 것 먼저, 나머지는 접힘) | T-307 역할 경로, 프로젝트 폴더 목록 |
| 연결선 | xref(DWG 참조), Rhino↔CAD Sync 쌍(SPEC-05.8), jig 입력→결과(SPEC-07.5), 데이터→보고서(검토용/보고용, PLAN-54), 로컬 체크아웃↔서버 원본(T-310/311), 참조 이미지→요청, 노트·회의록의 파일 언급 | 각 기능이 이미 가진 관계를 모으기만 한다(T-318) |
| 시간축 | 파일 사건 — Sync, 체크아웃, 반영, jig 실행, 요청으로 바뀜, 서버 판 갱신. 커서를 끌면 그 시점에 있던 연결과 사건이 켜진다 | 실행 기록(SPEC-02.13), Sync 기록, T-310/311 기록 |
| 상호작용 | 파일을 고르면 이어진 파일이 켜지고 나머지는 흐려진다. 요청을 쓰는 중 대상이 파일로 풀리면(연결·언급·핀) **보내기 전에** 영향받는 파일 묶음을 요청 카드 옆에 미리 보인다(SPEC-02 요청 카드 연동) | T-319 |
| 공유 부품 | 행 배치·글리프·연결선·시간축 부품은 `src/ui/chart/*`로 두고 [PLAN-53](PLAN-53-project-records.md)의 부위×시간 차트와 공유한다 — 먼저 착수하는 쪽이 만들고 다른 쪽이 재사용한다. 뒤에 기록(결정·근거)은 같은 파일 노드에 붙는다 | PLAN-53 |

1차 범위는 사용자 결정(2026-10-15)대로 **관계 + 영향 미리보기 + 시간축**이다. 화면 표현은 Design.md에 SCR을 더한 뒤 만든다. 시험은 합성 fixture(가짜 트리·가짜 관계·가짜 사건)로만 하고 실제 서버 파일은 쓰지 않는다.

## 검증

- **단위:** `src/core/workspace-config.ts`(두 스키마·역할 해석·서버 기억·템플릿 덮어쓰기), 구조 읽기의 역할 추정(이름·확장자·내용 합성 트리 → 제안, 빈 폴더·권한 없음·충돌 추정의 실패 코드), 산출물 경로 계산, `.gitignore` 생성, CLI 인자 해석, 파일 지도 연결선 수집(종류별). 기존 `tests/server/project-drives.test.mjs`에 UNC 모양 서버 기억과 정션 거절을 더한다.
- **통합(호스트 없음):** 임시 폴더에 만들기 → 산출물 쓰기 → DB 삭제 → 열기(재현) → 같은 id·경로. 가짜 서버 폴더(다른 드라이브·UNC 모양)로 제안 → 확정 → 기억 → 대화로 변경, 체크아웃·반영·보관 왕복(반영 위치는 기억 → 없으면 묻기). `vide` CLI는 가짜 엔진 상대. 파일 지도는 합성 fixture(파일·연결선·사건)로 API와 브라우저 시험.
- **실호스트(사용자에게 미리 알림):** 합성 3dm 체크아웃 뒤 연결 ID 유지(T-310), 합성 DWG+xref 서버 직접 열기와 백업(T-312). 모두 `.vide/` 아래 사본. 사용자의 Rhino·ZWCAD 창은 쓰지 않고 에이전트가 띄운 호스트는 끝나면 닫는다.
- **사용자 확인:** 회사 서버 폴더의 사본을 연결해 AI 제안이 실제 구조를 맞게 읽는지 1회(틀린 추정은 대화로 고치는 것까지), 대시보드의 '작업 중' 표시가 사이트에서도 보이는지(PLAN-35 배포 뒤), 파일 지도에서 요청 전 영향 미리보기가 "직관적으로 보이는지"(사용자 말 그대로의 기준, 페르소나 대행 판정 뒤 동승 1회).
- **회귀:** 폴더 없는 기존 프로젝트의 산출물 위치·AI 작업 디렉터리·폴더 밖 질문 카드(SPEC-01.13 3) 동작 유지. `npm run verify`.

## 완료 기준

- 새 프로젝트를 폴더로 만들면 템플릿의 트리와 세 파일이 생기고(템플릿 이름을 바꿔도 동작), 그 폴더를 다른 PC(또는 DB를 지운 같은 PC)에서 열면 같은 프로젝트가 다시 생긴다.
- 회사 서버 폴더는 이름·구조 그대로이고, 연결하면 AI가 구조를 읽어 역할을 제안하며 사람이 확정한 것만 기억된다. VIDE는 사람이 [서버에 반영]을 누르기 전에는 서버에 쓰지 않는다(DWG 서버 직접 모드의 요청 편집은 예외이며 하루 백업이 있다).
- 파일 지도에서 파일을 고르면 이어진 파일이 켜지고, 시간축 커서로 사건·연결의 변화를 볼 수 있으며, 요청을 보내기 전에 영향받는 파일이 보인다.
- 3dm 체크아웃·'작업 중'·반영·이전 판 보관이 왕복하고, 충돌(다른 사람 작업 중)이 미리 보인다.
- jig 결과·보고서·일지·검토본·프로젝트 jig가 트리의 정해진 역할 폴더에 사람이 읽는 파일로 남는다.
- 작업 폴더의 터미널에서 `vide jig list`·`vide jig run`이 설치본 엔진으로 동작한다.
- ARCH-01 「데이터 위치」 표가 실제 쓰기 위치와 같다.
