## 0. 제품 요약

Drawing IDE의 첫 MVP는 특정 건축 자동화 기능 하나가 아니라 **여러 프로그램을 같은 프로젝트에서 다룰 수 있는 공통 IDE 플랫폼**이다. 이후 법규 검토·사이트 모델링·매스 배치·구조 검토·평면 작성·건축 개요·일람표 작성을 전문 스킬과 플러그인으로 추가한다.

기본 환경은 빈 화면과 연결 버튼을 뜻하지 않는다. 지원 호스트에서 대상 읽기, 공간 입력, 제한된 네이티브 객체 생성·수정, 진행의 시각화, 사람의 개입, 결과 확인·보존까지 이어져야 한다. 전문 업무 전체를 자동화하지 않아도 이 기본 제어를 사용할 수 있어야 한다.

| 구분 | 제품 결정 | 경계 |
|---|---|---|
| 첫 MVP | 프로젝트·작업·데이터·AI 실행·호스트 제어·확장의 공통 기반 | 특정 매스 자동화 도구를 전체 MVP로 대체하지 않음 |
| 주 사용 환경 | Windows 우선 설치형 프로그램 | 앱 기술·설치 도구·지원 Windows 세부 버전은 별도 결정 |
| 호스트 | Rhino·Revit·CAD 계열의 기본 제어 | AutoCAD·ZWCAD의 첫 지원 조합과 버전·객체 범위는 확정 필요 |
| 결과 | 지원 객체 종류에 대한 네이티브 생성·수정과 후속 편집 | 보이는 형상이나 카테고리 지정만으로 네이티브 성공 처리 금지 |
| 입력과 개입 | 문장·핀·코멘트·좌표 기반 스케치, 실제 중간 상태에 대한 수정 | 코멘트 저장이 자동 실행 또는 원본 수정 권한이 되지 않음 |
| 확장 | 공통 기능 위에 전문 스킬·플러그인과 분야별 규칙 추가 | 기본 권한·대상·단위·상태 보호를 후속 단계로 미루지 않음 |
| 외부 참여 | iPad·Mac·Windows의 웹 브라우저를 통한 검토 | 첫 배포의 범위·지원 브라우저·동기화 방식은 확정 필요 |

## 1. 제품 정의와 책임

### 1.1 무엇을 만드는가

건축가가 여러 모델링 프로그램의 모델과 설계 자료를 하나의 프로젝트·작업 범위에서 다루고, AI와 함께 작업하면서 과정과 결과를 직접 통제하는 통합 작업환경을 만든다. <del>제품의 작업명은 **Integrated Drawing Environment**다.</del><ins>제품의 작업명은 **Drawing IDE**(Integrated Drawing Environment)다.</ins>

> **[검토 · claude · R-04 · 중간]** 1행 제목과 이 문장은 Integrated Drawing Environment, 4·11행과 Design.md·DEVELOPMENT_GUIDE.md는 Drawing IDE, 저장소 이름은 Vino-IDE라 이름이 셋이다. 다음 문서(SPEC·PLAN)가 인용할 작업명을 하나로 고정하고 긴 이름은 병기만 한다. 코드명 Vino를 PRD에 등록할지는 소유자 결정.

<!-- codex-review:start -->

> **[검토 · codex · R-24 · 낮음]** **부분 동의 · [Claude R-04](#review-R-04) 재검토.** Drawing IDE를 표시명, Integrated Drawing Environment를 풀어 쓴 이름으로 정리하는 안은 자연스럽다. 다만 Vino-IDE라는 저장소명은 제품 표시명과 달라도 문제가 없으며, 세 이름이 있다는 사실만으로 구현을 막지는 않는다. 코드명 변경·등록은 별도 사용자 선택이다.

<!-- codex-review:end -->

VS Code와 같은 확장형 IDE의 개념을 지향하되, VS Code 기반 개발이나 터미널 중심 화면을 필수로 정하지 않는다. 모델·도면·스케치·치수·자료가 주요 입력과 판단 대상이다. 사용자는 코드와 긴 터미널 출력을 읽지 않아도 대상과 변경을 이해할 수 있어야 한다.

새로운 범용 기하 커널, 모든 CAD/BIM 프로그램을 대체하는 모델러, 모든 네이티브 화면을 한 창 안에 넣는 제품은 아니다. 개별 호스트가 원본의 편집 의미를 소유하고, IDE는 연결된 작업과 근거·상태·결정을 관리한다.

### 1.2 제품이 책임지는 것

지정한 대상·입력·유지 조건을 보존하고, 실제 작업 상태와 결과를 보여주며, 사용자의 개입을 실행에 반영한다. 후보와 원본, 계획과 실행, 추정과 사실, 제출과 반영, 적용과 저장을 구분한다.

등록되지 않은 모든 설계 조건의 자동 발견이나 전체 설계의 적합성을 포괄적으로 보증하지 않는다. 지원하는 기본 제어에서는 정의된 네이티브 결과와 상태의 신뢰성을 확보한다. 전문 스킬은 별도의 완료 기준과 검토 범위를 갖는다. ‘미검토’ 표시가 낮은 완료율과 품질의 변명이 되어서는 안 된다.

### 1.3 사용 환경과 접근 역할

**주 작업자:** Windows에 설치한 IDE에서 로컬 프로젝트를 열고, 사용 권한이 있는 호스트 프로그램과 연결한다. 호스트 프로그램 자체의 설치·사용 권한이 IDE 설치만으로 제공되는 것으로 표시하지 않는다.

**외부 검토자:** 웹으로 공개된 권한 범위 안에서 모델·자료를 보고 코멘트·스케치를 제출한다. 이 웹 참여가 Windows 네이티브 API의 직접 실행이나 로컬 원본 쓰기 권한을 뜻하지 않는다.

**Local-first:** 입력·프로젝트 기록·원본 제어의 기준을 작업환경이 관리한다. 클라우드 모델을 사용할 수 있지만 전송할 자료와 권한을 확인할 수 있어야 한다. AI 연결이 끊겨도 가능한 열람·선택·스케치·코멘트·저장 작업은 유지한다. 외부 검토의 최신 상태나 온라인 추론까지 오프라인에서 가능하다고 표시하지 않는다.

## 2. 해결할 문제와 제품 가설

제품이 해결할 문제와 검증할 가설은 다음과 같다. 효과는 지원 과업의 사용자 시험에서 확인한다.

| 문제 | 제품의 대응 | 확인할 결과 |
|---|---|---|
| ‘여기’와 ‘이런 형태’를 문장만으로 전달하기 어렵다 | 실제 대상 핀, 좌표에 연결된 스케치, 단위 있는 치수 | 대상 오인과 의도 수정 부담이 줄어드는가 |
| 모델·BIM 정보·회의 결정이 분리되어 있다 | 설계 대상을 중심으로 자료·관계·근거 연결 | 관련 조건을 찾고 변경 영향을 확인할 수 있는가 |
| 큰 작업은 방향 오류를 늦게 발견한다 | 검토 가능한 단위로 분할하고 중간 결과를 남김 | 초기에 잘못된 대상을 찾고 방향을 바꿀 수 있는가 |
| 작업 중 무엇이 일어나는지 알 수 없다 | 실제 모델·도면·가정·계산 상태를 표시 | 설명 로그 없이도 현재 상태를 이해하는가 |
| 매 단계 승인하면 직접 CAD를 쓰는 것만큼 번거롭다 | 위임 범위 안에서는 진행하고 설계적 결정에서만 확인 | 불필요한 개입 없이 결과를 채택하는가 |
| 큰 문맥과 반복 검증이 시간·비용을 늘린다 | 필수조건 보존, 관련 정보 조회, 영향 범위 재계산 | 조건 누락 없이 총비용과 재작업을 줄이는가 |
| 후보·원본·보고서 상태를 혼동한다 | 후보 저장, 채택, 원본 반영, 발행을 분리 | 무엇이 실제 계획에 반영됐는지 확인 가능한가 |
| 대안과 피드백의 이유가 사라진다 | 기준 버전이 있는 이력·검토 요청·결정 기록 | 과거 판단과 현재 결과의 연결을 회수할 수 있는가 |

## 3. 사용자와 핵심 업무

**주 사용자 — 비개발자 건축 설계자.** Windows에서 Rhino·Revit·CAD를 사용한다. 프로젝트와 연결 문서를 관리하고, 모델·도면·선택·스케치로 요청하며, 후보와 실제 변경을 보고 방향을 바꾼다. 분야별 자동화 스킬이 없어도 기본 제어를 사용할 수 있어야 한다.

**보조 사용자 — BIM·계산설계 담당자.** 네이티브 객체의 의미, 데이터 관계, 입력 조건, 연결 상태와 결과의 충실도를 확인한다. 전문 설정을 일반 사용자의 매 작업 필수 절차로 만들지 않는다.

**확장 작성자 — 스킬·플러그인 개발자.** 공통 연결·입력·진행·결과·권한 기능을 재사용해 전문 기능을 추가한다. 일반적인 확장 등록을 위해 프로젝트 데이터·인증·호스트 제어를 매번 다시 만들지 않아야 한다.

**외부 검토자 — 동료·책임자·발주자 등.** 웹에서 게시된 기준 모델과 자료를 보고 의견을 남긴다. 변경의 의미를 이해하는 것과 전문적 적합성을 판정하거나 원본에 반영하는 권한은 구분한다.

## 4. MVP·후속 확장·제외 범위

### 4.1 플랫폼 MVP에 포함하는 공통 능력

프로젝트·작업 범위 관리, 호스트·문서 식별, 상태·속성·선택 읽기, 제한된 네이티브 생성·수정, 문장·핀·기본 평면 스케치·코멘트, AI 요청·재개, 실제 중간 결과, 수정·중단, 후보·원본 구분, 입력·결정·결과 보존, 기본 산출물 열람과 HTML 전달, 작은 확장의 등록·실행을 포함한다.

> **[검토 · claude · R-05 · 중간]** 13개 능력을 쉼표로 이은 약 130자 한 문장이라 끊어 읽기 어렵고, 내용은 §13 FR-01~18과 같다. FR ID가 달린 항목 목록(예: '- 프로젝트·작업 범위 관리 (FR-01)')으로 바꾸거나 '상세는 §13 FR-01~FR-18' 한 줄로 줄여 중복을 없앨 것.

<!-- codex-review:start -->

### 4.3 기본 실행 규칙과 전문 하네스의 경계

**MVP에서 제공:** 정확한 문서·객체·단위·권한, 입력·기준 보존, 실제 진행 표시, 개입·중단 상태, 사람 수정 보호, 중복 적용 방지, 불명확 결과 처리, 최소 품질·비용 관측.

**스킬별로 확장:** 법규 해석 절차, 구조 검토의 전제, 도면 작성 관례, 건축 분야의 경험칙·사례·평가, 전문 도구와 계산 흐름. 지침만으로 실행 권한을 바꾸거나 기본 보호를 끄지 않는다.

### 4.4 후보 기능과 비목표

즉석 HTML 자료 생성, 문단·표·도형 직접 선택과 부분 수정, 캔버스/DOM 기반 편집기는 **후보 기능 C-01**로 둔다. 채택 전에는 MVP 수용 조건이나 구현 티켓으로 자동 포함하지 않는다.

자유로운 화면 분할·도킹·Blender식 워크스페이스, 플러그인 마켓·결제, 모든 객체 유형의 쓰기, 범용 네이티브 파일 자동 병합, 모든 BIM 의미·편집 이력의 무손실 왕복, 장시간 무관찰 자율 설계는 MVP의 필수 범위가 아니다.

후속 연결 대상으로 Grasshopper·Archicad·SketchUp 등을 유지한다. 추가 호스트와 객체 종류는 동일한 지원·검수 원칙에 따라 별도 확장한다.

## 6. 건축 특화 데이터 요구사항

### 6.1 중심은 ‘설계 대상’이다

설계 대상에 형상·속성·관계·근거·버전·작업 결과를 연결한다. ‘형상 파일 + 임의 속성 목록’만으로 끝내지 않는다. 동시에 DB 전체를 완벽하게 분류해야만 작업을 시작할 수 있는 구조도 피한다.

초기 매스나 미분류 형상을 수용한다. 아직 모르는 용도·호스트 관계·BIM 분류는 미확정으로 남기고, 지원 작업에 필요한 의미부터 점진적으로 추가한다. 단순 메시를 벽·슬래브 같은 네이티브 요소로 자동 간주하지 않는다.

### 6.2 연결해야 할 정보

| 정보 | 요구 내용 | 사용자에게 가능한 일 |
|---|---|---|
| 설계 대상과 식별 | 프로젝트·대안·원본 모델 안의 식별과 대응 관계 | 현재 무엇을 가리키는지 확인 |
| 형상 표현 | 정밀 원본 참조, 표시용 형상, 평면·단면, 좌표·단위 | 같은 대상을 여러 표현으로 검토 |
| 속성과 수량 | 값·단위·정의·출처·기준 버전 | 치수·면적·용도 등의 근거 확인 |
| 대상 간 관계 | 포함, 경계, 호스트, 연결, 타입 공유, 계산 의존성 | 영향을 받는 대상과 작업 추적 |
| 근거와 조건 | 회의록·스케치·자료 위치, 적용 범위, 채택 여부 | 왜 유지·변경하는지 확인 |
| 작업과 결과 | 사용한 입력, 실제 생성물, 변경 내역, 개입, 결과 상태 | 중간 상태를 다시 보고 작업 이어가기 |

표현이 바뀌어도 확인 가능한 대응 관계는 유지한다. 그러나 객체의 분할·합침·삭제·재생성 뒤 동일성이나 부분 참조를 확인할 수 없다면, ‘연결 끊김’ 또는 ‘이전 버전 참조’로 표시한다. 가까운 객체로 조용히 재연결하지 않는다.

### 6.3 관계의 종류와 신뢰도를 구분한다

예를 들어 ‘문 → 개구부 → 벽’의 호스트 관계, ‘요소 → 타입’의 공유 관계, ‘스케치 → 후보 → 면적표’의 파생 관계는 서로 다르다. 단순히 ‘관련 있음’으로 저장하지 않는다. 공간적으로 가까운 것과 의미적으로 연결된 것도 구분한다.

관계와 값에는 **원본에서 읽음, 도구로 계산함, 사용자가 확정함, AI가 추정함**을 구분해 남긴다. 현재 문 폭과 목표 문 폭은 다른 정보이며, 서로 덮어쓰지 않는다. 원문 사실을 바꾸는 것, 계산 가정을 바꾸는 것, 설계 조건을 바꾸는 것도 다른 사건으로 기록한다.

### 6.4 데이터가 답해야 할 질문

사용자는 대상에서 관련 조건·코멘트·지표로 이동할 수 있고, 반대로 자료나 지표에서 관련 모델 대상을 확인할 수 있어야 한다.

대표 질문은 다음과 같다. “이 부분을 유지하는 근거는 무엇인가?”, “이 수치는 어느 모델과 방법으로 계산했는가?”, “이 스케치를 고치면 무엇이 다시 계산되어야 하는가?”, “이 관계는 확인된 사실인가 추정인가?”

알 수 없는 관계는 알 수 없다고 드러낸다. 모든 의존성을 알고 있다고 전제한 자동 재사용·자동 변경은 허용하지 않는다.

### 6.5 데이터 저장·조회 요구

데이터 저장·조회는 설계 대상과 관계를 탐색하고, 버전별 상태·출처·파생 결과를 구분할 수 있어야 한다. 큰 기하 데이터와 LLM 입력을 같은 저장 단위로 취급하지 않는다. 구체적인 관계 종류와 읽기·갱신 동작은 SPEC에서, DB 엔진·물리 스키마·저장 형식은 구현계획에서 결정한다.

## 7. 작업을 나누는 기준

### 7.1 한 단위는 하나의 설계 목적과 검토 가능한 결과를 갖는다

‘이 건물의 평면을 개선한다’는 WorkScope의 목표가 될 수 있지만 단일 무관찰 실행 단위로 삼지 않는다. 반대로 ‘객체 읽기 → 곡선 생성 → 면 생성’ 같은 내부 명령마다 사용자의 개입을 요구하지도 않는다.

한 작업 단위에는 **목적, 기준 버전, 변경 대상, 검토 범위, 유지 대상·조건, 기대 결과, 의존하는 작업, 수정·중단 가능한 지점**이 있어야 한다. 선택과 기존 프로젝트 정보로 채울 수 있는 내용은 자동으로 구성하고, 모호한 중요한 항목만 확인한다.

### 7.2 변경 범위와 검토 범위를 분리한다

변경 권한이 없는 주변 대상도 영향 확인을 위해 읽을 수 있다. 반대로 검토에 포함되었다고 변경 권한이 생기지는 않는다.

문을 옮기는 작업은 문과 개구부를 바꾸지만 벽·주변 공간을 함께 검토할 수 있다. 공통 타입 수정처럼 공간적으로 먼 객체에 영향을 주는 경우도 검토 범위에 포함한다. 실제 영향 범위를 좁게 확인하지 못하는 작업은 더 넓게 검토하거나 후보 실행으로 제한하며, 그 이유를 보인다.

### 7.3 더 나누어야 하는 경우

서로 독립적으로 채택할 수 있는 설계 판단이 여러 개 있거나, 중간 방향을 확인하지 못한 채 많은 후속 작업이 쌓이거나, 영향 범위가 원래 목표를 넘어가면 작업을 더 나눈다. 오래 걸리고 중단 제약이 큰 연산은 가능한 경우 검토 가능한 중간 단계로 분리한다.

반대로 문과 개구부를 함께 수정해야 일관된 후보가 되는 것처럼 강하게 결합된 변경은 하나의 검토 단위로 묶는다. 같은 조건의 여러 객체를 일괄 변경하는 것도 하나의 검토 가능한 결과가 있으면 허용한다.

객체 수·시간·토큰 수 하나만으로 고정 분할하지 않는다. 분할 자체가 새 AI 세션, 추가 검증자, 사용자 승인 단계를 자동으로 늘려서는 안 된다.

### 7.4 작은 작업과 전체 조건을 함께 유지한다

각 작업은 상위 WorkScope의 목표와 적용 중인 조건을 참조한다. 작업 결과를 합칠 때는 연결 부위와 전체 지표를 다시 확인한다. 개별 작업의 통과를 전체 설계의 적합으로 확대하지 않는다.

작업 간 선후관계는 사용자에게 이해 가능한 이름으로 제공한다. 병렬 준비 여부와 무관하게 같은 원본·공유 대상을 변경할 때는 충돌과 대상 상태를 관리해야 한다.

## 8. 핵심 사용자 여정

아래는 플랫폼의 사용 경험을 설명하는 여정이다. 개별 객체와 생성 동작은 각 호스트의 지원표에 있는 기능만 사용한다. 복잡한 건축 해석 스킬의 완성을 전제하지 않는다.

> **[검토 · claude · R-10 · 낮음]** §8 여정이 모두 추상 문장이라 §2 가설을 검증하거나 SPEC의 첫 기능을 고를 때 붙잡을 사례가 없다. 지원 확정으로 오해되지 않게 '예시'로 표시한 가상 모델 시나리오 하나(예: 소규모 근생 매스에서 코어 이동 → 면적표 갱신 → 원본 반영)를 §8 앞에 두는 것을 검토. 넣지 않기로 하면 SPEC 첫 기능의 예시로 대신한다.

### 8.1 설치하고 프로젝트·호스트를 연결한다

사용자가 Windows IDE를 설치하고 프로젝트를 연다. 연결 가능한 호스트와 문서를 확인한 뒤 작업 대상을 명시한다. 문서명뿐 아니라 구분 가능한 대상 정보, 단위, 현재 읽기·쓰기 수준을 확인한다. 설치된 호스트·버전이 지원되지 않으면 필요한 조건을 안내한다.

Rhino와 Revit 등 여러 호스트를 같은 프로젝트에 등록할 수 있다. 화면을 전환하거나 다른 프로그램을 활성화해도 진행 중인 요청이 다른 문서를 대상으로 바뀌지 않는다.

### 8.2 대상을 가리키고 의도를 전달한다

기존 객체를 선택해 문장에 핀을 넣고, 작업평면에 선을 그리거나 지원 파라미터를 지정한다. 변경 대상·유지 대상·자료 참조를 함께 전달한다. 예를 들어 ‘[이 객체]를 지정 방향으로 이동하고 [주변 객체]는 유지’ 또는 ‘[기준선]과 지정 치수로 지원 객체 생성’을 요청할 수 있다.

> **[검토 · claude · R-11 · 중간]** 핀·스케치를 IDE 자체 뷰에서 한다는 전제가 §1.1·§6.2(표시용 형상)·Design.md §03 배치에 암시돼 있지만, 그 결과 각 호스트가 제공해야 하는 최소 능력(표시용 형상 추출, 선택 양방향 동기화, 좌표계·단위 매핑, 대형 모델 지연)이 §12.2·§14.1 호스트 요구에 없다. IDE 뷰 전제를 문장으로 명시하고 §14.1 '요구할 능력' 열에 반영할 것. Revit은 뷰 단위 추출·모달 선택 제약이 있어 OQ-05·06과도 연결된다.

사용자가 입력한 선과 치수, 대상은 원본 데이터로 보존한다. 평면 스케치의 공간 기준을 확인하고, 등록되지 않은 이미지는 별도로 표시한다. 코멘트 저장은 AI 실행과 구분한다.

### 8.3 실제 중간 상태를 보며 작업한다

제품은 작업 대상과 적용 조건, 예상 변경, 마지막으로 만들어진 일관된 후보를 표시한다. 예정된 작업과 수행 중인 작업, 이미 생성한 결과를 구분한다. 자유로운 후보 탐색을 모든 내부 명령의 승인으로 끊지 않는다.

의미 해석이 필요한 스케치는 원본과 해석을 함께 보여준다. 지원 범위를 벗어난 요청은 일반 메시나 다른 유형으로 몰래 대체하지 않고 가능한 대안과 한계를 제시한다.

### 8.4 중간에 지시하거나 직접 수정한다

사용자가 유지 대상을 추가하거나 치수·스케치를 바꾼다. 제품은 지시 접수와 실제 반영을 구분하고, 영향을 받는 후속 작업만 재처리한다. 늦게 도착한 이전 결과가 새 조건이나 호스트에서 직접 수정한 객체를 덮어쓰지 않는다.

중단을 요청하면 새 작업을 멈추고, 진행 중인 연산의 실제 종료 여부를 보여준다. 원본이 이미 바뀐 부분은 후보 폐기와 구분해 기록한다.

### 8.5 결과를 반영하고 호스트에서 편집한다

사용자는 후보를 채택한 뒤 정확한 대상·변경을 확인해 원본 반영을 요청한다. 반영된 결과는 해당 호스트에서 지원하는 네이티브 유형이어야 한다. 기본 도구로 약속한 속성·치수·위치를 다시 수정할 수 있어야 한다.

반영 버튼을 이유로 모델이 새 변경안을 생성해서는 안 된다. 실제 반영과 파일 저장, 저장 후 다시 열기는 별도 상태로 확인한다. 저장되지 않은 문서 변경을 저장 완료로 표시하지 않는다.

### 8.6 확장과 자료를 같은 환경에서 사용한다

검증용 작은 확장을 등록해 동일 프로젝트·대상·권한·진행·결과 보존 흐름으로 실행한다. 시험용 확장은 플랫폼의 확장 접점을 확인하는 용도이며 완성된 법규·구조 스킬을 요구하지 않는다.

사용자는 선택한 기록 시점의 결과·근거를 열람하고 기본 HTML로 전달한다. 웹 검토가 제공되는 배포에서는 외부 의견을 기준 버전과 함께 수신해 검토한다. 외부 의견 제출이 자동 원본 반영으로 이어지지 않는다.

## 9. 진행의 시각화와 언제든 가능한 개입

### 9.1 무엇이 보여야 하는가

사용자는 코드 없이 **현재 대상, 사용 중인 가정과 조건, 마지막으로 준비된 결과, 실제 변경, 남은 검토, 지금 가능한 개입**을 확인할 수 있어야 한다.

| 단계 | 보여줄 실체 | 가능한 개입 |
|---|---|---|
| 대상·조건 정리 | 선택·변경·유지·검토 대상과 연결 근거 | 대상 추가·제외, 조건 변경 |
| 의도 해석 | 원본 스케치와 해석된 경계·방향 | 선·기준면·의미 교정 |
| 후보 생성 | 원본·후보의 차이와 마지막 일관된 중간 상태 | 직접 조정, 다른 후보 선택, 분기 |
| 영향 검토 | 변경 위치에 연결된 치수·수량·속성·미검토 사항 | 가정·참조 자료 수정 |
| 원본 반영 | 실제 적용 대상, 진행 상태, 적용 결과 | 반영 확인, 중단 요청, 복구 검토 |

형상 변화가 없는 데이터 작업도 포함·제외 자료와 가정·수치 변화를 보여준다. 텍스트 로그나 ‘생각 중’ 표시를 자주 출력하는 것만으로 시각적 진행 요구를 충족했다고 보지 않는다.

AI의 내부 사고를 만들어 보여주는 대신 실제 입력·조회·생성·계산·변경과 근거를 표시한다. 숫자형 완료율은 측정 가능한 진행 기준이 있을 때만 사용한다. 결과가 아직 없으면 없다고 알리고 이전 후보의 버전과 준비 시점을 명시한다.

### 9.2 개입과 일반 의견을 구분한다

사용자는 문장, 객체 선택, 스케치 수정, 치수 조절, 자료 교체, 유지 영역 지정, 후보 선택·분기로 개입할 수 있다. 코멘트 저장 자체는 AI 호출이나 진행 중 조건 변경을 뜻하지 않는다.

‘지금 작업에 반영’과 ‘다음 작업을 위한 의견 저장’을 구분한다. 기본 입력·코멘트·핀·스케치 저장은 AI 연결이나 승인 없이 가능해야 한다. AI 요청은 명시적 실행 행동에서 시작한다.

### 9.3 개입의 상태를 구분한다

<!-- codex-review:start -->

> **[검토 · codex · R-41 · 높음]** **추가 지적 · 상태 모델의 분리.** SPEC에서 실행 상태, 지시의 반영 상태, 후보 유효성, 원본 적용 결과, 파일 저장, 증거 수집을 하나의 상태 열거형으로 합치지 않도록 인계가 필요하다. 예를 들어 지시 접수·원본 적용 확인·파일 미저장은 동시에 참일 수 있다. 새 지시 반영됨은 새 지시가 후속 실행 기준으로 채택되었다는 뜻인지 결과까지 생성되었다는 뜻인지 정의해야 한다. 결과가 없는데 완료로 보이는 UI를 막되, 모든 개입이 새 형상을 생성해야 한다고 약속하지 않는다.

<!-- codex-review:end -->

제품은 최소한 **지시 접수, 반영을 위한 정리 중, 새 지시 반영됨, 적용 불가 또는 추가 결정 필요**를 구분한다. 입력을 받았다는 것만으로 이미 실행에 반영했다고 표시하지 않는다.

개입 이후에는 이전 지시와 충돌하는 새 작업을 시작하지 않는다. 진행 중 연산을 안전하게 멈출 수 없는 경우 그 연산의 종료까지 기다려야 함을 표시하고, 종료 결과가 새 조건을 위반하면 활성 후보나 원본에 자동 채택하지 않는다.

원본에 이미 일어난 변경은 별도로 기록하고 필요한 복구를 제시한다. 중단, 되돌리기, 이전 후보에서 분기하기는 다른 행동이다. 즉시 중단이나 전 프로그램 원자적 복구를 무조건 보장하지 않는다.

### 9.4 직접 수정과 이전 AI 결과의 충돌

IDE 또는 연결된 호스트에서 사람이 대상을 직접 바꾸면 그 변경을 새 기준으로 인식한다. 이전 기준의 AI 결과를 현재 상태 위에 자동 적용하지 않는다. 무관한 변경은 영향 확인 후 유지하고, 관련 변경은 재비교한다.

수정 중에도 원본 스케치·코멘트·완료된 후보는 보존한다. 안전하게 재사용할 수 없는 결과는 과거 결과로 남기되 현재 유효한 결과와 구분한다.

### 9.5 확인이 필요한 순간과 필요하지 않은 순간

위임 범위 안의 자료 읽기, 후보 생성, 계산, 후보 내부의 수정은 원칙적으로 연속 진행한다. 유지 조건 변경, 영향 범위 확대, 큰 비용의 추가 작업, 원본 반영·외부 공개는 해당 권한과 사용자 결정을 확인한다.

모든 단계에서 허락을 묻지 않되, 중요한 방향 결정을 AI가 조용히 대신하지 않는다. 모호함을 질문할지 표시된 가정의 후보로 진행할지는 영향·가역성·비용에 따라 정하고, 판단 기준을 사용자 시험으로 검토한다.

## 10. 큰 모델·BIM 문맥과 프로젝트 기억

### 10.1 전체 데이터와 모델 입력을 분리한다

전체 프로젝트 데이터, 계산에 필요한 데이터, LLM에 전달할 정보는 서로 다르다. 대량 기하·속성은 원본과 계산·조회 도구에서 다루고, LLM에는 목표·적용 조건·관계·필요한 결과와 참조를 제공한다.

필수조건을 보존하면서 관련 정보를 추가 조회하는 방식으로 설계한다. 전체 모델·전체 대화·전체 회의록을 매 요청마다 반복 입력하지 않는다. 이 방식을 사용한다는 이유만으로 누락이 없거나 항상 저렴하다고 주장하지 않는다.

### 10.2 기억의 권한과 수명을 구분한다

| 정보 | 의미 | 관리 원칙 |
|---|---|---|
| 입력 원본 | 사용자의 문장·핀·스케치·코멘트 | AI 해석과 별개로 보존 |
| 대화 이력 | 요청·응답·도구 사용 기록 | 이어가기 정보이며 원본 모델의 사실은 아님 |
| 작업 기억 | 현재 목표·가정·미해결 질문 | 해당 작업 범위와 대안에 연결 |
| 확정 결정 | 사용자가 채택한 조건과 근거 | 적용 범위·버전·대체 이력 유지 |
| 실제 모델 상태 | 호스트의 기하·속성·관계와 고정 스냅샷 | 재개·반영 시 필요한 범위에서 확인 |

대화 압축·세션 교체로 중요한 결정이 사라지지 않도록 제품이 관리한다. AI가 제안한 기억이 확정 조건으로 자동 승격되지 않는다. 화면의 대화, 실행 엔진의 세션, 실제 모델 버전을 같은 식별자로 취급하지 않는다.

### 10.3 이번 작업에 쓰이는 정보를 확인할 수 있다

사용자는 이번 입력에 포함된 대상·모델 버전·핵심 조건·참조 자료·가정을 확인하고 수정할 수 있어야 한다. 정보 선택을 위한 복잡한 수동 작업을 매번 요구하지는 않는다.

필수조건과 참고 의견을 구분하고, 서로 충돌하는 결정은 하나를 조용히 덮어쓰기보다 충돌로 드러낸다. 자동으로 발견하지 못한 관계나 확인하지 않은 분야는 결과의 검토 범위에 남긴다.

### 10.4 유효한 결과만 재사용한다

결과 재사용은 단순히 같은 객체가 존재하는지로 결정하지 않는다. 입력 버전, 관계, 계산 방법·가정, 질의 조건, 대상 집합의 변경까지 고려할 수 있어야 한다. 집계 대상에 새 객체가 추가된 경우도 결과를 낡게 만들 수 있다.

관련성을 확인할 수 없으면 재조회·재계산 범위를 넓히거나 미확인으로 표시한다. 무관한 원본 수정으로 프로젝트 전체를 재계획하거나, 영향을 받는 결과를 그대로 재사용하는 두 극단을 모두 피한다.

## 11. 품질·검증·시간·비용의 균형

### 11.1 플랫폼 품질과 전문 스킬 품질을 구분한다

플랫폼 MVP는 대상·입력 보존, 네이티브 기본 제어, 진행·개입·재개와 확장 계약의 신뢰성을 검수한다. 법규·구조·평면 설계의 전문 품질은 해당 스킬이 추가될 때 별도로 검수한다. 지원하는 각 작업은 의도 반영, 기하·속성의 정확성, 유지 조건, 네이티브 편집성, 결과 근거에 대한 완료 기준을 갖는다. 자동 검증 통과와 설계적으로 유용한 결과는 구분해 평가한다.

| 품질 측면 | 확인할 내용 |
|---|---|
| 대상·의도 | 지정 대상과 스케치의 의미를 반영했는가 |
| 기하·데이터 | 요구한 변경과 지원하는 유효성·단위 조건을 만족하는가 |
| 조건 보존 | 유지 대상과 등록된 필수조건을 지켰는가 |
| 네이티브 편집성 | 약속한 원본 객체 유형·속성을 가지며 호스트 기본 도구로 재편집·저장·재열기가 가능한가 |
| 근거 | 계산과 설명의 입력·방법·버전·미확인 범위가 드러나는가 |
| 설계적 활용성 | 사용자가 처음부터 다시 만드는 것보다 유용한가 |

완료 기준을 만족하지 못한 후보도 탐색용으로 보존할 수 있다. 다만 ‘초안’으로 이름만 바꾸어 완료율과 품질을 높게 집계해서는 안 된다. 지원 작업에서 안정적으로 채택 가능한 결과를 만드는지가 출시 판단의 핵심이다.

### 11.2 탐색·반영·공유를 구분한다

<!-- codex-review:start -->

> **[검토 · codex · R-42 · 높음]** **추가 지적 · 후보와 원본의 실행 경계.** 후보 탐색이 원본을 바꾸지 않아야 한다는 의미는 있으나, 호스트 실행 경로에서 이를 어떻게 확인할지 SPEC 인계 항목이 필요하다. 제안: 후보 생성의 원본 비변경, 반영할 후보/기준/변경 집합의 고정, 반영 직전 기준 변경 감지, 반영 버튼에서 새 변경안 생성 금지를 수용 기준으로 연결한다. 사본·별도 문서·변경 명령 미리보기 등 구체 방식은 기술 실험과 PLAN에서 비교한다.

<!-- codex-review:end -->

| 경계 | 기본 정책 | 필요한 확인 |
|---|---|---|
| 탐색 | 후보와 입력을 자유롭게 만들고 저장 | 원본과 분리된 상태, 데이터 보호, 미확정 조건 표시 |
| 원본 반영 | 사용자가 선택한 변경만 적용 | 정확한 대상·권한·관련 기준·필수조건·실제 적용 결과 |
| 공유·발행 | 선택한 시점과 목적에 맞게 전달 | 포함 범위·기밀정보·편집 충실도·검토 상태 |

필수조건에 미달한 결과를 승인 문자열 하나로 적합 결과로 바꾸지 않는다. 유효한 권한과 근거로 조건 자체를 변경하는 결정은 별도로 기록하며, 전문·법정 검토를 단순 선택으로 대체하지 않는다.

잘못된 대상과 권한 없는 원본 쓰기는 막는다. 설계 경험칙, 아직 안 한 추가 검토, 선택적 외관 평가 때문에 모든 후보 탐색과 저장을 막지는 않는다. 실제 검증이 필요한 경계만 통제한다.

### 11.3 최소한의 필수 확인과 사실 기반 표시

정밀 수치와 원본 변경 여부는 모델·계산·실행 결과에 근거해야 한다. 캡처와 시각 모델 판단은 보조 검토로 활용할 수 있지만 전체 기하·속성 검증을 대신하지 않는다.

원본 적용 결과, 시각 증거의 수집 상태, 보고서 생성 상태를 분리한다. 캡처나 보고서 생성 실패로 확인된 변경을 다시 실행하지 않는다. 적용 결과가 불명확하면 영향받는 대상의 후속 쓰기를 보류하고 상태를 확인하되 다른 비파괴 작업은 유지한다.

### 11.4 불필요한 반복을 줄인다

선택·선 그리기·코멘트 저장·이미 정의된 직접 조절은 불필요한 모델 호출 없이 처리한다. 같은 입력의 재조회와 전체 재검증을 줄이고, 필수적인 확인은 가능한 경우 일반 계산과 실행 기록으로 처리한다.

모든 단계에 별도의 LLM 감독자·검증자를 추가하지 않는다. 같은 오류에 진전 없이 반복하는 작업은 멈추고, 남은 문제와 현재 후보를 제공한다. 모델 호출 횟수·재시도·검토 강도는 실제 결과로 비교하며, 특정 횟수를 보편적 품질 보증으로 삼지 않는다.

### 11.5 예산이 부족해도 기준을 몰래 낮추지 않는다

지원 작업에 사용할 시간·비용 범위를 정하고, 초과 또는 진척 정체를 알린다. 사용자는 현재 후보 보존, 범위 축소, 추가 작업 허용, 다른 접근, 직접 수정으로 전환할 수 있어야 한다.

목표나 필수조건을 완화해야 한다면 설계 결정으로 명시한다. 무제한 반복과 무의미한 중간 질문 대신, 실제 남은 문제에 대한 선택을 제공한다. 토큰·비용을 관측할 수 없는 실행 경로에서는 추정과 미측정을 구분한다.

## 12. 네이티브 제어·확장·공유

### 12.1 네이티브 결과의 정의

지원 객체 종류에 대해서는 원본 프로그램의 해당 객체 유형과 약속한 의미·편집 동작을 갖는 결과를 생성·수정한다. 파일을 열 수 있음, 화면상 유사함, 표시용 형상에 분류를 붙임만으로 완료를 인정하지 않는다.

Revit에서 벽 생성을 지원한다면 카테고리 이름만 벽인 일반 형상이 아니라 실제 벽 객체와 선언한 타입·레벨·치수·후속 편집 동작을 요구한다. 생성 출발점이 매스였다는 이유로 결과를 판단하지 않고, 최종 객체와 동작으로 판단한다.

Rhino와 CAD에서도 지원하는 기하·엔티티 종류, 속성, 기본 도구의 재편집과 저장 후 지속성을 정의한다. 사용자가 메시를 요청했을 때의 네이티브 메시와, 벽을 요청했는데 표시용 메시로 대체한 결과는 다르다. 네이티브라는 말이 모든 생성 이력과 파라미터를 자동 복원한다는 뜻은 아니다.

지원하지 않는 형상이나 관계는 불가·제한을 알리고 후보를 제시할 수 있다. 대체 표현은 별도로 표시하며 네이티브 요구의 성공률에 합산하지 않는다. 치수·객체 종류·정확성 기준은 호스트별 SPEC 지원표에서 확정한다.

### 12.2 여러 호스트의 기본 제어

Rhino·Revit·CAD 계열을 같은 프로젝트에서 다룬다. AutoCAD와 ZWCAD는 별도 호스트로 취급한다. 실제 설치 버전·에디션·업데이트는 아직 정해지지 않았으며, 첫 MVP의 CAD 조합도 확정해야 한다.

> **[검토 · claude · R-12 · 중간]** 'CAD/BIM 프로그램'(7·37·137)은 Rhino·Revit 포함 전체 호스트, 'CAD 계열·선정 CAD·CAD'(19·94·383·432·464·473·587)는 AutoCAD·ZWCAD 묶음을 뜻해 같은 단어가 두 범위를 가리킴. SPEC hosts/ 파일과 지원표가 이 묶음을 부를 고정 명칭이 필요함. §5 Host 행에 묶음 명칭(예: 'DWG 계열 = ACAD·ZWCAD')을 정의하고 본문의 'CAD 계열/선정 CAD'를 그것으로 통일 제안. AutoCAD 약칭은 AC-(수용 시나리오 ID)와 충돌하지 않도록 ACAD로 고정.

각 지원 호스트는 문서 식별, 단위·상태·선택 읽기, 선언한 네이티브 생성·수정, 실제 적용 결과와 저장 상태 확인을 제공한다. 같은 기능명을 써도 호스트가 다른 의미를 제공하면 차이를 표시한다.

여러 호스트를 연결했다는 이유로 모델 전체의 자동 동기화, 임의 객체의 호스트 간 변환, 하나의 트랜잭션에 의한 전 프로그램 복구를 약속하지 않는다. 각각의 문서와 기준, 쓰기 결과를 보존한다.

### 12.3 스킬·플러그인 확장의 최소 요구

확장에는 목적, 사용 입력, 결과 유형, 필요한 호스트·도구·권한, 진행·개입의 지원 범위가 있어야 한다. 사용자는 활성 확장과 사용할 권한을 확인할 수 있어야 한다.

코어를 재작성하지 않고 작은 확장 하나를 등록·실행·비활성화하고, 진행·결과·실패를 공통 작업 기록에 남길 수 있어야 한다. 호스트용 어댑터 추가와 전문 업무용 확장 추가를 구분한다. 새로운 호스트 API가 필요한 전문 스킬은 그 어댑터 기능의 추가 구현이 필요할 수 있다.

초기 확장의 신뢰·배포 범위는 SPEC에서 정한다. 공개 마켓과 임의의 비신뢰 코드 실행은 MVP 전제가 아니다. 확장이나 외부 자료가 사용자 권한을 스스로 높이지 못한다. 분야별 규칙은 데이터 출처와 적용 범위를 갖는다.

### 12.4 대안 이력과 자료 의존성

후보·기준 기록·비교를 공통 기반으로 제공한다. 대안의 분기·선택 병합을 확장할 때 설계 이력과 자료·작업 파생 관계를 구분한다. 같은 형상으로 돌아와도 새로운 결정은 별도로 남길 수 있다.

대안 분기는 AI 대화 분기와 같지 않고, 기록을 연다고 네이티브 문서가 자동 복원되지 않는다. 임의 형상을 텍스트처럼 자동 병합하지 않는다. 고급 트리 편집과 범용 의미 병합은 MVP 필수 기능이 아니다.

### 12.5 웹 참여와 권한

외부 검토자는 iPad·Mac·Windows의 지원 브라우저에서 공개 범위의 모델·도면·자료를 보고, 기준 버전에 연결된 코멘트·스케치를 남기는 것을 목표로 한다. 실제 지원 브라우저·펜·터치·모델 크기는 검증한 범위만 선언한다.

웹 참여는 제품 요구이며, 첫 MVP에 포함할 깊이와 제공 방식은 미정이다. 파일 기반 검토 교환을 제공하더라도 온라인 제출·실시간 동기화가 구현된 것처럼 표시하지 않는다. 외부 검토용 서비스를 위해 작업 PC를 무제한 공개하거나 방화벽 전체 해제를 요구해서는 안 된다.

외부 코멘트, 변경 제안, 실행 가능한 변경안은 구분한다. 제출·채택·병합·원본 반영·공개는 각 권한과 실제 처리 상태를 확인한다. 작업 PC에 직접 접근하지 않은 외부 검토자에게 로컬 원본 제어 권한이 자동으로 생기지 않는다.

### 12.6 기본 산출물과 편집용 출력

MVP는 지원한 결과·기본 표·도면 표현·근거를 작업 안에서 열람하고, 선택한 기록 시점의 자료를 기본 HTML 검토 패키지로 전달할 수 있어야 한다. 지원 자산과 외부 의존, 미확인 사항을 함께 표시한다. HTML 한 파일만 열면 온라인 협업이 시작되는 것은 아니다.

네이티브 저장과 내보내기는 현재 후보를 반영한 결과인지, 이전 원본 파일의 동봉인지 구분한다. 3DM·DWG·SKP·XLSX·DOCX·PPTX 등은 각 형식의 지원 범위와 손실을 따로 선언하고, PDF는 고정 도면·보고서 전달 요구로 구분한다. 모든 포맷 변환의 동시 구현은 MVP 조건이 아니다.

즉석 HTML 편집기 C-01이 채택되면 문단·표·도형 선택과 데이터 연결, 편집 권한, 재생성 규칙을 별도 명세한다. 단순 산출물 열람을 그 편집기의 구현으로 간주하지 않는다.

모든 프로그램을 동등하게 깊이 지원한다는 약속이 아니라, **선언한 각 호스트의 기본 제어를 실제로 사용할 수 있는 상태**가 MVP 목표다. 호스트 하나만 완결한 결과는 내부 alpha가 될 수 있지만, 다중 호스트 플랫폼 MVP의 완료를 대신하지 않는다.

### 14.2 기반 검증용 작은 작업

<!-- codex-review:start -->

> **[검토 · codex · R-43 · 중간]** **추가 지적 · 동시 연결 시험과 MVP 호스트 수.** §14.2의 최소 두 호스트는 동시 연결 시험의 최소 조합이고, §13·§14.1의 Rhino·Revit·선정 CAD 전체를 두 호스트로 축소하는 출시 조건은 아니다. 첫 호스트 alpha, 두 호스트 동시 연결 시험, 선언한 전체 호스트의 MVP 완료를 구분하는 문장을 보강하자.

<!-- codex-review:end -->

각 호스트에서 대상 읽기 → 제한된 네이티브 생성 또는 수정 → 실제 후보·상태 표시 → 사용자 조정 → 원본 반영 → 호스트 기본 도구로 재편집 → 저장·재열기의 흐름을 검수한다. 기하 생성과 사용자의 조건 판단을 별개로 확인한다.

검증 사례의 후보는 Rhino의 지원 곡선·솔리드, Revit의 지정 벽 유형, CAD의 선·폴리라인 등이다. 이는 **SPEC을 정하기 위한 시험 후보**이며 모두 지원 확정된 목록은 아니다. 전문 법규·구조·평면 자동화까지 구현해야 이 시험을 수행할 수 있는 구조는 피한다.

최소 두 호스트가 같은 프로젝트에 연결된 상황에서 대상 혼동이 없고, 한쪽의 끊김이나 변경이 다른 문서의 잘못된 쓰기로 이어지지 않는지 확인한다. 같은 호스트의 복수 문서·인스턴스 구분도 해당 지원 환경에서 확인한다.

### 14.3 확장 가능성을 실제로 확인한다

작은 검증용 확장 하나로 등록, 필요한 입력·권한 전달, 실행, 진행·개입, 결과 보존, 실패, 비활성화를 확인한다. 예시는 선택 객체 속성 요약이나 허용된 기본 객체 생성이다. 이것은 플랫폼 시험이지 전문 스킬의 출시가 아니다.

manifest나 빈 플러그인 탭만 존재하는 것을 확장 구현 완료로 보지 않는다. 반대로 완성된 마켓플레이스를 만들 필요는 없다.

### 14.4 출시 판단

선정한 호스트·버전·객체별 기본 제어가 실제 시험에서 수용 기준을 충족해야 한다. 입력·개입·네이티브 결과·저장·복구·확장·설치의 품질을 확인한다. 특정 호스트에서 실패한 동작을 일반적으로 제공한다고 표시하지 않는다.

웹 참여 범위와 CAD 조합처럼 미정인 제품 항목은 관련 배포의 수용 범위를 확정하기 전에 결정한다. 숫자 목표는 기준 데이터·환경으로 측정해 정하되, 결정되지 않은 값을 달성했다고 주장하지 않는다.

구현 순서는 한 호스트의 내부 alpha부터 시작할 수 있다. 구현 순서가 PRD의 플랫폼 범위를 조용히 축소하거나 전문 스킬을 MVP로 앞당기는 이유가 되어서는 안 된다.

## 16. 성공 지표와 출시 판단

### 16.1 제품의 주요 성과

핵심 성과는 **지원 호스트의 기본 제어를 신뢰성 있게 수행하고, 결과 채택까지 필요한 총시간과 건축가의 부담을 줄이는 것**이다. 낮은 비용, 적은 승인, 빠른 초안 중 하나만 개선되었다고 성공으로 평가하지 않는다.

| 평가 축 | 측정할 항목 | 해석 기준 |
|---|---|---|
| 플랫폼 결과 품질 | 대상·단위·네이티브 유형·재편집·저장·입력·조건 보존 | 전문 스킬의 건축 판단 품질과 구분 |
| 실제 완료 | 지원 작업의 완료율·채택률·재작업량 | 초안 전환·중단·실패도 분모에 포함 |
| 시각적 이해 | 대상·변경·가정·미검토를 사용자가 찾아 설명하는지 | 상태 문구를 출력했다는 것만으로 통과 아님 |
| 개입성 | 접수·반영 지연, 중단 상태 이해, 이전 결과 충돌 | 입력 가능성과 실제 실행 통제를 모두 측정 |
| 가시성 | 첫 검토 결과까지 시간, 유의미한 상태를 알 수 없는 기간 | heartbeat와 진짜 검토 가능한 결과를 구분 |
| 효율 | 총경과시간·사용자 준비/검토/수정시간·대기·실패 포함 비용 | 토큰만 줄이고 사람의 재작업을 늘리지 않음 |
| 문맥 관리 | 필수조건 누락, 자료 선택·재조회, 결과 무효화 정확성 | 큰 입력 용량만으로 해결되었다고 보지 않음 |
| 검증 부담 | 불필요한 차단·질문·재시도, 검증 비용 | 필수 안전을 유지하면서 탐색 부담을 줄임 |
| 다중 호스트 | 선언한 각 호스트·버전·객체에서 기본 제어 완료 | 단일 호스트 시연으로 대체하지 않음 |
| 확장·설치 | 작은 확장의 실행·실패 처리, 지원 Windows 설치·재개 | 빈 확장 슬롯·개발 PC 성공만으로 완료 아님 |

### 16.2 비교 방법

동일한 과업과 원본·조건으로 기존 수작업 또는 익숙한 CLI 작업 흐름과 비교한다. AI 모델·도구·입력 정보·예산 차이를 기록한다. 입력 방식 비교는 텍스트, 핀 추가, 스케치와 명시 조건 추가를 나누어 보되, 정보량 증가와 표현 방식의 효과를 혼동하지 않는다.

> **[검토 · claude · R-18 · 낮음]** 기존 대안(Grasshopper·Dynamo 스크립트, 호스트 내장 AI 도우미, 범용 코딩 에이전트)과 비교하는 문단이 문서 전체에 없다. 가이드 §01의 PRD 역할에 경쟁 분석은 없으므로 필수는 아니지만, §2 문제표 옆에 '왜 기존 도구로 안 되는가' 한 문단이 있으면 이 절의 비교 대조군이 분명해진다. 소유자 결정.

<!-- codex-review:start -->

> **[검토 · codex · R-38 · 낮음]** **보류 권고 · [Claude R-18](#review-R-18) 재검토.** 대안 비교는 유익하지만 현재 SPEC 작성을 막는 누락은 아니다. 검증 없이 기존 도구로 안 된다는 경쟁 우위 문장을 추가하면 오히려 PRD가 부정확해진다. §16.2에 실제 사용자 수작업을 기준 과업의 대조군으로 고르고, 필요한 도구 비교는 후속 조사로 남기는 편이 낫다.

<!-- codex-review:end -->

성공 시연만 선택하지 않고 큰 모델, 불완전한 속성, 오래된 참조, 충돌 조건, 진행 중 사용자 개입, 연결 끊김을 포함한다. 전문가 품질 평가와 비전공자의 이해·피드백 능력 평가는 분리한다.

### 16.3 성능 목표와 출시 기준

반응 속도·토큰 한도·최대 무가시 기간·채택률·품질 평가의 수치 기준은 실제 장비·데이터의 기준 작업을 측정한 뒤 확정한다. 작업 종류·규모·환경별 목표와 측정 방법을 구분하고, 측정 전 임의의 수치를 서비스 보장으로 사용하지 않는다.

정확한 대상·권한, 사람 수정 보호, 중복 쓰기 방지, 불명확 상태의 정직한 표시는 초기 출시 필수 기준이다. 정의된 시험에서 중대한 위반이 발견되면 해당 원본 쓰기 기능은 출시하지 않는다. 시험 통과를 모든 환경에서 무오류라는 보증으로 확대하지 않는다.

지원 과업의 품질·완료율·총비용 목표를 충족하지 못하면 과업 범위나 구현을 조정한다. 단순히 ‘검토 필요’ 표시를 늘리는 것으로 제품 완성도를 대신하지 않는다.
