# 큰 모델 표시 비용 측정과 그리기 묶음(batching)

## 질문

큰 모델을 돌려 볼 때와 Sync할 때 느린 원인이 어디인가(전송·해석·화면 구성·프레임). 사용자 요청(2026-09-29): "렌더도 개선".

## 방법

- 코드: `tools/spikes/2026-09-29-render-perf/measure.mjs`. 합성 모델만 쓴다(사용자 파일 없음): 면 조각(삼각형 200개) N개 + 30구간 폴리라인 M개를 Sync 결과로 저장하고, 새 브라우저가 작업 공간을 열어 객체 목록에 모두 나올 때까지 잰다.
- 화면 비용: 뷰포트의 측정 함수 `benchmark()`가 한 프레임의 그리기 호출(draw call)·삼각형·선 수와, 궤도를 돌며 40프레임을 그리고 GPU 완료까지 기다린 평균 시간을 돌려준다.
- 환경: 이 PC의 Chrome(헤드리스, 실제 GPU: NVIDIA RTX 5070 Ti, ANGLE D3D11). 아이패드 등 약한 기기에서는 그리기 호출의 비용이 훨씬 크다.
- 주의: 한 표시 모델은 객체 20,000개까지 받으므로 18,000개로 쟀다. 저장된 빈 초안을 복원하면 "아무것도 보이지 않음"이 되므로 새 브라우저 문맥에서 잰다.

## 결과 (객체 18,000개: 면 9,000 + 선 9,000)

| 항목 | 이전 | 그리기 묶음 뒤 |
|---|---|---|
| 저장·전송 크기 | 68.5 MB (JSON) | 같음 |
| 받기 / 해석 (로컬) | 614 ms / 101 ms | 같음 |
| 새로 열어 모두 보일 때까지 | 4.0 s | 4.5 s (묶음 생성 +0.5 s) |
| 한 프레임 그리기 호출 | 27,001 | 74 |
| 한 프레임 시간(돌려 보기) | 83 ms (약 12 fps) | 9.7 ms (약 100 fps) |
| JS 메모리 | 424 MB | 386 MB |

원인은 객체마다(면은 모서리 선까지) 그리기 호출을 따로 쓰는 것이었다. 전송 68.5 MB는 로컬에서는 짧지만 원격(아이패드)에서는 크다. 원격 응답은 이미 gzip으로 압축된다.

## 한계와 다음

- 묶음은 일반 면·모서리·선만 대상이다. 선택·숨김 객체, 출력 미리보기(굵은 선), 해치·문자는 따로 그린다.
- 전송·저장 형식(JSON 숫자 배열)은 그대로다. 이진 형식은 PLAN-18의 다음 단계이며, 꺼진 PC용 보기 사본과 같은 형식을 쓴다.
- 실제 호스트 Sync(Rhino 메시 생성·페이지 읽기) 구간은 이번에 재지 않았다. 사용자 모델 사본으로 잴 때 구간별로 나눈다.
