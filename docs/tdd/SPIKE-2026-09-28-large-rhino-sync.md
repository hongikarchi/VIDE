## 질문과 범위

PLAN-02의 대형 실제 문서 Sync에 앞서 10,713개 합성 객체의 지문·네이티브 보존·표시 비용을 구분한다. 현재 제품의 10,000개 제한을 우회한 제품 성공으로 보고하지 않는다. 사용자 문서는 변경하거나 저장하지 않으며 별도 소유 시험 Rhino만 만들고 종료한다.

## 방법과 종료 조건

`tools/spikes/2026-09-28-large-rhino-sync/profile.mjs`가 점 10,000개, Brep 300개, 곡선 300개, 메시 100개, 블록 인스턴스 13개를 만든다. 각 단계의 시간·메모리, 직렬화 바이트, 네이티브 파일 보존 및 현재 표시 코드의 유형별 한계를 측정한다. 산출물은 `.vide/large-rhino-sync/`에 둔다. 한 실행은 180초 이내로 제한하고 실패 원인을 기록한다. 실제 모델과 동일 성능이라고 추정하지 않는다.

## 실제 결과

Rhino 8.34 합성 시험, 결과 `.vide/large-rhino-sync/339474a7-3228-4f31-b32c-b4e753a2f4c9/result.json`.

| 단계 | 시간 | 관찰 |
|---|---|---|
| 10,713개 생성 | 0.096초 | 점 10,000·Brep 300·곡선 300·메시 100·인스턴스 13 |
| 지문용 JSON 직렬화 | 0.137초 | 약 9.83MB, 단일 최대 18,543바이트. 해시 계산·전송 시간은 제외 |
| Brep/메시 변환 | 0.068초 | 12,600정점·8,400삼각형. 곡선/점/블록의 표시 비용은 제외 |
| 네이티브 쓰기 | 0.419초 | 약 6.13MB |
| 네이티브 읽기 | 0.089초 | 화면 객체 10,713개와 정의 내부 객체 1개로 파일에는 10,714개 |

프로세스 working set은 생성 후 약 659MB, 읽기 후 약 685MB다. peak 메모리나 사용자 386MB 모델의 성능 측정이 아니다. 기존 검증이 최상위 객체 수와 파일 내부 객체 수를 같다고 요구하는 문제가 드러났다. 블록 정의만 바뀌는 경우도 취득 기준에 포함해야 한다. 따라서 상한 증대 전에 정의 보존·변경 감지를 먼저 수정하고, 표시 페이지/예산은 후속으로 유지한다.

첫 실행은 .NET Int64 메모리 값을 IronPython JSON에 직접 넣어 직렬화 오류 창이 떴다. 해당 시험 Rhino만 종료했고 `int` 변환 후 재실행했다. 사용자 Rhino에는 이 계측을 실행하지 않았다. 제품 경로의 전체 Sync 성공은 아직 아니다.
