# 프로젝트 기록 웨이브 3 — 모델 위 타임라인·시점 형상·사이트 사본·성능 (T-333~T-337)

이 문서는 [PLAN-53](../plans/PLAN-53-project-records.md) 웨이브 3의 오프라인 검수(T-338 동승 전)를 적는다: T-333~T-335의 화면 검수, T-336의 경계 시험, T-337의 측정. 화면 기준은 [SPEC-17](../specs/SPEC-17-project-records.md) 17.5·17.8 3과 [Design](../../Design.md) SCR-46, 측정 기준은 [ARCH-01](../architecture/ARCH-01-system.md) §5 「성능 측정」 표, 경계 기준은 같은 절의 「사이트 사본」과 SPEC-17.6이다. C-09는 후보 기능이라 PRD §15에 기록 AC가 없으므로 SPEC-17.8 3의 문단을 기준으로 삼는다. T-338 동승은 이 문서에 이어서 적는다.

## T-336 사이트 사본 경계

| 단계 | 기대 | 실제 | 판정 |
|---|---|---|---|
| 기본값 | 설정하지 않은 프로젝트는 `records:false`이고 업로드가 0건 | 같음(`records-share.test.mjs`, HTTP `GET …/offline-view`) | 통과 |
| 올리는 범위 | 남김이면서 정정되지 않은 기록만 올림. 후보·뺀 기록·카카오톡/메일 출처(남김 포함)·그 정정본(원문 첨부를 이어받음)은 뺌 | 노트 1건과 정정본 1건만 올라감 | 통과 |
| 필드 | 정확히 `{id, date, type, text, parts(이름), chapter, updatedAt}` | 키 집합이 같음. 보낸 JSON에 출처·작성자·sourceKey·요청 id·메일 주소·제목·`기록/원문`이 없음 | 통과 |
| 다시 보내기 | 지문(SHA-256)이 같으면 보내지 않고, 뺀 기록이 생기거나 부위 이름이 바뀌면 새 사본 전체를 보냄 | 같음 | 통과 |
| 실패 | `SITE_UNREACHABLE`이면 1분 안에는 다시 보내지 않고, 1분 뒤 첫 묶음부터 다시 보냄 | 같음 | 통과 |
| heartbeat 지문 | 강제 실행이 아니면 남김 기록 전체를 읽는 지문은 프로젝트마다 1분에 한 번 | 1분 안에는 다시 읽지 않고 1분 뒤 새 사본을 보냄 | 통과 |
| 끄기·삭제 | `DELETE …/records`를 보냄. 확인되지 않으면 heartbeat마다 다시 보냄. 켠 적 없는 프로젝트를 지울 때는 보내지 않음 | 같음 | 통과 |
| 묶음 | 한 묶음은 500건·약 900 KB 이하. 0건이면 빈 묶음 하나 | 1,201건이 500·500·201로 나뉨. 19,000자 기록 100건도 묶음마다 900 KB 이하 | 통과 |
| HTTP 끝까지 | 로컬에서 켜면 엔진의 `RemoteAccess`가 기기 키로 `PUT …/records {items, first:true}`를 보내고, 끄면 DELETE를 보냄 | 같음 | 통과 |
| 원격 세션 | 원격 세션은 설정을 볼 수 있지만, `records`를 보내면 403 `FORBIDDEN` | 같음 | 통과 |
| 사이트 권한 | 그 프로젝트를 돌리는 소유자 PC만 쓸 수 있음. 다른 계정 PC와 같은 계정의 다른 PC는 404 | 같음(`tests/sharing/records.mjs`) | 통과 |
| 사이트 저장 | `first`면 바꿔치기, 아니면 덧붙임. 열은 여덟 개만이고 다른 키는 버림. 500건은 문장 하나로 저장되고 501건은 400 | 같음 | 통과 |
| 사이트 거절 | 잘못된 유형·날짜·id, 빈 본문, 20,001자, 부위 51개, 101자 장은 400이고 기존 행은 그대로 | 같음 | 통과 |
| 할 일과 분리 | `DELETE …/summary`를 해도 기록과 `records_at`은 남고, `DELETE …/records`는 기록만 지움 | 같음 | 통과 |
| 사이트 삭제 | 사이트에서 프로젝트 행을 지우면 기록도 지워짐(cascade) | 같음 | 통과 |

## T-337 측정

중앙값이다. node 쪽 시험은 예열 1회 뒤 5회를 돌렸다. 브라우저 쪽은 매번 새 브라우저 문맥으로 3회를 돌렸고, 첫 회에는 서버 예열이 들어간다. 1′·2·3의 괄호 밖 값은 수정 단계의 재측정(연결 파일 하나에 문서 Sync 객체 20,000을 더해 모델 탭이 함께 그려지는 상태)이고, 괄호 안 '처음'은 모델 없이 잰 첫 측정이다.

- **판정:** 잰 항목은 모두 기준 안이므로 고친 코드는 없다. 다음 후보 처방은 적용하지 않았다(AI.md §8 「실행 우선」).
  - `rowsOf`의 프로젝트 전체 스캔
  - 행마다 하는 `undone` 계산
  - 기록 탭의 목록 2회 읽기와 전체 그리기
  - 차트 가상 스크롤
  - 역색인 캐시
- **5·6:** 수정 단계에서 `browser-records-perf.mjs`에 합성 연결 파일(문서 Sync 객체 20,000, 레이어 31 — 30개는 부위 하나씩)을 더해 쟀다. 기준 안이므로 `fade`의 청크 다시 짓기(`rebatchIds`)는 고치지 않았다. [전부 보기](84 ms)가 기준에 가장 가깝다 — 흐림 단계가 한 번에 거의 모든 객체에서 바뀌는 경우다. 실제 설치 PC·실제 모델에서 100 ms를 넘으면 그때 색 버퍼만 바꾸는 쪽으로 고친다.
- 1′·3이 첫 측정보다 느린 것은 같은 페이지가 객체 20,000의 모델과 띠를 함께 그리는 중이기 때문이다. 모두 기준 안이다.
- `browser-records-perf.mjs`는 `test:browser`에 등록했다(`browser-records-timeline.mjs` 다음).
- 묶음 계산(4)은 T-333 시험이 출력한 값이다.
- 8의 '다시'가 43 ms인 까닭: 색인은 그대로 쓰지만 부를 때마다 기록 5,000건을 `list`로 읽는다. 기준 안이므로 그대로 둔다.

## 미시험

- 사용자 동승(T-338): 실제 프로젝트의 기록·실제 모델로 커서를 끌며 결정 흐름을 읽는 일.
- 실제 Rhino 문서의 Sync와 Live Sync 중의 띠(합성 Sync만 썼다).
- 실제 프린터 인쇄 출력(인쇄 직전 뷰포트 그림 + 한 줄 요약만 구현).
- 사이트 배포: D1 0018 적용과 Worker 배포는 사용자 T-357 배포와 묶는다. 배포 전 Worker는 `PUT …/records`를 모르므로, 스위치를 켠 프로젝트는 연결 칸에 경고 한 줄 '사이트에 올리지 못했습니다 · 1분 뒤 다시'(이유는 가리키면)가 서고 1분마다 다시 보낸다. 끄기의 DELETE가 404면 지워진 것으로 본다. 스위치는 기본 끔이다.
- [분리]가 켜진 동안 뷰포트에서 찍은 핀·스케치 좌표(아래 P2).

  - 검토본 저장 대화상자의 기록 체크는 제목 입력 줄(제목·표 구성·[검토본 저장]) 바로 아래에 있다. [검토본 저장]이 체크보다 앞에 오는 탭 순서를 바꿀지는 Design 확인 뒤로 둔다.
  - 사용자 결정: SPEC-17 R-86~R-89, ARCH-01 R-91·R-92, Design R-91, SPEC-03 R-23.
