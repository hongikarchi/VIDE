# 본격 구현 전 문서 정합성과 착수 범위 검수

## 1. 범위와 판정의 의미

사용자의 ‘본격적인 구현 전까지의 작업 마무리’ 요청에 따라 수정된 SPEC의 정상 사용자 경험을 Design과 PLAN에 연결했다. 기준은 PRD 0.7, SPEC-00 0.6·SPEC-01~04 0.3·SPEC-05 0.4, Design 0.8, PLAN 0.10, 가이드 0.5, AI 규약 0.7다. 문서/소스 대조와 생성물 검수이며 제품 수용 시험이 아니다. 이 기록의 관련 AC는 후속 검증 범위를 나타내며 이번에 통과한 AC 목록이 아니다.

## 2. 기능에서 화면·구현으로 이어지는지

| 사용자 작업 | 기능 정본 | 화면 정본 | 구현/시험 정본 | 문서 대조 결과 |
|---|---|---|---|---|
| 모델·도면 탐색과 공간 입력 | SPEC-01.9·10 | Design §12.6·9; SCR-01·02·07 | PLAN §4.4·6.3, T-013~016 | 연결/선택/핀/선/치수/저장/요청을 구분. 별도 작업 양식 강제 문구 교정 |

문서에서 정상 작업을 설명할 수 있는 수준까지 대응을 보강했다. 실제 사람이 화면을 사용해 이해하는지, 스케치·후보가 실제 호스트와 대응하는지는 구현 후 검수해야 한다.

## 3. 기존 코드 대조

`src/core/store.mjs`의 프로젝트/입력/실행/명령 API, `src/server/`의 프로젝트/입력 HTTP 경로, `src/ai/providers.mjs`와 CLI 어댑터 구성, `src/ui/app.mjs`의 메모 저장·편집 흐름을 대조했다. 현재 코드는 제품 전체가 아니라 기반 구현이다. PLAN §6.4에 재사용과 보완을 구분했다.

현재 UI 초안은 메모리 보존이며 앱 종료 뒤 미저장 초안의 내구성을 보장하지 않는다. 모델 뷰어·공간 입력·설계 실행 루프·실제 호스트 후보가 연결되어 있지 않다. 기존 코드의 존재로 새 SPEC/Design을 구현 완료 처리하지 않았다. 이번 작업에서 src·tests의 코드는 변경하지 않았고 기존 자동 시험·CLI/호스트 시험을 다시 실행하지 않았다.

## 4. 문서 검증 방법과 결과

- Design의 기존 Claude/Codex 검토 블록을 보존하고 승인/해소로 처리하지 않았다.
- Markdown의 상대 링크, 기능 ID 참조, 코드 블록 닫힘, 문서 헤더와 UTF-8 내용을 정적으로 검사했다.
- `node tools/docs/build.mjs --quiet`로 HTML을 생성하고 `node tools/docs/build.mjs --check --quiet`로 일치를 검사했다.
- `git diff --check`로 변경 내용의 공백 오류를 검사했다.

정적 참조 검사·검토 블록 보존 검사·HTML 일치 검사·공백 오류 검사는 모두 통과했다. 생성 HTML의 새 화면 설명·와이어프레임은 구현 UI 스크린샷이나 브라우저 사용성 시험 결과가 아니다.

## 5. 착수 범위와 남은 확인

첫 입력/프런트 묶음은 SPEC·Design·입출력·검증·기존 코드 이행 기준이 준비되어 있다(PLAN §6.3~4). 실제 지원 라이브러리 선정과 좌표 대응은 T-015, 네이티브 쓰기는 OQ-03·10의 지원안·보존 실증, 웹 운영은 OQ-04, 배포는 OQ-09의 조건을 따른다. 단계별 제한과 기본 진행안은 PLAN §9.2가 소유한다.

기존 Design R-41/R-45의 상태 표시 위치는 §12.1·10에서, R-38/R-35의 첫 경험 범위는 §12.6 및 PLAN §6.3에서 구체화했다. 이는 해당 리뷰 스레드를 사용자 대신 수락/삭제했다는 뜻이 아니다. 문서 검토 상태를 임의로 approved로 올리지 않았다.

이번 결과는 구현 전 문서 준비이며, 실호스트·실기기·외부 서버·설치·사용자 이해·성능의 제품 검수는 미시험이다. 후속 작업은 문서 전체를 다시 작성하는 일이 아니라 PLAN §6.3의 첫 구현 묶음과 T-015의 한정 실험이다.

## 6. 문서 역할과 개발 재개 설정 정리

Design의 기능 동작·실행 규칙·시험 절차 중복을 제거하고 DNA·색/글꼴·배치·컴포넌트·화면별 표현을 남겼다. 기능 의미는 기존 SPEC을 참조한다. SPEC-00 §6의 물리 큐/저장 구현 설명은 PLAN §4.3으로 참조하고 관찰 가능한 보존 의미만 남겼다. 화면 검수 방법은 PLAN §7.5가 소유한다.

가이드 §01은 문장 소유자와 충돌 판단, §12는 다음 개발 지시를 받은 뒤의 자율 실행·검증·재개를 정의한다. PLAN §6.5는 T-001~018의 현재 수준·증거·남은 조건, §6.6은 전체 완료 관문, §9.3은 개발 환경 확인 명령을 소유한다. 첫 작업은 T-013이며 제품 구현은 이번에 시작하지 않았다. 과거 검토 블록은 보존하며 이후 사용자 지시와 현재 실행 규약을 구분한다.

pre-commit은 미추적 tools/docs 입력과 빌드 뒤 남은 미스테이징/미추적 HTML을 검사하도록 보완했다. 현재 저장소의 core.hooksPath는 .githooks다. 실제 작업 트리를 스테이징하거나 커밋하지 않았다.

| 검증 | 결과 | 한계 |
|---|---|---|
| npm.cmd test | 30개 통과 | 기존 코어·HTTP·CLI 어댑터 자동 시험이며 전체 제품 수용 시험이 아님 |
| 격리 저장소의 훅 시험 | 정상 입력 통과, 미리 생성한 HTML 누락 차단, 미추적 도구 차단, 미스테이징 MD 차단, 새로 생성한 HTML 포함 — 5개 통과 | 실제 커밋 없이 임시 인덱스와 종료 코드를 검사; 렌더러 호출은 시험용 stub |
| src/tests 해시 대조 | 준비 시작 시점과 동일 | 이전 세션에서 작성한 기반 코드는 존재함 |

문서 정합성 검사는 §4의 방법으로 수행한다. 외부 계정·비용·공개·실기기·사용자 검수가 필요한 시점에는 구체적인 요청이 필요하며, 세션/사용량 제한을 넘어 무한 실행하거나 미시험을 완료로 처리하는 설정은 아니다.


## 7. 후속 검토로 정정된 준비 판단

위 기록은 해당 시점의 검사 결과다. 후속 검토에서 승인 관문·입력 상세·복합 상태·기술 선택의 미비가 확인되어 당시 “첫 작업 T-013/준비 완료” 판단은 현재 진행 기준으로 사용하지 않는다. 보완과 프런트 착수 범위, 실제 검사·미완료는 [공간 작업 검수 기록](VERIFY-2026-09-20-workspace-review.md)에 있다. 현재 순서는 PLAN §6.1·6.5를 따른다.
