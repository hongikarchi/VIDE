# VIDE 안 AI와 터미널 Claude Code의 모델링 동등성 A/B

**상태: 1회 실행함(2026-09-30).** 사용자 Rhino·CAD가 닫힌 검증 창에서 에이전트가 띄운 숨김 Rhino 8 하나에 합성 시험 모델을 만들고, 같은 문서에 VIDE(A)와 rhino MCP(B)를 차례로 붙여 같은 요청 5개를 돌렸다. 아래 「한계」의 편향 때문에 수치는 방향만 본다.

## 질문

사용자 관찰(2026-09-30): VIDE 안 AI가 터미널 Claude Code보다 모델링을 못 한다. 원인 후보는 기본 시스템 프롬프트 대체, 결과를 볼 수 없음(화면·측정 없음), 좁은 도구 예산·읽기 범위, 이전 교환 전달 방식, 질문 불가였다([RESEARCH-10](../research/RESEARCH-10-vide-restructure.md) §1·§8). 물결 5·6은 기본 프롬프트 유지 + VIDE 지시 묶음, 화면·측정 도구, 넓힌 읽기, 열린 문서에 바로 적용([ADR-022](../decisions/ADR-022-direct-apply-plan-auto.md))을 넣었다. 이 기록은 그 뒤 **같은 요청 5개**에서 VIDE(A)가 터미널(B)과 얼마나 가까운지 잰다.

## 합격 기준 (실행 전)

- A의 성공 수가 B 이상, 또는 B보다 1개 적고 실패 원인이 기록돼 있음.
- 성공한 요청에서 A의 시간·토큰이 B의 2배를 넘지 않음(넘으면 원인 기록).
- 원본 문서 무변경: 사용자 원본은 열지 않고, 두 쪽 모두 합성 시험 모델에서만 한다. 요청마다 되돌려 같은 시작 상태에서 시작한다.

## 방법·환경

- 시험 모델: `tools/ab/fixture.py`가 만드는 합성 mm 문서(축선 7, 보 3, 2층 슬래브 1, 층 표시점 3, 난간 기준 곡선 1). 실제 프로젝트 자료 없음. 숨김 Rhino의 시작 스크립트로 만들고 `.vide/h3/ab-fixture.3dm`에 저장했다(열린 문서는 이름 없는 문서로 남음, 「한계」).
- 요청과 판정: `tools/ab/requests.json`(R1 기둥 격자, R2 보 춤 600, R3 슬래브 3층 복사, R4 곡선 따라 난간, R5 축선 이름 X·Y). 판정 코드는 `tools/ab/checks.mjs`이며 A·B가 같은 코드를 쓴다.
- A: 개발 엔진(포트 47843, 격리 데이터 `.vide/h3-data`)에 개발 빌드 플러그인으로 숨김 Rhino를 연결하고 프로젝트에 Link·Sync한 뒤 `tools/ab/run.mjs`. 요청마다 새 대화, **자동 모드**(`permission: candidate` → `mode: auto`), 모델 미지정(기본 경로). 자동 모드는 열린 문서에 바로 적용하므로 `run.mjs`가 끝난 뒤 다시 Sync해 판정하고 제품의 [되돌리기]로 원상 복구한다(아래 「하네스 수정」).
- B: 같은 숨김 Rhino에서 `mcpstart`로 rhino MCP를 열고, 이 검증을 수행한 에이전트(Claude Code 하위 에이전트)가 터미널 쪽 모델로서 rhino MCP 도구만으로 요청을 수행했다. R4는 기준 곡선을 선택해 둔 상태로 시작했다. 끝난 뒤 장면을 `dump_scene.py`와 같은 형식으로 덤프해 `tools/ab/terminal.mjs`로 판정하고 Rhino Undo로 되돌렸다.

## 관찰

1. **[되돌리기] 뒤 다음 실행이 막힌다(제품 결함, 높음).** 호스트의 `direct-undo`가 명령 밖에서 `RhinoDoc.Undo()`를 부르면 Rhino가 그 Undo 동작의 기록 번호를 연 채로 남긴다(`UndoRecordingIsActive = true`, `NextUndoRecordSerialNumber` 고정). 그 뒤 `direct-execute`의 `BeginUndoRecord`가 0을 돌려 `UNDO_UNAVAILABLE`을 던지고, 엔진은 이를 응답 분실처럼 `HOST_RESULT_UNKNOWN`으로 기록한다. 같은 문서의 이후 쓰기 요청은 모두 `HOST_RESULT_UNRESOLVED`로 거절된다. 합성 문서에서 실행 → [되돌리기] → 실행 순서로 재현했고, 열린 기록을 `EndUndoRecord(n-1)`로 닫으면 다음 실행이 된다. rhino MCP의 `undo`도 같은 상태를 남기므로 VIDE 코드가 아니라 명령 밖 Undo의 Rhino 동작이다. 첫 연속 실행에서 R1의 하네스 [되돌리기]가 R2를, 수동 Undo가 R5를 막았다. 수정 후보: `UndoRecord` 뒤 열린 기록 닫기, 또는 Undo를 명령 문맥에서 실행; 실행 전에 실패한 `UNDO_UNAVAILABLE`은 문서를 바꾸지 않았으므로 `unknown`이 아닌 실패로 처리. 이번 검증에서는 제품 코드를 고치지 않았다.
2. **`unknown` 요청을 풀 방법이 없다(중간).** 바로 적용 경로의 `unknown`은 `reconcile`(`executionMode: 'sdk'` 전용) 대상이 아니어서, 문서를 바꾸지 않은 실패였는데도 그 프로젝트·문서의 쓰기가 계속 막혔다. 이번에는 새 프로젝트를 만들어 이어 갔다.
3. **`IsValid` 금지가 매번 한 번의 왕복을 쓴다(중간).** 성공한 A 턴 5개 중 4개(R1~R4)에서 첫 `execute`가 `API not permitted: Rhino.Runtime.CommonObject.IsValid`로 거절됐다. 모델이 습관적으로 쓰는 읽기 전용 속성이다. 허용 목록에 넣거나 지시 묶음에 금지 사실을 적으면 턴마다 실행 1회와 수 초를 줄일 수 있다.
4. **VIDE의 화면 캡처가 숨김 Rhino에서 빈 화면이다(중간, 환경 한정일 수 있음).** R1·R4에서 `capture_view`가 두 번씩 흰 화면을 돌려 AI가 다시 캡처하고 "눈으로 확인하지 못했다"고 답했다. 같은 숨김 Rhino에서 rhino MCP의 `capture_viewport`는 정상 이미지를 돌려줬다. 사용자가 띄운 보이는 창에서도 같은지 확인이 필요하다.
5. **[되돌리기] `not-latest`(R4).** 적용 실행 뒤 바뀐 것 없는 실행과 화면·치수 도구가 이어졌고, 하네스의 [되돌리기]가 `not-latest`로 거절됐다. 막은 기록이 무엇인지(빈 실행의 기록 처리, 캡처가 만드는 기록)는 이번에 가리지 못했다. Rhino Undo로 복구했다.
6. **시간 차이.** 모든 요청에서 A가 B의 2~4배였다(R1 3.0배, R2 3.1배, R3 4.0배, R4 3.2배, R5 2.0배). A에는 CLI 턴 시작, 지시 묶음·문서 조회, `IsValid` 재시도, 빈 캡처 재시도가 붙는다. 다만 B는 편향돼 있어(「한계」) 배율을 그대로 합격 판정에 쓰지 않는다.
7. **단위 표현.** R5 답에서 축선 위치를 "x = 6"처럼 미터로 적었다(문서는 mm). 조회 결과의 단위 표기가 모델에게 섞여 보이는지 확인할 만하다. 판정에는 영향 없음.

## 결론과 한계

- 결과 품질: 결함을 피하면 A도 5개 모두 기준을 통과했고, 치수 가정·확인 보고는 B보다 자세했다. 모델링 능력 자체의 차이는 이번 요청 수준에서는 보이지 않았다.
- 합격 기준: 성공 수는 동률(재실행 기준), 시간 2배 기준은 5개 모두 넘었다(원인 6). 첫 연속 실행 기준으로는 되돌리기 결함(1·2) 때문에 불합격이다.
- 다음 조치: 1(되돌리기 뒤 열린 기록)과 2(`unknown` 해소 경로)를 먼저 고치고, 3(`IsValid`)·4(빈 캡처)를 고친 뒤 같은 절차로 다시 잰다.

한계:

- **B는 맹검이 아니다.** 터미널 쪽 모델은 이 검증을 수행한 에이전트여서 `requests.json`의 판정 기준, 시험 모델 구성, A의 답을 이미 알고 있었다. B의 시간·도구 수는 하한에 가깝고, B의 토큰은 잴 수 없었다. 공정한 B는 사람이 README 절차대로 `claude -p … --output-format stream-json`으로 다시 잰다.
- A와 B의 모델이 같다는 보장이 없다(A는 CLI 기본 모델, B는 검증 에이전트 모델).
- A의 판정용 장면은 적용 뒤의 표시 Sync(m, 1000배)이고, B는 Rhino 덤프(mm)다. 판정은 경계 상자 기반이라 난간 모양 같은 세부는 비고에 적었다.
- 시험 문서는 저장 경로가 없는 열린 문서였다(`fixture.py`의 `SaveAs`가 시작 스크립트 안에서 경로를 문서에 붙이지 않음). 연결 이름이 'Untitled'라 `run.mjs`에는 `--base`를 직접 줬다.
- 요청 사이 복구는 제품 [되돌리기] 또는 Rhino Undo 뒤 열린 기록을 닫는 방식이었다. 매 요청 전 Sync가 시험 모델과 같음을 확인했다(R4 뒤 빈 레이어 `S-COLUMN`·`A-RAIL`은 레이어 표에 남았으나 판정 대상 아님).

## 하네스 수정

- `tools/ab/run.mjs`: 자동 모드 결과에 후보 장면이 없으므로, 끝난 뒤 연결 문서를 다시 Sync해 기준과 비교(`checks.mjs`의 `diff`)하고, 적용된 실행을 제품 [되돌리기]로 역순 복구한 뒤 복구 Sync의 차이를 `restored`로 남긴다(`--keep-applied`·`--chain`이면 복구하지 않음).
- `tools/ab/fixture.py`: 다른 스크립트 안에서 `RunScript('_-SaveAs …')`가 거절되면 `doc.SaveAs(path)`로 저장한다.
