# 채팅·스케치·클릭 중심 제품의 비판 검수

2026-10-06 사용자 요청: 누구나 채팅·스케치·클릭으로 모델링·협업·도면·회의록·산출물을 다루는 목표에 맞춰 기능과 UI/UX의 제거·추가·보완·수정 사항을 찾고, 제공한 사본으로 실제 오류와 부하를 확인한다. 제품 변경을 확정하거나 구현한 기록이 아니라 **실행 결과와 개선 제안**이다.

## 1. 판정과 범위

**기능은 넓게 배치되어 있으나, 처음 연결해서 원하는 결과를 얻는 핵심 경로의 신뢰성이 부족하다. 기능 확장보다 실파일 읽기·요청 분류·핀 복구·엔진 안정성을 우선해야 한다.** 자동 테스트의 성공과 실무 사용 성공이 크게 갈린다.

기준은 [PRD](../PRD.md) §0·8·14~16, [SPEC-00](../specs/SPEC-00-common.md)의 세 가지 사용자 작업, [Design](../../Design.md) §01이다. 특히 설명·내부 상태를 읽지 않아도 대상과 다음 행동을 알 수 있어야 한다는 기준으로 검수했다. 각 AC 전체를 재검수한 것은 아니다.

- 소스 기준: `846b823`, 시작 시 작업 트리 변경 없음. 제품 코드는 수정하지 않았다.
- 설치본 관찰: 10월 6일 UTC 로그의 0.2.19~0.2.26. 최신 실행은 0.2.26이다. 이전 버전 오류를 최신 버전에서 재현한 것으로 집계하지 않는다.
- UI: 현재 소스로 빌드한 분리된 로컬 서버, Chrome headless 1440×900 및 800×700. 실제 UI 클릭·입력·화면 캡처, 실제 서버 요청, 응답 주입 시험을 구분했다.
- 모델: 사용자가 허용한 `vide-test` 자료를 `.vide/critical-audit-20261006/fixtures`에 다시 복사했다. 원본과 사용자 프로젝트를 수정하지 않았다. DWG는 XREF 폴더도 복사했다.
- 네이티브: 제품의 `SdkExecution.importFile`과 `inspectDwg`를 실제 Rhino/ZWCAD로 실행했다. 기존 플러그인 빌드를 사용했으며 이번에 재빌드하지 않았다.
- 데스크톱 직접 조작은 computer-use 네이티브 파이프 연결 실패, 브라우저 커넥터는 연결 가능한 브라우저 없음으로 사용할 수 없었다. 저장소 Playwright 검수 경로로 화면을 확인했다. 설치된 WebView2 창을 직접 검수한 것은 아니다.
- 로컬 재현 자료: `.vide/critical-audit-20261006/`. 원시 로그·덤프·모델·계정이 보이는 화면은 저장소 증거 자산으로 복제하지 않았다.

### 엔진 덤프에서 추가 확인한 사실

기존 덤프 세 개(`094448`, `155257`, `163916`)의 예외 스트림과 모듈 목록을 읽었다. 모두 예외 코드 `0xC0000409`, 첫 예외 매개변수 `0x2`, 예외 주소가 `node.exe + 0x21f2189`였다. 로드 주소가 다른 실행에서도 오프셋이 같다. 덤프가 이미 있으므로 ‘다음 충돌까지 기다려 덤프를 받기’가 아니라 이 세 덤프의 호출 스택 분석이 다음 행동이다. 심볼 기반 스택은 이번에 분석하지 않았으며, V8·SQLite·구조 모듈 중 무엇이 원인인지 확정하지 않았다.

## 3. 코드에서 확인한 구조적 원인과 위험

1. **읽기와 편집 검증의 결합.** [sdk-execution.ts](../../src/server/sdk-execution.ts)의 `importFile`은 단위 정규화 → worker 실행/저장 → 재열기 검증 → 표시 추출 순서다. [WorkerScene.cs](../../hosts/rhino/worker/WorkerScene.cs)의 `Validate`는 하나의 유효하지 않은 형상, 중복/형식 불일치 ID에도 문서 전체를 거절한다. 큰 파일의 실패는 [WorkerReadback.cs](../../hosts/rhino/worker/WorkerReadback.cs)의 `GeometryEquals` 불일치로 확인됐다. 표시·핀 입력의 시작 조건이 지나치게 강하다.
2. **동일한 DWG라도 경로마다 지원 수준이 다르다.** [DwgReader.cs](../../hosts/zwcad/worker/DwgReader.cs)는 Line/직선 Polyline 외 객체, 곡선 bulge, 일부 3D 조건을 거절하고 객체 500개 한도를 둔다. 따라서 ‘3DM/DWG 파일에서 열기’라는 일반적 표현이 실무 도면 지원 수준을 전달하지 못한다. 기존 연결형 CAD의 부분 표시 기록과 파일 가져오기를 혼동하면 안 된다.
3. **파일 업로드 전체를 메모리에 모은다.** [import-model.ts](../../src/server/import-model.ts)는 chunks를 모아 `Buffer.concat`한 뒤 파일로 쓴다. 563MB 업로드는 입력 조각과 합친 버퍼만으로도 대략 두 벌이 잠시 공존할 수 있다. 후속 UI 시험에서 실제 HTTP 업로드도 실행했지만 메모리 최고치는 계측하지 않았다. 스트리밍 디스크 저장·진행·취소를 검토해야 하며 이를 기존 0xC0000409의 원인이라고 단정할 수 없다.
4. **폴링 오류를 전부 일시 오류로 취급한다.** [links-sync.ts](../../src/ui/app/links-sync.ts)의 `pollLinks`는 catch 후 이전 표시를 유지하고 다시 폴링한다. 404의 안내·프로젝트 재선택 분기가 없다. 원래 서버 로그의 각 프로젝트가 없어진 경위는 이번에 조사하지 않았다.
5. **핀 실패의 안내가 너무 큰 단위다.** [pin-carry.ts](../../src/server/pin-carry.ts)는 동일 링크의 최신 Rhino Sync에서 ID/nativeId를 찾고, 하나라도 없으면 요청 전체를 막는다. 보호 취지는 맞지만 누락 개수와 ‘다시 고정하세요’만으로는 큰 모델에서 복구 부담이 크다. 객체가 삭제됐는지, Sync에서 아직 읽지 못했는지, ID가 바뀌었는지 구분할 진단이 필요하다.

| 보완할 것 | 연결 상실·읽기 실패·부족한 입력이 작업 시작 뒤에 드러남 | 보내기 근처에 이유와 바로 해결할 행동, 문장·핀·첨부는 유지 |

| 수정할 것 | JIG 목록에 사용 가능·준비 중·작성 중, 긴 입력 설명, 수정 불가 안내가 섞임 | 바로 쓸 수 있는 도구를 기본으로, 이름+결과+실행 중심. 개발자용 만들기/버전/형식 설명은 별도 상세 |
| 수정할 것 | 미연결 노트 화면이 ‘새 노트로 시작’과 연결 불가를 동시에 안내 | 현재 가능한 행동 하나를 제시. 로컬 작성 지원 여부는 제품 결정 후 구현 |

전면 재디자인보다 **빈 상태·오류 상태·첫 성공 경로**를 먼저 고치는 편이 효과가 크다. 전문 사용자의 제어 기능은 없애기보다 상황에 맞춰 드러낸다.

## 7. 미검증과 환경 실패

- 샌드박스 Rhino/CAD 시작은 각각 약 90초 후 `WORKER_START_TIMEOUT`. 일반 실행 환경에서 재실행하여 위의 서로 다른 실제 파일 오류를 확인했다. 둘을 합산해 제품 오류 횟수로 세지 않는다.
- 기존 `rhino-sync-perf.mjs`로 작은 사본의 열린 Rhino 연결 시험도 시도했으나 ready 보고를 받지 못했다. 연결·핀·수정·되돌리기의 실제 왕복은 통과 처리하지 않는다. 해당 시험 프로세스와 시험 호스트만 정리했다.
- 두 사람이 서로 다른 PC에서 협업·의견 반영·동시 편집하는 실제 검수, AI가 실모델을 수정한 뒤 사용자 네이티브 재편집, 도면 출력 품질, 장시간 부하는 이번 통과 범위가 아니다.
- ‘오류가 전혀 없음’은 이번 시험으로 보증할 수 없다. 출시 판단은 사용자 입력·원본 보존, 요청의 정확한 실행 대상, 실패 후 복구, 결과 파일의 유효성으로 구체화해야 한다.

## 8. 사용자 지적 후 화면 경로 재검증

사용자는 코드로 여는 방식이나 경로 때문에 오류가 생겼을 가능성을 지적하고 computer-use 직접 조작을 요청했다. 이 지적에 따라 함수 직접 호출의 실패와 사용자 진입 경로의 실패를 분리해 재검증했다.

- computer-use 세션을 초기화하고 `sky.list_windows()`를 다시 호출했으나 커널이 `windows sandbox failed: CreateProcessWithLogonW failed: 1909`로 종료됐다. 네이티브 창 조작은 수행하지 못했다.
- 대안으로 **일반 권한의 격리 VIDE 서버와 실제 프런트**를 띄워 Playwright로 `#model-file` 파일 선택 입력을 설정했다. 실제 onchange → HTTP 파일 업로드 → 제품 처리 → 화면 결과의 경로를 거쳤다. 파일 선택기 자체를 마우스로 클릭한 시험이나 설치 WebView2 창 시험은 아니다.
- 첫 시도는 큰 응답을 Playwright `response.json()`으로 읽다가 inspector cache 오류가 났다. 이는 시험 도구 오류이며 제품 오류로 집계하지 않았다. 후속 시도는 실제 화면의 완료 상태와 요청 요약 API를 사용했다.

| 파일 선택 UI 시험 | 소요 | 실제 상태 | 실제 화면 |
|---|---|---|---|
| 작은 Rhino 사본 | 8,569ms | `failed / INVALID_GEOMETRY` | 모델 미표시, ‘AI의 형상 제안이 검증을 통과하지 못했습니다.’ |
| 큰 Rhino 사본 | 36,602ms | `unknown / HOST_RESULT_UNKNOWN` | 모델 미표시, ‘호스트 결과 확인 필요’, ‘저장된 후보 다시 확인’. 진단도 동일한 `Readback geometry mismatch` |
| CAD 사본 | 7,010ms | `failed / UNSUPPORTED_DWG_CONTENT` | 모델 미표시, 직선 XY 폴리라인 지원과 호·블록·다른 유형 때문에 가져오지 않았다는 안내 |

세 요청 모두 HTTP 200이지만 업무 상태는 실패/결과 불명이다. HTTP 성공과 파일 읽기 성공은 다르다. 원래 파일은 시험 사본의 ASCII 이름으로 복사하여 한글·괄호 경로 변수를 제거했다. 큰 Rhino 파일은 실제로 읽고 저장한 뒤 재검증에서 실패했다. 따라서 **직접 함수 호출만의 오류나 단순 파일 경로 인식 실패로 설명할 수는 없다.** 다만 열린 Rhino/CAD의 Link 경로는 미검증이며, Rhino 자체가 파일을 열 수 없다는 결론도 아니다.

화면 실패에서도 연결 파일 목록·대화 입력은 유지되고 별도 엔진 충돌은 관찰하지 않았다. 모델 없음 안내가 계속 ‘파일을 불러오세요’라고 하는 점과, 파일 읽기에 ‘AI의 형상 제안’이라는 문구를 사용하는 점은 실제 화면에서도 확인했다.

## 9. 제안하는 실행 순서와 완료 기준

1. **P0 안정성·실파일 진입** — 세 덤프 스택 분석, Rhino 두 파일·CAD 도면의 열람 실패 해결. 정상 객체가 표시되고 누락/편집 제한을 식별할 것. 원본 변경 없이 표시할 수 있어야 한다.
2. **P1 요청·핀·복구** — 회의 요약은 Rhino 없이 응답; 기존 핀은 문서 재열기 후 유지, 사라진 핀만 재지정; 404는 끝없는 폴링에서 벗어남; 엔진 재시작 후 초안 복원. 불명확한 쓰기는 자동 중복 실행하지 않을 것.
3. **P1 화면 정리** — 미완성 기본 화면·개발용 문자열·중복 안내 제거. ‘연결 → 선택/그리기 → 요청 → 결과 → 되돌리기/저장’이 추가 설명 없이 이어지는지 검수.
4. **P2 업무 완결** — 회의록·결정·할 일·모델 대상을 연결하고, 실제 제출 가능한 산출물 하나부터 완성. 동일 자료로 두 사람 협업과 재접속까지 확인.

새 전문 도구·노드 편집기·상시 상태 배지를 늘리는 작업보다 위 순서가 사용자 목표에 직접 기여한다. 관련 작업 정본은 [PLAN-16](../plans/PLAN-16-document-links.md), [PLAN-26](../plans/PLAN-26-chat-stage.md), [PLAN-27](../plans/PLAN-27-sync-storage-stability.md)에서 연결한다.
