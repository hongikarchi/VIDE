# SPIKE — 프로젝트 서버 폴더로 지식 DB 구축

## 질문

1. 회사 서버의 프로젝트 폴더 경로 하나만으로, 규칙·파서·Jev·LLM을 이어 “어느 파일이 무엇을 말했나”를 담은 SQLite DB를 실제로 만들 수 있는가.
2. 각 단계에 걸리는 시간·양·비용은 얼마인가.
3. Jev를 쓰면 LLM만 쓸 때보다 빠르거나 싸면서 놓치지 않는가.
4. 그 DB로 “구조 설계에서 고려해야 할 조건”에 근거와 함께 답할 수 있는가.

## 방법

- **대상:** RESEARCH-04 출처 S-06 프로젝트의 회사 서버 폴더 전체(메일 백업 포함). 계약·회계·제안서도 포함했다(사용자 결정).
- **DB 위치:** 사용자가 VIDE에 만든 해당 프로젝트의 ID로 `%LOCALAPPDATA%\VIDE\knowledge\<프로젝트 ID>.sqlite`. 작업 엔진 DB(`vide.sqlite`)는 읽기만 했다.
- **경계:**
  - 서버 원본은 읽기만 했다.
  - DWG는 `.vide/knowledge-crawl/dwg/`의 사본을 에이전트가 띄운 숨은 ZWCAD가 읽었고, 끝난 뒤 그 프로세스만 종료했다. 사용자가 열어 둔 ZWCAD는 건드리지 않았다.
  - 저장소에는 코드와 이 기록만 두고, 내용·경로·발주처명은 넣지 않았다.
- **코드:** `tools/spikes/2026-09-29-knowledge-crawl/`
  - `crawl.mjs --root <폴더> --project <VIDE 프로젝트 ID|이름> [--stages …]`
  - 단계 모듈: inventory → names → extract(Python 추출기 `extract.py`) → dwg(ZWCAD 명령 `dwg/KnowledgeDwg.cs`) → link → select → audit → statements → verify → query
  - Jev 호출은 T-032의 `tools/locate/jev.mjs`를 재사용했다. Claude는 구독 CLI(`claude -p`, 도구·MCP·설정 없음, Sonnet)를 썼다.
- **환경:** Windows 11, Node 24.15, Python 3.14(PyMuPDF 1.28, openpyxl, pyhwp), ZWCAD 2023, 회사 서버는 네트워크 드라이브. Jev `jev-1.13.0`.
- **측정:** 각 단계의 시간·호출 수·토큰을 DB의 `run` 표에 남겼다.

**합계(첫 실행):** 단계 시간 약 23분(그중 9분은 네트워크 해시). Jev 약 8,100회·665만 토큰(약 $0.28). Claude 183회·입력 244만·출력 34만 토큰(구독 CLI). 이 합계에는 중단 후 다시 시작한 진술 추출의 첫 6묶음과 일회성 대조가 빠져 있다. DB 파일 약 52MB.

### 이름 해석: 규칙 · Jev · Claude (무작위 100개 파일)

Claude 판정을 기준으로 삼았다.

| 방법 | 기준과 일치 | 시간 | 사용량 |
|---|---|---|---|
| 규칙 | 95개를 분류, 그중 91개 일치 | 즉시 | 없음 |
| Jev(파일마다 1회) | 100개 중 94개 일치. 확신 0.8 이상 91개 중 90개 일치 | 1.8초 | 100회·6.2만 토큰(약 $0.003) |
| Claude(목록 한 번에) | 기준 | 8.4초 | 1회·입력 7,840·출력 1,462 토큰 |

- 폴더 규칙(보낸/받은 자료, 협력사, 날짜 폴더, 회의록 폴더)만으로 대부분이 풀린다. 이 사무소의 폴더 규칙이 잘 지켜져 있기 때문이다.
- 불일치 10건은 대부분 애매한 경우였다(회의 준비 자료를 회의록과 보고 자료 중 어디로 볼지 등).
- **토큰 수는 Jev가 더 많다.** Jev는 파일마다 기준 설명을 반복해 보내고, Claude는 100개를 한 번에 받는다. 대신 Jev 단가가 낮아 금액은 Jev가 훨씬 싸고(입력 100만 토큰당 $0.042), 구독 CLI 한도를 쓰지 않는다.

### 선별: Jev 확신도로 나누기

Jev가 발췌마다 종류(결정·요청·조건·의견·정보·없음)와 구조 관련 여부를 판정했다. 확신 0.8 이상은 Jev 판정을 채택하고 나머지는 Claude가 다시 판정했다.

| 구간 | 개수 | 비율 |
|---|---|---|
| Jev 확신 · 내용 있음(채택) | 1,344 | 27% |
| Jev 확신 · 내용 없음(제외) | 863 | 17% |
| 확신 낮음 → Claude | 2,760 | 56% |

확신 구간에서 각각 40개를 뽑아 Claude로 대조했다.

| 확인 | 결과 |
|---|---|
| “내용 없음” 확신 40개 | **40개 모두 Claude도 내용 없음.** 놓친 결정·요청·조건·의견 0개 |
| “내용 있음” 확신 40개 | 같은 종류 25개, 내용 유무 일치 28개. 불일치 대부분은 “정보 ↔ 내용 없음” 경계(자재 목록, 표제란, 참고 사례 슬라이드)였고, “조건 ↔ 정보” 혼동이 3개였다 |
| 확신 낮음 2,760개 | Jev 판정이 Claude와 같은 종류 1,742개(63%), 내용 유무 일치 2,160개(78%) |

**해석**

- **Jev는 “내용 없음”을 버리는 필터로는 믿을 만하다.** 이번 표본에서는 확신 구간의 놓침이 없었다.
- **“내용 있음” 쪽은 넓게 잡는다.** 잘못 채택된 발췌는 다음 단계(진술 추출)에서 진술 없음으로 끝나므로, 누락이 아니라 비용 증가로 나타난다.
- **한국어 발췌에서 Jev가 확신한 비율은 44%에 그쳤다.** 절반 이상이 LLM으로 넘어갔다.
- **LLM 사용 감소:** 전부 Claude로 판정할 때 추정(입력 약 215만·출력 약 8.8만 토큰) 대비, 이번 흐름의 Claude 사용은 입력 122만·출력 5만 토큰으로 약 43% 줄었다. 대신 Jev 468만 토큰(약 $0.20)과 1분이 더 들었다.

### 검증: 인용이 진술을 뒷받침하는가

| 확인 | 결과 |
|---|---|
| Jev “인용이 뒷받침함” 표본 40개 | Claude도 38개 뒷받침 |
| Jev “인용이 약함” 표본 40개 | Claude도 38개 약함(뒷받침 2개) |
| 약한 1,068개를 발췌 전체와 다시 대조(Jev) | 1,033개 뒷받침, 35개 약함 |
| 발췌 전체 기준 뒷받침 표본 40개 | Claude도 36개 뒷받침 |

- **Claude 진술의 흔한 결함은 지어낸 내용이 아니라 짧은 인용이다.** 요약은 발췌 전체를 반영하는데, 인용은 그 일부만 잘라 온다(예: 요약은 “검토 결과 재료를 바꿨다”, 인용은 “검토해 보니 무게가 감당이 안 될 것 같아서”처럼 이유 부분만 있음). 제품에서는 근거를 발췌 단위로 보여 주고 인용은 강조 위치로 쓴다.
- **Jev는 이 판정에서 Claude와 95% 일치했다.** 항목마다 한 번씩 확인하는 일을 LLM 없이 1분 안에 처리했다.
- **주체 합치기:** Jev가 17건을 합쳤다. 15건은 맞았다(같은 회사의 약칭, 담당자 이름이 붙은 표기, 위원 번호 등). 2건은 지나쳤다(기관 전체 → 그 기관의 특정 부서, 기준 문서 이름 → 발행 기관). 합치기는 제안으로만 두고 사람이 확정해야 한다.

### 질의 결과: 구조 설계 고려 조건

결과 문서는 DB 옆 `…\knowledge\<프로젝트 ID>.structural-conditions.md`(프로젝트 자료라 저장소 밖)에 있다.

- **주제 8개:** 기존 구조체의 허용하중과 하중 전달, 조경·인공지반 하중, 기존 주차장 슬래브·부재 상태, 지반·기초, 스팬·보 춤·캔틸레버·기둥 배치, 높이·공간 제약, 구조 형식·재료·내화, 업무 범위·심의·인허가
- **근거 연결:** 조건마다 진술 번호가 붙고, 각 번호는 파일·쪽/슬라이드/도면 위치·원문 인용으로 이어진다.
- **서로 다른 값 표시:** 자료마다 다른 값을 날짜와 함께 나란히 보여 준다. 예: 허용하중 단위, 스팬 상한, 재료 강도, 기초 공법의 시공 높이.
- **확인 필요 항목 10개:** 발주처와 설계 방향의 합의, 횡력 저항 방식과 책임 주체, 기존 조사 자료로 대체할 수 있는지 등
- **사람 판정은 아직 없다.** 빠진 조건과 틀린 조건은 사용자 판정이 필요하다.
- **날짜 없는 진술:** 233개는 파일 경로에 날짜가 없고 메일도 아니라 날짜가 비어 있다. 파일 수정 시각은 원본 작성 시점과 다를 수 있어 쓰지 않았다.

## 결론

1. **경로 하나로 구축이 가능하다.** 서버 폴더와 VIDE 프로젝트만 지정하면 첫 실행 약 23분, 다시 실행 30초 안팎으로 “어느 파일(쪽·도면 위치)이 누가 언제 무엇을 말했나”를 담은 DB가 만들어졌다. 구조 설계 조건 질의에 근거와 함께 답했다.
2. **가장 큰 절감은 AI가 아니었다.**
   - 같은 문장 합치기로 발췌가 약 2만 개에서 5천 개로 줄었다.
   - 폴더 이름 규칙이 문서 종류의 95%를 풀었다.
   - 결정적 추출기(문서·DWG)는 AI 없이 5분 안에 끝났다.
3. **Jev는 판정의 방향에 따라 효과가 다르다.**
   - **잘 맞은 곳:** “내용 없음”으로 확신한 발췌 버리기(표본 놓침 0), 인용·발췌가 진술을 뒷받침하는지 확인(Claude와 95% 일치), 이름 해석 잔여 분류
   - **약한 곳:** 한국어 발췌의 종류 판정. 확신 비율 44%, 확신한 “내용 있음”도 넓게 잡혔다.
   - **LLM 사용 감소:** 종류 판정 단계에서 약 43%, 검증을 LLM 대신 한 몫까지 합하면 Claude 입력 약 3분의 1(추정)이다. 비용은 $0.28, 시간은 약 3분이 더 들었다.
4. **제품으로 옮길 때의 단계 순서**
   1. 규칙·파서
   2. 같은 문장 합치기
   3. Jev로 빈 발췌 버리기
   4. LLM 판정·진술 추출(여러 발췌 묶음)
   5. Jev로 근거 확인
   6. 사람이 확정

   PLAN-08 K1·K2에 반영한다.

## 한계

- **기준 판정:** 사람 판정이 아니라 Claude 판정을 기준으로 삼았다. Claude의 오류는 측정에 포함되지 않는다.
- **표본 크기:** 확신 구간 대조는 40개씩이라 오차 범위가 크다.
- **스캔 PDF:** 26개는 글자가 없어 빈 결과다. 이미지 판독(OCR·AI)은 하지 않았다.
- **3DM:** 137개(30GB)는 이번에 읽지 않았다.
- **ZIP:** 41개(6.8GB) 안의 자료는 풀지 않았다.
- **옛 형식:** DOC·PPT·XLS는 추출기가 없다.
- **PDF 주석:** 주석 11,526개는 거의 모두 참고 도면 PDF 한 개에서 나왔다. 협력사의 다른 현장 준공도면이며, 사람이 단 검토 의견은 아니었다.
- **이름 규칙:** 이 사무소 폴더 규칙에 맞춘 규칙이다. 다른 프로젝트는 규칙 적용률이 낮을 수 있고, 그만큼 Jev의 몫이 커진다.
- **도면 문자 묶음:** DWG 문자는 배치(모형/배치 탭)·블록별로 모아 발췌를 만들었다. 가까운 문자끼리 묶는 공간 군집은 하지 않았다.
