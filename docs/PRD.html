제품 기준 · 플랫폼 MVP

문서 목적: 제품의 사용자·가치·MVP 범위·요구사항·수용 기준을 정의한다. 기능의 구체적인 동작은 SPEC, 화면과 상호작용은 Design, 기술·Stack·개발 순서·시험 방법은 PLAN이 소유한다.
제품: VIDE (Vibe Integrated Drawing Environment) · 건축가를 위한 통합 설계 작업환경.

여러 설계 프로그램과 데이터를 하나의 프로젝트로 연결하고, 건축가가 가리키고 그리며 AI에 작업을 맡기고, 실제 중간 상태를 보면서 개입하는 확장형 IDE.

00 / 제품 요약

VIDE는 특정 건축 자동화 업무 하나가 아니라 여러 프로그램과 설계 자료를 함께 다루는 공통 IDE 플랫폼이다. 이름의 Vibe는 코드와 명령어를 직접 작성하는 대신 의도·대화·가리키기·그리기로 설계를 진행하는 작업 방식을 뜻한다. 장시간 무관찰 자율 실행을 의미하지 않는다.

기본 환경은 빈 화면과 연결 버튼이 아니다. 대상 읽기, 공간 입력, 선언한 네이티브 객체의 생성·수정, 실제 중간 결과, 사람의 개입, 원본 반영·재편집·보존까지 이어져야 한다. 분야별 전문 스킬 전체를 완성하지 않아도 이 능력을 사용할 수 있어야 한다.

구분 제품 기준
제품 형태 Windows 우선 설치형 로컬 IDE와 공통 화면·표시 기능을 활용하는 웹 검토 환경 (§1.3)
지원 호스트 제품은 여러 설계 도구를 지향한다. 첫 출시의 호스트 집합과 완료 수준은 §14.1
입력 문장, 객체 핀, 기준에 연결된 스케치, 코멘트·자료 참조 (§8)
실행 위임 범위 안에서는 진행하고, 실제 상태를 보여주며 사용자가 개입 (§9)
결과 네이티브 객체와 호스트 기본 도구의 후속 편집 (§12.1)
연계 한 작업에서 여러 호스트의 자료·변경을 연결하고 독립 작업을 병렬 처리 (§12.2)
데이터 설계 대상 중심의 근거·관계와 기본 조회·집계·표 갱신 (§6)
기록·공유 최신 웹 공유 상태, 과거 검토본, 별도 파일 내보내기를 구분 (§12.4~§12.6)
확장 작은 확장의 실제 등록·실행과 분야별 전문 스킬을 구분 (§12.3)
첫 출시 범위 포함·제외는 §13~§14, 대표 검수 과업은 §16.4

핵심 경험: 프로젝트와 호스트를 연결한다 → 대상을 가리키고 의도를 그린다 → 작업을 맡긴다 → 실제 후보와 데이터를 보며 조정한다 → 네이티브 결과를 반영·재편집한다 → 공유된 상태에서 의견을 받고, 검토본·파일로 결과를 보존한다.

즉석 HTML 자료 생성과 문단·표·도형의 직접 선택 편집은 후보 기능 C-01이다(§4.4). 웹 작업 공간 공유나 파일 내보내기가 그 편집기의 구현을 뜻하지 않는다.

01 / 제품 정의와 책임

1.1 무엇을 만드는가

VIDE는 Rhino·CAD·Revit 같은 설계 도구와 프로젝트의 데이터·문서를 한데 엮고 AI로 제어하는 통합 관리 환경이다. 건축가는 여러 프로그램의 모델과 설계 자료를 하나의 프로젝트·작업 범위에서 다루고, AI의 과정과 결과를 직접 통제한다.

VS Code와 같은 확장형 IDE의 개념을 지향하되, VS Code 기반 개발이나 터미널 중심 화면을 필수로 정하지 않는다. 모델·도면·스케치·치수·자료가 주요 입력과 판단 대상이며, 사용자는 코드와 긴 터미널 출력을 읽지 않고도 대상과 변경을 이해할 수 있어야 한다.

새로운 범용 기하 커널, 모든 CAD/BIM 프로그램을 대체하는 모델러, 모든 네이티브 화면을 한 창 안에 넣는 제품은 아니다. 개별 호스트가 원본의 편집 의미를 소유하고, IDE는 연결된 작업과 근거·상태·결정을 관리한다.

1.2 제품이 책임지는 것

지정한 대상·입력·유지 조건을 보존하고, 실제 작업 상태와 결과를 보여주며, 사용자의 개입을 실행에 반영한다. 후보와 원본, 계획과 실행, 추정과 사실, 의견 제출과 작업 실행, 지시 반영과 결과 생성, 원본 적용과 파일 저장을 구분한다.

등록되지 않은 모든 설계 조건을 자동으로 발견하거나 전체 설계의 전문적 적합성을 포괄적으로 보증하지 않는다. 지원 기본 제어에서는 정의된 네이티브 결과와 상태의 신뢰성을 확보한다. 전문 스킬은 별도의 완료 기준과 검토 범위를 갖는다. '미검토' 표시가 낮은 완료율과 품질의 변명이 되어서는 안 된다.

1.3 사용 환경과 접근 역할

로컬 작업자: Windows에 설치한 IDE에서 프로젝트를 열고 사용 권한이 있는 호스트와 연결한다. 화면을 브라우저 탭으로 제공할지 데스크톱 창으로 감쌀지는 PLAN에서 정한다. 작업 PC에서 사용하는 HTML 기반 화면도 로컬 IDE일 수 있다. 호스트 설치·사용 권한이 IDE 설치만으로 제공된다고 표시하지 않는다.

웹 참여자: 공유 권한 범위에서 모델·도면·표·후보·공개된 작업 상태를 보고 의견을 남긴다. 웹은 로컬 화면의 필요한 구성요소를 활용할 수 있지만, 같은 화면을 쓴다는 이유로 같은 실행 권한을 갖지 않는다. 구체적인 허용 행동은 §12.5와 §14가 정한다.

Local-first: 로컬 입력·프로젝트 기록·호스트 제어를 작업환경이 관리한다. 웹 공유에 반영된 자료의 보존은 로컬 호스트의 실행 상태와 분리한다. 클라우드 모델을 사용할 수 있지만 전송할 자료와 권한을 확인할 수 있어야 한다. AI 연결이 끊겨도 가능한 열람·선택·스케치·코멘트·저장은 유지한다. 미연결 호스트의 최신 정보나 온라인 추론까지 오프라인에서 가능하다고 표시하지 않는다.

원본 호스트 상태, IDE가 확인한 상태, 원본 파일 저장 상태, 웹 공유에 반영된 상태는 서로 다를 수 있다. 사용자가 이 차이와 마지막 확인 시점을 알 수 있어야 한다.

02 / 해결할 문제와 제품 가설

효과는 지원 과업의 실제 사용으로 확인한다. 위임 범위 안의 실행과 설계적 결정에서의 개입을 함께 제공한다는 전제는 §9.5가 소유한다.

문제 제품의 대응 확인할 결과
'여기'와 '이런 형태'를 문장만으로 전달하기 어렵다 실제 대상 핀, 좌표에 연결된 스케치, 단위 있는 치수 대상 오인과 의도 수정 부담이 줄어드는가
모델·BIM 정보·회의 결정이 분리되어 있다 설계 대상 중심의 자료·관계·근거 연결 관련 조건과 변경 영향을 확인할 수 있는가
큰 작업은 방향 오류를 늦게 발견한다 검토 가능한 단위와 실제 중간 결과 잘못된 대상을 일찍 찾고 방향을 바꿀 수 있는가
작업 중 무엇이 일어나는지 알 수 없다 실제 모델·도면·가정·계산 상태 표시 코드 로그 없이도 현재 상태를 이해하는가
매 단계 승인하면 직접 CAD를 쓰는 것만큼 번거롭다 위임 범위 안의 진행과 선택적 개입 불필요한 승인 없이 채택할 만한 결과를 얻는가
큰 문맥과 반복 검증이 시간·비용을 늘린다 필수조건 보존, 관련 정보 조회, 영향 범위 재계산 조건 누락 없이 총부담과 재작업을 줄이는가
도면과 모델에 같은 변경을 반복 전달한다 호스트 간 연계 요청과 호스트별 결과 확인 재입력 부담을 줄이고 부분 반영을 식별하는가
후보·원본·보고서 상태를 혼동한다 적용·저장·공유·검토본·내보내기 구분 무엇이 실제로 반영되고 누구에게 공유되었는가
대안과 피드백의 이유가 사라진다 기준 버전의 의견과 과거 검토본 작성 당시의 판단과 현재 결과를 연결하는가

비교 목표와 두 기준선은 §16.1, 대표 사용자 과업은 §16.4가 정한다. 입력 방식 하나의 효과나 단일 지표만으로 다른 사용자 가치를 자동으로 부정하지 않는다.

03 / 사용자와 핵심 업무

주 사용자 — 비개발자 건축 설계자. 로컬 IDE에서 프로젝트와 연결 문서를 관리한다. 선택·스케치·치수·문장으로 요청하고, 후보와 실제 변경을 보며 방향을 바꾼다. 전문 스킬 없이도 기본 제어와 데이터 확인을 사용할 수 있어야 한다.

보조 사용자 — BIM·계산설계 담당자. 네이티브 객체의 의미, 데이터 관계, 입력 조건, 연결 상태와 결과 충실도를 확인한다. 전문 설정을 일반 사용자의 매 작업 필수 절차로 만들지 않는다.

확장 작성자 — 스킬·플러그인 개발자. 공통 연결·입력·진행·결과·권한 기능을 재사용해 업무 기능을 추가한다. 일반적인 확장 등록을 위해 인증·프로젝트 데이터·호스트 제어를 매번 다시 만들지 않아야 한다.

웹 검토자 — 동료·책임자·발주자 등. 허용된 공유 상태와 검토본을 보고 대상에 연결된 의견을 남긴다. 의견 작성은 전문적 적합성의 판정이나 원본 반영 승인이 아니다.

표는 확장 목표다. 각 업무의 외부 데이터 수집기·계산 엔진·전문 해석 전체가 공통 기반에 이미 제공된다는 뜻이 아니다. 필요한 추가 능력은 해당 스킬의 SPEC·PLAN에서 선언한다. 첫 전문 스킬의 종류와 개발 순서는 OQ-07의 후속 항목이다.

4.3 기본 실행 규칙과 전문 하네스의 경계

플랫폼은 정확한 문서·객체·단위·권한, 입력·기준 보존, 실제 진행, 개입·중단, 사람 수정 보호, 중복 적용 방지, 불명확 결과 처리와 최소 품질·비용 관측을 책임진다. 늦은 이전 결과가 새 조건이나 직접 수정한 객체를 덮어쓰지 않는다.

스킬은 분야별 해석 절차·경험칙·사례·평가·전문 도구를 보강한다. 외부 자료·지침·확장이 실행 권한을 스스로 높이거나 공통 보호를 끄지 못한다. rule book의 문장만으로 프로그램이 강제해야 할 규칙을 대신하지 않는다.

4.4 후보 기능과 비목표

C-01: 필요한 자료의 즉석 HTML 생성과 문단·표·도형의 직접 선택·부분 수정. 캔버스와 직접 HTML 편집 중 어느 방식도 정하지 않는다. 별도 채택 없이 구현 범위로 자동 포함하지 않는다.

범용 네이티브 파일 자동 병합, 모든 BIM 의미·편집 이력의 무손실 왕복, 요청 없는 호스트 간 원본 자동 동기화, Camera Sync, 장시간 무관찰 자율 설계는 목표로 삼지 않는다. 호스트 상태를 IDE 표시로 자동 갱신하는 Live Sync는 후속 목표로 구분한다. Grasshopper·Archicad·SketchUp 등 추가 호스트는 지원·검수 원칙에 따라 확장할 수 있다. 첫 출시의 제외 범위는 §14.2가 정한다.

다른 프로젝트의 자료는 명시적으로 연결한다. 열린 탭·같은 파일 이름·같은 AI 모델을 쓴다는 이유로 문맥이나 권한이 합쳐지지 않는다.

06 / 건축 특화 데이터 요구사항

6.1 중심은 설계 대상이다

형상·속성·관계·근거·버전·작업 결과를 설계 대상에 연결한다. 동시에 DB 전체를 완벽하게 분류해야 작업을 시작할 수 있는 구조도 피한다. 초기 매스·미분류 형상을 수용하고, 모르는 용도·관계는 미확정으로 남기며 지원 작업에 필요한 의미부터 확보한다.

6.2 연결해야 할 정보

형상 표현 정밀 원본 참조, 표시용 형상, 도면 표현, 좌표계·단위

확인 가능한 대응은 표현이 바뀌어도 유지한다. 확인할 수 없으면 끊김을 드러내며 가까운 다른 객체에 조용히 재연결하지 않는다. 지원 관계와 갱신 행동은 SPEC에서 선언하고, 모든 건축 관계를 안다고 전제하지 않는다.

6.3 관계·값의 출처와 사용 역할을 구분한다

원본에서 읽음, 도구로 계산함, 사용자가 확정함, AI가 추정함을 구분한다. 원문 사실·계산 가정·설계 조건은 서로 다르며 추정은 자동으로 확정 사실이 되지 않는다. 현재 치수와 목표 치수를 같은 값으로 덮어쓰지 않는다.

가까이 있다는 것과 호스트·경계·타입·계산으로 연결되었다는 것은 다르다. 필수조건과 참고 의견이라는 사용 역할도 출처 구분과 별도로 유지한다.

6.4 데이터가 답해야 할 질문

대상에서 조건·코멘트·지표로, 자료나 지표에서 관련 모델 대상으로 이동할 수 있어야 한다. '이 부분을 유지하는 근거는 무엇인가', '이 수치는 어느 모델과 방법으로 계산했는가', '이 스케치를 바꾸면 무엇을 다시 계산해야 하는가', '이 관계는 사실인가 추정인가'를 확인한다.

6.5 저장·조회와 문맥의 경계

큰 기하 데이터, 계산 입력, LLM 입력을 같은 단위로 취급하지 않는다. 논리적 읽기·갱신·유효성 규칙은 SPEC이, DB 엔진·물리 스키마·저장 형식·질의 구현은 PLAN이 정한다. 단순 조회·필터·정의된 계산 때문에 불필요한 AI 호출을 만들지 않는다.

6.6 기본 조회·집계·표 갱신

지원 객체의 속성·수량을 조회하고 명시한 조건으로 필터·그룹·집계하여 표로 확인할 수 있어야 한다. 결과에는 대상·단위·출처·계산 기준·기준 버전이 연결된다. 관련 입력이 바뀌면 결과의 유효성을 구분하고 갱신할 수 있어야 한다.

모든 값의 상시 실시간 재계산을 약속하지 않는다. 계산·집계·갱신 동작은 SPEC에서 선언한다. 법규상 면적과 기하학적 면적을 같은 것으로 표시하지 않으며, 층 기준이 없는 매스에서 층별 면적을 임의 확정하지 않는다. 분야별 전문 일람표와 전문 면적 해석은 FR-21과 구분한다.

코어 또는 신뢰된 기본 확장 중 어디에서 이 능력을 제공할지는 구현 선택이다. 기본 집계가 확장으로 제공되어도 제품의 약속은 동일하다.

07 / 작업을 나누는 기준

7.1 설계 목적과 검토 가능한 결과

큰 목표를 단일 무관찰 실행으로 처리하지 않고, 내부 기하 연산마다 사용자의 승인을 요구하지도 않는다. 작업 단위의 목적·대상·유지 조건·영향 범위·기대 결과·선후관계를 확인할 수 있어야 한다. 기존 선택과 자료로 채울 수 있는 내용은 자동 구성하고, 중요한 모호함만 확인한다.

7.2 변경 범위와 검토 범위

읽기 권한이 있는 주변 대상을 영향 확인에 사용할 수 있지만, 검토에 포함되었다는 이유로 변경 권한이 생기지는 않는다. 공간적으로 멀어도 같은 타입이나 공유 조건에 의존하면 영향을 검토한다. 영향을 확인하지 못하면 이를 드러내고 필요한 검토나 범위 결정을 거친다.

7.3 분할과 묶음

독립적으로 채택할 판단이 여러 개이거나, 방향을 확인하지 못한 후속 작업이 누적되거나, 영향이 원래 목표를 넘어가면 더 나눈다. 함께 바꾸어야 일관된 후보가 되는 대상은 묶을 수 있다. 여러 객체도 같은 조건과 검토 결과를 갖는다면 일괄 처리할 수 있다.

객체 수·시간·토큰 수 하나만으로 고정 분할하지 않는다. 분할이 자동으로 새 AI 세션·감독자·승인 단계를 늘려서는 안 된다.

7.4 전체 조건과 호스트 간 의존성

작업을 나누어도 상위 목표·필수조건을 공유하고, 결과를 합칠 때 관련 부위와 전체 지표를 확인한다. 한 작업의 통과를 전체 설계의 적합으로 확대하지 않는다.

독립 작업은 병렬로 진행할 수 있고, 앞선 결과가 필요한 작업이나 같은 대상을 변경하는 작업은 필요한 순서를 관리한다. 부분 실패와 미확인 결과를 전체 완료로 합치지 않는다. 세부 조정 규칙은 SPEC에서 정한다.

08 / 핵심 사용자 여정

8.1 설치하고 프로젝트·호스트를 연결한다

사용자가 지원 Windows 환경에 IDE를 설치하고 프로젝트와 호스트 문서를 등록한다. 문서명뿐 아니라 대상 식별·단위·읽기/쓰기 지원 수준을 확인한다. 화면 전환과 다른 프로그램의 활성화가 이미 시작한 요청의 대상을 바꾸지 않는다.

8.2 대상을 가리키고 의도를 전달한다

객체를 문장에 핀하고, 작업평면에 선을 그리거나 치수·파라미터를 지정한다. 변경 대상과 유지 대상, 참고 자료를 함께 전달한다. 호스트 뷰포트와 IDE 자체 뷰에서 확인된 같은 객체를 가리킬 수 있지만 선택 상태와 카메라 시점을 자동으로 맞추지 않는다. 필요할 때 지정한 호스트·문서의 상태는 Sync로 IDE 표시를 갱신한다(§12.2).

원본 문장·선·치수·대상을 보존한다. 평면 스케치의 공간 기준을 표시하고 미등록 이미지를 확정된 3D 입력으로 취급하지 않는다. 작은 요청도 같은 구조로 처리하며 별도의 빠른 모드를 강제하지 않는다.

8.3 실제 중간 상태를 보며 작업한다

목표와 조건을 받은 AI는 위임 범위에서 여러 단계를 진행한다. 사용자에게 대상·조건·예상 변경·실제로 준비된 일관된 후보·관련 지표를 보여준다. 예정된 행동과 완료된 결과를 구분한다. 스케치 원본과 해석을 함께 보여주고 지원 불가를 유사 형상 생성으로 숨기지 않는다.

8.4 진행 중 개입하거나 직접 수정한다

로컬 작업자는 유지 영역·치수·스케치·자료를 바꾸거나 전체 작업 또는 하위 작업의 중단을 요청할 수 있다. 지시 접수와 실제 반영·종료를 구분한다. 새 조건에 영향받는 후속 작업을 조정하고 이미 만들어진 유효한 결과와 입력은 보존한다.

8.5 후보를 반영하고 네이티브 도구로 편집한다

사용자가 검토한 변경의 정확한 대상과 내용을 확인하여 원본 반영을 요청한다. 반영 버튼을 누른 이유로 AI가 다른 변경안을 다시 생성하지 않는다. 결과는 선언한 네이티브 유형과 후속 편집 능력을 제공하며, 적용·파일 저장·재열기를 서로 구분한다.

8.6 도면과 모델을 하나의 요청으로 연결한다

지원하는 CAD 정보로 Rhino 후보를 만들거나, 하나의 설계 변경을 양쪽의 지정 대상에 반영한다. 사용자 지정 또는 확인된 대응을 사용하며 모든 대상의 자동 대응을 전제하지 않는다. 호스트별 진행과 결과를 확인하고, 일부만 적용되었다면 남은 작업과 영향받는 결과를 구분한다.

8.7 데이터를 확인하고 검토를 이어간다

변경과 관련된 기본 표·수량을 확인하고 필요할 때 갱신한다. 주요 시점을 검토본으로 남긴다. 외부 참여자는 허용된 공유 상태를 탐색하고 핀·코멘트·스케치를 제출한다. 로컬 설계자는 의견을 검토한 뒤 작업에 연결하고, 전후 검토본을 비교하거나 표·검토 요약을 파일로 내보낸다.

09 / 진행의 시각화와 언제든 가능한 개입

9.1 화면에 보여줄 실제 상태

코드 없이 현재 대상, 사용 중인 가정·조건, 마지막으로 준비된 결과, 실제 변경, 미검토 사항, 가능한 개입을 확인할 수 있어야 한다. 한 요청에 여러 호스트가 관련되면 전체 목적과 호스트별 상태를 함께 보여준다.

형상 변화가 없는 작업도 사용한 자료·가정·계산 결과를 보여준다. 긴 독백, 꾸며낸 내부 사고, 반복적인 '생각 중' 문구가 실제 진행을 대신하지 않는다. 수치형 완료율은 측정 근거가 있을 때만 사용한다. 마지막 후보를 표시한다면 그 기준과 새 지시 반영 여부를 드러낸다.

9.2 개입과 의견 저장

'현재 작업을 바꾸는 지시'와 '검토 의견 저장'을 구분한다. 코멘트·핀·스케치의 저장 자체는 AI 호출·원본 쓰기를 시작하지 않는다. 기본 입력은 AI 연결 없이도 가능한 범위에서 보존한다. 웹에서 제출된 의견의 실행 연결은 §12.5의 권한을 따른다.

9.3 접수·반영·정지를 구분한다

지시를 받았다는 것과 후속 실행 기준에 반영되었다는 것은 다르다. 지시 반영은 형상 생성과도 다르며, 제외·중단 지시는 새 형상 없이 반영될 수 있다. 적용하지 못한 이유와 필요한 결정을 알린다.

중단 요청은 즉시 정지나 원상복구를 뜻하지 않는다. 새 지시와 충돌하는 후속 실행을 시작하지 않고, 멈출 수 없는 연산의 실제 종료와 남은 결과를 확인한다. 이미 적용된 원본, 남은 후보, 파일 저장 상태를 구분한다. 중단·되돌리기·과거 열람은 서로 다른 행동이다. 상태 축·전이·허용 행동은 SPEC-00-common에서 정한다.

9.4 직접 수정과 이전 결과

호스트 또는 IDE에서 사람이 대상을 직접 바꾸면 관련 변경을 새 기준으로 인식한다. 이전 AI 결과가 그 수정을 자동으로 덮어쓰지 않는다. 원본 입력과 완료된 후보를 보존하며 관련성에 따른 유지·재비교·노후화 동작은 SPEC이 정한다. 무관한 변경 때문에 다른 작업을 불필요하게 멈추지 않는다.

9.5 위임 범위와 확인 경계

사용자가 맡긴 목표·대상·유지 조건·허용 범위 안에서 AI는 자료 읽기·후보 생성·계산·후보 내부 수정을 이어서 진행한다. 사용자는 언제든 진행을 보고 개입할 수 있다. 내부 명령이나 중간 후보마다 반복 승인을 요구하지 않는다.

원본 반영과 외부 공개는 사용자 권한·결정에 따른다. 유지 조건 변경, 범위 확대, 큰 추가 비용을 AI가 조용히 결정하지 않는다. 허용된 공유 범위의 상태 갱신과 공개 범위 확대도 구분한다. 확인 시점의 상세 동작은 SPEC에서 정의하며 전문적인 적합성 판단을 승인 버튼 하나로 대체하지 않는다.

10 / 큰 모델·BIM 문맥과 프로젝트 기억

10.1 전체 데이터와 모델 입력을 분리한다

대량 기하·속성은 원본과 계산·조회 도구가 다루고 LLM에는 목표·필수조건·관계·필요한 결과와 참조를 전달한다. 전체 모델·전체 대화·회의록을 매 요청에 반복 입력하지 않는다. 이런 구조만으로 누락이 없거나 항상 저렴하다고 주장하지 않는다.

10.2 기억의 권한과 수명

세션 교체·압축으로 확정 조건을 잃지 않도록 제품이 관리한다. AI의 기억 제안은 자동으로 확정 조건이 되지 않는다. 대화·실행 엔진 세션·모델 버전을 같은 식별자로 취급하지 않는다.

10.3 이번 요청의 문맥 확인

이번 입력에 포함된 대상·버전·조건·자료·가정을 확인하고 수정할 수 있어야 한다. 매번 복잡한 수동 자료 준비를 요구하지 않는다. 충돌하는 조건은 조용히 덮어쓰지 않고 드러내며, 미확인 관계와 분야는 검토 범위에 남긴다.

10.4 결과 재사용과 갱신

객체가 존재한다는 사실만으로 결과가 유효한 것은 아니다. 지원 작업의 입력·관계·계산 방법·가정·질의 조건·대상 집합이 바뀌면 관련 결과의 유효성을 확인한다. 대상 집합에 새 객체가 추가된 경우도 포함한다.

관련성을 확인하지 못하면 재조회·재계산 범위를 넓히거나 미확인으로 표시한다. 프로젝트 전체를 매번 재계획하는 것과 낡은 결과를 현재 결과로 재사용하는 것을 모두 피한다. 지원하는 의존성의 구체 범위는 SPEC이 정한다.

11 / 품질·검증·시간·비용의 균형

11.1 플랫폼 품질과 전문 품질

자동 검사 통과와 설계적으로 유용한 결과를 구분해 평가한다. 기준 미달 후보도 탐색용으로 보존할 수 있으나 '초안'으로 이름만 바꾸어 완료율을 높게 집계하지 않는다. 전문 법규·구조·도면 품질은 해당 스킬의 별도 범위다.

11.2 후보와 원본의 보호 경계

후보는 현재 설계와 명확히 구분하며 같은 호스트 문서 안에 존재할 수 있다. 원본 반영 승인 전에는 후보 작업이 기존 설계 대상의 형상·속성·관계를 변경해서는 안 된다. 후보 추가로 발생하는 문서 변경과 저장 시 포함 여부를 사용자에게 알린다.

후보 폐기는 해당 후보를 대상으로 하며, 그동안 사람이 직접 수정한 원본을 과거 상태로 되돌리지 않는다. '기존 대상 보호'를 '문서·파일 전체 무변경'으로 표현하지 않는다. 전용 레이어·그룹을 모든 호스트·객체의 유일한 방법으로 강제하지 않으며, 실제 분리·저장·폐기·반영 방식은 SPEC·PLAN에서 정의하고 호스트에서 확인한다.

탐색은 이 경계와 권한 안에서 진행한다. 원본 반영은 사용자가 검토한 변경에 한정하고, 공유·발행은 허용된 자료와 시점을 따른다. 잘못된 대상과 권한 없는 변경은 막지만, 선택적 외관 평가나 미실시 전문 검토 때문에 모든 탐색·입력 저장을 막지 않는다.

11.3 실제 결과에 근거한 표시

정밀 수치와 원본 변경 여부는 모델·계산·실행 결과에 근거한다. 캡처·Vision은 보조 검토이며 전체 기하·속성 확인을 대신하지 않는다.

원본 적용, 파일 저장, 시각 증거, 표·보고서, 웹 공유는 서로 다른 완료 상태다. 쓰기 결과가 불명확하면 성공·실패를 추측하여 다시 쓰지 않는다. 한 호스트의 성공을 다른 호스트의 성공으로 확장하지 않는다. 확인된 적용 뒤 보고서나 공유가 실패했다고 원본 변경을 중복 실행하지 않는다.

11.4 불필요한 반복과 비용

선택·선 그리기·정의된 직접 조절은 불필요한 모델 호출 없이 처리한다. 매 단계에 추가 LLM 감독자·검증자를 붙이지 않고 일반 계산·실행 기록으로 확인 가능한 부분을 활용한다. 새 정보나 진전 없이 같은 오류를 무제한 반복하지 않는다.

작업 준비·대기·검토·수정·실패를 포함한 총부담을 줄인다. 비용을 줄이려고 필수조건이나 결과 품질을 몰래 낮추지 않는다. 예산·정체의 관찰과 동작은 SPEC, 계측·재시도 구현은 PLAN이 소유한다. 측정할 수 없는 비용은 추측한 실제값 대신 미측정으로 표시한다.

12 / 연결·확장·협업·산출물

12.1 네이티브 결과의 의미

지원 객체 종류에 대해 해당 호스트의 네이티브 객체를 생성·수정하고, 호스트 기본 도구로 후속 편집할 수 있어야 한다. 표시용 메시·일반 형상·카테고리 이름만으로 네이티브 성공을 선언하지 않는다.

예를 들어 Revit의 벽을 목표로 한다면 실제 벽의 의미와 선언한 편집 동작이 필요하다. 이 예시는 Revit의 첫 출시 포함을 뜻하지 않는다. 호스트별 객체 종류·필수 속성·수정·저장·재열기 범위는 SPEC 지원표로 선언한다. 모든 유형·파라메트릭 이력을 한꺼번에 지원하지 않는다.

12.2 복수 호스트의 연계와 병렬 실행

복수 연결과 한 작업 범위의 호스트 간 연계를 제공한다. 지원하는 CAD 정보를 다른 호스트의 생성 입력으로 사용하거나, 같은 설계 변경을 도면과 모델의 지정 대상에 반영할 수 있어야 한다. 필요한 대상 대응·좌표·단위·사용 기준을 확인한다.

독립적인 작업은 병렬로 진행하고, 결과에 의존하거나 충돌하는 작업은 필요한 순서를 관리한다. 사용자는 전체 요청과 호스트별 진행·후보·적용 결과를 확인하고 개입할 수 있어야 한다. 현재 화면의 활성 호스트를 모든 실행의 유일 대상으로 취급하지 않는다.

호스트 상태를 IDE로 가져오는 표시 갱신은 원본 변경과 구분한다. 첫 출시는 사용자가 지정한 호스트·문서의 현재 지원 상태를 한 번 읽어 IDE 표시 데이터를 갱신하는 Sync를 제공한다. Sync는 후보의 원본 반영, 다른 호스트의 원본 변경, 네이티브 파일 저장, 외부 공개 승인과 다른 행동이다. 마지막으로 Sync한 대상·기준과 갱신 결과를 확인할 수 있어야 한다.

호스트 변경을 지속적으로 IDE 표시로 반영하는 Live Sync는 후속 목표다. Camera Sync는 현재 제품 목표에서 제외하며, 선택 상태의 자동 동기화도 첫 출시에서 요구하지 않는다. 수동 Sync를 기본으로 하더라도 VIDE가 수행 중인 작업의 진행·개입 상태와 검토 가능한 중간 결과 표시, 사람의 직접 수정 보호 요구는 유지한다. 지원 데이터와 Sync의 실패·재시도·노후화 동작은 SPEC에서, 감지·전달·렌더링 방법은 PLAN에서 정한다.

요청 없는 호스트 간 원본 자동 동기화, 임의 객체의 무손실 변환, 모든 호스트의 일괄 성공·취소·복구는 보장하지 않는다. 일부 성공·실패·결과 불명을 드러내고, 확인된 변경을 중복 적용하지 않으며, 재시도·복구 가능 범위를 알린다.

12.3 작은 확장의 실제 실행

개발자가 제공하는 작은 확장을 등록·실행·비활성화할 수 있어야 한다. 확장은 프로젝트 문맥·입력·허용 도구와 권한·진행·결과·실패를 공통 기반과 연결한다. 빈 슬롯이나 manifest만 있는 것을 완료로 보지 않는다.

공개 마켓·임의의 비신뢰 코드 실행·모든 전문 스킬의 요구를 만족하는 영구 계약을 전제하지 않는다. 실제 전문 스킬의 요구로 계약을 발전시킬 수 있다. 확장 실행 형식·세부 선언과 도구 계약은 SPEC·PLAN에서 정한다. 새로운 호스트 기능이 필요한 스킬은 어댑터의 추가 구현이 필요할 수 있다.

12.4 주요 시점의 검토본과 비교

사용자가 주요 작업 상태를 검토본(체크포인트)으로 남기고, 보존된 모델·도면 표현·관련 표·검토 상태를 다시 열람하거나 현재 상태와 기본 비교할 수 있어야 한다. 검토본은 대상·기준 시점·원본/후보 구분·호스트별 적용/저장 상태를 보존한다.

한쪽은 적용되었고 다른 쪽은 후보인 시점을 기록할 수 있으나, 이를 양쪽이 모두 완료된 상태로 표시하지 않는다. 검토본 열람은 현재 호스트 문서를 변경·자동 복원하지 않는다. 비교는 모든 객체의 자동 의미 분석이나 고급 대안 트리·병합을 뜻하지 않는다. 외부 참여자는 허용된 검토본만 열람한다.

12.5 웹 작업 공간 공유와 의견

로컬 IDE와 공통 화면·표시 기능을 활용하는 웹 작업 공간을 제공한다. 사용자는 공개 범위를 정하고 링크로 공유하며, 권한 있는 참여자는 공유된 모델·도면·표·후보·작업 상태를 탐색한다. 개인의 카메라·선택·패널이 동일할 필요는 없고 발표자 따라보기는 별도 채택 대상이다.

VIDE가 확인한 AI 작업 결과와, 사용자가 호스트에서 직접 수정한 뒤 Sync 등으로 IDE에 확인된 상태는 허용된 공유 대상의 갱신에 포함할 수 있다. 호스트에서 바뀌었지만 IDE에 아직 확인되지 않은 상태를 최신 공유 상태로 표시하지 않는다. 공유에 반영이 완료된 마지막 상태는 로컬 호스트와 연결이 종료된 뒤에도 열람할 수 있어야 한다. 이후 공유 갱신이 완료되면 같은 프로젝트 링크에서 새 상태를 제공한다. 마지막 갱신 시점과 갱신 중·실패·단절을 구분하며, 전송하지 못한 변경을 최신 공유 상태라고 표시하지 않는다. 공유의 전송·보존 동작은 SPEC·PLAN에서 정한다.

참여자는 객체·위치에 문장·핀·스케치를 연결해 의견을 제출한다. 작성 당시 대상·기준 버전·입력 원본을 보존하고, 현재 대상과의 대응이 불명확하면 이를 드러낸다. 제출된 의견은 프로젝트의 기록이며 AI 세션과 독립한다.

의견 제출·설계자의 채택·AI 실행·원본 반영·공개를 구분한다. 실행이나 원본 변경 권한이 의견에 자동으로 부여되지 않는다. 세부 권한과 검토 역할, 입력 환경의 첫 지원 범위는 §14가 정한다.

공유 범위와 접근 권한은 데이터를 제공하고 행동을 처리하는 경계에서 유지한다. 외부 자료가 지시로 오인되어 권한을 높이지 못한다. 작업 PC를 무제한 공개하거나 방화벽 전체 해제를 전제하지 않는다.

12.6 산출물과 별도 파일 내보내기

지원 결과·기본 표·도면 표현·근거를 작업 안에서 확인한다. 기본 조회·집계 결과는 외부 도구에서 재사용할 데이터 파일로 내보내고, 선택한 검토본의 모델·도면 이미지·표·설명·검토 상태를 포함한 요약을 별도 파일로 보관·전달할 수 있어야 한다.

내보낸 결과에 기준 시점·포함 범위·계산 근거·미확인 사항과 형식상 제한을 표시한다. 내보낸 파일은 이후 원본 변경을 자동으로 따라가지 않는다. 웹에서 최신 상태를 보기 위해 사용자가 매번 파일을 내보내야 하는 것은 아니다.

원본 호스트 파일의 저장, 웹 공유, 과거 검토본 열람, 파일 내보내기를 구분한다. 특정 확장자 목록 전부를 지원한다고 해석하지 않으며, 실제 형식과 보존할 데이터·표현 범위는 OQ-08에 따라 SPEC에서 선언한다. 고급 문서 편집기나 모든 형식의 무손실 변환은 요구하지 않는다.

14 / 첫 출시(MVP)의 확정 범위

14.1 호스트와 기본 제어의 완료 수준

첫 출시의 호스트는 Rhino와 ZWCAD다. 두 호스트 모두 SPEC에서 선언한 객체·동작 범위 안에서 문서·객체 읽기, 공간 입력, 네이티브 생성·수정, 결과 확인, 호스트 기본 도구 재편집, 저장·재열기를 제공한다. Revit과 AutoCAD는 후속 확장이다. 한 호스트만 완결한 단계는 내부 alpha이며 두 호스트 MVP의 완료를 대신하지 않는다. 결정 근거는 ADR-001.

복수 연결·호스트 간 연계·독립 작업 병렬 실행을 포함한다(§12.2). WorkScope나 Run을 호스트 문서 하나로 제한하지 않는다. 각 실제 실행의 대상은 명시하며, 전체와 하위 작업의 의존·충돌·부분 결과를 구분한다. 단일 활성 호스트만 제어하는 안은 채택하지 않는다. 근거는 ADR-009.

구체적인 지원 버전·에디션·객체·명령은 OQ-02·03에 따라 선언한다. Revit의 예시나 후속 호스트 파일이 존재한다는 사실로 출시 지원을 확대하지 않는다.

14.3 출시 조건

§13의 MVP 능력이 선언한 환경·객체·동작 범위에서 §15의 적용 AC를 충족해야 한다. §16.4의 대표 과업은 연결된 경험의 검수이며, 개별 필수 기준을 대체하지 않는다. 각 호스트의 실제 네이티브 편집성·저장·재열기, 연계·병렬·부분 실패, 웹·확장·설치를 검수한다.

정확한 대상·권한·사람 수정 보호·중복 적용 방지·불명확 결과 처리에 중대한 위반이 발견되면 해당 쓰기 기능을 출시하지 않는다. 시험 미완료를 통과로, 기능 일부를 전체 완료로 표시하지 않는다.

구현은 작은 기능부터 진행하며 모든 후속 명세·실험·기준선 측정을 첫 구현의 공통 선행조건으로 두지 않는다. 구현 순서와 시험 방법은 PLAN이 소유한다. 목표 미달 시 사용자가 유지·보완·범위 변경을 판단하며, 범위는 자동으로 축소되지 않는다. 첫 호스트만 완료했거나 계획을 조정했다는 이유로 이 절의 약속이 바뀌지 않는다.

14.4 작업자·배포·입력 환경

프로젝트별 한 로컬 작업환경이 호스트 제어와 원본 반영을 담당한다. 한 작업환경에서 Rhino와 ZWCAD의 연계·병렬 작업이 가능하다. 다른 사용자들이 독립 프로젝트에 설치하여 쓰는 것은 제한하지 않되, 같은 프로젝트를 여러 PC에서 공동 제어하는 기능은 후속으로 둔다.

웹은 열람·탐색·의견 작성까지다. AI 작업 시작, 진행 중 개입·중단, 원본 반영 승인은 로컬 IDE에서 수행한다. 설계자 본인이 다른 기기로 접속해도 같다. 코멘트 제출은 실행 요청이 아니며, 로컬 설계자가 검토한 뒤 작업에 연결한다.

개발 소유자와 선정된 소수의 검증 사용자에게 제한 배포한다. 외부 검토자는 권한에 따라 웹에 참여한다. 개발 환경 밖에서도 설치·최초 연결·기본 작업·저장·재개·제거와 자료 보존을 확인한다. 정확한 인원·장비·설치 방법은 선언할 지원 범위와 검수 계획에서 정한다. 제한 배포를 이유로 확정 기능이나 보호 요구를 생략하지 않는다. 사내 전체·불특정 사용자 공개 배포의 운영 범위는 후속이다. 근거는 ADR-002.

로컬 입력은 키보드·마우스가 필수다. 로컬 선택·핀·스케치·검토·제어를 해당 환경에서 제공한다. Windows 펜 입력은 금지가 아니라 필수 지원·검수에서 제외한다. 웹은 선언한 iPad 환경에서 터치 탐색과 펜 스케치를, 지원 Mac·Windows 브라우저에서 키보드·마우스를 제공한다. 펜 없이도 기본 열람·의견 작성이 가능해야 한다. 모든 펜의 필압·기울기·버튼을 보장하지 않는다. 기기·브라우저·동작은 OQ-04에 따라 SPEC에서 정한다.

16 / 성공 지표와 출시 판단

16.1 제품의 주요 성과

핵심은 선언한 기본 제어를 신뢰할 수 있게 수행하면서 채택까지의 총시간과 건축가의 부담을 줄이는 것이다. 낮은 비용·적은 승인·빠른 초안 하나만으로 성공을 판단하지 않는다.

수작업과 에이전트+MCP의 두 기준선 대비 개선 목표를 유지한다. 같은 지원 과업에서 총시간·대상 오인·재작업을 비교한다. 비교는 자동 축소 관문이 아니며 미달 시 사용자가 재결정한다. 기존 ADR-012의 이 원칙을 유지하고, 대표 과업은 §16.4를 따른다.

16.2 비교와 검수의 해석

원본·입력·조건을 맞추고 모델·도구·정보량·예산 차이를 기록한다. 텍스트·핀·스케치 비교에서 정보량 증가와 표현 방식의 효과를 혼동하지 않는다. 성공 시연뿐 아니라 큰 모델·불완전 정보·오래된 참조·충돌·중간 개입·단절도 포함한다.

전문가의 결과 품질과 비전공자의 이해·피드백을 구분한다. 소수 사용자 검수는 실제 사용의 문제를 찾는 것이며 모든 사용자에 대한 우위의 입증으로 확대하지 않는다. 구체적인 모집·판정·반복·대조 방법은 PLAN에서 정한다.

16.3 목표와 필수 기준

규모·품질·시간·비용의 수치 목표는 OQ-05·06에서 남은 결정을 표시한다. 측정 전 숫자를 보장으로 쓰지 않는다. 두 기준선의 범위를 똑같이 재현하지 못하면 차이와 미측정을 드러낸다.

출시 필수 기준은 §14.3다. 목표 미달은 유지·구현 보완·범위 조정의 사용자 판단 자료이며, '검토 필요' 표시를 늘리는 것으로 완성도를 대체하지 않는다. 해당 단계 평가에 필요한 기준선을 준비하되, 후속 전문 스킬의 측정을 모든 초기 구현의 선행조건으로 요구하지 않는다.

16.4 대표 검수 과업

아래 세 가지를 연결된 사용자 경험의 대표 검수 과업으로 채택한다. 플랫폼 범위를 특정 매스 도구나 평면 자동화 앱으로 바꾸는 정의가 아니다. 결정 근거는 ADR-006.

② 도면과 모델의 연계 지원 CAD 정보를 Rhino 후보에 사용하고, 같은 설계 변경을 도면·모델의 지정 대상에 반영하는 흐름을 확인 한 요청의 연계와 호스트별 진행·결과·부분 상태가 식별됨; 독립 작업 병렬과 의존 작업의 순서를 구분

작은 확장의 실제 등록·실행·비활성화와 설치·재개·자료 보존은 별도 필수 검수로 남는다. 대표 과업 통과가 다른 AC의 자동 통과를 뜻하지 않는다.

PRD는 과업과 성공의 의미를 정한다. SPEC은 지원 객체·동작·계산·유지 조건·기대 결과를, PLAN은 시험 모델·장비·순서·반복·허용 오차·검증 방법을 구체화한다. 세 과업 전체를 먼저 준비해야 첫 코드를 쓸 수 있다는 뜻은 아니다.

OQ-01의 CAD 선택은 Rhino·ZWCAD의 첫 출시로 해소되었다(§14.1). OQ-11에서 다뤘던 뷰·갱신 범위는 MVP 수동 Sync, Live Sync 후속 목표, Camera Sync와 선택 상태 자동 동기화 제외로 종결되었다(ADR-004). Sync와 웹 공유 갱신은 서로 다른 상태다. OQ-12의 AI 실행 형태는 PLAN §9의 기술 결정이며 특정 모델·CLI·SDK를 여기서 채택하지 않는다. OQ-13에서 제기된 첫 사용 환경·호스트 집합은 §14.1·§14.4에 반영했고, 상세 개발 순서는 PLAN의 소유다. 이 번호들을 다른 질문에 재사용하지 않는다.

기본 집계의 계산·갱신 범위, 검토본의 보존 자료와 비교 행동, 호스트 간 대상 대응·의존·충돌·부분 실패, 표시 상태의 게시 규칙은 관련 SPEC에서 정한다. DB·라이브러리·전송 형식·실행 큐·저장 구조는 PLAN에서 선택한다. 기능의 세부 지원이 제품 약속을 바꾸어야 하는 경우에만 PRD의 범위 결정으로 돌아간다.

PRD 승인과 구현 완료는 다르다. 이 문서는 2026-09-19까지 사용자와 합의한 제품 약속과 MVP 범위의 기준으로 승인한다. 남은 OQ는 이미 확정된 범위를 뒤집는 미정이 아니라 기능별 지원·행동·검수 범위를 구체화하는 항목이다. SPEC·Design·PLAN은 이 기준을 따라 상세화하며, 구현·시험 완료나 모든 기술 결정의 확정을 의미하지 않는다. 기능의 세부 지원이 제품 약속을 바꾸어야 하는 경우에만 PRD의 범위 결정으로 돌아간다.
