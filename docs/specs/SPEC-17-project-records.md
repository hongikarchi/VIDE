# 프로젝트 기록 — 결정·이력·영향

근거: 2026-10-15 사용자 결정(PRD §4.4 **C-09**, [RESEARCH-17](../research/RESEARCH-17-workspace-and-records.md) §2, [PLAN-53](../plans/PLAN-53-project-records.md)). 프로젝트의 결정·근거·영향을 시간과 건물 부위 위에 놓아 "이 객체는 왜 이 모양인가"로 거슬러 가게 한다 — 사용자의 말로 "진정한 의미의 BIM". 이 명세는 **기록의 의미·유형·부위·연결·권한·실패**를 소유한다. 저장 표·API·사본의 경로 모양은 [ARCH-01](../architecture/ARCH-01-system.md)이, 구현 순서와 검증은 PLAN-53이, 화면 표현은 Design.md의 해당 SCR이 소유한다. 제품 약속은 아직 후보(C-09)이므로 이 문서는 FR을 새로 만들지 않고, 각 항이 기대는 기존 FR을 인용한다(AI.md §7).

지금 VIDE가 가진 것은 앞으로 가는 추적뿐이다 — 요청 → 바뀐 객체(SPEC-02.13, ADR-027), 검토본 비교(SPEC-03.6), 사실·추정·결정 문장(SPEC-08), 설정값 이력(SPEC-07.6), 노트·일지(SPEC-10). 기록은 이것들을 **대신하지 않고 가리킨다**. 기록을 지워도 요청·객체·노트는 그대로다.

## 1. 기록이란 — SPEC-17.1

- **기록(record)** 은 날짜가 있는 **한 문장**이다: 누가 언제 무엇을 요구했고(요구), 설계자가 무엇을 원했고(의도), 그 부위를 얼마나 알았고(앎), 무엇을 확인했고(근거), 그래서 무엇을 정했는지(결정). 한 기록은 출처·유형·부위·본문·이어진 기록을 가진다(2).
- **목적.** 객체를 고르면 그 객체를 이렇게 만든 결정과 그 결정을 부른 요구·근거까지 거슬러 읽을 수 있고(SPEC-03.8의 "대상에서 근거로"), 부위×시간 차트와 모델 위 타임라인으로 프로젝트의 판단 흐름을 한눈에 본다(4·5).
- **범위 밖.** 기록을 고치면 형상이 따라 바뀌는 기능(그것은 C-03 편집 가능한 작업 이력의 영역), 기록으로 AI가 무엇을 자동 적용하는 일(PRD 비목표, FR-18), 노트·요청·검토본을 기록으로 대체하는 일, 사이트에서 기록을 편집하는 일(6).

**수용 결과:** 뷰포트에서 객체 하나를 고르면 '이 객체의 기록'에 그 객체를 바꾼 요청의 결정 기록과 그 부위의 요구·근거 기록이 시간순으로 보이고, 하나를 누르면 그 요청 카드·노트·검토본으로 간다.

## 2. 기록의 의미 모델 — SPEC-17.2

| 항목 | 뜻 | 허용 값 |
|---|---|---|
| `date` | 기록이 **생긴** 날(시각은 선택). 가져온 원문은 원문의 날짜, VIDE 안 활동은 그 활동의 시각 | 날짜, 선택 시각 |
| `source` | 어디서 왔나 | `request`(요청 실행) · `chat`(대화 문장) · `note`(노트) · `journal`(일지) · `meeting`(회의록) · `sync`(동기화) · `jig`(jig 실행·설정값 변경) · `checkout`(체크아웃·서버에 반영<ins>·폴더 역할 확정 — 작업 폴더 활동</ins>) · `kakao` · `mail` · `site-report`(현장 보고) · `manual`(사람이 직접 적음) |
| `type` | 기록의 성격 다섯 가지(RESEARCH-17 §2) | **R 요구** — 법·행정·건축주·이웃·브리프가 요구한 것 · **I 의도** — 설계자가 원한 것 · **K 앎** — 그 부위를 얼마나 알았나(도면 없음, 열어 봄, 실측함) · **E 근거** — 실측·개구·구조 검토·계산·법규 체크처럼 확인된 것 · **D 결정** — 부위의 역할·사양·형상이 바뀐 결정. 유형 미정(`?`)은 자동 후보에만 허용되며 사람이 거르면서 정한다 |
| `parts[]` | 어느 부위 이야기인가 | 부위 사전(아래)의 항목 id. 비어 있을 수 있다('부위 없음'으로 보인다) |
| `text` | 본문 한 문장(길면 펼쳐 전체) | 자유 글. 가져온 원문은 원문 그대로, 요청은 요청 문장 |
| `follows[]` | 이 기록이 **불러온** 뒤 기록 | 같은 프로젝트의 기록 id. 앞 → 뒤 한 방향이며 순환은 거부한다. 체인은 들어오는 선이 없는 뿌리부터의 도달 집합이다 |
| `attachments` | 가리키는 것 | 요청 id(바뀐 객체는 요청에서 읽음, SPEC-02.13), 검토본 id(SPEC-03.6), 노트·일지 위치(SPEC-10), jig 인스턴스·설정값 이력(SPEC-07.6), 가져온 원문의 파일과 줄 번호 |
| `state` | 사람이 보았나 | `candidate`(자동 후보, 아직 안 봄) · `kept`(O, 기록으로 둠) · `dropped`(X, 집계 제외) |
| `by` | 누가 적었나 | `ai`(자동 후보·AI 분류 제안) · 사람(계정, SPEC-01.14 12의 작성자 규칙과 같음). AI가 적은 것은 사람이 `kept`로 바꾸기 전까지 'AI 제안'이다 |
| `chapter` | 프로젝트별 선택 분류(예: 우회·보강·교체·대비) | 프로젝트가 정한 목록 중 하나 또는 비움. 기본 목록은 없다 |

- **부위 사전.** 프로젝트마다 사람이 만드는 부위 목록 `{id, 이름, 그룹(신설·기존 등), 역할 문장(시작 → 끝), 매핑}`. 매핑은 연결 파일의 레이어·객체군·jig 결과 단위(SPEC-07.5)이며, 레이어 이름이 바뀌어 닿지 않으면 '끊김'으로 표시하고 숨기지 않는다. 부위는 SPEC-08의 자료 주제와 별개다(자료는 찾은 사실, 기록은 판단).
- **마일스톤.** `{label, date}` 프로젝트당 목록(당선·납품·착공·사용승인 등). 사람이 적고 차트·타임라인의 눈금이 된다.
- **덧붙이기만 한다.** 기록은 지우지 않고 `dropped`로 뺀다. 본문·유형을 고치면 고친 사람과 시각이 남고, 뜻이 달라지는 정정은 새 기록을 만들어 옛 기록이 `follows`로 가리키게 한다(옛 기록은 '정정됨' 표시).

## 3. 자동 기록과 거르기 — SPEC-17.3

1. **자동 후보.** 다음 활동이 끝나면 VIDE가 `candidate` 기록을 만든다. 후보는 차트·타임라인의 기본 보기에 나오지 않고 거르기 화면에만 쌓인다. 만드는 일은 요청 처리 뒤 비동기이며 요청 시간을 늘리지 않는다.
   | 활동 | 유형 | 본문·부위 |
   |---|---|---|
   | 요청 실행 완료(SPEC-02.13) | 바뀐 객체가 있으면 **D**, 읽기·검토만이면 **E** | 요청 문장; 바뀐 객체의 레이어가 부위 사전에 매핑돼 있으면 그 부위, 아니면 비움 |
   | 대화의 결정 문장(AI가 '…로 하기로' 응답, 사람이 "결정·확정·…로 가자") | **D** | 그 턴의 문장. 규칙 기반이며 판정 모델 보강은 뒤 |
   | 노트·일지·회의록 저장(SPEC-10) | 미정 `?` | 문단 단위, 하루 30건 상한. 사람이 유형을 고른다 |
   | jig 설정값 변경(SPEC-07.6의 누가·왜) | **D** | 바뀐 설정값과 이유; 부위는 jig 결과 단위 매핑 |
   | 동기화·체크아웃·[서버에 반영]·스키마 확정(SPEC-01.13 8~9) | **K** | 어느 파일을 열어 보았나·어느 판을 올렸나 |
   | 법규 체크·구조 검토 같은 jig의 확정 결과(SPEC-15, SPEC-06) | **E** | 결과 요약 한 줄; 상세는 attachments |
   | 갱신 제안 카드의 [적용]·[무시](SPEC-05.12) | **D** | 어느 동기화 쌍·몇 행·적용인지 무시인지. [적용]이 요청 실행으로 이어지면 그 요청 실행 행과 합쳐 한 건(4) |
   | 자료 진술에서 사람이 [기록으로 남기기]를 누름(SPEC-08.5) | **E** | 진술 문장; attachments에 진술 번호. 자료 확정만으로는 만들지 않는다 |

> **[검토 · claude · R-47 · 중간]** 표 다섯째 행의 '동기화' K 후보는 웨이브 1에서 만들어지지 않는다. 문서 Sync는 요청 완료 경로를 지나지 않고 따로 저장되기 때문이다(ARCH-01 §5 「프로젝트 기록」 자동 후보 진입점). 수동·자동·Live Sync를 모두 후보로 만들면 하루에 수십 건이 쌓일 수 있다. 제안: '동기화는 연결 파일마다 하루 1건(그날 첫 Sync)'처럼 넘침 조건을 이 행에 적은 뒤 PLAN-53 후속 작업에서 연결한다. 또는 웨이브 1 범위에서 동기화를 빼고 체크아웃·[서버에 반영]·스키마 확정만 둔다. 표 일곱째·여덟째 행(갱신 제안 카드, 자료 [기록으로 남기기])도 PLAN-53에 아직 티켓이 없다(PLAN-53 「현재 상태」). 사용자 결정 항목.
<!-- claude-review:end -->

2. **AI 분류는 제안이다.** 유형·부위의 자동 값은 SPEC-08.7의 출처 구분과 같이 'AI 제안'으로 표시하고, 사람이 `kept`로 바꾸기 전에는 사실로 쓰지 않는다. AI는 기록을 `kept`로 바꾸지 못한다(7).
3. **거르기(O/X).** 거르기 화면은 후보를 날짜·출처·본문 한 줄로 늘어놓고, 사람이 **O**(둔다, `kept`) · **X**(뺀다, `dropped`) · 지움(미표시로 되돌림)으로 거른다. 거르면서 유형(R/I/K/E/D)·부위·앞뒤 연결(`follows`)을 고르거나 고친다. 보이는 것 전체에 한 번에 O/X를 줄 수 있다. 거른 결과는 한 글자 한 건의 `o/x/.` 문자열과 JSONL로 내보내고 다시 들일 수 있다(같은 수의 후보에만 적용).
4. **중복.** 같은 요청·같은 노트 문단·같은 원문 줄에서 후보를 두 번 만들지 않는다. 한 행동이 두 행에 걸리면(예: 갱신 제안의 [적용]과 그 요청 실행 완료) 후보는 한 건이고 본문에 두 출처를 함께 적는다. 되돌린 요청의 후보는 지우지 않고 '되돌림' 표시가 붙는다(SPEC-02.13의 되돌리기 기록과 같다).
5. **가져오기(PLAN-53 웨이브 2).** 카카오톡 내보내기(`.txt`)와 메일(`.eml`·`.mbox`)은 줄·통 단위 후보가 되고 유형은 미정이다. 원문 파일은 작업 폴더의 운영 역할 아래 기록 원문 위치에 복사하고 attachments가 파일·줄을 가리킨다. 같은 파일·같은 줄은 두 번 들이지 않는다. 자동 O/X는 하지 않고, 질문문·결정 어휘·부위 사전 단어가 있는 줄을 앞에 보이는 도움만 준다.

> **[검토 · claude · R-84 · 낮음]** 웨이브 2 구현은 카카오톡을 **메시지 단위**로 나눈다 — 형식에 맞지 않는 다음 줄은 앞 메시지에 붙고 줄 번호는 첫 줄이다(`src/core/import/kakao.ts`). 메일은 `Date` 머리가 없거나 읽지 못하면 날짜만 가져온 날로 두고 시각은 비운다(ARCH-01 '가져오기' 파서 항목). 제안: <del>줄·통 단위 후보</del><ins>메시지·통 단위 후보</ins>로 고친다.

**수용 결과:** 합성 프로젝트에서 요청 10건·노트 5건·설정값 변경 3건을 만들면 후보 18건 안팎이 쌓이고(중복 0), 거르기 화면에서 키로 100건을 10분 안에 O/X 할 수 있으며, 내보낸 `o/x/.` 문자열을 다시 들이면 같은 상태가 된다.

## 4. 부위×시간 차트 — SPEC-17.4

- **무엇을 보이나.** 가로는 시간(월 격자·마일스톤), 세로 행은 **부위**(기본) 또는 **유형 다섯** 또는 **장**으로 바꿀 수 있다. 기록은 유형별 표식(R·I·K·E·D 각각 다른 모양, 색은 하나)으로 놓이고, `follows`는 연결선, 기존 부위는 '열어 본 날'(첫 K 기록) 전은 점선·후는 실선, 아래에 날짜별 기록 수의 밀도 띠가 붙는다.
- **거르기.** 유형 다섯 토글(건수 표시), 출처, 작성자(AI 제안 포함 여부), 상태(기본은 `kept`만; 후보는 켜야 보인다), 장.

<!-- claude-review:start -->
> **[검토 · claude · R-82 · 낮음]** '작성자(AI 제안 포함 여부)' 거르기는 SCR-44 칩(Design SCR-44 왼쪽 열: 유형·출처·부위·상태·기간), 목록 API(`GET /records` 거르기), 차트 스위치(`src/ui/records-chart.tsx`) 어디에도 없다. 제안: 이 낱말을 빼거나, 상태 거르기의 '후보'(AI 제안은 늘 후보로 들어옴)로 갈음한다고 적는다. 필요하면 PLAN-53 후속 티켓으로 둔다.
<!-- claude-review:end -->
- **고르기.** 표식 위에 올리면 본문 풍선, 누르면 그 기록이 속한 **체인**만 진하게 남고 나머지는 흐려진다. 체인의 뿌리(들어오는 선이 없는 기록)에서 끝까지가 "한 결정의 이야기"다. 기록을 누르면 attachments의 요청 카드·노트·검토본으로 갈 수 있다.
- **인쇄.** 넓은 판과 번호 색인(번호·날짜·부위·유형·본문)을 함께 낸다(SPEC-03.6의 검토본 인쇄 규칙과 같은 등급 — 내부 ID 없음).
- **하지 않는 것.** 차트에서 형상·요청·노트를 고치지 않는다. 차트는 기록의 `state`·`parts`·`follows`만 바꿀 수 있고(거르기와 같은 권한), 그 밖은 읽기 전용이다.

<!-- claude-review:start -->
> **[검토 · claude · R-83 · 낮음]** 웨이브 2 구현은 차트 자체를 읽기 전용으로 두고, 글리프를 누르면 목록의 자세히 칸을 연다(Design SCR-45 '고르기와 고치기'). 그 칸에서는 본문 고치기·정정도 되므로 글자 그대로는 이 문장과 다르다. 제안: <del>차트는 기록의 `state`·`parts`·`follows`만 바꿀 수 있고(거르기와 같은 권한), 그 밖은 읽기 전용이다</del><ins>차트 자체는 읽기 전용이고, 고르면 열리는 자세히 칸에서 목록과 같은 권한으로 고친다</ins>.
<!-- claude-review:end -->

**수용 결과:** 기록 200건·부위 15개를 한 화면에서 읽고, 결정 하나를 누르면 그것을 부른 요구·근거와 그 뒤의 결정이 선으로 이어진 체인만 남는다. 같은 입력은 항상 같은 배치다.

## 5. 모델 위 타임라인 — SPEC-17.5

- **부위와 형상.** 열린 연결의 최신 동기화(SPEC-07.5의 7)에서 부위 사전의 매핑으로 객체를 부위별 묶음으로 나눈다. 매핑되지 않은 객체는 '그 밖' 묶음으로 흐리게 보인다. 좌표를 다시 풀지 않고 표시 형상의 id 목록만 다룬다(ARCH-01의 `lazy` 독자 규칙).
- **커서.** 뷰포트 아래 가로 타임라인(행 = 부위)에 커서 하나가 있다. 커서를 끌거나 재생하면 그 날짜까지 `kept` 기록이 있는 부위는 켜지고(불투명) 없는 부위는 흐리며, 커서 앞뒤 60일 안의 기록은 라벨이 뜬다. 에피소드(장 또는 체인)를 고르면 그 체인의 부위만 켜지고 연결선이 이어진다. 신설/기존 분리 보기, 전부 보기 토글이 있다.
- **그 시점의 모델.** 커서 날짜에 검토본(SPEC-03.6)이나 동기화 기록이 있으면 그 시점의 형상을 겹쳐 보이고, 없으면 가장 가까운 **이전** 시점의 것을 보이며 '○월 ○일 검토본 기준'이라고 적는다. 시점 형상이 하나도 없으면 현재 모델 위에 부위만 켠다.
- **객체에서 기록으로.** 뷰포트·호스트에서 객체를 고르면 인스펙터의 '이 객체의 기록'(1)으로 이어진다 — 그 객체를 바꾼 요청의 기록(요청 결과의 추가·변경·삭제 목록 → 객체 id → 요청 id 역색인, 여러 파일의 객체 id 충돌 없음 ADR-027)과 그 객체의 레이어가 매핑된 부위의 기록을 시간순으로.
- **하지 않는 것.** 타임라인은 호스트 문서를 고치지 않는다. 검토본을 겹쳐 보는 것은 기존 비교 화면(SPEC-03.6)을 그대로 쓴다.

**수용 결과:** 커서를 끌면 그 시점에 이야기가 있는 부위가 켜지고 "이때 이 부위가 왜 이렇게 됐는지"를 기록에서 읽는다. 커서 이동 응답은 100 ms 안이다.

## 6. 저장·사본·공유 — SPEC-17.6

- **정본은 프로젝트 DB.** 기록·연결·부위 사전·마일스톤은 이 PC의 프로젝트 DB에 있다(표·열은 ARCH-01 §5). 본문 검색은 기록 자체의 색인으로 하며 SPEC-08 자료 검색과 섞지 않는다.
- **사람용 사본.** 작업 폴더(SPEC-01.13 7, ADR-042)가 있으면 **운영 역할 폴더 아래의 기록 경로**에 월별 JSONL과 사람이 읽는 `README.md`(부위 사전·마일스톤·장)를 쓴다(경로 모양은 ARCH-01). 사본은 DB에서 언제든 다시 만들 수 있다. 사본을 사람이 고치면 다음 열기 때 '사본이 달라졌어요' 카드로 들일지 묻는다(PLAN-52의 사본 규칙). 작업 폴더가 없거나 쓰지 못하면 DB에만 두고 '폴더에 아직 안 씀'을 보인다.
- **가져온 원문은 이 PC에만.** 카카오톡·메일 원문과 그 후보는 사이트(D1)에 올리지 않고, 진단 묶음·AI 문맥·공유 사이트 업로드·검수 증거에서 뺀다(ADR-037 4의 모델링 대화 미업로드와 같은 경계).
- **팀 공유.** 공유 프로젝트(ADR-037)에서는 **거른 기록(`kept`)의 본문·유형·부위·날짜만** 올릴지 프로젝트 설정으로 정하며 기본은 끔이다. 켜도 후보·`dropped`·원문·attachments의 파일 내용은 올리지 않는다. 올리는 경로는 노트와 같다(SPEC-10). 다른 PC는 올라온 기록을 읽기만 한다.
- **원격 세션.** 원격 세션(SPEC-04)은 차트·타임라인·목록을 보기만 하고 거르기·고치기는 하지 못한다.
- **프로젝트 삭제.** 프로젝트를 지우면 그 기록과 사본 쓰기 작업도 지운다(SPEC-01.1). 작업 폴더의 사본 파일은 폴더 규칙을 따른다(VIDE가 사용자 폴더의 파일을 지우지 않는다).

## 7. 권한·실패 — SPEC-17.7

- **누가.** 프로젝트 구성원은 모두 기록을 보고, 후보를 거르고, 적고, 부위 사전과 마일스톤을 고친다(SPEC-10.2의 노트와 같은 넓이). 열람자 역할은 보기만 한다. 작성자는 SPEC-01.14 12의 규칙으로 남는다.

- **AI는.** 후보를 만들고 유형·부위를 **제안**만 한다. `kept`·`dropped`로 바꾸지 못하고, 사람이 `kept`로 둔 기록의 본문을 고치지 못한다. 대화의 AI가 "기록으로 남겨 줘"를 받으면 `candidate`를 만들고 거르기 화면으로 안내한다(FR-18의 실행 권한 구분).
- **실패와 표시.**
  | 상황 | 동작 |
  |---|---|
  | 작업 폴더 없음·쓰기 불가 | DB에만 저장, '폴더에 아직 안 씀' |
  | 부위 매핑의 레이어가 사라짐 | 기록은 그대로, 부위에 '끊김' 표시, 다시 잇기 제공 |
  | 연결 파일이 닫혀 있어 객체를 찾을 수 없음 | '이 객체의 기록'은 보이되 형상 강조는 '연결이 닫혀 있어 표시 못 함' |
  | 같은 원문을 두 번 들임 | 두 번째는 거부하고 첫 번째 위치를 알림(`RECORD_SOURCE_DUPLICATE`) |
  | 원문 파일이 없어짐 | 기록은 남고 attachments가 '원문 없음'으로 보임 |
  | 순환 연결 시도 | 거부(`RECORD_LINK_CYCLE`) |
  | 원격 세션의 쓰기 | 거부(SPEC-00의 원격 쓰기 규칙) |

## 8. 수용 결과 — SPEC-17.8

1. **웨이브 1.** 합성 프로젝트에서 요청·노트·설정값 변경으로 후보가 중복 없이 쌓이고, 거르기 화면에서 100건을 10분 안에 O/X 하며, 객체를 골라 '이 객체의 기록' → 요청 문장까지 두 번 눌러 간다.
2. **웨이브 2.** 합성 카카오톡·메일을 들여 거르고 부위에 묶은 뒤 부위·유형·장 세 행 모드의 차트와 인쇄 보기가 나오고, 기록 1,000건에서 첫 그리기가 1초 안이다. 원문은 사이트·진단 묶음에 없다.
3. **웨이브 3.** 커서를 끌면 시점의 부위가 켜지고 검토본이 있는 날에는 그 시점 형상이 겹치며, 커서 응답이 100 ms 안이다.
4. **사용자 동승.** 사용자가 실제 프로젝트의 기록을 직접 들여 거르고 차트·타임라인을 본 뒤 "내가 아는 그 프로젝트의 결정 흐름과 같다"고 판정한다(PLAN-53 T-338). 에이전트는 원문을 읽지 않는다.

## 9. 이 명세 범위 밖

기록에서 형상을 바꾸는 일, 사이트에서 기록 편집, 판정 모델로 유형을 자동 확정하는 일, 외부 협업 도구(Notion·Slack 등) 연동, 기록의 버전 비교. 파일 사이의 관계(xref·동기화 쌍·jig 입력→결과)는 파일 지도(SPEC-01.13 7~9, PLAN-52)가 소유하며, 기록은 뒤에 파일 지도의 같은 파일 노드에 붙는다.
