작동 안정성 점검 — 엔진 꺼짐·Sync 실패·멈춤의 코드 원인

2026-10-01 사용자 요청: "엔진이 중간에 꺼지는 원인 분석", "꺼지거나 sync가 터지거나 작동을 멈추는 문제를 코드 단위로 분석". 설치본 0.2.12(792e31d)와 저장소 HEAD(d733f52)를 읽고, 이 PC의 기록(엔진 로그, WebView Breadcrumbs·Crashpad, Velopack 로그, Windows 이벤트)과 사용자 DB 사본으로 측정했다. 원본 데이터·실행 중인 엔진·Rhino는 건드리지 않았다. 사실(검증)과 추정을 구분해 적는다.

01 / 엔진이 꺼지는 경우

1.1 기록으로 본 사실

  • 09-29~10-01 사이 엔진이 정리 기록(engine-stop) 없이 끝난 것이 8번이다. 7번은 VIDE 창(VIDE.exe)이 살아 있는 채 엔진(node.exe)만 죽고 셸이 다시 띄웠다(09-29 15:18, 09-30 08:29·08:51·08:59·15:54, 10-01 08:29·08:33 KST). 1번은 업데이트 자동 적용이 죽였다(09-30 08:01, 1.3).
  • 7번 모두 engine-crash, 엔진 오류 출력 로그(logs/engine-stderr-*.log), Windows 오류 이벤트, 덤프가 없다.
  • 이 PC의 node.exe는 네이티브 충돌(스택 넘침, abort)에서도 Windows 오류 이벤트·덤프를 남기지 않는다(설치본 런타임으로 실측). 반대로 JS 예외·처리 안 된 rejection·V8 메모리 한계는 반드시 stderr에 출력하고, 앞의 둘은 engine-crash도 동기 기록한다. 셸은 stderr를 파일로 남기는데 파일이 한 번도 생기지 않았다. 따라서 원인은 JS 오류나 메모리 한계가 아니라, 네이티브 충돌 또는 외부 강제 종료다.
  • 셸·화면·플러그인에 "응답이 느린 엔진을 죽이는" 코드는 없다. 이 PC의 에이전트 기록에도 그 시각 47821 엔진을 죽인 명령은 없다.
  • 7번 중 5번은 큰 문서(10,086개, 표시 78 MB)의 연결 직후나 수 초짜리 Live Sync 직후 몇 분 안에 일어났다. 3번은 한가한 때였다.

1.2 가능성 순위(추정)

순위 원인 근거
1 node.exe 안의 네이티브 충돌(Rust 구조 해석 코어, node:sqlite의 큰 행, V8) 흔적 없음과 일치, 큰 Sync·Live Sync 직후 집중
2 다른 도구의 강제 종료 흔적 없음과 일치하나 기록상 명령 없음
3 콘솔 제어 이벤트 가능성 낮음

종료 코드가 둘을 가른다(0xC0000005 등 = 네이티브 충돌, 1 = taskkill, 0xFFFFFFFF = 강제 종료). 셸은 종료 코드를 이미 구하지만 버린다(src/desktop/shell/Engine.cs SafeExitCode). 다음 배포의 첫 진단 항목이다.

1.3 확인된 별도 원인

  • 업데이트 자동 적용이 실행 중인 엔진을 죽인다: Program.cs가 단일 실행 확인(Mutex) 전에 VelopackApp.Build().Run()을 부른다. 받아 둔 업데이트가 있으면 두 번째 실행(바로가기, Rhino 패널의 "VIDE 실행")이 실행 중인 VIDE.exe와 node.exe를 강제 종료한다(Velopack 로그 09-30 08:01:44 "Killing process … node.exe"). 업데이트 공급처가 저장소의 .vide/releases/installer라서 로컬에서 설치 파일을 만들 때마다 무장된다.
  • 셸 재시작 횟수가 초기화되지 않는다: ShellContext.cs의 restarts는 늘기만 한다. VIDE를 켜 둔 동안 엔진이 네 번째 죽으면 다시 띄우지 않고 "작업 엔진이 계속 종료됩니다"에서 멈춘다(09-30 오전에 실제로 소진).

02 / Sync가 터지거나 느린 원인

  • 같은 Sync를 여러 화면이 동시에 한다: 데스크톱 창과 Rhino 패널(브라우저 탭·원격 기기도)이 각자 연결 파일을 감시하고 각자 Sync·Live Sync를 보낸다. 엔진은 같은 문서의 동시 요청을 하나로 합치지 않는다. 실제 DB에 3초 안에 만든 78 MB Sync 세 벌이 두 번 있고(연결 한 번에 약 235 MB 증가), Live Sync는 1.5초 간격 쌍으로 기록된다.
  • Live Sync 한 번에 결과 전체를 다시 쓴다: 변경 객체가 하나여도 기준 Sync 전체(78~112 MB)를 읽어 파싱·검증·직렬화·저장·재파싱한다(엔진 주 스레드에서 약 1.5초, 일시 할당 약 1 GB). 화면 수만큼 반복된다. 기록상 Live Sync가 5~6.3초 걸린 적이 있다.
  • 결과가 계속 쌓이고 지워지지 않는다: 전체 Sync마다 78~112 MB 행이 새로 생기고, 기준이 참조 중이면 Live Sync도 새 사본을 만든다. 프로젝트 삭제·파일 빼기 말고는 지우지 않는다. 오늘 DB는 903 MB(결과 845 MB, 53행)다.
  • 크기에 비례해 느려지는 경로: 프로젝트 전체 결과 파싱(570 MB 프로젝트에서 1.8초·힙 1.6 GB), 고정 객체마다 기준 Sync 전체 파싱(5개에 3.1초), 15초마다의 heartbeat가 결과 표 전체를 훑음(0.45초), 엔진 재시작 뒤 첫 목록(1.9초).
  • 크기 상한에 가까움: 한 Sync의 상한이 128 MB인데 가장 큰 결과가 이미 111.8 MB다. 모델이 15~20% 커지면 전체 Sync가 계속 실패한다(추정).
  • 편집 중 Sync가 실패한다: 전체 Sync는 여러 페이지로 읽는데, 그 사이 Rhino에서 편집하면 SOURCE_CHANGED로 실패하고 다시 시도하지 않는다. AI가 문서를 고치는 중에도 Sync·Live Sync가 기다리지 않는다.
  • Live Sync "곧 다시 Sync"가 다시 오지 않는다: 재시도 응답을 받아도 다시 시도하지 않아 다음 편집까지 화면이 멈춘 상태로 남는다.

03 / 화면이 멈추거나 꺼지는 원인

  • 화면 프로세스가 죽으면 복구하지 않는다: 데스크톱 셸에 WebView2 ProcessFailed 처리가 없어 "Out of Memory" 페이지가 그대로 남는다(09-30 실제). Rhino 패널도 같다.
  • Sync 결과가 화면 메모리에 쌓인다: 불러온 전체 결과를 버리지 않아 전체 Sync마다 JS 힙이 약 78 MB씩 는다(합성 10,086개 모델로 실측: 145 → 455 MB, 5회). 프로젝트를 바꿀 때만 풀린다.
  • Rhino 패널이 보이지 않는 3D 장면을 만든다: 패널은 3D 화면이 없는데도 전체 결과를 받아 메시를 만든다(열자마자 284 MB, 변경 한 번에 442 MB).
  • 주 스레드 작업: 전체 Sync 응답을 JSON으로 받아 검증·복사(첫 Sync 1.2초, 이후 0.5초 멈춤), Live Sync마다 모든 그리기 묶음 재구성(0.3초), 많이 선택했을 때 선택 계산이 제곱으로 늘어남(전체 선택 시 키 입력마다 0.65초).
  • 멈춘 채 남는 상태: 작업 상태 확인이 한 번 실패하면 영영 다시 묻지 않아 "AI 작업 중"과 그 파일의 자동 Sync 보류가 남는다. 요청에 시간 제한이 없고, 한 파일의 Sync가 끝날 때까지 다른 파일 감시가 모두 멈춘다.

04 / Rhino·ZWCAD 쪽

  • AI 코드가 Rhino UI 스레드에서 시간·반복 제한 없이 실행된다. 무한 반복이면 Rhino가 멈추고, 스택 넘침이면 Rhino가 꺼져 저장 안 한 작업이 사라진다. ZWCAD도 같다.
  • 10,086개 Sync가 Rhino UI 스레드에서 8~10초 걸린다(대부분 UI 스레드 작업, 추정). 화면이 여럿이면 배로 는다.
  • ZWCAD: 60초 시간 초과로 실패를 알린 쓰기가 나중에 실행될 수 있다(재시도하면 두 번).
  • Rhino 플러그인은 한 창에 문서 하나만 연결한다(두 번째 연결이 첫 연결을 끊음).

05 / 프로세스를 죽일 수 있는 JS 경로(이번 꺼짐과는 별개)

  • cloudflared·jig 실행 자식 프로세스에 error 처리가 없어, 실행 실패나 죽어 가는 자식에 쓰기가 엔진을 끝낸다(재현됨). 이 경우는 engine-crash가 남으므로 이번 7번과는 다르다.
  • unhandledRejection 안전망이 없고, 실행 완료 처리 등 몇 곳의 rejection이 처리되지 않을 수 있다.
  • Rust 구조 해석 코어가 일부 경로(구조 초안·편집의 안정성 검사)에서 엔진 주 스레드로 직접 불린다. 코어의 오류는 엔진을 흔적 없이 끝낸다(1.2의 1순위 후보).

06 / 고칠 순서(제안)

묶음 내용 효과
P0 진단 셸이 엔진 종료 코드·가동 시간을 logs/engine-exits.jsonl과 안내 문구에 남김. 엔진이 1분마다 메모리·이벤트 루프 지연을 기록하고 1초 넘는 작업을 크기와 함께 기록. Rhino 연결·구조 해석 실행 기록 다음 꺼짐의 원인을 확정
P0 복구 WebView2 ProcessFailed 시 다시 불러오기(데스크톱·Rhino 패널). 셸 재시작 횟수를 10분 정상 가동 뒤 초기화. 업데이트 자동 적용으로 실행 중인 엔진을 죽이지 않음 꺼진 채 남지 않음

P1 메모리 화면에 보이지 않는 Sync의 형상 버림. 패널은 3D 장면을 만들지 않음. 전체 Sync 응답을 요약으로 받고 형상은 바이너리로 화면 OOM 방지
P1 멈춘 상태 작업 상태 확인 재시도, Live Sync 재시도, 요청 시간 제한, 파일별 Sync 진행 "작동을 멈춤" 해소

P2 저장 구조 Live Sync가 바뀐 객체만 저장, 오래된 표시 Sync 정리(파일별 최근 몇 개와 참조된 것만), heartbeat 색인, 프로젝트 전체 파싱을 SQL 조회로 쓸수록 느려지는 문제 해소

P0은 기존 동작을 바꾸지 않는 진단·복구다. P1 중 "Rhino 패널은 자동 Sync를 하지 않음"과 오래된 Sync 정리는 SPEC-01.11의 Sync 규칙에 닿으므로 착수 때 SPEC을 먼저 고친다.
