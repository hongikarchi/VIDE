구조 분석 jig(J-09) 자산 통합 조사

01 / 목적과 범위

J-09 구조 분석 jig를 만들기 위해, 지금까지 수행한 구조 자동화 자산을 한곳에 모으고 무엇을 가져오고 무엇을 새로 만들지 판단 근거를 정리한다. RESEARCH-04 J-09 절은 이전 프로젝트(S-05·S-06·S-08·S-10·S-13)만 다뤘다. 이 문서는 가장 깊이 진행한 철골 구조 자동화 프로젝트(S-18)를 추가하고, 이전 자산을 실제 파일로 다시 대조한 결과를 합친다.

  • 조사일: 2026-09-29. 방법: 파일 메타데이터 수집 → Jev 폴더 분류(1차 필터) → 읽기 전용 코드·문서 조사 4갈래. 스크립트·서버·호스트는 실행하지 않았다. 따라서 이 문서의 수치는 각 출처가 남긴 로그·결과 파일의 기록이며 이번에 재현한 값이 아니다.
  • 출처는 코드로만 적는다(AI.md §8). S-01~S-17은 RESEARCH-04 표를 따른다. 새 출처는 다음과 같다.
코드 형태 내용 시기
S-18 공유 드라이브 프로젝트 폴더(약 1.97만 파일, 37 GB) P-2603 — 단층(일부 2층) 철골 공장. 배치 계획과 철골 구조 자동화를 Claude·Codex가 병행 수행 2026-07~09

02 / S-18 폴더 분류 — Jev 1차 분류와 폴더 안내 대조

폴더 284개(3단계 깊이)에 대해 확장자 분포와 파일명 표본만 Jev(jev-1.13.0)에 보내 두 번 판정했다. 1회 약 7초, 입력 약 28만 토큰이었다. 파일 내용은 보내지 않았다.

판정 결과 폴더 안내 문서와의 대조
내용 종류(10분류) 팀 표준 폴더·도구·아카이브는 대부분 일치 불일치 2곳. AI 지식베이스 폴더를 "자동화 산출물"(0.54)로, 공유본 폴더를 도면·3D 사이(0.34~0.41)로 판정. 분류 항목에 지식베이스·공유본이 없었고, 한국어 폴더명 의미를 반영하지 못함
구조 관련 여부(Noul) 0.5 이상 91개 폴더 안내 문서의 구조 작업 폴더 9곳을 모두 포함(0.66~0.97). 안내에 없는 Codex 구조 폴더 4곳도 찾음. 대신 백업·아카이브도 섞여 정밀도는 낮음

판단: Jev는 대량 폴더에서 후보를 추리는 데에는 쓸 만했다(놓친 구조 폴더 0). 그러나 최종 판단은 코드를 직접 읽어야 했다. RESEARCH-02가 지적한 한국어 신뢰도 한계와 일치한다.

3.8 검증 체계

S-18이 가장 두텁고, 그대로 jig 시험 체계로 옮길 수 있다.

  1. 닫힌 해 벤치(bench_fe.py, B1~B12) — 해석기 단위 시험
  2. 독립 해석기 교차(xcheck_pynite.py) — 같은 모델을 PyNite로 다시 풀어 비교
  3. 교환 파일 왕복(mgt_roundtrip.py) — 내보낸 MGT를 다시 읽어 비교
  4. 검정식 독립 재구현(hand_checks.py)과 하중 장부 대조(load_audit.py)
  5. 기하·위상 감사(integrity.py, 겹침·관통·떠 있는 끝)
  6. 골든 회귀(gh_result.txt, MstCore2 TestRunner 133체크)
  7. 결함 회귀 목록 — Codex 감사가 찾은 결함 7건과 점검표 13항목(아래 §4)
  8. S-10 테스트 12개, S-05 스모크 6개 — fixture로 흡수

교훈 실제 사례
일부 게이트만 보고 초록을 띄우지 않는다 화면은 기하 게이트(V1~V12)만 보고 통과 표시, 확장 검사는 4/13·최대 검정비 5.56~6.41

사용자 결정이 캐시보다 우선한다 사용자가 뺀 축선이 이전 고정값으로 되살아남

4.1 구조사무소 협의(2026-09-29) — 계획 단계 범위

S-18 설계팀이 협력 구조사무소(구조기술사 2인)와 53분 동안 구조 자동화 결과를 검토했다. 출처는 S-18의 회의록·전사본과, 회의 직후 정리된 구조 규칙 정본(규칙 R1~R11, 이하 "협의 R번호")이다. 아래는 jig 설계에 직접 걸리는 결론이다.

주제 구조사무소 의견 jig에 주는 영향
역할 분담 설계사무소는 ① 횡력 저항 방식 결정 ② 중력 설계까지만 하고, 횡력·전 조합·최종 검토는 구조사무소가 맡는다. 계획 단계로는 이것으로 70~80% 1단계 범위를 계획 단계 중력 설계로 한정할 수 있음
해석 조건(협의 R2) 계획 단계는 1.2D+1.6L 한 조합(다설 지역 제외), 지붕 기둥 상단을 X·Y로 구속해 중력 결과만 얻는다 1단계에 전체 P-Δ·풍·지진·고유치 해석이 필요 없음. 횡력·층간변위·인발·EJ는 실패가 아니라 "구조사무소 최종 검토"로 표시
접합(협의 R3) 보·거더가 기둥에 붙는 단부는 강접, 작은 보가 큰 보에 붙는 단부는 핀. 예외는 구조사무소가 표시해 주면 규칙으로 등록. 해석 뒤 절점 모멘트가 0이면 핀, 있으면 연속으로 판정 단부 조건을 "부재 종류"가 아니라 무엇에 붙는가로 정하는 규칙 + 예외표. 모멘트도 기반 자동 검사
지붕 다이어프램(협의 R4) 슬래브 없는 경량 지붕은 다이어프램이 아니다. 실제 지붕 수평가새(외곽 한 바퀴 + 약 2베이마다, 약 30 mm 봉·앵글)를 넣는다. 기둥 상단 한 곳에 수평력을 주어 그 골조만 움직이면 가요성으로 판정. 중력만 볼 때도 항상 잡는다 가상 부재·등가 사재 대신 실제 부재 생성, 다이어프램 판정 시험을 자동 검사로
수직 가새(협의 R5) 모서리 쌍 + 가운데 1~2개, 인장 봉이면 약 4베이마다, 넓으면 내부 20~30 m마다, 분산할수록 인발·기초 부담 감소 가새 배치 규칙과 경고(2단계)
기준 반영(협의 R6·R7) 기둥은 **확대 모멘트(B1)**로 장주·단주를 구분해 검토. KDS 한계를 빠짐없이 입히고, NG가 입력·하중 오류 때문인지 스스로 가리는 검사가 필요 B1은 전체 P-Δ가 아닌 부재 단위 식이라 1단계에 포함. NG 원인 분류(입력·모델 의심 / 부재 부족)
하중(협의 R11) 구조사무소가 도면을 받아 실별 설계하중표를 먼저 만들고, 프로그램은 실마다 입힌다 하중표 입력 경로와 값 출처(하중표 / 가정) 표시
경제성(협의 R8) 지붕만 있는 단층은 6~9 m × 9~12 m가 경제적, 15 m까지 가능. 설비 제약 안에서 강재(t) 최소안 대안 비교 지표 = 강재 중량(2단계 이후)
EJ·기초(협의 R9·R10) 190 m 방향 최소 1개(구간 ≤ 약 100 m), 횡력 시스템과 함께 결정. 기초는 독립기초 + SOG, 지반조사 전 가정 지내력 2단계 이후
교환·검증 단면을 입힌 MGT를 보내면 midas Gen으로 바로 받아 검토. 프로젝트 기간 동안 구조사무소의 midas 계정 공유 제안 S-18 고유 방식이며 일반 요구로 두지 않는다(2026-09-29 사용자). 구조사무소와는 보통 CAD·Rhino 파일로 주고받는다. MGT는 프로젝트별 선택 내보내기로만 둔다
해석 방식 차이 우리 FE와 midas(보 요소)는 요소 분할 방식 차이로 결과가 다를 수 있음 상용 SW와 교차 검토할 때 차이 허용 기준을 미리 정함

회의 전 질문 21개 중 처짐·치올림, 강종, 퍼린 간격, 주각 조건, 무주 구간 등은 답을 받지 못해 후속 협의로 남았다.

05 / RESEARCH-04 J-09 절과 다른 점

실제 파일과 대조한 결과다. RESEARCH-04 본문은 이 문서 검토 뒤 고친다.

  1. 가장 깊은 구조 자동화 출처(S-18)가 빠져 있다. KDS 부재 검정·풍·지진·P-Δ·검증 체계는 S-18에만 있다.
  2. 재사용 목록에서 S-10 실행 코드(solver.py·layout.py·C# 축 추출·하중·사이징, 테스트 12개)가 빠지고 스킬 파일만 올라 있다. load-tables.json·layout.py는 로컬에만 있다.
  3. S-05 단면 CSV는 8종이 아니라 7종이다. "3단 폴백"은 실제로 2단(PyNite → frame)이고 truss는 직접 지정할 때만 쓴다.
  4. S-08 유보사항은 4건("부재 수급 가능 여부 확인" 추가). S-08 부재는 원형강관인데 어느 출처에도 강관 단면표가 없다.
  5. S-06의 도면-모델 짝은 스크립트(헝가리안 할당·강체 정합)로 계산했고 사람은 적용·검수를 했다. S-06의 구조 GH 파일 3개는 내용 미확인(압축 바이너리).
  6. VIDE 카탈로그의 J-09 항목(src/jigs/catalog.ts)은 이름이 "구조 검토"이고 근거가 S-05·S-06·S-08뿐이다.

06 / 어느 출처에도 없는 것

  • 명시적 해석 모델 계약. S-18 결과 파일에는 지점·하중이 없고 해석기 안에서 규칙으로 생성된다. 절점·부재·지점·하중·조합이 드러나는 모델은 MGT 내보내기에서만 나온다.
  • 일반 건물 형상: 사선·곡선 평면, 다층 골조, 콘크리트·목구조
  • KS 강관·각형관 전체 단면표, KS 재료표(SS275·SM355 등), 접합부·기초 설계
  • 상용 SW(midas 등)와의 절대값 대조. MGT는 준비됐지만 실제로 불러 본 적 없음
  • VIDE 쪽: jig manifest, Python 실행 런타임, 뷰포트 색·다이어그램 오버레이 API, 결정적 호스트 굽기 단계(RESEARCH-05 결정 1~15 모두 미결)

7.2 실행 방식 — 결정 필요(RESEARCH-05 결정 11)

안 내용 장점 비용·위험
A. TS 이식 L3·L4를 TypeScript로 옮겨 서버 안에서 실행(현재 Sync jig와 같은 방식) Python 번들 불필요, 설치·배포 단순, 기존 jig 경로 재사용. 해석 코어 약 250줄 + 검정식이라 규모가 작고, 스카이라인 LDLᵀ 이식 선례(C#)가 있음 이식 오류 위험 → S-18 벤치·PyNite 골든 결과를 fixture로 삼아 수치 일치를 시험
B. Python 자식 프로세스 S-18·S-10 코드를 거의 그대로 실행 검증된 코드를 그대로 씀, PyNite 교차 검증이 쉬움 데스크톱 패키지에 Python이 없음. 런타임 번들·numpy/scipy 설치·버전 관리 필요, 사용자 PC 의존

권고: A안. 검증 체계(§3.8)를 먼저 옮기면 이식 정확도를 수치로 확인할 수 있고, 배포 부담이 가장 작다. Python 원본은 개발용 교차 검증 도구로 남긴다.

이 권고는 A·B 두 안만 비교한 것이다. Rust·C#·C++ 등을 포함한 성능 우선 비교와 새 권고는 RESEARCH-09 §5가 소유한다.

08 / 사용자 결정이 필요한 항목

정한 방향(2026-09-29 사용자): 구조 도메인 지식은 반입한다 — 하중조합, KDS 강구조 부재 검정, midas 교환(MGT), PyNite 기반 교차 검증. 이 지식(검정식·조합 계수·단면표·조문 근거·검증 사례)은 실행 언어와 무관하게 옮기며, 아래 1번은 그 계산을 어떤 언어로 실행할지의 문제다.

  1. 실행 방식 — 결정: 해석 코어는 Rust로 구현한다(2026-09-29 사용자). 비교 근거는 RESEARCH-09 §5
  2. 1단계 입력 — 결정: 입력은 프로젝트마다 다르다. CAD, Rhino Brep, Rhino 중심선 곡선 등으로 오며, AI가 개입해 해석 모델 입력을 만들거나 조정한다(2026-09-29 사용자). 배치 → 구조 자동 생성은 입력 경로 중 하나로 이후 단계에 둔다
  3. 교환 형식 — 결정: MGT 내보내기와 구조사무소의 midas 직접 검토는 S-18 고유 방식이라 일반 요구로 두지 않는다. 일반적인 교환은 CAD·Rhino 파일이다(2026-09-29 사용자)
  4. 1단계 하중 범위: 중력만으로 시작할지, 풍·지진까지 포함할지. §4.1의 구조사무소 의견(계획 단계 = 1.2D+1.6L 한 조합 + 상단 구속)이 참고 근거
  5. 완료 기준에 상용 SW 대조 포함 여부: 사무소에 midas 라이선스가 없다(2026-09-29 사용자 확인). 대체 검증 방법은 후속 조사에서 정리한다. 결과를 "탐색용 예비값"으로 표시하는 문구는 어느 경우든 유지
  6. J-09 이름: 카탈로그의 "구조 검토"와 RESEARCH-04의 "구조 분석" 중 하나로 통일
  7. S-18 코드의 반입 범위: 원본은 프로젝트 폴더에 두고 필요한 부분만 일반화해 가져온다(원형 유지 여부는 구현 중 판단한다는 2026-09-25 결정과 같음)
