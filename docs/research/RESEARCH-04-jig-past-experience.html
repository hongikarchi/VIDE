00 / 조사 목적·범위·방법

0.1 배경 — 사용자가 정한 개념

사용자는 플러그인·위젯을 jig라는 개념으로 부르기로 했다. 사용자가 그때그때 필요에 따라 기능을 만들 수 있는 놀이터(playground)를 제공하고, 각자 만든 도구를 업로드해 다른 사용자도 쓸 수 있게 하되 건축·AI 환경에 특화한다. food4rhino·3D Warehouse에 가깝지만 도구에 한정하지 않고 AI 특화이며, Claude·GPT의 마켓플레이스·스킬 공유 사이트와 비슷한 역할일 수 있다. 건축은 프로젝트마다 필요한 것이 달라 jig라는 개념이 어울린다. 공식 제공 예정 목록이 J-01~J-09이며, 각 기능은 사용자가 과거 프로젝트에서 실제로 수행한 작업이다.

이 문서는 실제 구현 계획 이전에 그 과거 경험을 파악하기 위한 조사다. 위 문단은 사용자가 말한 개념을 요약한 것이고, 이 문서가 그 개념을 결정이나 요구로 확장하지 않는다.

0.2 조사한 것과 방법

1차 조사(S-01~S-17)는 로컬 프로젝트 폴더·GitHub 계정 저장소·Claude 세션 기록 세 유형의 출처를 기능별로 훑었다. 보충 조사(F-01~F-06)는 1차 조사가 남긴 미결 항목 — 자체 Grasshopper MCP 브리지의 본체 위치, GitHub 계정 저장소 전수와 가시성, 이전 IDE의 런타임 실행 로그, 사용자 전역 Claude 설정, 스킬 정의 파일 형식 원문, 일정표·회의록 세션의 파일 조작 기록 — 을 실측으로 닫았다. 보충 조사에서 1차 판정이 뒤집힌 것이 최소 5건 있고, 본문에 그 사실을 표시했다.

사용자 요청("내 계정 GitHub repo에 올렸던 것도 참고")에 따라 계정 저장소를 gh repo list로 전수 열거하고(19개), 기능과 겹치는 저장소는 얕은 clone으로 내용을 확인했다. 저장소별 판정은 §1·§2에 반영했다.

0.3 읽지 않은 것의 원칙

  • 발주처·개인 식별정보가 섞일 수 있는 회의 자료 PDF·계약/견적 문서·대지 식별정보가 든 산출물 HTML은 열지 않았다.
  • .gh·.3dm·.drs 등 바이너리는 열지 않았다. 관련 서술은 파일명·주변 텍스트 기록에 근거하며 추정인 경우 본문에 "추정"으로 표시했다.
  • 비밀값(API 키, 계정 자격증명, MCP 시크릿 헤더)은 존재 사실만 기록하고 값은 옮기지 않았다.
  • 미확인으로 남은 구역은 각 절 끝에 명시했다.
  • 출처 코드(S-NN·F-NN)와 실제 로컬 폴더·세션 기록 경로의 대응표는 저장소에 두지 않는다(사용자에게 채팅으로 보고했고, 상세 메모는 조사 세션의 작업 폴더에 있다).

0.4 이 문서가 결정하지 않는 것

이 문서는 조사 사실과 대안 비교만 담는다. jig의 범위·우선순위·마켓 운영·결제·호스트 지원 범위·이식 대상 선정 같은 제품 결정은 쓰지 않는다. PRD와의 관계는 §5에 사실로만 적는다.

02 / 기능별 조사 결과

J-01 사이트 모델링 (지형·주변 건물·도로·필지 + 공공 데이터 상세화)

한 줄 결론 — 반복 수행. 다만 두 갈래 스택으로 갈라진 채 한 번도 통합된 적이 없고, 두 갈래의 유통 상태가 비대칭이다.

과거 수행 내역. 네 출처에 실제 대지 적용·검증된 파이프라인이 각각 있다. ① S-02(Site Maker, 하루 만에 완성) — 국토부 SHP 임포트 → 필지 검색 → 3D 매스업을 GH Python 컴포넌트 3종으로 구현, 외부 파이썬 의존성 0. 한 도엽(약 600×600m, 12레이어)에서 피처 임포트 누락 0, 건물 수백 동 매스업 전부 닫힌 솔리드, 자체 좌표변환식을 상용 GH 플러그인 출력과 대조해 격자수렴각 차가 일치함을 확인. ② S-01/S-03/S-04/S-15(Node 계보) — 주소 한 줄 → PNU → 대지 사실 수집, 등고선·표고점 IDW 보간 지형, 건축물대장으로 기존 건물을 층별 용도까지 상세화, 간선도로변 고층 건물 전수 조사 자동화, 발급 건축물대장 PDF 좌표 기반 파서, watertight STL 3벌, rhino3dm .3dm 내보내기. 세 개 대지에 실제 적용.

F-01이 Site Maker의 발생 경위를 세션 로그로 복원했다: 상용 플러그인의 좌표계 왜곡 해결 요청 → 좌표계/인코딩 판별 → 국토부 설명서 PDF에서 코드 사전 추출 → 지번 검색 → 필지/건물/접도 필터링 → 층수 기반 매스업 → 사용자 요청("나중에 재활용하고 싶어서")으로 스킬 패키지화. 즉 스킬화는 사후 요청이었다.

입력·데이터. 국토정보플랫폼 연속수치지형도 1:5000(EPSG:5179, UTF-8), 국가공간정보포털 연속지적도(EPSG:5186, EUC-KR), 연속수치지형도 데이터 설명서 PDF 153p → JSON 사전(레이어 107/속성 66/코드값 503/통합코드 423), VWorld Open API, 주소기반산업지원(→ PNU 19자리), 건축HUB 건축물대장, 세움터 발급 대장 PDF, 서울도시공간포털(무인증 내부 API). SHP는 전 출처에서 사람이 웹에서 수동 다운로드했다.

절차. 경로 ①(Rhino/GH 완결): 사람이 SHP 다운로드·.prj 확인 → 자동 파싱/재투영/인코딩 판별 → 사람이 Panel로 좌표계·앵커·피처 수 육안 확인 → 반자동 체크리스트 생성 → 사람 수배선(폴더가 둘이면 origin→anchor, epsg→crs 두 줄) → 자동 질의·분리·돌출 → 사람이 Rhino 없이 도는 selftest 통과 후 캔버스 확인. 경로 ②(Node): 주소→PNU→수집→규제 기하→법정 외피→대안→매스까지 완전 자동, 접도·건축한계선·고시 확정값은 사람 수기(estimated 플래그), 자동 수집값 *.auto.json이 사람 확정본 site.json을 덮지 않고 대조로 드리프트를 탐지.

재사용 자산. 그대로: 1_importer.py(675줄, SHP/DBF/PRJ/CPG 파서 + TM 정·역변환 + 좌표계·인코딩 판별), 2_site.py(285줄), 3_mass.py(218줄), IO.json, ngii_spec.json 코드 사전, gh_stubs.py(328줄)+selftest.py(Rhino 없이 컴포넌트 회귀 테스트), Node 계보의 massing.js·geofiles.js·terrain.js·export_3dm.js, API 실측 문서 2종. 손봐야 함: Site Maker 미구현 4종(건물 실측 높이·지형 서피스 생성(지반 항상 Z=0)·구 좌표계 데이텀 변환·도로명 매핑), 검토엔진의 대지 고유 가정 미분리. 재작성: 두 스택 간 공유 코드 없음(SHP 파싱·좌표변환·필지 검색이 파이썬과 JS로 각각 독립 구현).

AI 활용 방식. SKILL.md description에 사용 조건과 금지 지시를 한 문장에 담음("검증된 컴포넌트 세트가 이미 있으므로 처음부터 새로 짜지 말 것"). 폴더 진입 규약(읽는 순서 → 절대 규칙 6가지 → 작업 방식 → 환경 전제 → 커버하지 않는 것 + "사용자에게 이 한계를 숨기지 말 것"). 효과가 확인된 지시: "로컬에서 먼저 돌리고 캔버스는 나중", "에러 없음을 성공으로 읽지 마라", "남의 컴포넌트 출력으로 내 계산을 교차검증하라", "캔버스는 사용자의 문서(진단용 컴포넌트를 만들지 말고 print()만)", 도구 부재 시 폴백 병기.

문제·함정. 반복 실패가 거의 전부 **"에러 없이 틀린 결과"**다 — 파일마다 원점을 새로 잡는 임포터(레이어 간 최대 70.5m 어긋남), 제품별 좌표계 불일치, 앵커 이동, 두 데이터셋 배선 누락, 셰이프파일 외곽링 시계방향(매스가 지하로 감), 도로경계면 레이어를 건물로 오인, 무벽건물이 연면적을 27% 부풀림, typeHint 누락 시 System.Guid 마샬링으로 조용히 빈 결과, 인코딩 통념 오류, 건축HUB 페이지네이션 누락. 코드로 못 고치는 것: 원본 데이터의 지적불부합(수십 cm대 체계적 오프셋), IDW 보간의 정보 한계. 운영 사고: 무보호 정적 호스팅으로 대지 위치·규모 노출(정책 2회 변경), --project 누락으로 다른 대지 자료 덮어쓰기, API 키 3종이 세션 메모 .md에 평문 저장.

문제·함정. 보안이 가장 크게 대가를 치른 항목 — 2026-08-20 정적 리포트 2건이 비밀번호·SSO·IP 제한 없이 공개돼 대지 주소·면적·계획 규모 노출, 즉시 중단 후 "호스팅하지 않는다, 파일 하나 전달"로 정책 전환, 2026-09-23 Cloudflare 비밀번호 게이트로 재시도. 지자체 포털 API가 소유자 성명·주민번호 앞자리를 무인증 반환 → 호출 금지 목록 등재. 조용히 틀리는 렌더링 버그 다수(필드명 불일치로 — 렌더, 법령 언어 키와 엔진 키 불일치로 조인 전량 누락, id 중복 앵커 충돌, JSON 배열의 문자열 키가 JSON.stringify에서 소실, iframe 내장 시 localStorage 오염). 정본 단절: 다이어그램 정본이 Figma에만 남고 폴더에는 캡처 PNG만, SVG는 저장되지 않으며 보고서로 되돌아오는 경로가 없다 — 본인의 감사 워크플로가 "재현·보고서 편입에 공백"으로 직접 지목했고, 분석 차트와 발표 HTML도 이어지지 않는다고 적었다.

설명과 과거 경험의 간극. ① "사이트 분석"이 과거 기록에서 최소 5개 산출물로 갈라져 있고 빌더도 다르며, 프로젝트 자체 분석 목록에 아직 그래프화되지 않은 항목이 더 있다. ② pptx는 데이터도 있고 서식 복제 기술도(xlsx에서 완주) 있는데 슬라이드 레이아웃 규범만 없다. ③ Figma는 "해본 적 없다"가 아니라 "한 번 해보고 단절된 채로 두었다"이며 필요한 것은 왕복과 정본 위치 결정이다. Figma MCP는 플러그인으로 이미 설치돼 있으나 그 작업에는 쓰이지 않았다. ④ MCP는 과거에 형상 전용이었고 분석 경로에 붙은 유일한 사례(Rhino↔HTML 동기화)도 실시간이 아니라 명시적으로 실행하는 파일 기반 동기화라고 두 문서가 각각 못박았다.

문제·함정. 수집: 법제처 API가 특정 공포본에 고정돼 법령 4종이 최대 2년 뒤처진 채 조용히 사용되고 있었음, 재수집 시 시행일 역행 사고, 건축HUB 페이지네이션 누락, 자치구 심의기준은 API가 아예 없음. 텍스트·DB: 한국어 FTS5 recall 3%(2-gram 자체 색인으로 회복), 부칙이 정규화 단계에서 통째로 버려짐, 별표 43건 소리 없이 소실, 별표 줄바꿈 병합으로 한글 단어 35.9%가 중간에서 끊김, 조 레코드의 text가 제목뿐이라 그대로 인용하면 "원문을 실었다"는 거짓 근거가 됨. 판정: 구역명 매칭으로 고시 적용 여부를 판단하면 두 사례 모두 틀림, 상한용적률 오독, 근거 없는 산식을 단정적으로 써 온 사건(사용자가 "이 산식 어디서 나온 거야?"라고 캐물어서야 드러남 → 코드에서 제거, law-review의 "산식 발명 금지" 조항이 됨). 누락: 3중 게이트를 모두 통과한 검토서에서도 6건 누락(법정 목록에 없는 실무 관행 항목). 도면 판독: CID 폰트·폰트 서브셋으로 한글 추출 실패 → 페이지 이미지 렌더 우회, 파일명 신뢰 금지. 운영: 무보호 배포 노출 사고, API 키 3종 평문 저장, 워크플로 크레딧 소진으로 전량 실패 2회, 조사 결과가 파일로 안 남아 사후 감사 불가.

J-06 렌더 이미지 (노드 자동화 · 스케치 지칭 · 레퍼런스/느낌/합성)

AI 활용 방식. description에 한/영 트리거 촘촘히 나열, 본문 고정 구조(When to use / Prerequisites → Procedure → Gotchas(baked in — do not "fix" out) → Parameters → Not yet implemented → Reference), diagnose → confirm → apply 3단 + 계획을 Rhino 세션 sticky에 저장, 로더 패턴(코드를 채팅에 붙이지 않고 절대경로 exec() 한 줄 — "검증된 코드가 매번 바이트 동일하게 돌게"), 메모리 되먹임. 레퍼런스 쪽은 확인 질문 예산 0~2턴 하드캡, 필수 슬레이트 우선순위를 프롬프트가 규정. 공통: 비용 게이트(N=10→100→전체 스모크 사다리, 임계 초과 승인), 판정자 하나를 믿지 않기(단일 판정 정확도가 부풀려진 것을 독립 모델 블라인드 A/B로 재검증해 오류율 9.3%→2.7%로 정정), 생성 출력에 결정적 critic-in-loop.

문제·함정. AI 활용 방식. Rhino 연결이 조형물 경로에서는 MCP 소켓(RhinoScript 코드 문자열 원격 실행), 제품 경로에서는 자체 툴 네임스페이스 + 인덱스 온디맨드. 결정론/LLM 경계가 가장 반복된 원칙이다 — "탐지·계산은 결정론적 서버 코드, 해석·판단은 LLM", 그리고 저장소 최우선 규칙 "모델의 성공 주장은 검증이 아니다 — 실행기 predicate만이 성공을 표시한다". 실행 전 요약표 강제(| Step | Agent/Model | Files | Scope | Depends on |, scope를 small/medium/large로 사전 선언), 서브에이전트 역할 분리표(메인=계획·큰 결정 / builder=1~2파일 surgical edit / investigator=위치 추적 / reviewer=diff 리뷰), 영구 진행 문서 금지(stale 방지), 코드형/지식형 스킬 구분("스킬 코드는 verbatim, 레퍼런스 노트는 자유 각색").

문제·함정. 자체 코드가 스스로 **"construction-ready 승인용이 아닌 탐색적 설계 도구"**라고 선언했고 실무 사인오프는 상용 SW + 사람이 따로 수행했다. PyNite API가 릴리스마다 변경돼 두 이름으로 순차 import 후 폴백. 임시 가정값이 코드에 남음. 구조 세션이 정작 구조 지식형 스킬 본문을 한 번도 skill_read하지 않았다 — 서버 결정론 툴만으로 일이 굴러갔고 "표본에 해당 과제가 없었을 수도 있다"는 대안 설명이 함께 남아 있어 단정하지 않지만, 스킬 본문이 실제로 소비된다는 증거는 없다. 승인 카드가 드물게 쓰인다(11세션 합계 approval_request 2회 vs 가벼운 ask_user 12회). heavy-solve 45초 예산 초과로 recovery_resume 7회. 도면-모델 정합이 전부 사람 확인 기반. 대안 비교가 파일 분기라 diff 불가. 법규 게이트도 "구조안전 확인" 누락을 못 잡았다. 기존 구조 정보가 파이프라인 입력에 들어온 적이 없다.

설명과 과거 경험의 간극. ① 6개 요소의 선례 밀도가 불균등하다. ② "최적화"가 세 가지 뜻으로 쓰였다 — 위상+단면 동시 다목적 최적화(Pareto를 사람이 선택) / 단면 사이징 사다리(자동) / 실무의 "균일 단면 NG → 모듈별 확대 → OK" 반복(상용 SW, 사람). ③ 자동 계산과 사인오프 사이에 고정된 경계가 이미 존재한다. ④ 일람표의 가장 가까운 선례 셋이 전부 문서가 아니다(화면 표 / 모델 UserString / JSON). ⑤ 도면-모델 연동의 유일한 선례는 방향이 한쪽이다(도면 기준으로 모델 위치 보정). ⑥ 재이식이 이미 두 번 일어났고 VIDE가 세 번째다 — 두 번째 이식에서 인터페이스가 "column/girder curve 입력 → beam 자동 생성 → 하중 계산 → 단면 탐색"으로 건축 쪽에 가깝게 재설계됐다.

3.2 반복된 구성 패턴

  • 3~4문서 세트. 가장 완성도 높은 선례는 전부 묶음이다 — 원칙(SKILL.md) + 체크리스트(게이트) + 함정 카탈로그(TRAPS.md/PITFALLS.md) + 절차(PLAYBOOK.md). 함정 카탈로그가 본체보다 길어지는 것을 정상으로 취급한다. TRAPS의 실효성은 "어휘가 둘이다"(법령 언어 키와 엔진 키를 혼동하면 통째로 빈 값), "배열에 문자열 키를 넣으면 조용히 사라진다" 같은 항목으로 실증된다.
  • 얇은 포인터 스킬. 배포되는 것은 SKILL.md 한 장뿐이고 무거운 자산(검증된 컴포넌트 세트·함정 카탈로그·사전 데이터)은 원본 폴더에 두고 절대경로로 가리키기만 한다. 본문에 "옮겼다면 이 경로를 고칠 것. 없으면 사용자에게 위치를 묻는다", "처음부터 새로 짜지 말 것. 거기서 시작해서 필요한 부분만 고친다"가 들어 있다.
  • 정적 빌드 / 실행 분리. 문서 규범을 실행 가능한 게이트로 내린다 — 검증·게이트·스캐너가 실패하면 exit 1. 빌드가 같은 원본 파일을 EmbeddedResource로 구워 "폴백이 자산과 드리프트할 수 없게" 만든 사례도 있다.
  • 로더 패턴. 코드를 채팅에 재타이핑하지 않고 Glob으로 절대경로를 찾아 exec(open(r"<ABS>\script.py").read()) 한 줄만 전송한다. 이유가 문서에 명시돼 있다("so the validated code runs byte-identical every time (no re-typing, no model drift)"). "하드코딩 금지"가 스킬 9개 전부에 반복된다.
  • diagnose(비파괴) → confirm(사람) → apply(파괴) 3단계. diagnose가 세션 메모리에 plan을 저장하고 apply가 같은 plan을 읽어 실행한다.
  • 메모리 승격 사다리. 발견을 먼저 정의별 MEMORY.md에 적고, **"새 파일에도 성립하는 규칙인가?"**를 기준으로 cross-file 규칙만 공유 defaults.md의 "Promoted lessons"로 올린다(현재 6건 승격, review 대기). 별도 계보에서는 반복 지적 3회 이상이면 프로젝트 스코프 메모리 파일로 고정하는 것이 실제 워크플로다.
  • 도구가 에이전트 환경을 스캐폴딩한다. 파일 열림을 감지하면 홈 폴더에 .claude/·.mcp.json·CLAUDE.md·MEMORY.md·설정 JSON을 만들고 MCP에 연결한 뒤 CLI를 자동 기동한다. CLAUDE.md는 <!-- 도구:begin --> … <!-- 도구:end -->로 도구가 매 연결마다 덮어쓰는 구역과 사용자 자유 영역을 분리하고, @defaults.md·@MEMORY.md import로 공유 규칙과 정의별 기억을 매 세션 주입한다.
  • 워크플로 오케스트레이션 최소 API. 28개 스크립트가 전부 같은 런타임 주입 API 위에 작성됐다(import 문 0): export const meta = {name, description, phases} · pipeline(items, ...steps) · parallel([...]) · agent(prompt, {label, phase, schema}) · log/phase. 반복되는 골격은 조사 → 적대적 검증 → 완결성 비평 → 갭 보완 2라운드이고, 검증자는 발견자의 주장을 의심하고 파일을 다시 열어 confirmed/partial/refuted로 판정한다. 백그라운드로 던지고 메인 스레드는 기다리지 않는다.
  • 예약 에이전트 런북. "당신은 이 저장소에서 예약 실행되는 세션이다. 루틴 프롬프트가 워크플로 하나를 지정한다. 정확히 그 워크플로만 실행하고 멈춰라"로 시작하고, 상태변경 호출은 전부 스크립트 경유로 멱등성을 강제하며 에이전트는 초안·해석·개정만 한다. 사용자 교정을 라운드별로 "하지 말 것" 목록에 누적 기록하는 설정 파일도 있다.
  • 자율 루프 안전모델. 객관 게이트(존재·규모 / 과잉제거 탐지 / 라벨==내용 일치 / 테스트 green) 전부 통과분만 자동 배포, 베이스라인 대비 악화 시 자동 revert, 크론 충돌은 루프 동안 비활성화 후 재활성화.

3.3 반복된 지시 패턴 (사용자 쪽)

번호 매긴 다중 질문(1, 1-1, 1-2…)을 한 번에 던지고 같은 번호로 답변받기 · 큰 방향 전환 전에는 "코드 작업은 하지 말고 계획부터, 승인 나면 진행" → 승인 후 "중간에 멈추지 말고 끝까지" · 결정 사항은 한 번에 하나씩 객관식으로 확인한 뒤에만 공식 계획 문서 작성(200줄짜리 영어 계획 문서 금지) · 실행 전 요약표 의무화 · 항상 plan mode로 시작하고 영구 진행 문서를 만들지 않음(stale 방지) · "세션 하나 = 산출물 하나" · 재현성 시험("이 스킬만 읽은 새 세션이 같은 형식으로 채울 수 있는가. 채울 수 없으면 스킬이 부족한 것이지 세션이 부족한 것이 아니다") · 스킬은 기본 동작이 아니라 옵트인 · 비용 게이트(N=10→100→전체 스모크 사다리) · 판정자를 하나만 믿지 않기 · effort/model을 작업 성격별로 전환 · 판단용 미니 UI는 앱을 만들지 않고 아티팩트로 즉석 생성 · CLAUDE.md ↔ AGENTS.md 동일 본문 미러링으로 두 CLI 병행(@ import 한 줄 관용구는 2026-07부터 이미 사용).

3.4 텍스트 규범의 한계 — 실측 2건

강제 수준이 이미 A(서버 결정론 툴, 기계적 강제) / B(verbatim 스킬, 규범 강제) / C(서버가 모델 페이로드 재작성) 3계층으로 자체 분류돼 있고, 스킬은 B다. 그리고 B가 무시된 실측 사례가 둘이다.

  1. 코드 주석 원문: "house-rules norm alone was verified live to be ignored by the model, so the intent is FORCED through the required resultOutput field ... and enforced here on the server." — 텍스트 규범이 안 지켜져 스키마 필수 필드로 승격됐다.
  2. 규칙 파일은 모델만 구속하는데 자동 정리는 호스트 소유 훅이라 그것을 무시했고, "자동정리 금지"라고 쓴 사용자의 배치를 서버가 되돌리는 사고가 났다. 텍스트 규범이 모델도 사람도 아닌 호스트 자신의 코드에조차 안 먹힌 사례다.

B를 C로 올리는 안(스킬 이름 + 파라미터만 받아 서버가 canonical 소스를 주입)은 작성 시점에 **이미 논의됐으나 미착수(이연)**로 남아 있다. 덧붙여 선언과 실사용의 괴리도 실측됐다 — "mandatory"라고 적은 툴이 11세션 중 1회 호출, 무거운 승인 카드 2회 vs 가벼운 질문 카드 12회, 유일하게 트리거 문장이 없는 스킬이 15회 중 4회로 가장 많이 읽혔고 트리거 문장이 있는 6개는 한 번도 안 읽혔다(표본이 11세션으로 작다는 단서 포함). 인덱스 140자 절단이 13개 중 5개의 문장을 중간에서 자른다.

3.5 하네스가 항상 이득은 아니다

자체 하네스가 baseline(순정 CLI + MCP)보다 우월하다는 결론에 이르지 못했다. 사용자 발언이 남아 있다: "일단 이번 실험에서도 하네스가 없는 버전이 시각적으로는 더 우수하다고 판단되네. 자율성과 퀄리티는 비례할 수 밖에 없는건가?" role/mode 추상화를 만들었다가 폐기했고, 적응형 모델 라우팅도 만들었다가 수동 고정으로 되돌렸으며, 버전업에서 오히려 신뢰성이 후퇴한 기록(비커밋률 17.4% → 29.6%)도 있다. 다만 품질 게이트를 어떻게 설계할지는 실물이 있다 — 고정 과제 + 외부 성공판정 기준 + 의도적 버그 주입 후 자가수리 검증까지 갖춘 벤치마크 하니스 문서, 그리고 §3.2의 자율 루프 안전모델이다.

3.6 배포·버전·인벤토리의 공백

  • 버전 관리가 어디에도 없다. 배포 스크립트(51줄)는 filecmp 동일성 검사만 하고 버전 비교를 안 한다. "스킬이 바뀌면 이미 뿌린 사본을 어떻게 갱신하나"에 대한 답이 조사 전체에 없다. 마켓플레이스 경로만 version + gitCommitSha 고정 개념을 갖고 있다.
  • 마켓플레이스 설치 = 저장소 전체 clone. 제3자 마켓플레이스는 플러그인 본체 외에 벤치마크·테스트·문서까지 통째로 내려받는다.
  • 로컬 경로 플러그인 설치의 재현성이 불명하다(어떤 영속 레지스트리에도 안 남는다).
  • 동기화 세대 미정리 — 계정/조직을 바꿔 쓴 흔적이 비활성 세대 3세트로 쌓여 있다(자동 청소 없음). 비슷한 캐시를 설계하면 세대 GC를 처음부터 넣어야 한다는 반면교사.
  • 자산 인벤토리 자체가 없다. 흩어진 스킬/에이전트 자산이 로컬 6곳 이상 + GitHub 19개 저장소 + 전역 설정 3계층(직접 만든 스킬 / 마켓플레이스 설치본 / 계정 동기화 내장본)에서 발견됐다. 그중 하나는 버전관리가 없고, 하나는 커밋 0인 빈 저장소이며, 하나는 동기화 장치 없는 완전 중복 두 벌이고, 하나는 설치 흔적이 사라졌다.
  • "사용자가 스스로 도구를 만드는" 흐름의 선례가 다르다. 과거에 도구가 만들어진 방식은 (a) 사용자가 성공한 코드를 붙여주고 에이전트가 정리 (b) 에이전트가 자기 조사 노트에서 "수확"해 파생 (c) 실패 로그를 근거로 쿡북을 채점해 고침 (d) 반복 지적 3회 → 메모리 고정 — 넷 다 사후 정리이지 사전 생성이 아니다.
  • "사무소 동료에게 준다"의 유일한 실물이 텍스트 체크리스트 한 장(온보딩 파일 31줄, 소프트웨어·계정·AI 도구 카테고리)이고 그마저 자격증명이 평문이다. 사무소 공용 자산으로 확인된 다른 것은 엑셀 서식·인허가 원표 같은 문서이지 에이전트 도구가 아니다.
  • 옵트인 기능이 한 번도 안 켜졌다 — 개발자 피드백 스킬의 로그 파일이 애초에 생성된 적이 없다.

07 / 결론

  1. 재사용 가능한 자산이 예상보다 많고, 대부분 사용자 계정 안에만 있다. J-01·J-03·J-04는 2~3세대에 걸쳐 실제 대지에 적용된 코드가 있고, J-05와 J-09도 보충 조사에서 실동 코드가 새로 드러났다. 다만 J-03·J-04 계열은 비공개 저장소, J-01의 가장 잘 패키징된 세트는 버전관리 밖 로컬 폴더, J-09의 최신 스킬은 공개본에 없는 로컬 전용이다 — 이식은 "공개 코드 가져오기"가 아니라 비공개·비버전관리 자산 반입의 문제다.
  2. 선례가 진짜로 없는 것은 셋뿐이다 — 회의록 전 구간(J-08의 앞단), "노드 방식 렌더 자동화"(J-06), 그리고 jig의 주는 쪽(업로드 받기·검수·승인·버전 갱신·신뢰 표시). 나머지는 신규 개발이 아니라 재패키징·통합 문제다.
  3. 반복된 실패 유형이 하나로 수렴한다 — "에러 없이 틀린 결과". 그리고 그것을 실제로 막은 것은 문서 규범이 아니라 결정론 코드와 exit 1 게이트였다. 텍스트 규범이 모델에게도 호스트 자신에게도 무시된 실측 사례가 각각 하나씩 있다.
  4. 기능 설명과 과거 경험 사이의 간극이 기능마다 다른 종류다. J-05는 "관리"가 통째로 미경험이고, J-02는 Figma 왕복과 정본 위치 결정이며, J-07은 사용자가 이미 한 번 내린 반대 방향 판단이고, J-08은 형식 원본 자체의 부재다. 이 간극들은 조사로 메울 수 없고 사용자 결정이 필요하다.
  5. 오케스트레이션·게이트·승인의 최소 설계는 이미 실물이 있다 — pipeline/parallel/agent(schema) 위의 4단계 검증 골격, dry-run→확인→적용, ask-back + CAS, 객관 게이트 통과분만 자동 배포와 악화 시 revert. jig가 이것들을 제공한다면 발명이 아니라 재현이다.

다음 문서(PLAN 또는 SPEC)를 쓰기 전에 필요한 것. ① §6의 확인 목록 중 최소한 1~5(jig 자체의 형식·강제 수준·배포 범위·버전·자산 흡수 여부)에 대한 사용자 결정 — 이것이 정해지지 않으면 어느 기능도 확장 계약을 쓸 수 없다. ② FR-13이 요구하는 "작은 확장 하나"의 대상 선정과 그 확장이 쓸 공통 입력·권한·진행·결과 계약(OQ-07). ③ 미확인으로 남은 두 구역의 확인 — 사이트 모델링 확장 계획 본문과 대응 워크플로 4종(J-01), 한 프로젝트의 대형 세션 6개를 회의·협의 키워드로 재검색(J-08). ④ 이식 후보 자산의 라이선스·소유권 정리(서드파티 포크 계보, 사무소 고유 데이터를 배포본에 넣을지 사용자별 로컬로 뺄지).
