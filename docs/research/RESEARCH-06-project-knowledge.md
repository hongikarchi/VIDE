# RESEARCH-06 — 프로젝트 지식 DB(온톨로지)

## 0. 목적과 범위

### 0.1 사용자 요청(2026-09-28~29)

- 메일·첨부파일(PDF·PPTX·CAD·Rhino 등)·회의록을 모아 **어느 회사(누가) 무슨 말을 했는지, 주요 쟁점, 진행 경과**를 DB로 정리한다.
- 이를 바탕으로 질문에 답하고, 도면·모델 크리틱과 판단을 돕는다.
- 시각화 여부와 위치는 실무 효용을 따져 정한다.
- 협의가 계속 오가고 기하학적 판단이 많은 방대한 정보를 어떤 구조와 DB에 담을지 정한다.
- 공유 목표는 **여러 팀원이 함께 자료를 쌓고 질문하는 수준(아래 §5의 3단계)**이다.
- 원본 자료는 **회사 서버에 있을 가능성이 높다.**

### 0.2 이 문서가 하는 일과 안 하는 일

현재 약속·코드와의 관계, 기능의 층, 데이터 구조, 저장소 비교, 공유 단계와 구성, 회사 서버 원본의 처리, 활용·시각화 판단, 위험과 사용자 결정 항목을 정리한다. 제품 범위는 PRD(C-02 제안), 저장·공유 구조의 결정은 [ADR-018 초안](../decisions/ADR-018-project-knowledge-store.md), 동작 계약은 후속 SPEC, 구현 순서는 [PLAN-08](../plans/PLAN-08-project-knowledge.md)이 소유한다. 실제 프로젝트 자료로 추출 품질을 측정하지 않았으므로 품질 수치는 제시하지 않는다.

## 1. 이미 있는 약속·자산과의 관계

새 개념처럼 보이지만 PRD가 이미 뼈대를 약속하고 있다. 빠진 것은 **외부 자료의 수집·정리와 여러 사람의 공동 축적**이다.

코드 자산(2026-09-28~29 확인):

- **로컬 저장:** SQLite(`node:sqlite` 3.51). 추가 설치 없이 다음이 동작한다.
  - FTS5 trigram 전문 검색: 한국어 부분 문자열 검색
  - R*Tree 공간 색인: 범위 상자 검색
  - JSON 함수
  - 재귀 쿼리: 관계 따라가기
  - 확장 불러오기: Windows·Node 24에서 켜짐. 벡터 확장을 나중에 붙일 수 있다.
- **첨부:** 현재 요청 첨부는 TXT·MD·CSV·JSON, 파일당 50,000바이트이고 요청 본문에 그대로 들어간다(SPEC-01). 프로젝트 단위 자료함은 없다.
- **AI 실행:** 구독 CLI(Claude Code·Codex)가 VIDE MCP 도구만 쓴다(ARCH-01 §2·3). 지식 조회는 같은 방식의 **읽기 전용 도구**로 붙이면 기존 권한 경계를 유지한다.
- **도면·모델:** ZWCAD 연결 Sync가 문자·레이어·해치·xref를, Rhino Sync가 레이어·객체명·속성(user text)을 이미 읽는다.
- **수량:** 기본 집계(FR-22)와 측정 캐시·체크포인트가 모델 시점별 계산 결과를 보존한다. 기하 판단을 계산으로 기록하는 기반이 된다.

## 2. 기능을 네 층으로 나눈다

| 층 | 하는 일 | AI 필요 | 먼저 쓸모가 생기는 시점 |
|---|---|---|---|
| ① 수집 | 원본을 참조·해시로 등록하고 텍스트·메타데이터를 뽑는다(보낸 사람·날짜·쪽·슬라이드) | 대부분 불필요 | 자료가 한곳에 모이고 원문 검색이 되는 순간 |
| ② 정리 | 원문에서 “누가·언제·무엇을(요구/결정/의견/질문/일정)”을 진술로 뽑고 주체·대상에 연결 | 필요(근거 구간 필수) | 브리핑·타임라인·쟁점 표 |
| ③ 활용 | 질의응답(인용 포함), 모델 요청 시 관련 조건 제안, 도면·모델 크리틱, 변경 영향 확인 | 필요 | 실무 판단 보조 |
| ④ 표시 | 목록·표·타임라인·객체의 근거 표시, (선택) 관계 그래프 | 불필요 | ②와 함께 |

①만으로도 “그 메일 어디 있었지”에 답할 수 있다. ②③은 원문 근거가 있어야 환각을 통제할 수 있다. 따라서 **수집 → 원문 검색 → 구조화 → AI 활용** 순서가 맞다.

## 3. 데이터 구조 — 엔진보다 기록 방식이 핵심

정보가 방대하고, 협의가 계속 바뀌고, 기하 판단이 섞인다는 어려움은 DB 엔진을 바꿔서 풀리지 않는다. 다음 다섯 층의 **기록 방식**으로 푼다. 이 구조는 SQLite·PostgreSQL·그래프 DB 어디에도 올라간다.

### 3.1 근거(원문) — 고치지 않는다

| 개념 | 예 | 핵심 속성 |
|---|---|---|
| Source(자료) | 메일, PDF, PPTX, 회의록, DWG, 3DM | 원본 위치 참조(§6), 내용 해시, 형식, 작성·수신 시각, 보낸 사람·받는 사람, 공개 범위, AI 전송 허용 여부 |
| Excerpt(근거 구간) | PDF 3쪽 두 번째 문단, 메일 본문 5–8행, 슬라이드 7, 도면의 문자 객체 | Source, 위치(쪽·슬라이드·행·CAD handle), 원문 텍스트 |

모든 판단은 근거 구간으로 돌아와야 하며, 근거 구간은 수정하지 않는다.

### 3.2 진술 — 덮어쓰지 않고 쌓기만 한다(시간축 두 개)

- **종류:** 요구·결정·의견·질문·사실·일정·변경.
- **필수 속성:** 말한 주체, 대상, 근거 구간(1개 이상), 출처 구분(원문 / AI 추정 / 사용자 확정), 역할(필수조건·결정·요청·의견·질문·참고).
- **두 시간축:** “언제부터 유효한 내용인가”(유효 시간)와 “우리가 언제 알게 됐나”(기록 시간)를 따로 둔다. 그래야 “9월 10일 기준 합의 내용”, “그 모델을 만들 때 알고 있던 조건”에 답한다.
- **대체와 무효:** 새 결정이 오면 이전 진술을 지우지 않고 “유효 종료 + 대체한 진술”로 연결한다. 모순은 자동 판정하지 않고 쟁점으로 올린다.
- **확정도 사건이다:** 확정·기각·수정은 누가 언제 했는지를 새 기록으로 남긴다. 이전 상태를 덮어쓰지 않는다.

이 방식은 시간축 지식 그래프(Graphiti)와 시간 여행 DB(XTDB, Datomic)가 쓰는 모델과 같다. 특정 엔진 없이 유효 시작·끝, 기록 시각, 대체 관계 열로 구현한다. 또한 §5의 공동 축적에서 **동기화 충돌을 거의 없애는** 핵심이다.

### 3.3 대상과 관계 — 표준 어휘를 빌린 이름 붙은 연결

| 개념 | 예 |
|---|---|
| Party(주체) | 발주처 한빛건설, 구조사무소, 김OO 소장(조직/사람, 역할, 별칭) |
| Subject(대상) | 대지·건물·층·공간·요소·시스템·도면 |
| Issue(쟁점) | 주차 대수 부족, 일조 사선 저촉(관련 진술 묶음, 상태, 최신 결정) |
| Milestone(일정) | 인허가 접수, 중간 보고 |
| Episode(묶음) | 회의 한 번, 메일 스레드 하나(그 안의 진술을 묶어 타임라인이 됨) |

노드와 연결(요청했다, 결정했다, ~에 영향, ~에 포함, ~와 인접)을 표 두 개로 둔 속성 그래프다. 따라가기는 재귀 쿼리로 한다. 공간·요소 분류는 새로 만들지 않고 W3C 건물 위상 온톨로지(BOT: 대지·건물·층·공간·요소)와 IFC 분류명을 빌린다. RDF 저장소 전체를 도입하지는 않는다.

### 3.4 기하 — 형상은 넣지 않고 모델 시점과 연결된 계산 결과를 기록한다

- **형상 자체:** 3dm/DWG와 기존 표시 캐시에 둔다. 지식 DB에는 “어느 모델 시점의 어느 객체”라는 참조(모델 Sync/체크포인트 ID + 네이티브 객체 ID)만 둔다.
- **기하 판단은 관측 기록:** 예를 들어 “공간 S-301 면적 28.2㎡, 모델 Sync #12 기준, 기하 면적 계산”처럼 값·단위·계산 방법·모델 시점을 함께 남긴다. 모델이 바뀌면 그 관측만 오래됨으로 표시하고 다시 계산한다(측정 캐시·체크포인트 구조와 같음).
- **요구는 구조화된 조건으로도 저장:** 예를 들어 `대상=3층 회의실, 항목=면적, 조건=≥30㎡`처럼 둔다. 그러면 “28.2 < 30 → 쟁점”을 AI 추측이 아니라 계산으로 잡아낸다. 이것이 크리틱의 뼈대다.
- **공간 검색:** “근처·안에 무엇이 있나”는 객체 범위 상자를 공간 색인(R*Tree)에 넣어 후보를 먼저 거르고, 정밀 판단은 호스트 기하 도구로 한다.

### 3.5 규모

큰 프로젝트라도 자료 수만 건, 진술 수십만~백만 건 수준이다. 부피가 큰 형상은 파일에 남으므로 저장 엔진의 규모 한계는 쟁점이 아니다.

## 4. 저장소(DB) 비교

| 방식 | 좋은 점 | 걸리는 점 | 판단 |
|---|---|---|---|
| **SQLite**(+FTS5, R*Tree, JSON) | 이미 제품 저장소, 설치·서버 불필요, §3 구조 전부 가능(확인) | 여러 PC가 공유 폴더의 같은 파일에 동시에 쓰면 손상 위험 | **각 PC의 로컬 사본으로 사용** |
| **PostgreSQL**(+PostGIS, pgvector) | 공간·벡터·전문 검색 한곳, 다중 사용자·행 단위 권한에 강함 | 서버 필요(사내 설치 또는 호스팅) | **팀 공용 원본 후보**(§5.3) |
| **Neo4j / AuraDB**(그래프 DB) | 관계 따라가기 편함 | 별도 Java 서버, Community판 GPLv3의 배포 문제, 실제 질문 대부분은 거르기+인용이라 효용 낮음 | 보류 |
| **Kùzu**(설치 없는 그래프 DB) | 앱 안에 넣는 그래프 DB | 2025-10 인수 뒤 개발 중단(저장소 보관), 커뮤니티 포크만 남음 | 제외 |
| **RDF 저장소**(Ontotext GraphDB 등) | 건축 표준 온톨로지(BOT·ifcOWL)와 추론 | 무겁고 SPARQL, 무료판 동시 질의 2개·11.0부터 라이선스 키 필요 | 어휘만 빌림 |
| **XTDB v2 / Datomic**(시간 여행·불변 기록 DB) | 두 시간축 조회가 기본 기능, 무료 공개 라이선스 | Java 서버, 틈새 기술 | 개념만 참고 |
| **Graphiti**(시간축 지식 그래프 라이브러리) | §3.2 구조를 이미 구현 | 그래프 DB 서버와 자체 LLM API 키 필요 — 구독 CLI 방식과 맞지 않음 | 설계만 빌림 |
| **Obsidian** | 사람이 읽는 Markdown, 링크·그래프 뷰, 2026-02부터 업무용 무료 | 구조 강제·트랜잭션·동시 편집 처리 없음 | **DB가 아니라 한 방향 내보내기(보기 창)** |
| **벡터 검색**(sqlite-vec 등) | 의미 검색 | 구독 CLI는 임베딩을 만들지 않음 — 로컬 모델이나 API 키 필요 | 전문 검색 + 구조 조회 + AI 도구 검색으로 부족함이 측정될 때 추가 |

## 5. 공유 단계와 구성

### 5.1 단계

| 단계 | 무엇 | 필요한 것 |
|---|---|---|
| 0. 나만 | 내 PC에서 쌓고 질문 | 현재 구조 |
| 1. 결과 보여주기 | 브리핑·쟁점표를 웹 게시본으로 열람·의견 | 기존 웹 공유(SPEC-04) 확장 |
| 2. 다른 사람도 질문 | 팀원이 직접 질문 | 지식 DB 공유 + 질문하는 사람의 AI 실행 경로 |
| **3. 같이 쌓기(목표)** | 여러 팀원이 자료를 넣고 진술을 확정·수정 | 팀 공용 원본 + 동기화 + 역할·공개 범위 |

### 5.2 3단계 권장 구성 — 공용 원본 + 각자 로컬 사본 + 각자 AI

- **팀 공용 원본:** 모든 팀원의 기록(사건)이 모이는 중앙 저장소.
- **각 PC의 로컬 사본(SQLite):** 검색·질문·모델 연결은 빠른 로컬 사본으로 하고 오프라인에서도 쓴다.
- **AI는 각자 PC에서:** 자기가 넣은 자료의 정리와 자기 질문은 자기 구독 CLI로 처리한다. 서버 쪽 AI 실행(API 비용)은 필요하지 않다.
- **동기화:** §3.2처럼 모든 기록을 고유 ID가 있는 사건으로 쌓기만 하므로, 동기화는 “모르는 사건 가져오기 + 내 새 사건 보내기”다. 두 사람의 다른 판단은 덮어쓰지 않고 나란히 남아 쟁점으로 보인다. 같은 자료를 두 사람이 넣어도 내용 해시로 한 번만 저장된다.
- **호스트 제어는 그대로 한 작업환경:** 지식 공동 축적은 Rhino/CAD 원본 제어가 아니다. PRD §14의 “프로젝트별 한 로컬 작업환경이 호스트 제어·원본 반영” 원칙은 유지하고, 지식 기록만 여러 PC가 함께 쓴다(ADR-018에서 결정).

### 5.3 팀 공용 원본의 후보

| 후보 | 좋은 점 | 걸리는 점 |
|---|---|---|
| **A. 사내 팀 서버**(회사 서버·NAS에서 VIDE 팀 서비스 + DB) | 원본 자료 옆에 두고 사내망 안에서 완결, 기존 사내 백업 체계, 외부 반출 없음 | 누군가 운영(설치·업데이트·백업), 외부 접속은 VPN 필요, 새로 만들 서버 구성 |
| **B. Cloudflare D1 + R2**(기존 웹 공유 기반) | 계정·멤버십·권한 이미 구현, D1이 SQLite라 로컬과 같은 구조, 한국어 FTS5 사례 확인, 운영 부담 적음 | 파생 데이터(진술·인용)가 외부 클라우드로 감, DB당 10GB(조직·프로젝트별 분할), 동기화 직접 구현 |
| **C. Supabase**(PostgreSQL, 서울 리전) | 행 단위 권한·공간·벡터·파일·인증이 한곳 | 공유 시스템을 새 업체로 이중화, 무료 500MB |
| (참고) Turso | 로컬 SQLite ↔ 클라우드 자동 동기화 | 오프라인 쓰기 동기화 공개 베타, 인증·권한 별도, 업체 추가 |

**동기화 방식을 저장소와 분리**하면 A와 B를 나중에 바꾸거나 함께 쓸 수 있다(예: 사내는 A, 외부 협력사 게시본은 B).

## 6. 원본 자료가 회사 서버에 있는 경우

2026-09-29 사용자 의견: 원본 데이터는 회사 서버(파일 서버·NAS)에 있을 가능성이 높다.

- **원본은 옮기지 않는다:** VIDE는 원본을 복사·업로드하지 않고 **위치 참조 + 내용 해시 + 추출 텍스트·근거 구간**만 저장한다. “원문 열기”는 회사 서버의 원본을 연다.
- **읽기 전용 접근:** 사용자 계정의 권한으로 읽기만 한다. 원본 폴더에 쓰거나 이동하지 않는다.
- **경로 정규화:** PC마다 드라이브 문자(Z: 등)가 달라도 같은 자료로 보도록 UNC 경로나 설정한 “프로젝트 루트” 기준 상대 경로로 저장한다. 파일이 옮겨지거나 이름이 바뀌어도 해시로 다시 찾는다.
- **공유 폴더에 SQLite 파일을 두지 않는다:** 회사 서버의 공유 폴더에 지식 DB 파일 하나를 두고 여러 PC가 직접 쓰면 손상될 수 있다. 사내에 두려면 §5.3 A처럼 서비스를 거친다.
- **권한 누수:** 제한된 폴더의 자료를 권한 있는 팀원이 정리하면 그 진술이 공용 원본을 통해 권한 없는 팀원에게 보일 수 있다. 자료별 공개 범위(팀 공개 / 특정 멤버 / 나만)를 두고 기본값을 정해야 한다. 폴더 권한을 자동으로 따라가는 방식은 구현이 어렵고 오판 위험이 있다.
- **사외 접속:** 회사 밖에서는 원본을 열 수 없어도 로컬 사본의 근거 구간으로 답할 수 있다. 원문 열기만 VPN이 필요하다.
- **외부 전송 정책은 두 겹이다:** 공용 원본을 사내에 두더라도, AI 정리 단계에서 원문이 AI 공급자(Anthropic·OpenAI)로 전송된다. 회사 정책에서 “외부 클라우드 저장 금지”와 “외부 AI 처리 허용”을 따로 확인해야 한다.

**판단:** 원본은 회사 서버에 그대로 두는 것을 기본으로 한다. 팀 공용 원본은 회사 정책에 따라 고른다.
- 사내 서버를 운영할 수 있고 외부 저장이 부담되면 **A(사내 팀 서버)**.
- 파생 데이터의 외부 저장이 허용되고 운영 부담을 줄이려면 **B(D1)**.

### 7.3 표본 프로젝트 폴더 조사 (2026-09-29, 읽기 전용 집계)

사용자가 알려준 회사 서버 프로젝트 폴더 하나(RESEARCH-04 출처 S-06 프로젝트의 서버 원본)를 파일 목록·크기·날짜와 개수만 읽어 집계했다. 파일 내용은 저장하지 않았고 계약·회계 폴더는 열지 않았다.

- **규모:** 파일 6,286개, 61.5GB, 최대 깊이 11단. 목록 전체를 읽는 데 25.6초.
- **용량 대부분은 문자 정보가 적다:** 3dm 137개(27.9GB), 렌더 메시·압축·영상(d5mesh·zip·mp4 등 약 13GB), 이미지 3,500여 개. 문자 정보가 많은 형식은 DWG 202·PDF 190·PPTX 27·XLSX 22·DOCX 16개로 약 450개다.
- **자동 생성·백업이 많다:** 3dmbak·bak·dwl·tmp·save 등 120여 개, 확장자 없는 파일 858개, json 594개(렌더러 캐시로 보임). 경로·확장자 규칙만으로 제외할 수 있다.
- **폴더·파일 이름에 정보가 이미 있다:**
  - 번호 붙은 최상위 폴더(기초자료·도면·문서·데이터·발표·3D 등)가 자료 종류를 나눈다. 일부(최종 산출물·감리·문서화)는 비어 있다.
  - 회의록은 `<YYMMDD 상대기관>/…회의록.docx|pdf|hwp`처럼 **날짜·상대 기관이 폴더 이름**에 있고, 같은 회의록이 여러 형식으로 있다.
  - 도면은 `YYMMDD 기본도면.dwg`처럼 날짜가 붙은 판이 이어지고, 심의 도면·XREF 폴더가 따로 있다. 검토본은 접미사로 구분된다.
  - 계약·회계와 제안서 폴더는 민감 자료로 기본 제외 대상이다.
  - 메일은 첫 집계 뒤 사용자가 문서화 폴더 아래에 두 메일함의 백업(EML 97통, 397MB, 2026-06-29~09-14)을 넣었다. 제목·보낸 사람·날짜·Message-ID는 97통 모두, 본문은 97통 모두 UTF-8로 해독된다(한 메일함은 본문이 HTML에만 있음). 답장·전달 제목 24통, 답장 헤더(In-Reply-To·References) 약 18통, 보낸 사람 주소 8개. 첨부는 52통에 85개(DWG 35·PDF 18·ZIP 11 등)라, 메일로 오간 도면 판과 서버의 도면 판을 해시·이름으로 이을 수 있다. 별도 파서 없이 표준 MIME 처리로 읽힌다.
- **검토 표기의 위치:**
  - PDF 187개 중 주석 객체가 있는 파일은 9개였다. 11,530개 전부 사각형(Square) 주석이라 사람이 단 검토 의견이라기보다 출력 과정에서 생긴 도형일 가능성이 높다. 작성자·내용 필드가 있는지는 아직 보지 않았다.
  - Office 문서 65개(DOCX·PPTX·XLSX)에는 메모(comment)가 하나도 없었다.
  - 따라서 이 프로젝트에서 “누가 무엇을 말했나”는 주로 **회의록 본문, 검토본 PDF의 그려진 표기, DWG 안의 문자·지시선**에 있다. PDF 주석 목록만 뽑는 방식으로는 대부분을 놓친다.

### 7.4 도면 안의 표기 추출

| 위치 | 결정적으로 얻는 것 | 판정이 필요한 것 |
|---|---|---|
| DWG 문자·MText·블록 속성 | 문자, 레이어, 좌표, 배치(모형/배치 탭), 도면 판(파일 날짜) | 설계 내용 표기인지 검토 의견인지 |
| DWG 지시선·MLeader·치수 문자 재정의 | 가리키는 좌표·객체, 문자 | 같음 |
| DWG 구름 표시(리비전 클라우드)·검토 레이어 | 호 폴리라인·레이어 이름, 둘러싼 영역 안의 객체·문자 | 어느 의견과 짝인지 |
| PDF 주석(Acrobat·Bluebeam) | 작성자·날짜·쪽·영역·내용·답글 | 내용 없는 도형은 제외 |
| PDF에 그려진 표기(평면화된 검토본) | 쪽 이미지 | 이미지 판독(AI)만 가능 → 비용 큼 |
| 3DM | 레이어·객체 이름·user text·문자 객체 | 같음 |

- **DWG 읽기:** 이미 있는 ZWCAD 연결의 `Database.ReadDwgFile` 경로로 문자·지시선·구름·XREF를 읽는다(AttachedDisplay의 문자·지시선 처리 재사용). ZWCAD가 없는 PC를 위해 ODA File Converter(무료, DWG→DXF 일괄 변환)를 대안으로 둔다. LibreDWG는 GPL이라 제품에 넣지 않는다.
- **3DM 읽기:** rhino3dm(Rhino 없이 3dm 읽기)으로 문자·이름·user text만 읽는다. 파일이 크므로(평균 200MB) 최신 판과 명시한 파일만 읽는다.
- **검토본 판별:** 같은 이름의 원본과 검토본(접미사) 쌍이 있으면 두 판의 문자 차이와 쪽 이미지 차이로 “추가된 표기”만 골라 이미지 판독 대상을 줄인다.
- **“어느 파일이 무엇을 말했나”의 단위:** 모든 추출 결과는 근거 구간(Excerpt)으로 남는다. 파일 해시·경로·판 날짜와 함께 쪽/슬라이드/DWG 핸들·좌표·영역을 가진다. 진술은 반드시 근거 구간을 가리킨다(§3).

### 7.5 경로 하나로 구축하는 흐름 — LLM 사용 최소화

사용자가 프로젝트 폴더 경로만 주면 아래 순서로 처리한다. 싼 단계가 먼저 거르고, 비싼 단계는 걸러진 일부만 받는다.

| 층 | 하는 일 | 도구 | 비용·시간(표본 기준 추정) |
|---|---|---|---|
| ① 목록 | 경로·크기·날짜·해시. 백업·캐시·렌더 자산·민감 폴더 제외. 같은 해시·같은 이름의 다른 형식(docx/pdf/hwp)을 한 자료로 묶기 | 규칙 | 30초 안팎, 무료 |

| ④ 구간 선별 | 각 근거 구간이 결정·요청·조건·의견을 담는지, 어떤 대상(동·층·실·요소)에 관한 것인지 | Jev(Choice·Noul) | 구간 수만 개 × 수백 토큰 → 수십 센트, 병렬 수 분 |
| ⑤ 진술 추출 | 선별된 구간만 진술 JSON으로 | 구독 CLI(LLM) | 전체 구간의 일부. 비율은 K0에서 측정 |
| ⑥ 검증 | 인용 문자열 원문 대조(규칙) → 인용이 진술을 뒷받침하는가(Jev Noul) → 주체 별칭 합치기 후보(Jev Choice) | 규칙 + Jev | 소액 |
| ⑦ 확정 | 결정·필수조건만 사람이 확정 | 검토 큐 | 사람 |

- **증분:** 다음 실행에서는 해시가 바뀐 파일만 ③부터 다시 처리한다. 폴더 감시는 ①만 자주 돈다.
- **Jev를 쓰는 이유:** T-032 실측에서 한국어 요청→파일 찾기가 단어 일치로는 거의 실패했고(5위 안 14%) Jev는 100%였다. 구간 선별·대상 연결도 같은 “많은 후보 중 의미로 고르기” 문제다. 호출 한 번 0.3초 안팎, 입력 100만 토큰당 $0.042로, 같은 양을 LLM으로 읽는 것보다 훨씬 싸다.
- **Jev에 맡기지 않는 것:** 공식 문서상 숫자·날짜·개수 판단이 약하고 한국어 신뢰도가 낮다. 날짜·판 순서는 이름 규칙과 파일 날짜로, 치수·면적은 계산으로 얻는다. 한국어 구간 선별 정확도는 K0에서 사람 표시와 대조해 잰다. 기준에 못 미치면 ④를 규칙+LLM으로 바꾼다.
- **외부 전송:** ②④⑥은 경로·구간 문장이 TypeSafe로, ⑤는 선별 구간이 AI 공급자로 간다. 자료별 AI 전송 허용(§6)을 두 곳 모두에 적용한다. 제품에서는 키를 배포물에 넣지 않고 서버가 중계한다(PLAN-05 §7).
- **참고한 방식:** GraphRAG류는 전체 텍스트를 LLM으로 읽어 그래프를 만들어 색인 비용이 크다. LightRAG는 그보다 훨씬 적은 호출로 색인한다고 보고한다. 여기서는 그보다 한 단계 더 나아가, LLM 이전에 규칙·파서·Jev로 대부분을 거른다. 건설 문서 대상 RAG 연구(BifrostRAG)도 문서 구조와 의미 그래프를 따로 두는 방식을 쓴다.

**실측으로 고친 점(2026-09-29, [SPIKE-2026-09-29-knowledge-crawl](../tdd/SPIKE-2026-09-29-knowledge-crawl.md)):**

- 위 표의 추정 가운데 ④의 비용은 맞았다. Jev 468만 토큰, 약 $0.20, 1분이었다.
- ④의 역할은 좁혀야 한다.
  - 한국어 발췌에서 Jev가 확신한 비율은 44%뿐이었다.
  - 확신한 “내용 없음”은 대조 표본에서 놓침이 없었다.
  - 확신한 “내용 있음”은 넓게 잡혔다.
  - 그래서 Jev는 **“내용 없음”을 버리는 필터와 이름 해석 잔여 분류**에 쓰고, 나머지 판정은 LLM이 여러 발췌를 한 번에 받아 처리한다.
- 짧은 항목을 판정할 때는 LLM에 목록으로 한 번에 넘기는 편이 토큰 수가 적었다. Jev는 항목마다 기준 설명을 반복하기 때문이다. 금액과 구독 한도 면에서는 Jev가 싸다.
- 가장 큰 절감은 AI가 아니라 **같은 문장 합치기**(발췌 약 2만 → 5천)와 **폴더 이름 규칙**(문서 종류 95%)에서 나왔다.

### 7.6 기능 위치 — JIG가 아니라 기본 기능

2026-09-29 사용자 판단: 이 수집·정리는 모든 프로젝트에 똑같이 들어가는 시스템이므로 JIG(선택해서 쓰는 작업 도구)가 아니라 **왼쪽 레일의 기본 기능**으로 둔다.

- 현재 왼쪽 레일에는 작업 문서, 작업 이력, 참고 자료, JIG, 설정이 있다. 지금의 “참고 자료”(채팅에 첨부한 파일)를 **프로젝트 자료**로 넓혀 자료함·쟁점·타임라인을 함께 보이는 방식을 권한다(§10의 3번). 화면 배치는 Design이 정한다.
- JIG는 이 DB를 읽기 전용으로 쓰는 쪽이다. 예: J-08 회의록은 정리된 진술을 입력으로 받고, J-03·J-04 법규 검토는 확정된 조건을 받는다.
- 처음 폴더를 지정할 때 ①② 결과(자료 종류별 개수, 제외될 폴더, 예상 시간·전송량)를 먼저 보여 주고 사용자가 확인한 뒤 ③부터 진행한다.

### 7.7 문서 텍스트 추출 — 현재 상태와 권고안 (2026-10-06 보충)

2026-10-06 사용자 결정: xlsx·docx·hwp·pdf 텍스트 추출을 자료 DB 수집기에 넣는 일은 **계획안에만 두고 나중에 다듬어 구현한다.** 이 절은 그 계획안의 조사 근거이고, 실행 항목은 [PLAN-08](../plans/PLAN-08-project-knowledge.md) K1에 짧게 둔다. 출발점은 [RESEARCH-15](RESEARCH-15-s18-feature-harvest.md) M-34(S-18의 자료 텍스트 사이드카)다.

**현재 상태(코드 확인, 2026-10-06):**

- 자료 DB를 읽고 찾는 쪽은 제품에 있다. `src/jigs/knowledge.ts`가 `knowledge.sqlite`를 읽기 전용으로 열고, `excerpt_fts`(FTS5 trigram)와 bm25로 찾으며 2글자 이하 낱말은 포함 검색으로 보충한다. AI 도구 `project_brief`·`project_search`·`project_issue`·`project_statement`가 이 DB를 조회한다([SPEC-08](../specs/SPEC-08-project-facts.md).7, PLAN-22 T-065). 추출 결과를 발췌 테이블에 넣으면 자료 탭과 AI 검색이 고치지 않고 그대로 쓴다.
- 채우는 쪽(수집기)은 SPIKE 코드뿐이다(`tools/spikes/2026-09-29-knowledge-crawl/extract.mjs`·`extract.py`, PyMuPDF·openpyxl·hwp5txt). 약 1,200자 단위로 자르고, XLSX는 빈 셀을 버린 뒤 탭으로 이어 **열 위치까지 잃는다.** 어느 형식에서도 표 구조가 남지 않고, 암호 파일은 파일 단위 오류로만 남으며 OCR은 없다(표본 262개 중 스캔 PDF 26개가 빈 결과).
- 채팅 첨부와 PLAN-30 T-136(파일에서 할 일 만들기)은 첨부 경로를 CLI가 직접 Read한다(ADR-031 8 이후 `file_read`·`attachment_read` 없음). 그래서 docx·hwp·xlsx를 놓으면 내용을 읽지 못할 것으로 본다(실행 확인 안 함). `src/server/attachments.ts`의 `readFileContent`는 호출하는 곳이 없는 코드다.
- 프로젝트 데이터 폴더는 이미 묻지 않고 읽기 전용으로 열리는 작업 폴더(`WorkFolders.records`)라, 그 아래 추출 캐시도 새 게이트 예외 없이 읽힐 가능성이 크다(폴더 단위인지 실행 확인 필요).

**권고안 — 엔진 안 수집기가 자료 DB에 쓰고, DB를 정본으로 한다:**

| 항목 | 권고 |
|---|---|
| 위치 | VIDE 엔진(Node)의 백그라운드 작업. 수집기만 `knowledge.sqlite` 쓰기 연결을 따로 연다 |
| 저장 | 자료·발췌 테이블과 `excerpt_fts`. 원본 옆에는 쓰지 않는다(원본 무변경). CLI용 파생 캐시 `<data>/projects/<id>/extracted/<자료>.md`는 언제든 다시 만드는 생성물이며, 검색 정본은 FTS다 |
| 증분 | 폴더 등록 때 한 번 전체, 이후 프로젝트 열기와 [자료 새로 고침]에서 크기·수정 시각이 바뀐 파일만 다시 추출. 해시는 추출 중 계산. 실시간 감시는 하지 않는다(PLAN-08 「기술 선택」) |
| 표 보존 | 표는 Markdown 표로 남기고 위치(쪽·시트·표 번호)를 함께 저장. XLSX는 빈 셀도 자리를 지키고(열 위치 유지) 행 묶음마다 머리행을 반복 |

**라이브러리 후보(Node, AGPL 제외):**

- **kordoc**(MIT, Node ≥18) — 1순위. HWP3·HWP5·HWPX·HWPML·PDF·XLS·XLSX·DOCX를 Markdown으로 바꾸고 병합 표를 복원한다. PLAN-08 K0에 이미 후보로 적혀 있었으나 실측은 pyhwp로 해서 판정이 없다. 주의점:
  - win32에서 파일 **경로**를 넘기면 배포용 HWP·DRM HWPX에 한컴 COM(`HWPFrame.HwpObject`)을 자동 실행한다. 엔진은 **Buffer**를 넘겨 이 경로를 막는다.
  - `KORDOC_OFFLINE=1`로 외부 통신을 막는다.
  - 새로 늘어나는 의존성은 cfb·jszip·@xmldom/xmldom·markdown-it·commander·zod 3(엔진의 zod 4와 중복)이다. OCR 계열 선택 의존성(onnxruntime 등)은 뺀다. THIRD_PARTY 고지가 필요하고 PLAN-03의 의존성 규칙을 따른다.
  - 옛 형식 가운데 XLS만 지원한다(DOC·PPT 없음).
- **pdfjs-dist**(Apache-2.0) — PDF 텍스트·주석.
- **ZIP+XML 직접 해석**(jszip·fflate) — DOCX·PPTX·XLSX·HWPX. XLSX는 sharedStrings와 수식 캐시값 처리가 필요하다.
- **HWP 5.x 단독**(cfb + `node:zlib`, 본문 레코드만) — 의존성은 작지만 표가 나오지 않는다.
- **제외:** PyMuPDF·pyhwp(AGPL, Python 번들). PLAN-08의 구현 언어 결정(TS·C#만)과도 맞지 않는다.

**대안:**

- **A. 원본 옆 사이드카(S-18 관례):** 가장 단순하지만 공유 드라이브를 더럽히고, 쓰기 권한·동기화 충돌이 생기며, 발췌 ID와 연결이 끊긴다. 개인 로컬 폴더 전용으로만 의미가 있다.
- **B. 첨부 요청 때 변환:** 채팅 첨부·파일 칩·T-136으로 들어온 문서만 같은 추출 모듈로 바꿔 첨부 옆에 `.md`를 둔다. CLI Read가 바로 읽으므로 첨부의 docx·hwp·xlsx 문제를 먼저 푼다. 호출되지 않는 `readFileContent`를 되살리기보다 현재 구조(ADR-031 8)에 맞다.
- **C. 최소 직접 작성:** ZIP+XML, pdfjs-dist, HWP 본문 레코드만. 의존성이 가장 작지만 표·HWP3·암호 처리를 직접 해야 한다.

**착수 전 정할 질문:** (1) 앱 안 수집기를 티켓으로 등록할 시점, (2) 추출 캐시를 CLI Read·Grep에도 열지(`records` 범위 확인), (3) 원본 옆 사이드카 허용 여부, (4) 스캔 PDF 처리(표시만 / AI 판독 / 로컬 OCR), (5) DOC·XLS·PPT 옛 형식 포함 여부, (6) 크기 상한과 파일당 시간 제한, (7) 한컴 COM 경로를 완전히 막을지(Buffer 입력), (8) 같은 모듈을 첨부·T-136에도 쓸지(쓰면 대안 B를 먼저). 기록 위치는 정해지면 동작은 SPEC-08 §8에서 꺼내거나 프로젝트 지식 SPEC, 물리 열·캐시 경로는 ARCH-01, kordoc 대 직접 작성 선택은 ADR, 비교 실측은 SPIKE로 둔다.

### 7.8 메신저·메일함 입력 — 카톡·Slack·mbox (2026-10-06 보충)

S-18의 커뮤니케이션 아카이브(`13_OFFICE-ARCHIVE`, 표준 라이브러리 Python)를 VIDE의 대화 공유(ADR-037 4)·공유 노트([SPEC-10](../specs/SPEC-10-shared-notes.md))·할 일 추출(PLAN-30 T-136)·지식 공유(ADR-037 3)와 대조한 결과, **새로 구현할 것은 없고** 아카이브에만 있는 의미 있는 차이는 메신저·mbox 수집 경로와 주간 요약(§9) 두 가지다. 이 절은 수집기 입력 후보로만 기록한다.

| 입력 | 형식 | 참고 구현(S-18) |
|---|---|---|
| 카카오톡 대화 내보내기 | txt, PC·모바일 두 형식 자동 감지, 24시간제, 여러 줄 메시지, 시스템 줄 처리 | `pipeline/ingest_kakao.py` |
| Slack 내보내기 | export zip(채널별 JSON) | `pipeline/ingest_slack.py` |
| 메일함 | mbox(Takeout)·eml | `pipeline/ingest_*.py` |

- **상태:** 참고 구현은 시험만 했고 운영하지 않는다. 제품은 TS·C#만 쓰므로(PLAN-08 「기술 선택」) Python을 옮기지 않고 TS로 다시 쓴다. 정규식 위주라 작다.
- **메시지 단위 출처 ID:** `kakao:<방>:<분>:<내용 해시 앞 8자>`, `email:<Message-ID>`, `slack:<채널>:<ts>` 형식으로, 같은 내보내기를 다시 수집해도 ID가 같아 검토 기록과 근거 칩이 유지된다(SPEC-08의 "검토 기록이 재수집 뒤에도 유지"와 맞음). **한계:** 카톡을 일부 기간만 다시 내보내면 같은 분 안의 순서가 밀려 ID가 바뀔 수 있다.
- **개인정보·공개 범위:** 카톡 방에는 개인 대화와 외부인이 섞인다. ADR-037 3에 따라 진술과 발췌가 계정 사이트로 올라가므로 **메신저 원문 조각이 서버로 간다.** 참여자 동의, 출처 제외 규칙(방·사람·기간), 공개 범위를 먼저 정해야 한다(§11, §12).
- **채택하지 않는 것:** 아카이브의 SHA-256 해시 체인 커스터디·3층 검증과 원본 raw·첨부 보관은 증거 보존이 목적이라 VIDE의 목적(설계 작업과 팀 공유)과 다르고, 원본을 PC·회사 서버에 두는 원칙(§6, ADR-037)과 충돌한다. 위치 참조와 내용 해시만 둔다(기존 방식). 아카이브 DB를 수집 원천으로 읽는 길은 아카이브를 실제로 운영하게 될 때 다시 본다.

## 8. 정리(구조화) 방법

- **추출 단위:** 근거 구간마다 AI가 진술 후보를 JSON으로 뽑는다. 진술마다 근거 구간 ID와 원문 인용을 필수로 하고, 인용이 원문과 일치하지 않으면 버린다(RESEARCH-04의 인용-원문 대조 선례).
- **주체·대상 정규화:** 다른 표기(“한빛”, “한빛건설(주)”)는 별칭 후보로 두고 사람이 합친다.
- **검토 큐:** 새 진술은 “AI 추정”으로 들어온다. 결정·필수조건처럼 판단에 영향이 큰 종류만 확정을 요구하고, 의견·참고는 목록화에 그친다. 3단계에서는 확정 권한을 역할로 제한한다.
- **증분 처리:** 새 자료가 이전 결정을 대체할 가능성이 있으면 “대체 후보”로 표시하고 자동 확정하지 않는다.
- **실행 경로:** 기존 구독 CLI를 도구 없는 추출 작업으로 재사용하고, 진행률·중단·재개(FR-15·16)를 적용한다.

## 9. 활용

| 활용 | 방식 | 필수 조건 |
|---|---|---|
| 질의응답 | AI가 읽기 전용 찾기 도구로 필요한 진술만 찾아 답한다(아래 “찾기”) | 근거는 판단이 애매할 때(값 충돌·결정 없음)와 사용자가 요청할 때만 보인다. 근거가 없으면 “자료에 없음”, 답에 기준 날짜 표시 |
| 검토 요청·JIG 빌드 | 사용자가 검토를 요청하거나 JIG를 만들 때만 관련 조건·결정을 찾아 대조한다 | 모델·설계 수정 요청마다 자동으로 검토하지 않는다(응답이 느려짐, 2026-09-29 사용자 결정) |
| 도면·모델 크리틱 | 구조화된 조건(§3.4)과 현재 모델의 계산 관측을 대조하고, 시각 판단은 화면 캡처로 | 결과는 “AI 추정” 쟁점으로 객체에 연결. 법규 판단은 FR-21 |
| 변경 영향 | “이 결정을 바꾸면?” → 연결된 대상·진술·과거 작업 | 연결된 것만 말하고 없으면 모른다고 표시 |
| 브리핑 | 주체, 열린 쟁점, 최근 결정, 다가오는 일정 | 요약 문장마다 근거 링크 |
| 주간 요약(후보, 2026-10-06) | 한 주의 노트·일지·대화 기록 사본·진술을 ①진행 ②결정 ③리스크 ④액션(담당) 형식으로 묶는다(S-18 아카이브의 형식, 담당 표기는 T-136의 '(담당: 이름)'과 같음) | 저장 위치(일지·새 노트 종류·지식 현황)와 인용 게이트 확장(진술 `[S번호]` 외에 노트 id·대화 요청 id) 미정. 서버에서 AI를 돌리지 않으므로 PC에서 실행 |

크리틱은 확정된 요구·결정이 쌓인 뒤에야 의미가 있으므로 가장 뒤 단계에 둔다.

주간 요약은 후보로만 둔다. 사용자가 요청하는 형태("이번 주 정리해 줘")는 지금도 노트·대화 기록 사본으로 할 수 있다(SPEC-10.1). 정기 자동 요약은 저장 위치와 인용 게이트가 정해진 뒤 PLAN-08 K3 또는 SPEC-10.8 후속으로 넘긴다.

**찾기 — 코드 → Jev → LLM(2026-09-29 제안, 미측정):** 모든 진술을 LLM에 한 번에 넣는 방식은 자료가 커지면 쓸 수 없다. K0의 질의는 구조 관련 진술 1,009개, 약 10만 토큰을 한 번에 넣었다. 개발용 위치 찾기(T-032)와 같은 구조로 찾는다.

1. **코드:** 분야·이슈·종류·주체·기간 조건과 FTS 검색으로 후보를 좁힌다. 날짜·수치 조건은 여기서만 처리한다.
2. **Jev:** 질문에 대해 후보를 255개 묶음별 Choice로 순위화해 상위 20~50개를 고른다. 질문을 이슈 목록 중 하나로 보내는 일도 같은 방식이다.
3. **LLM:** 고른 진술만 읽고 답한다. 목록만 원하면 LLM 없이 결과를 그대로 보여 준다.

위치 찾기의 한국어 요청 실측(5위 안 100%)은 파일 요약을 대상으로 한 것이다. 진술을 대상으로 한 정확도는 질문 목록을 만들어 다시 잰다.

## 10. 시각화 판단

전체 관계 그래프 화면은 보기에는 좋지만 실무 질문(“이 대상에 걸린 조건”, “이 쟁점의 최신 결정”, “누가 언제 말했나”)에 직접 답하지 못한다. 권하는 순서는 다음과 같다.

1. **채팅 답변의 인용:** 누르면 원문 구간이 열린다.
2. **Inspector의 근거 표시:** 객체를 고르면 연결된 요구·결정·쟁점·계산 관측이 나온다.
3. **프로젝트 자료(왼쪽 레일, §7.6):** 자료함, 브리핑, 쟁점 표, 타임라인, 주체 목록.
4. **검토 큐:** AI가 뽑은 진술의 확정·수정·기각.
5. **(선택) Obsidian 내보내기 또는 국소 그래프:** 전체 그래프는 VIDE에 만들지 않는다. 필요하면 쟁점·결정·주체 노트를 Obsidian 폴더로 한 방향 내보내 그 그래프 뷰를 쓴다.

## 12. 사용자 결정이 필요한 항목

1. **제품 범위:** C-02 채택 여부와 시점(현재 개발과 병행 / MVP 이후).
2. **공동 축적 허용:** 호스트 제어는 한 작업환경으로 유지하고 지식 기록만 여러 PC가 함께 쓰는 예외를 둘지(ADR-018).
3. **팀 공용 원본 위치:** 사내 팀 서버(A) / Cloudflare D1(B) / Supabase(C). 회사 서버 운영 가능 여부와 외부 저장 정책에 달림.
4. **회사 정책:** 외부 클라우드 저장과 외부 AI 처리 각각의 허용 여부.
5. **역할과 공개 범위:** 관리자·편집(자료 추가·확정)·열람(질문)·외부 협력사의 권한, “결정”을 확정할 수 있는 사람, 자료 공개 범위 기본값.
6. **범위:** 사무소 내부 팀만인지, 협력사도 참여하는지.
7. **자료 입력:** 회사 서버 폴더 경로와 제외 규칙, 메일 환경(Outlook/Gmail, .msg 여부). 표본은 웹메일 EML 백업이다(§7.3). 같은 방식으로 계속 내보낼지, 계정을 직접 연결할지.
10. **Jev 사용:** 경로·구간 문장의 TypeSafe 전송(§7.5)을 회사 정책상 허용할지. 허용하지 않으면 ②④⑥을 규칙+LLM으로 대신하고 비용이 커진다.
8. **표본 자료:** 품질 측정에 쓸 실제 프로젝트 자료 1세트(사본).
9. **크리틱 범위:** 첫 크리틱을 “구조화된 요구 대비 모델 대조”로 한정할지, 도면 표기 누락까지 볼지.
11. **문서 텍스트 추출(§7.7):** 수집기 티켓 등록 시점, 추출 라이브러리(kordoc / 직접 작성), 스캔 PDF·옛 형식·크기 상한, 같은 모듈을 첨부·T-136에 먼저 쓸지(대안 B).
12. **메신저·mbox 수집(§7.8):** 수집 허용 여부, 참여자 동의와 외부인 처리, 제외 규칙, 사이트로 가는 발췌의 공개 범위.
13. **주간 요약(§9):** 만들지, 저장 위치(일지·노트·지식 현황), 인용 대상 확장.
