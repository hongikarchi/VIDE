# jig 후보 기능의 과거 수행 경험 조사

## 0. 조사 목적·범위·방법

### 0.1 배경 — 사용자가 정한 개념

사용자는 플러그인·위젯을 **jig**라는 개념으로 부르기로 했다. 사용자가 그때그때 필요에 따라 기능을 만들 수 있는 놀이터(playground)를 제공하고, 각자 만든 도구를 업로드해 다른 사용자도 쓸 수 있게 하되 건축·AI 환경에 특화한다. food4rhino·3D Warehouse에 가깝지만 도구에 한정하지 않고 AI 특화이며, Claude·GPT의 마켓플레이스·스킬 공유 사이트와 비슷한 역할일 수 있다. 건축은 프로젝트마다 필요한 것이 달라 jig라는 개념이 어울린다. 공식 제공 예정 목록이 J-01~J-09이며, 각 기능은 사용자가 과거 프로젝트에서 실제로 수행한 작업이다.

이 문서는 실제 구현 계획 이전에 그 **과거 경험을 파악하기 위한 조사**다. 위 문단은 사용자가 말한 개념을 요약한 것이고, 이 문서가 그 개념을 결정이나 요구로 확장하지 않는다.

### 0.2 조사한 것과 방법

1차 조사(S-01~S-17)는 로컬 프로젝트 폴더·GitHub 계정 저장소·Claude 세션 기록 세 유형의 출처를 기능별로 훑었다. 보충 조사(F-01~F-06)는 1차 조사가 남긴 미결 항목 — 자체 Grasshopper MCP 브리지의 본체 위치, GitHub 계정 저장소 전수와 가시성, 이전 IDE의 런타임 실행 로그, 사용자 전역 Claude 설정, 스킬 정의 파일 형식 원문, 일정표·회의록 세션의 파일 조작 기록 — 을 실측으로 닫았다. 보충 조사에서 1차 판정이 뒤집힌 것이 최소 5건 있고, 본문에 그 사실을 표시했다.

사용자 요청("내 계정 GitHub repo에 올렸던 것도 참고")에 따라 계정 저장소를 `gh repo list`로 전수 열거하고(19개), 기능과 겹치는 저장소는 얕은 clone으로 내용을 확인했다. 저장소별 판정은 §1·§2에 반영했다.

### 0.3 읽지 않은 것의 원칙

- 발주처·개인 식별정보가 섞일 수 있는 회의 자료 PDF·계약/견적 문서·대지 식별정보가 든 산출물 HTML은 열지 않았다.
- `.gh`·`.3dm`·`.drs` 등 바이너리는 열지 않았다. 관련 서술은 파일명·주변 텍스트 기록에 근거하며 추정인 경우 본문에 "추정"으로 표시했다.
- 비밀값(API 키, 계정 자격증명, MCP 시크릿 헤더)은 존재 사실만 기록하고 값은 옮기지 않았다.
- 미확인으로 남은 구역은 각 절 끝에 명시했다.
- 출처 코드(S-NN·F-NN)와 실제 로컬 폴더·세션 기록 경로의 대응표는 저장소에 두지 않는다(사용자에게 채팅으로 보고했고, 상세 메모는 조사 세션의 작업 폴더에 있다).

### 0.4 이 문서가 결정하지 않는 것

이 문서는 조사 사실과 대안 비교만 담는다. jig의 범위·우선순위·마켓 운영·결제·호스트 지원 범위·이식 대상 선정 같은 제품 결정은 쓰지 않는다. PRD와의 관계는 §5에 사실로만 적는다.

### 1.1 2026-10-07 보충 — 법규·규모검토 출처의 대응과 S-19

사용자가 2026-10-07 규모검토·법규 Q&A·도면 기능을 채택하며 "기존에 만들어놓은 코드와 repo들을 잘 활용할 것", cLAWde는 "새 저장소로 시작하는데, 옛 비공개 CLAWDE랑 규모검토 때 했던 법규 검토, ARCO-FULL에서 만들었던 것까지 3개를 모두 종합"하라고 했다. 세 출처의 대응은 다음과 같다. 조사는 각 출처의 README·안내 문서·최상위 구조만 읽었고, 비밀키 폴더·`.env`·키 파일과 대지 자료는 열지 않았다.

- **옛 비공개 CLAWDE = S-01.** 법규 검토 2세대(J-03의 5단계 파이프라인, 법제처 Open API 수집, 누락 방지 게이트).
- **규모검토 때의 법규 검토 = S-04(논현동 규모검토 작업공간).** 이 작업공간의 검토엔진은 S-01 코드를 이어받아 프로젝트 전용으로 발전시킨 3세대 작업본이며(작업공간 안내 문서가 그렇게 적는다), 법규 검토서·방법론·기계해석서(A/B/C)와 법규 질의 기록, 형상 계산(외피·대안·`.3dm` 내보내기)·검사 스크립트가 함께 있다. 공통 도구와 대지 어댑터가 한 코드에 섞여 있어 그대로 옮길 수 없다. S-03은 다른 대지의 1세대 작업본(지구단위계획 판독 절차서, 규모검토 PDF·건축개요 표)이다.
- **ARCO-full = S-19.** 실행본·개발 저장소·비밀키가 폴더로 나뉜 데스크톱 앱이다. 개발 저장소의 MCP 서버 가운데 이 기능들과 겹치는 것은 다음과 같다.
  - 법규: TypeScript MCP 서버. 법령·지자체 건축조례 온톨로지 DB(약 230 MB, Git 밖)와 법제처 API 수집·조례 수집·규칙 추출·관계 보강·적용 범위 검사 스크립트, 도구(법령 검색·조례 검색·해석례·판례·용적률·높이 제한·이격·주차·조경 검사·설계 전 체크리스트·준수 보고서·개정 이력).
  - 대지: 국토지리정보원 수치지형도 → `.3dm` 변환(GeoPandas·Shapely·rhino3dm, 좌표계 변환·지형 삼각분할).
  - 매스: 법규·기하·시뮬레이션 모듈로 나뉜 Python 매스 생성(외피·법규 자료원).
  - 지역 분석: VWorld 지오코딩·지적·용도지역, 건축물대장, 공시지가·실거래가, 국가통계 연동.
  - 도면: 조닝 결과 → DXF 2D(ezdxf)·3DM 매스 생성. 템플릿·기존 도면의 형식 보존은 다루지 않는다.
  - 조닝(실 배치)·공모 지침서 체크리스트는 이번 세 기능과 직접 겹치지 않는다.

  저장소 안내가 적은 한계: 시험 묶음이 없고, 대지·매스 서버의 일부 모듈이 빠져 있으며, 법규 서버는 표준 출력 오염 문제가 알려져 있다. 실행본의 사용 제한을 제거했다는 기록이 있어 코드·데이터의 소유·라이선스 관계는 재사용 전에 확인한다(§7 결론 ④와 같은 항목).

세 출처의 종합 방법과 재사용 지도는 [PLAN-46](../plans/PLAN-46-legal-qa.md) T-215(법규), [PLAN-45](../plans/PLAN-45-site-massing-jigs.md)·[PLAN-47](../plans/PLAN-47-drawing-generator.md) 「재사용할 기존 코드·저장소」가 소유한다.

## 2. 기능별 조사 결과

### J-01 사이트 모델링 (지형·주변 건물·도로·필지 + 공공 데이터 상세화)

**한 줄 결론 — 반복 수행. 다만 두 갈래 스택으로 갈라진 채 한 번도 통합된 적이 없고, 두 갈래의 유통 상태가 비대칭이다.**

**과거 수행 내역.** 네 출처에 실제 대지 적용·검증된 파이프라인이 각각 있다. ① S-02(Site Maker, 하루 만에 완성) — 국토부 SHP 임포트 → 필지 검색 → 3D 매스업을 GH Python 컴포넌트 3종으로 구현, 외부 파이썬 의존성 0. 한 도엽(약 600×600m, 12레이어)에서 피처 임포트 누락 0, 건물 수백 동 매스업 전부 닫힌 솔리드, 자체 좌표변환식을 상용 GH 플러그인 출력과 대조해 격자수렴각 차가 일치함을 확인. ② S-01/S-03/S-04/S-15(Node 계보) — 주소 한 줄 → PNU → 대지 사실 수집, 등고선·표고점 IDW 보간 지형, 건축물대장으로 기존 건물을 층별 용도까지 상세화, 간선도로변 고층 건물 전수 조사 자동화, 발급 건축물대장 PDF 좌표 기반 파서, watertight STL 3벌, `rhino3dm` `.3dm` 내보내기. 세 개 대지에 실제 적용.

F-01이 Site Maker의 발생 경위를 세션 로그로 복원했다: 상용 플러그인의 좌표계 왜곡 해결 요청 → 좌표계/인코딩 판별 → 국토부 설명서 PDF에서 코드 사전 추출 → 지번 검색 → 필지/건물/접도 필터링 → 층수 기반 매스업 → **사용자 요청("나중에 재활용하고 싶어서")으로 스킬 패키지화**. 즉 스킬화는 사후 요청이었다.

**입력·데이터.** 국토정보플랫폼 연속수치지형도 1:5000(EPSG:5179, UTF-8), 국가공간정보포털 연속지적도(EPSG:5186, EUC-KR), 연속수치지형도 데이터 설명서 PDF 153p → JSON 사전(레이어 107/속성 66/코드값 503/통합코드 423), VWorld Open API, 주소기반산업지원(→ PNU 19자리), 건축HUB 건축물대장, 세움터 발급 대장 PDF, 서울도시공간포털(무인증 내부 API). SHP는 **전 출처에서 사람이 웹에서 수동 다운로드**했다.

**절차.** 경로 ①(Rhino/GH 완결): 사람이 SHP 다운로드·`.prj` 확인 → 자동 파싱/재투영/인코딩 판별 → 사람이 Panel로 좌표계·앵커·피처 수 육안 확인 → 반자동 체크리스트 생성 → **사람 수배선(폴더가 둘이면 `origin→anchor`, `epsg→crs` 두 줄)** → 자동 질의·분리·돌출 → 사람이 Rhino 없이 도는 selftest 통과 후 캔버스 확인. 경로 ②(Node): 주소→PNU→수집→규제 기하→법정 외피→대안→매스까지 완전 자동, 접도·건축한계선·고시 확정값은 사람 수기(`estimated` 플래그), 자동 수집값 `*.auto.json`이 사람 확정본 `site.json`을 덮지 않고 대조로 드리프트를 탐지.

**재사용 자산.** 그대로: `1_importer.py`(675줄, SHP/DBF/PRJ/CPG 파서 + TM 정·역변환 + 좌표계·인코딩 판별), `2_site.py`(285줄), `3_mass.py`(218줄), `IO.json`, `ngii_spec.json` 코드 사전, `gh_stubs.py`(328줄)+`selftest.py`(Rhino 없이 컴포넌트 회귀 테스트), Node 계보의 `massing.js`·`geofiles.js`·`terrain.js`·`export_3dm.js`, API 실측 문서 2종. 손봐야 함: Site Maker 미구현 4종(건물 실측 높이·**지형 서피스 생성**(지반 항상 Z=0)·구 좌표계 데이텀 변환·도로명 매핑), 검토엔진의 대지 고유 가정 미분리. 재작성: 두 스택 간 공유 코드 없음(SHP 파싱·좌표변환·필지 검색이 파이썬과 JS로 각각 독립 구현).

**AI 활용 방식.** SKILL.md `description`에 사용 조건과 금지 지시를 한 문장에 담음("검증된 컴포넌트 세트가 이미 있으므로 처음부터 새로 짜지 말 것"). 폴더 진입 규약(읽는 순서 → 절대 규칙 6가지 → 작업 방식 → 환경 전제 → **커버하지 않는 것** + "사용자에게 이 한계를 숨기지 말 것"). 효과가 확인된 지시: "로컬에서 먼저 돌리고 캔버스는 나중", "에러 없음을 성공으로 읽지 마라", "남의 컴포넌트 출력으로 내 계산을 교차검증하라", "캔버스는 사용자의 문서(진단용 컴포넌트를 만들지 말고 `print()`만)", 도구 부재 시 폴백 병기.

**문제·함정.** 반복 실패가 거의 전부 **"에러 없이 틀린 결과"**다 — 파일마다 원점을 새로 잡는 임포터(레이어 간 최대 70.5m 어긋남), 제품별 좌표계 불일치, 앵커 이동, 두 데이터셋 배선 누락, 셰이프파일 외곽링 시계방향(매스가 지하로 감), 도로경계면 레이어를 건물로 오인, 무벽건물이 연면적을 27% 부풀림, typeHint 누락 시 `System.Guid` 마샬링으로 조용히 빈 결과, 인코딩 통념 오류, 건축HUB 페이지네이션 누락. 코드로 못 고치는 것: 원본 데이터의 지적불부합(수십 cm대 체계적 오프셋), IDW 보간의 정보 한계. 운영 사고: 무보호 정적 호스팅으로 대지 위치·규모 노출(정책 2회 변경), `--project` 누락으로 다른 대지 자료 덮어쓰기, API 키 3종이 세션 메모 `.md`에 평문 저장.

**설명과 과거 경험의 간극.** ① 기능 설명의 "공공 데이터로 상세화"(건축물대장)는 스킬화된 쪽(Site Maker)에 **명시적으로 범위 밖**으로 적혀 있고, 대장 연동은 비공개 저장소 계보에만 있다. ② "지형"이 가장 약하다 — Site Maker는 등고선을 파싱만 하고 지반이 항상 Z=0이다. ③ "도로"는 형상까지만 있고 이름 대조표가 없다. ④ 입력 첫 단계가 여전히 수작업이고, 사용자가 2026-08-19와 08-31 두 세션에서 "SHP를 직접 받아야 하나 API로 자동화되나"를 물었으나 둘 다 미해결로 종료됐다. ⑤ F-02 확정: Site Maker 세트는 **GitHub에 올린 적이 없고 로컬에 `.git`조차 없다**(저장소 19개 전수 + 코드검색 3질의 `total_count:0`). 조사 전체에서 가장 잘 패키징된 자산이 버전관리 밖에 있다.

**미확인.** 사용자 계정 계획 저장소의 사이트 모델링 확장 계획 본문과 대응 워크플로 스크립트 4종(`phase0-env-setup-wf`·`phase1-web-expansion-wf`·`phase2-rhino-incremental-wf`·"사이트 모델링 설계 검토")을 아직 읽지 못했다. J-01 조사에서 가장 큰 공백이다.

### J-02 사이트 분석 (분석 자료 HTML 생성, pptx·Figma 내보내기, MCP 연결)

**한 줄 결론 — 네 갈래로 수준이 갈린다. 커스텀 HTML 생성은 반복 수행(최소 6개 코드베이스), MCP 연결도 반복 수행하되 용도가 형상 전용, Figma는 1회 실제 수행 후 단절, pptx만 여전히 전부 사람 손.**

**과거 수행 내역.** HTML: S-01/S-03/S-04가 정적 규모검토 리포트 빌더를 제품 수준으로 구축 — 백엔드 불필요·런타임 JS 없는 단일 파일 `index.html`, A4 가로 1장 인쇄 규범 `review.html`, 아티팩트 발행용 래퍼 제거본 `review.artifact.html`, three.js 3D 뷰어·대안 조합기. 법규 HTML 3종(A 검토서/B 방법론/C 기계해석)과 분석 HTML 2종(대장 경향, 임대료·공개공지). S-13은 "markdown은 diff/세션복원용, HTML은 사람 보고용"을 정식 ADR로 명문화. S-05·S-11도 각자 자기완결 HTML 대시보드를 만들었다.

**이전 판 정정 — Figma는 "기록 없음"이 아니다.** 2026-09-07에 Rhino 씬 스냅샷(preflight JSON 1.8MB) → UserString 메타데이터로 객체 선별 → **Rhino 밖 CPython에서 shapely·pymupdf로 SVG path 직접 조립**(`render_diagram_vectors.py`, 파일 머리 주석 `"No geometry is invented or moved here"`) → 단계 5개를 **완전히 동일한 파라렐 카메라**로 캡처(camera/target/frustum 일치를 코드가 `assert`로 검증, 결과 JSON에 `same_camera_verified: true`) → PNG → Figma 경로를 실제로 완주했다. 1차 메모 17건이 이를 못 본 이유는 그 코드가 조사에서 건너뛴 하위 폴더에 있었기 때문이다.

또한 "발표자료"의 실체가 pptx가 아니라 **3D 뷰어 HTML 위의 프레젠테이션 레이어**(장면 챕터 네비게이션, 캡션 블록, 범례, 주석 라벨 칩+리더선, 도넛/막대 차트 규격, 회색 컨텍스트→대상 강조 연출)였고, 그 규범 문서 `DESIGN.md`를 **3안 병렬 초안 → 심사위원 3인 5기준 채점 → 종합 → 적대적 완전성 비평 2회 루프** 워크플로로 생성한 원본 스크립트(135줄)가 남아 있다.

**입력·데이터.** 건축HUB 대장, 세움터 발급 PDF(소유자·설계자·시공자 칸은 의도적 미판독), VWorld, 법제처 Open API + 로컬 FTS5 DB, 임대료 표본, Rhino 문서 상태(`active_document.json` → `rhino-scene.json`, JSON + base64 양자화 정수 버퍼), 다이어그램 팔레트 JSON, 레퍼런스 이미지 6장, 기존 사무소 서식 xlsx. 형식은 전부 **JSON을 단일 출처로 두고 산출물을 빌드**하는 구조다.

**절차.** 자동: 수집(프로젝트당 외부 호출 24~26회, 이후 네트워크 없이 로컬 재현) → 판정 계산(순수함수) → 차트·HTML 조립 → 다이어그램 조립(씬 JSON → 투영·유니온·파선 dedupe → SVG → PNG) → 카메라 일치 자동 검증 → `report:verify` 게이트(실패 시 exit 1) → 브라우저 실검증(Playwright류 스크린샷; 오피스 문서는 Excel COM→PDF→PNG). 사람: 분석 질문·가설 설정, 표본 선정·확정값 기입, 레이아웃·색·타이포 판단(스크린샷·참고 사이트 URL·레퍼런스 이미지로 지시), 서술형 판단 문장(LLM 개입을 `plan-A.json`·`review-direction.json` **두 파일로만** 제한), **Figma 안의 모든 편집**, pptx 전 과정.

**재사용 자산.** 그대로: 검토서 HTML 형식 규범 문서(A4 가로 1장, "결정→이득" 구성, 근거 위임사슬 전 구간 링크화, 발주처 전달본 톤 규칙, LLM 슬롯 2개 한정) — **사무소 산출물 형식 규범이 성문화된 유일한 사례**. 디자인 규범 생성 워크플로 스크립트. 결정적 SVG 렌더러. ADR 형식. Cloudflare Workers 비밀번호 게이트 최소 예시(HMAC 서명 쿠키, 8시간 세션). 손봐야 함: 발표 HTML 템플릿(좌측 레이어 패널·그림자/채광 슬라이더·뷰 저장·PNG 내보내기·**출처 태그칩 3종(대장/API/추정)**·localStorage 설정 — 구조는 좋으나 좌표·레이어·색이 대지 전용), 서식 복제 xlsx 생성기. 재작성: pptx 생성기(선례 0건, Desktop 전체에서 `python-pptx` 사용 파일 0), Figma **역방향**, 웹 채팅 UI(설계만 있고 미구현).

**AI 활용 방식.** 산출물을 먼저 아티팩트로 만든다(빌드 산출물에 아티팩트 발행 전용 변형본이 정식으로 들어가 있고, 이전 IDE 런타임 11세션에서 `artifact_write`가 전체 툴 호출 중 2위 206회). "왜 그럴지 가설을 먼저 세우고 검증하라". 정답이 없는 산출물에는 경쟁 초안 + 심사 + 적대적 비평. 디자인 규범 문서를 코드보다 먼저 고친다. 결정적 코드에 "지어내지 말 것"을 주석으로 박음. 입력 JSON에 `basis` 문자열로 전제의 불확실성을 데이터에 같이 기록.

**문제·함정.** 보안이 가장 크게 대가를 치른 항목 — 2026-08-20 정적 리포트 2건이 비밀번호·SSO·IP 제한 없이 공개돼 대지 주소·면적·계획 규모 노출, 즉시 중단 후 "호스팅하지 않는다, 파일 하나 전달"로 정책 전환, 2026-09-23 Cloudflare 비밀번호 게이트로 재시도. 지자체 포털 API가 소유자 성명·주민번호 앞자리를 무인증 반환 → 호출 금지 목록 등재. 조용히 틀리는 렌더링 버그 다수(필드명 불일치로 `—` 렌더, 법령 언어 키와 엔진 키 불일치로 조인 전량 누락, id 중복 앵커 충돌, JSON 배열의 문자열 키가 `JSON.stringify`에서 소실, iframe 내장 시 localStorage 오염). 정본 단절: **다이어그램 정본이 Figma에만 남고 폴더에는 캡처 PNG만, SVG는 저장되지 않으며 보고서로 되돌아오는 경로가 없다** — 본인의 감사 워크플로가 "재현·보고서 편입에 공백"으로 직접 지목했고, 분석 차트와 발표 HTML도 이어지지 않는다고 적었다.

**설명과 과거 경험의 간극.** ① "사이트 분석"이 과거 기록에서 최소 5개 산출물로 갈라져 있고 빌더도 다르며, 프로젝트 자체 분석 목록에 아직 그래프화되지 않은 항목이 더 있다. ② pptx는 데이터도 있고 서식 복제 기술도(xlsx에서 완주) 있는데 **슬라이드 레이아웃 규범만 없다**. ③ Figma는 "해본 적 없다"가 아니라 "한 번 해보고 단절된 채로 두었다"이며 필요한 것은 왕복과 정본 위치 결정이다. Figma MCP는 플러그인으로 이미 설치돼 있으나 그 작업에는 쓰이지 않았다. ④ MCP는 과거에 형상 전용이었고 분석 경로에 붙은 유일한 사례(Rhino↔HTML 동기화)도 **실시간이 아니라 명시적으로 실행하는 파일 기반 동기화**라고 두 문서가 각각 못박았다.

### J-03 법규 검토 1 (주소 입력 → 법·시행령·조례 원문 구조화 수집 → DB → 검토용 HTML)

**한 줄 결론 — 조사 대상 중 과거 경험이 가장 두껍다. 3세대에 걸쳐 재작성됐고 서로 다른 대지 3건 이상에 실제 적용·발행됐다.**

**과거 수행 내역.** 1세대(S-03, 3일): 지구단위계획 PDF 15건(약 320p, 스캔본 3건 포함)을 파이썬 3종으로 판독하고 문서 12개로 재구조화, 함정 12개·골든 데이터 12항목을 담은 재현 절차서를 남김 — 재사용 단위가 코드보다 **절차서**였다. 2세대(S-01 CLAWDE, 89~91커밋): 5단계 파이프라인(SCOPE→RAW→NORM→RULES→VERDICT), 법제처 Open API로 하루에 법령 31종 13,719레코드 수집, `project:init`으로 주소 한 줄 → 프로젝트 DB, 지구단위계획 PDF 분류→OCR→결정도 색상 판독→고시 이력 판정, 원본 대조 47개 항목 전수 검증(불일치 2건), 누락 방지 3중 게이트(한국건축규정 필수 140조문 대조 + 재위임 스캐너 + 사무소 표준 35항목). 3세대(S-04 검토엔진): 산출물을 A(원문 검토서)/B(방법론)/C(기계해석서 + `constraints.auto.json`) 3종으로 분리, 법령 DB 41종 21,367레코드, 위임 그래프·부칙·별표 파싱, `law:coverage` 게이트.

**보충 조사로 특정된 것.** 종전에 "15개 병렬 서브에이전트"로만 적혀 있던 적대적 검증의 **실제 기구와 스크립트 원본**이 확인됐다. Claude Code `Workflow` 툴 위에서 도는 JS(ESM)이며 `export const meta = {name, description, phases}` + `pipeline(items, fn...)` + `parallel([...])` + `agent(prompt, {label, phase, schema})` + `log`/`phase` API 위에 작성됐다(import 문이 하나도 없다). 같은 트리에 28개가 있고, 확인된 2종은 (a) 사무소 공용 인허가 원표 22행을 현행 법령과 대조하는 2단계 `Audit→Verify`, (b) 6개 분야 × (조사+검증) + 비평 1 + 갭 2 = **정확히 15콜**, 그리고 (c) 10개 감사 영역 4단계 `Audit→Verify→Critique→Synthesize`로 **한 실행에 20~40콜**이다.

**입력·데이터.** 법제처 Open API(법률/시행령/시행규칙/자치법규/행정규칙 본문·**별표**·**부칙**, `Referer` 헤더 필수), 주소기반산업지원, VWorld, 건축HUB, 서울도시공간포털(브라우저 XHR 역설계, 진입 키는 사람이 지도 클릭), 서울건축문화포털 가로구역별 최고높이(수치가 이미지 PDF), **자치구 건축위원회 심의기준(API 없음, 웹+PDF/HWP, 2019~당해년 작성분 혼재)**, 국토부 한국건축규정 별표1(408조문 중 필수 140), 지구단위계획 원본 PDF(API로 못 가져오는 유일한 소스), 사무소 공용 인허가 체크리스트 엑셀 22행, 사무소 수기 검토서 145행·13섹션. 오픈소스(`korean-law-mcp` 등)의 텍스트 정규화·별칭 해석을 "새로 발명하지 않는다"는 규약으로 이식.

**절차.** 전 세대를 관통하는 3원칙(원문 인용): *"① 숫자는 코드가 계산한다 — 재현되지 않으면 검토가 아니다. ② 자연어 해석은 LLM이 초안을 만들고 사람이 확정한다 — 확정 전에는 verified:null. ③ 도면과 현장은 사람이 본다."* 데이터는 3계층 — 원문 아카이브(시점 고정, **재수집으로 절대 덮지 않음**), 검색 정본(결정적 재생성), 판정 레코드(`{value, 출처, 확인일}`). "공포 후 시행 전" 법령은 별도 JSON으로 분리 보관. 3세대에 "세션 하나 = 절 파일 하나" 규율 추가. **끊긴 구간**: 다중 에이전트 조사의 병합 결과가 파일로 저장된 흔적을 찾지 못했다 — `journal.jsonl`에 `result` 이벤트는 있으나 대응 산출 JSON이 없고 사람이 손으로 다음 입력에 옮겨 적은 것으로 보인다.

**재사용 자산.** 그대로: 법제처 연동 3종(`fetch_law`/`normalize`/`index_law`), 텍스트 정규화, 트리거→법령 지도·용어사전·KBR 인덱스·조례 표준 데이터, 지구단위계획 JSON Schema, 판독 3종(각 100~160줄, 외부 상태 없음), 누락 방지 게이트(코드보다 "무엇을 검증하는가"의 패턴), `law-review` 스킬 3파일, **법규 대조 워크플로 스크립트(대지 팩트 블록만 갈아끼우면 다른 대지에 적용 가능)**, 절 정의 계약 `_SCHEMA.md`(9개 절, 7종 어휘), 설계 원칙 문서 7종, 실행계획 문서 틀. 손봐야 함: 판정 로직(저장소 자체가 "대지 고유 가정과 미분리 혼합 코드"로 분류), 법령 JSONL(시행일이 있어 최신성 재확인 필수), 체크리스트 데이터(구조만 이식). 재작성: 웹 질의응답 UI(설계만 있고 미구현), 스킬 버전 관리·재배포 장치(어디에도 없음).

**AI 활용 방식.** 세대별로 패키징이 달랐다 — 2세대는 `.claude/` 설정·서브에이전트·MCP·훅이 **전혀 없고** `CLAUDE.md` 한 파일이 규약과 작업 로그를 겸했다(278줄/40KB까지 비대). 3세대는 `AGENTS.md`와 `CLAUDE.md`를 동일 본문으로 두고 짧은 진입 문서(12줄)가 긴 아키텍처 문서(297줄)로 라우팅하며, **"추가 세션 절차·승인 양식·자동 훅은 두지 않는다"**를 명시한 뒤 품질을 코드 게이트로 강제했다. 효과가 있었던 지시: LLM 개입 슬롯을 파일 2개로 못박기("완전 자동화가 아니라 균일한 결과가 목표"), 검색과 생성의 분리(법령 정본 116만 토큰 대신 컨텍스트팩 5.8K + 검색결과 2~4K = 회당 약 9.5K), 고정 답변 규칙을 인용문으로 첨부, 환각 방지를 기계 검증으로(`ref` 화이트리스트 + 수치가 인용문 안에 실제 등장하는지 문자열 매칭), `verified:{by,date}` 게이트, **규범은 문서가 아니라 게이트가 강제**("MD 규범만으로는 일관성이 보장 안 된다"가 명시적 근거로 문서에 남아 있다), 조사 규율을 프롬프트 상수로("1차 출처 우선, 블로그만으로 확정 금지"), LLM이 틀리기 쉬운 지점 4종을 문서에 명문화("전부 그럴듯한 오답이라 검증 장치 없이는 안 걸러진다").

**문제·함정.** 수집: 법제처 API가 특정 공포본에 고정돼 법령 4종이 최대 **2년 뒤처진 채 조용히** 사용되고 있었음, 재수집 시 시행일 역행 사고, 건축HUB 페이지네이션 누락, 자치구 심의기준은 API가 아예 없음. 텍스트·DB: 한국어 FTS5 recall 3%(2-gram 자체 색인으로 회복), **부칙이 정규화 단계에서 통째로 버려짐**, **별표 43건 소리 없이 소실**, 별표 줄바꿈 병합으로 한글 단어 35.9%가 중간에서 끊김, 조 레코드의 `text`가 제목뿐이라 그대로 인용하면 "원문을 실었다"는 거짓 근거가 됨. 판정: 구역명 매칭으로 고시 적용 여부를 판단하면 두 사례 모두 틀림, 상한용적률 오독, **근거 없는 산식을 단정적으로 써 온 사건**(사용자가 "이 산식 어디서 나온 거야?"라고 캐물어서야 드러남 → 코드에서 제거, `law-review`의 "산식 발명 금지" 조항이 됨). 누락: **3중 게이트를 모두 통과한 검토서에서도 6건 누락**(법정 목록에 없는 실무 관행 항목). 도면 판독: CID 폰트·폰트 서브셋으로 한글 추출 실패 → 페이지 이미지 렌더 우회, 파일명 신뢰 금지. 운영: 무보호 배포 노출 사고, **API 키 3종 평문 저장**, 워크플로 크레딧 소진으로 전량 실패 2회, **조사 결과가 파일로 안 남아 사후 감사 불가**.

**설명과 과거 경험의 간극.** ① "법·시행령·조례 순서"는 실제로는 5계층 + 위임 그래프 + 부칙·별표였고, 부칙과 별표는 각각 한 번씩 통째로 소실된 전력이 있다. ② "DB 구축"은 1회 작업이 아니라 유지 작업이다. ③ "사람이 검토할 HTML"이 1종에서 3종으로 갈라졌고 C만 지오메트리로 넘어간다. ④ 서울 밖은 사실상 미지원이다. ⑤ J-03 자산은 전부 계정 안에만 있다 — 이식은 "공개 코드 가져오기"가 아니라 **비공개 자산 반입**의 문제다.

### J-04 법규 검토 2 (모델 연계: 일조사선·건축선으로 가능 매스 자동화, 고시는 사용자 투입)

**한 줄 결론 — 반복 수행. 2026-08~09 약 6주간 2세대 코드로 최소 3개 대지에 적용했고 npm 명령 한 줄로 법정 외피가 나오는 수준까지 갔다.**

**과거 수행 내역.** 2026-09-01~04에 「법규→지오메트리 자동화」 집중 작업 — 건폐율 후퇴 이진탐색, 민법 이격, 정북일조 제외 판정, 일조 절삭을 **캡슐(선분 팽창)로 교정**, **지적 기반 일조 기준선**(인접 대지를 실측으로 분절), 5단계 뷰어 파이프라인 도입. 대안 비교 엔진(밀도완화 × 층수 × 주차 전 조합). 2026-09-10~15에 정북일조 완화안 조건부 비교, 대안 A/B/C 매스(공개공지 미설치/옥외형/필로티형), 지하주차 계획, **사람이 CAD에서 편집한 PDF/DWG/Excel을 역으로 반입해 층별 면적표를 재현**.

**입력·데이터.** 자동: VWorld, 연속지적도(일조 기준선 분절의 실측 근거), 연속수치지형도, 법제처(건축법 §86 등), 건축HUB, 주소 API, 서울도시공간포털. 사람 투입: 가로구역별 최고높이 지침도(이미지 PDF), 지구단위계획 결정조서·결정도·시행지침 PDF, 접도·건축한계선, 발급 대장 PDF, 사람이 편집한 CAD/Excel.

**절차.** 자동: `clean-rhino`(purge → material 순서 강제), `export-d5`(dry-run 카운트 → 확인 → `D5_APPLY=True`). **사람(대체 불가)**: D5 Sync/LiveSync 클릭, 카메라·태양광·앵글 세팅, 2안 비교 레이아웃, 변경 부위 색상 다이어그램 작성, 인페인팅 마스크 범위 지정, PSD 합성, 배포용 압축. 레퍼런스 쪽은 반대로 자동 비중이 크되 업로드는 항상 사람 승인(`--upsert --confirm-db-write` 없으면 dry-run), 동일 건물 병합은 끝까지 자동 승인하지 않고 사람 승인 큐.

**재사용 자산.** 그대로: `export-d5` SKILL.md + `exportd5_prep.py`(매핑 API가 라이브 검증됨), `export-common/strip_prep.py`, `clean-rhino`. 손봐야 함: "느낌 → 구조화 필터 + 영어 HyDE 묘사 → 임베딩" 프롬프트 구조(출력이 검색용이라 렌더 입력용으로는 재설계 필요), 통제 어휘 단일 소스, 레퍼런스 스키마·새 소스 추가 런북, D5 JSON 스키마(역공학 필요). 재작성: 2안 비교 레이아웃·Façade sketch(전부 사람 손), **AI 후처리 — 코드·설정·프롬프트가 어디에도 남아 있지 않다**. 존재하지 않음: D5 자동 푸시(SKILL.md가 "blocked — no D5 command surface"로 명시), 최적 exemplar 자동 선택, D5 재질 3종 검사 스킬(요청됐으나 미착수).

**AI 활용 방식.** `description`에 한/영 트리거 촘촘히 나열, 본문 고정 구조(When to use / Prerequisites → Procedure → **Gotchas(baked in — do not "fix" out)** → Parameters → Not yet implemented → Reference), **diagnose → confirm → apply 3단** + 계획을 Rhino 세션 sticky에 저장, **로더 패턴**(코드를 채팅에 붙이지 않고 절대경로 `exec()` 한 줄 — "검증된 코드가 매번 바이트 동일하게 돌게"), 메모리 되먹임. 레퍼런스 쪽은 확인 질문 예산 0~2턴 하드캡, 필수 슬레이트 우선순위를 프롬프트가 규정. 공통: 비용 게이트(N=10→100→전체 스모크 사다리, 임계 초과 승인), **판정자 하나를 믿지 않기**(단일 판정 정확도가 부풀려진 것을 독립 모델 블라인드 A/B로 재검증해 오류율 9.3%→2.7%로 정정), 생성 출력에 결정적 critic-in-loop.

**문제·함정.** D5는 스크립팅이 불가능하다(커맨드도 대시 매크로도 없음) — 자동화는 Rhino 준비까지이고 마지막 Sync는 항상 사람 클릭. 매핑 네임스페이스 혼동, prep 자체가 파괴적이라 매 실행 복사본 질문이 필수, SketchUp export 모달 대화상자가 무인 실행을 멈춤. 용량이 반복 문제(컨텍스트 3dm 80MB→656MB, 제안서 PDF 469MB→3.8MB 별도 제작, D5 zip 1.5GB 중복). **AI 후처리의 재현성 0** — 남은 것은 결과 파일명뿐. 비전 파생 태그는 통제 어휘 이탈률 약 24%로 "advisory로만 취급".

**설명과 과거 경험의 간극.** ① "노드 방식 자동화"에 대응하는 과거 경험이 없다 — 렌더를 GH 그래프나 파이프라인 노드로 자동화한 증거가 어느 출처에도 없고 이전 IDE 메모가 명시적으로 없다고 기록한다. 사용자가 말한 "노드"가 GH 캔버스인지 jig 내부 파이프라인 그래프인지에 따라 참조할 선례 자체가 달라진다. ② "스케치로 지칭"은 이미 실무 습관이지만 기계가 읽는 포맷이 아니었다(다만 펜 스트로크를 프레임 좌표로 AI에 전달하는 구현 선례가 S-14에 있고, 대상이 렌더가 아니라 모델 편집이다). ③ "느낌(말)" 입력은 강한 선례가 있으나 출력이 **생성이 아니라 검색**이다. ④ 레퍼런스 자산이 두 갈래로 존재하고(프로젝트 폴더에 흩어진 수집 이미지 vs 정본화된 4만 건 DB) 스키마·태깅 수준이 전혀 다르다.

### J-07 패널링 (파사드·브릿지 패널링, Grasshopper 연계)

**한 줄 결론 — 반복 수행. 서로 독립적인 네 경로로 여러 차례 해봤고, 이전 판의 "실무 패널링 수식·파라미터 증거 0" 판정이 보충 조사로 뒤집혔다.**

**과거 수행 내역.** ① S-06: 브릿지 패널링 `.gh`가 날짜별로 5차까지 누적(0723·0812·0818·0819·0824), 앞단에 "선정리" 3차. 후속으로 3D 프린팅용 미소모형 단계에서 지붕·측면 패널·기둥·천장을 native Brep 솔리드로 재구성(Python venv 오프라인 메시 처리 → C# RhinoCommon을 `csc.exe`로 즉석 컴파일 → 라이브 문서 반입 → 재읽기 검증). ② **F-01 신규**: 그 GH 작업이 실제로는 Wireify(자체 GH MCP 브리지) 에이전트 루프로 구동됐고 정의별 홈 3개가 J-07 계열이다. `MEMORY.md`가 사실상 산출물로, **v8→v13 개정 이력이 날짜별 symptom/cause/fix 형식**으로 남아 있다 — 타일 클러스터링 임계값 **1.45 × 최근접거리 중앙값**, **Euler 곡률 기반 타입 분류**, **attractor 개구부 스케일 공식**. ③ S-12(`rhino-easy-panelling`, 커밋 15개): 원통 곡면 위에 **Hat monotile 비주기 패턴** 생성 → **mold-type(제작 몰드 수 제한) 분류** → Rhino 8에 Block/Instance + closed Brep으로 bake → mold별 색상·UserText → 실패 패널은 `FAILED_CLOSED_BREP` 레이어 격리. **Grasshopper를 쓰지 않는다**(순수 RhinoScript/RhinoCommon + FastAPI + React/r3f). ④ S-10/S-17/F-03: 이전 IDE의 `gh-paneling-cookbook.md`(6,993B) 외 쿡북 2종.

**보충 조사가 확보한 검증된 수식(F-03).** isotrim UV 그리드는 `Interval.ParameterAt(t)`로 정규화 좌표를 실제 도메인에 매핑한 뒤 `srf.Trim(uInterval, vInterval)`(0..1을 직접 가정하지 않는 게 핵심). attractor 개구율은 `t = min(1, dist(centroid, attractor)/falloff)` → `ratio = near + (far-near)*t` → `inner.Transform(Transform.Scale(centroid, min(0.95, ratio)))`(축척 상한 0.95로 가장자리 침범 방지). 후판 솔리드화는 `Brep.CreateOffsetBrep(panel, thk, solid:true, extend:true, ...)`. 곡면 다중 개구는 커브를 `Curve.CreateBooleanUnion`으로 먼저 합치고 `Curve.CreateBooleanDifference` 후 **전체를 한 번에** `Brep.CreatePlanarBreps`에 넣어야 홀이 내부 루프로 분류된다(하나씩 넣으면 원반으로 막히는 "고전적 실패"). 오프셋 안전 판정은 UV 8×8 샘플 `CurvatureAt().Kappa()`의 최대값으로 `minRadius = 1/kappaMax`, 경험칙 `|offset| < 0.7 * minRadius`. 세 파일 모두 "실패 시 조용히 덮지 말고 `report`에 남기고 해당 패널을 결과에서 제외"를 반복 명시한다.

**입력·데이터.** 공공 데이터·API·법령 DB를 전 출처에서 전혀 쓰지 않는다. 유일한 실질 입력은 Rhino/GH 안에서 사용자가 선택한 지오메트리다(S-12는 Mesh → best-fit 평면 투영 → UV(mm) → 로컬 백엔드 POST, F-01은 `introspect_component`로 캔버스 라이브 지오메트리 실측). 파라메트릭 기본 곡면은 원통 R=8000 / H=9000 / arc=120°. 외부 알고리즘 레퍼런스로 2023 발표 Hat monotile JS 구현을 파이썬으로 포팅.

**절차.** 경로 A(수동): 사람이 선정리 → GH 정의 작성 → 슬라이더 조정 → 차수별 파일 저장 → 육안 판단. 자동은 GH 솔버뿐이고 버전관리·차분·검증 자동화가 없다. 경로 B(Wireify 루프): `.gh` 열림 감지 → 홈 자동 스캐폴딩 → HTTP MCP 연결 → CLI 자동 기동 → `get_document_summary`(사람에게 되묻기 전에 먼저 확인하도록 강제) → `introspect_component` → **타입 힌트 명시한** CPython3 작성 → `set_source`/`set_io` → `wire` → `read_runtime_errors` → 원인별 재시도. 경로 C("one-paste"): 웹 UI가 만든 명령 한 줄 복사 → Rhino 커맨드바 붙여넣기 → 지오메트리 선택 → UV 투영 후 POST → 슬라이더 조정(200ms debounce) → "Export Python" 버튼이 패턴 엔진 + Brep 빌더 + 엔트리포인트를 **하나의 `.py`로 인라인 번들링**하고 설정값을 리터럴 dict로 주입 → Rhino에서 실행해 그 자리에서 재계산 + bake. 경로 D(IDE 내장): 인덱스 한 줄만 상시 주입, 본문은 `skill_read` 온디맨드.

**재사용 자산.** 그대로: `hat_substitution.py`(외부 CAD 의존 0), **`python_exporter.py`**(정규식으로 내부 import를 제거하며 concat → 설정값 주입 → 단일 `.py` export → 호스트에 붙여넣어 실행. **플러그인 설치 없이 호스트에 기능을 배포하는 선례로 J-07 밖에도 재사용 가치가 크다**), `APANEL_EXPORT_SURFACE.py`, `rhino_block_builder.py`, Pydantic 스키마(backend↔rhino 유일 공유 계약), **Wireify 홈의 `MEMORY.md`(유일한 실무 패널링 알고리즘 원장, 텍스트라 그대로 읽고 이식 가능)**, 쿡북 3종, 벤치마크 하니스 문서, `gh_stubs.py`. 손봐야 함: 서브에이전트·권한 설정 템플릿(저장소 밖 절대경로가 박혀 있어 이식 시 경로 수정 필수). 재작성: mold-type 산정·relief·boundary drop(원통형 스킨 전용), 프론트엔드, 쿡북의 **코드**(C#/.NET + named-pipe 브리지 강결합), Wireify/Cordyceps 브리지 자체(Rhino/GH 전용).

**AI 활용 방식.** **정본 스펙을 툴 권한으로 read-only 강제** — 문서에 "직접 수정 금지"라고 쓰는 데 그치지 않고 `settings.json`의 `permissions.deny`에 그 파일 하나의 절대경로를 콕 집어 `Write`/`Edit`를 차단. 스펙 문서 안에 복붙 가능한 첫 프롬프트를 내장. 서브에이전트 스폰 **4조건 게이트**(①≤2파일·≤300줄 ②프롬프트 ≤8줄 ③툴 ≤2개 ④단일 명령 검증 가능, 넷 다 만족해야 스폰. "탐색해봐"·"A/B 결정해줘"는 금지) + 핸드오프 3줄 형식. 스펙 편차 로그(번호 + 승인일). 오버핏 금지 프로토콜(벤치 점수를 올리는 개선은 하네스 본체가 아니라 스킬/쿡북 계층에만 — "스킬은 과제 특화 지식을 격리하는 안전판"). 발견의 승격 기준을 한 문장으로 규정("새 `.gh` 파일에도 성립하는 규칙인가?"). 커뮤니티 스킬 vendor-in 규율(라이선스 확인·커밋 해시 고정·보안 스캔 후 "베끼지 않고 그대로 vendor, 충돌 나는 곳에만 한 줄 오버라이드", `PROVENANCE.md`에 기록). **정반대 사례**: 같은 사용자가 실무 세션에서는 인계 문서에 `**No agents.**`를 두 번 박아 AI 병렬화를 완전히 껐다.

**문제·함정.** **`set_io`가 출력 배선을 항상 끊는다** — 3개 정의에서 독립 재발, 근본 수정 없이 매번 재배선 수작업으로 우회. **타입 힌트 없는 지오메트리 입력이 `System.Guid`로 마샬링돼 조용히 빈 결과** — 최소 3개 정의에서 독립 재발견, 공유 규칙으로 승격됐지만 도구가 강제하지 않고 기억에 의존. `convert_staged` 이후 소켓 id 교체로 `WIREIFY_NOT_FOUND`. **같은 머신에 자동화 채널 3개 공존**(자체 MCP 9473 / 이중 설치된 서드파티 `.gha` / `uvx rhinomcp`)이고 실사고가 있다 — 한 패널링 세션 중 **외부에서 순차 GUID의 C# 스위트가 캔버스에 무단 주입**된 것을 담당 에이전트가 발견하고 "내 작업 아님"으로 기록했다. 로그 신뢰도: connect 로그 361개 중 "failed"는 3건뿐인데 실제 마찰 대부분은 `MEMORY.md` 서술로만 남았다. 호스트 API: `InstanceDefinitionTable.Add` 5-arg 시그니처 오류를 바깥 `try/except`가 조용히 삼켜 원인 불명으로 오래 방치. `.gh` 바이너리라 diff 불가 → "단일 owner" 명문화, 실무는 차수별 파일 복제로만 버전 관리.

**설명과 과거 경험의 간극.** ① **"Grasshopper 연계"라는 기능 설명과 과거 판단 사이의 간극이 날카롭다** — 사용자는 2026-07-23에 Wireify식 GH MCP 배선 대 결정론적 단일-writer 브로커를 벤치마크로 실측 비교했고(R0 실패 11m07s → R1c 4m21s·R2b 4m05s·R3b 3m35s 성공, 마지막은 의도적 버그 주입 후 자가수리 검증), 이후 이전 IDE 제품에서 GH MCP 서드파티를 `DisabledDirectMcpNames`로 **코드 차단**했다. ② 정본 알고리즘이 둘로 갈린다(실무 브릿지 패널링의 텍스트 원장 vs Hat monotile 생성기, 후자는 GH를 쓰지 않는다). ③ 제작성 판정이 미완이다(mold budget 초과는 경고만, 지오메트리 검증은 스텁). ④ 경계 셀은 드롭하고 최종 경계는 시공 단계 사람 처리로 타협했다. ⑤ 파사드 패널링의 정본 스펙(v0.7, 37~38KB)이 저장소 밖 로컬 폴더에만 있고 동명 GitHub 저장소는 **커밋 0의 빈 저장소**이며, JSON round-trip 폐기 같은 구현 변경이 스펙에 반영되지 않았다.

### J-08 회의록 (녹음 → 정해진 형식의 회의록 → 변경 필요 사항 첨삭)

**과거 수행 내역(부재의 근거).** S-07이 가장 명시적이다 — **정식 회의록 서식이 발견되지 않았고**, 협의 흔적은 회의 전 준비 pptx 1건, 메신저 이미지가 폴더에 그대로 남은 것, 외부 발신 비정형 편지 docx뿐이다. 재사용 자산 판정에서 "회의록 — 다시 만들어야 함. **재사용할 형식 자체가 없음**"으로 단정했고, 문제 기록에 "협의 자료가 정식 문서와 메신저 캡처에 섞여 남아 **의사결정 이력을 나중에 재구성하기 어려운 구조**"를 남겼다 — 회의록 부재의 실제 피해가 관측된 유일한 기록이다. 녹음 실물은 최소 2건 있으나(S-06의 mp4, S-15의 약 39MB 파일) **둘 다 내용 미확인**이라 회의 길이·화자 수 같은 기본 수치가 없다.

**뒷단은 선례가 강하다.** F-06이 "원본 유지 → 사본에 피드백 8건 반영 → 사용자 확인 → 원본에 병합 → 구버전 삭제 → 표기 단위 일괄 치환" 사이클을 **추정이 아니라 실제 파일 조작 기록**으로 확정했다(J-05 참조). 더해 자동화·LLM 3원칙, `verified:{by,date}` 게이트와 경고 배지, ref 화이트리스트 + 인용-수치 문자열 매칭 검증, 누락 방지 3중 게이트, 규범 드리프트의 메모리화, 산출물 3종 분리, 빌드 게이트 exit 1이 모두 이 뒷단에 그대로 전이 가능하다.

**입력·데이터.** 확인된 J-08 입력물은 전부 로컬 파일이고 공공 데이터·API가 하나도 없다. STT·화자 분리 도구·회의록 템플릿·스키마는 어느 메모에도 없고, F-04가 전역 설정을 전수 확인했으나 등록된 MCP 서버는 `rhino` 하나뿐이며 오디오·전사 도구가 전혀 없다. 한국어 문서 도구 `kordoc`은 제3자 마켓플레이스로 실제 설치돼 있으나 **기록된 용도가 전부 읽기(HWP/PDF 파싱)**이고 생성 방향은 미검증이다.

**재사용 자산.** 그대로 사용 0건. 구조만 이식 가능한 것: 체크리스트 데이터화 게이트, `law-review` 3파일 세트(원칙+체크리스트+함정), 초안/확정 분리 메커니즘, 사본→정본 병합 절차(코드로는 없으나 절차가 완전히 기록돼 있어 코드화 가능), 프로젝트 스코프 메모리 형식, 버전관리되는 페르소나·금지목록 설정 파일, 구조 검토 보고서 양식(정해진 형식의 실무 문서가 어떻게 생겼는지의 유일한 표본), Workflow 오케스트레이션 API. 전부 재작성: 녹음 입력 처리, 전사, 화자 분리, 발언→안건 매핑, 회의록 템플릿, 첨삭 UI.

**문제·함정.** 회의 입력물은 민감정보와 분리 불가능하다 — 회의 PDF는 발주처 정보 혼재 가능성으로 미열람, 외부 발신 docx는 시스템 PII 처리로 접근 자체가 차단, 계약·견적 문서는 의도적 미열람. **회의 자료는 기본적으로 "열 수 없는 파일"로 취급돼 왔다.** 민감 값이 규약 밖 경로로 샌 전력이 둘(세션 메모 `.md`의 API 키, 사무소 온보딩 텍스트 파일의 공유 계정 자격증명) — "코드가 아니라 메모라서 보호망 밖"이라는 게 함정의 본질이고 **전사본도 같은 성격의 파일이다**. 자동 매핑 오연결 전력, 대형 미디어 무규칙 누적, 긴 처리의 사용량 한도.

**설명과 과거 경험의 간극.** ① **"정해진 형식"을 과거 산출물에서 역추출할 수 없다.** 다른 기능은 과거 산출물이 곧 형식 명세 역할을 했지만(법규검토서 13섹션, 구조검토 보고서 5단 구성, 일정표 탭 서식) 회의록에는 **복제할 원본 자체가 없다**. ② 앞단과 뒷단의 준비도가 극단적으로 다르다. ③ 녹음을 다루는 기능은 기존 규약("개인정보 금지·호스팅 안 함·파일 하나 전달", 둘 다 사고를 겪고 승격된 규칙)과 정면으로 충돌하는 첫 사례가 된다. ④ 남은 미탐색 구역은 한 프로젝트의 대형 세션 6개(134MB, 회의·협의 키워드로는 미검색) 하나뿐이다.

### J-09 구조 분석 (기존 구조 분석 · 그리드 생성 · 구조도 · 최적화 · 도면-모델 연동 · 일람표)

**한 줄 결론 — 반복 수행. 두 갈래로 갈라져 있었고 보충 조사로 두 갈래가 한 번 만난 지점이 확인됐다. 6개 요소 중 그리드 생성·최적화는 강한 선례, 도면-모델 연동은 1건의 수작업 선례, 기존 구조 분석·구조도 작성·일람표 관리는 선례 없음이다.**

**과거 수행 내역.** ① S-05/S-13(공개 저장소 서브트리): 규칙 격자가 아니라 **ground-structure 그래프** — 고정 지점·모듈 타겟·중간 레벨 보조 노드를 Rhino 좌표에서 생성하고 최근접 기준으로 후보 부재 5종을 연결. 각 후보 부재 = 정수 유전자 1개(0=비활성, 1..N=단면 인덱스), pymoo NSGA-II **3목적**(지점 개수 / 재료량 / 시각적 노출도) **+ 7개 부등식 제약**(안정성·연결성·응력비·처짐·세장비·지점반력·지점모멘트), custom sparse sampling/mutation/repair 오퍼레이터 주입. 해석 엔진 **3단 폴백**(PyNite → 자체 3D frame → 자체 3D truss), pymoo/numpy 없으면 순수 파이썬 랜덤서치가 같은 인터페이스 제공. Rhino 베이크 4레이어(centerlines / profiles TextDot / solid_preview / loads)와 부재별 **UserString 메타데이터**(단면명·응력비·축력). 4탭 대시보드(외부 차트 라이브러리 없이 canvas 직접 드로잉) — **Members 탭이 일람표에 준하는 유일한 화면**. 스모크 테스트가 **캔틸레버 처짐을 재료역학 폐형해와 대조**한다.

② **F-03 신규 — 이전 IDE의 건축형 서버 결정론 툴**: A계층 전체 목록이 `rhino_audit` · **`structural_extract`/`solve`/`loads`/`layout`/`size`** · `layer_scheme_draft` · `rhino_layers`인데, 이 중 **`structural_layout`은 작은보 자동 배치 제안**이고 **`structural_size`는 단면 자동 사이징 사다리**다 — 조형물 ground-structure와 다른 계보의 건축형 "그리드 생성" 선례다. 커브를 역할별(기둥/보/브레이스)로 자동 분류, 단면·지지·하중 ask-back 승인 카드, SLS 처짐 + ULS 활용률 스크리닝, 판정색 진단 뷰어 bake, `results.json` 단일 아티팩트. **라이브 실행 증거 확보**: 런타임 세션 1개에서 `solve`/`loads`/`size`/`extract`가 다회 호출됐고 `approval_request`가 구조 변경 승인에 실제로 쓰였으며, 승인 항목의 지문이 바뀌자 **CAS가 스테일 지문을 실제로 막았다**.

③ S-08(실무): 자동 최적화 코드가 **이 단계에 전혀 등장하지 않는다**. 하중표 작성(사람, 제공 자료 인용) → 균일 단면 1차 처짐 검토(**상용 SW**) → NG 모듈 식별 → 모듈별 단면 확대 재검토 → 보고서화. 보고서 양식(검토조건 표 → 다이어그램 → 처짐표(스팬/처짐/제한값/OK-NG) → 조정 후 재검토표 → 검토 의견)과 **유보사항 3건**(수평변위 기준 권장, "이번 부재 크기는 사용 가능한 **하한값**", 기존 바닥 구조가 이 하중을 반영하지 않았을 가능성)이 남아 있다. ④ S-06(유일한 도면-모델 연동): 도면 레이어 배치 → **대응 짝을 사람이 확인** → 객체별 이동량 X/Y/회전을 표로 기록 → 미대응 항목은 TextDot 표시 → 백업 후 이동/비이동 객체 수 재확인. GUID 단위로 근거를 남겼다.

**입력·데이터.** 주 입력은 **Rhino 레이어 명명 규약**이 사실상 API였다(`env::structure_start`, `structure_env::analysis_members`/`analysis_nodes`/`supports` 등). 강재 단면표는 KS/JIS H형강 8종 seed CSV(README가 "최종 검토 전 인증 제작사 export로 교체할 것" 명시)와 제품 쪽 `sections-ks.json`, 구조기준은 KDS 41 12 00 계열을 데이터 테이블화한 `load-tables.json`. 설계하중은 제공 자료를 그대로 인용(계산 근거 미기재). **공공 데이터·API·법령 DB는 J-09에 한 번도 쓰이지 않았다.**

**절차.** 코드 경로: 사람이 레이어를 미리 그림 → 좌표 추출(MCP 소켓) → 자중 추정 → 그래프 생성 → **사람이 대시보드에서 하중·제약·GA 파라미터 조정** → NSGA-II 진화 → FEA → **사람이 Pareto 후보 중 하나를 골라 베이크 지정** → 4레이어 베이크. 제품 경로: 읽기전용 extract(대기열 밖, 병렬 허용) → 자동 분류 → loads → layout → **ask-back 승인 카드**(grantId로 응답, 지문 변경 시 CAS가 막고 재발급) → size → solve → 스크리닝 → 뷰어 bake → 게이트 스크립트 회귀 검증.

**재사용 자산.** 그대로: `fea.py`(869줄, PyNite 우선 + 순수 파이썬 폴백. **PyNite 미설치 환경에서도 동작을 보장하는 방어적 import 패턴**이 특히 유용), `ground_structure.py`(격자가 아닌 위상최적화의 일반 패턴), `smoke_tests.py`, 단면 CSV(인증 단면표로 교체 필요), 공개 저장소의 `structural_check.py`. 손봐야 함: `optimize_structure.py`(1001줄, 목적함수·제약이 조형물 전용), 대시보드 2파일(**공개 저장소에 없고 로컬 스냅샷에만 존재**), 로컬 전용 스킬 3종(`structural_bake.py` 8,164B · `structural_profile.py` 10,707B · `structural_viewer.py` 9,569B), 지식형 문서 2종, 게이트 스크립트, 구조 검토 보고서 양식, 도면-모델 정합 표 포맷(객체 ID / 이동량 X·Y / 회전각 / 미대응 항목). 재작성: 구조 검토 요청 양식(비정형이라 재사용할 형식이 없음), **일람표**(어느 출처에도 부재/부호 일람표를 문서로 출력한 코드가 없음), **"구조도 작성"**(대응 코드 없음).

**공개본과 실물의 시차(정량화).** 공개 `main`은 2026-08-20에서 멈춰 있고 로컬이 앞선다. 스킬 파일 수가 로컬 13개 vs GitHub 7개로 **산술적으로 일치**해(로컬 전용 추가분 6개) 공개 스냅샷에서 바로 가져올 수 있는 J-09 자산은 `structural_check.py`·`structural-analysis.md`·`gh-pynite-cookbook.md` + 데이터 JSON 2종뿐이고 bake/profile/viewer와 최신 게이트는 로컬에만 있다. **GitHub만 보고 이전 자산을 평가하면 구조 기능을 과소평가한다.**

**AI 활용 방식.** Rhino 연결이 조형물 경로에서는 MCP 소켓(RhinoScript 코드 문자열 원격 실행), 제품 경로에서는 자체 툴 네임스페이스 + 인덱스 온디맨드. **결정론/LLM 경계**가 가장 반복된 원칙이다 — "탐지·계산은 결정론적 서버 코드, 해석·판단은 LLM", 그리고 저장소 최우선 규칙 *"모델의 성공 주장은 검증이 아니다 — 실행기 predicate만이 성공을 표시한다"*. 실행 전 요약표 강제(`| Step | Agent/Model | Files | Scope | Depends on |`, scope를 small/medium/large로 사전 선언), 서브에이전트 역할 분리표(메인=계획·큰 결정 / builder=1~2파일 surgical edit / investigator=위치 추적 / reviewer=diff 리뷰), 영구 진행 문서 금지(stale 방지), 코드형/지식형 스킬 구분("스킬 코드는 verbatim, 레퍼런스 노트는 자유 각색").

**문제·함정.** 자체 코드가 스스로 **"construction-ready 승인용이 아닌 탐색적 설계 도구"**라고 선언했고 실무 사인오프는 상용 SW + 사람이 따로 수행했다. PyNite API가 릴리스마다 변경돼 두 이름으로 순차 import 후 폴백. 임시 가정값이 코드에 남음. **구조 세션이 정작 구조 지식형 스킬 본문을 한 번도 `skill_read`하지 않았다** — 서버 결정론 툴만으로 일이 굴러갔고 "표본에 해당 과제가 없었을 수도 있다"는 대안 설명이 함께 남아 있어 단정하지 않지만, **스킬 본문이 실제로 소비된다는 증거는 없다**. 승인 카드가 드물게 쓰인다(11세션 합계 `approval_request` 2회 vs 가벼운 `ask_user` 12회). heavy-solve 45초 예산 초과로 `recovery_resume` 7회. 도면-모델 정합이 전부 사람 확인 기반. 대안 비교가 파일 분기라 diff 불가. 법규 게이트도 "구조안전 확인" 누락을 못 잡았다. **기존 구조 정보가 파이프라인 입력에 들어온 적이 없다.**

**설명과 과거 경험의 간극.** ① 6개 요소의 선례 밀도가 불균등하다. ② **"최적화"가 세 가지 뜻으로 쓰였다** — 위상+단면 동시 다목적 최적화(Pareto를 사람이 선택) / 단면 사이징 사다리(자동) / 실무의 "균일 단면 NG → 모듈별 확대 → OK" 반복(상용 SW, 사람). ③ 자동 계산과 사인오프 사이에 고정된 경계가 이미 존재한다. ④ 일람표의 가장 가까운 선례 셋이 전부 문서가 아니다(화면 표 / 모델 UserString / JSON). ⑤ 도면-모델 연동의 유일한 선례는 방향이 한쪽이다(도면 기준으로 모델 위치 보정). ⑥ **재이식이 이미 두 번 일어났고 VIDE가 세 번째다** — 두 번째 이식에서 인터페이스가 "column/girder curve 입력 → beam 자동 생성 → 하중 계산 → 단면 탐색"으로 건축 쪽에 가깝게 재설계됐다.

## 3. jig 선례 — J-00 (스킬·플러그인·MCP·에이전트를 어떻게 패키징했나)

**한 줄 결론 — "내가 다시 쓰려고 만드는 쪽"은 반복 수행, "남이 설치해 쓰게 하는 쪽"은 여전히 0. 그러나 정반대 축(남이 만든 것을 받아 쓰는 소비자 경험)은 이미 실운영 중이다.**

2026-04부터 09까지 약 6개월간 최소 20개 저장소·폴더에서 에이전트 도구를 패키징했다. F-02 실측으로 계정 저장소 19개 중 14개가 PUBLIC이지만 **설치 안내(남이 자기 환경에 깔아 쓰라는 문서)가 있는 저장소는 0개**이고 전부 본인 재현용 setup 안내뿐이다. 유일한 예외가 `rhino-mcp-skills`로, README가 스킬 9종을 이름·용도 표로 소개하고 "각 스킬 폴더는 `SKILL.md`와 파이썬 스크립트를 갖는다"는 패키징 규칙까지 적어 **"발견 가능한 배포"** 형태를 갖췄다. 정확한 서술은 **"공개는 기본값으로 해뒀고 유통은 시도한 적 없다"**이다.

반면 F-04가 확인한 **받는 쪽은 실운영 중**이다 — 마켓플레이스 2곳 등록(공식 1 + 제3자 1), 플러그인 5개 설치(그중 하나는 `scope:"local"` + `projectPath`로 **이 저장소 한정 설치**, 나머지는 전역), 별도 오픈소스 도구로 커뮤니티 스킬 3종을 라이선스 확인 → 커밋 해시 고정 → 보안 스캔 → 그대로 vendor하고 `PROVENANCE.md`에 출처 저장소·커밋·번들 해시·스캔 결과를 기록. **조사 전체에서 유일한 "스킬 공급망 위생" 선례다.**

### 3.2 반복된 구성 패턴

- **3~4문서 세트.** 가장 완성도 높은 선례는 전부 묶음이다 — 원칙(`SKILL.md`) + 체크리스트(게이트) + **함정 카탈로그(`TRAPS.md`/`PITFALLS.md`)** + 절차(`PLAYBOOK.md`). 함정 카탈로그가 본체보다 길어지는 것을 정상으로 취급한다. TRAPS의 실효성은 "어휘가 둘이다"(법령 언어 키와 엔진 키를 혼동하면 통째로 빈 값), "배열에 문자열 키를 넣으면 조용히 사라진다" 같은 항목으로 실증된다.
- **얇은 포인터 스킬.** 배포되는 것은 `SKILL.md` 한 장뿐이고 무거운 자산(검증된 컴포넌트 세트·함정 카탈로그·사전 데이터)은 원본 폴더에 두고 **절대경로로 가리키기만** 한다. 본문에 "옮겼다면 이 경로를 고칠 것. 없으면 사용자에게 위치를 묻는다", "처음부터 새로 짜지 말 것. 거기서 시작해서 필요한 부분만 고친다"가 들어 있다.
- **정적 빌드 / 실행 분리.** 문서 규범을 실행 가능한 게이트로 내린다 — 검증·게이트·스캐너가 실패하면 exit 1. 빌드가 같은 원본 파일을 EmbeddedResource로 구워 "폴백이 자산과 드리프트할 수 없게" 만든 사례도 있다.
- **로더 패턴.** 코드를 채팅에 재타이핑하지 않고 Glob으로 절대경로를 찾아 `exec(open(r"<ABS>\script.py").read())` 한 줄만 전송한다. 이유가 문서에 명시돼 있다("so the validated code runs byte-identical every time (no re-typing, no model drift)"). "하드코딩 금지"가 스킬 9개 전부에 반복된다.
- **diagnose(비파괴) → confirm(사람) → apply(파괴)** 3단계. diagnose가 세션 메모리에 plan을 저장하고 apply가 같은 plan을 읽어 실행한다.
- **메모리 승격 사다리.** 발견을 먼저 정의별 `MEMORY.md`에 적고, **"새 파일에도 성립하는 규칙인가?"**를 기준으로 cross-file 규칙만 공유 `defaults.md`의 "Promoted lessons"로 올린다(현재 6건 승격, review 대기). 별도 계보에서는 **반복 지적 3회 이상**이면 프로젝트 스코프 메모리 파일로 고정하는 것이 실제 워크플로다.
- **도구가 에이전트 환경을 스캐폴딩한다.** 파일 열림을 감지하면 홈 폴더에 `.claude/`·`.mcp.json`·`CLAUDE.md`·`MEMORY.md`·설정 JSON을 만들고 MCP에 연결한 뒤 CLI를 자동 기동한다. `CLAUDE.md`는 `<!-- 도구:begin -->` … `<!-- 도구:end -->`로 **도구가 매 연결마다 덮어쓰는 구역과 사용자 자유 영역을 분리**하고, `@defaults.md`·`@MEMORY.md` import로 공유 규칙과 정의별 기억을 매 세션 주입한다.
- **워크플로 오케스트레이션 최소 API.** 28개 스크립트가 전부 같은 런타임 주입 API 위에 작성됐다(import 문 0): `export const meta = {name, description, phases}` · `pipeline(items, ...steps)` · `parallel([...])` · `agent(prompt, {label, phase, schema})` · `log`/`phase`. 반복되는 골격은 **조사 → 적대적 검증 → 완결성 비평 → 갭 보완 2라운드**이고, 검증자는 발견자의 주장을 의심하고 파일을 다시 열어 `confirmed`/`partial`/`refuted`로 판정한다. 백그라운드로 던지고 메인 스레드는 기다리지 않는다.
- **예약 에이전트 런북.** "당신은 이 저장소에서 예약 실행되는 세션이다. 루틴 프롬프트가 워크플로 하나를 지정한다. **정확히 그 워크플로만 실행하고 멈춰라**"로 시작하고, 상태변경 호출은 전부 스크립트 경유로 멱등성을 강제하며 에이전트는 초안·해석·개정만 한다. 사용자 교정을 라운드별로 "하지 말 것" 목록에 누적 기록하는 설정 파일도 있다.
- **자율 루프 안전모델.** 객관 게이트(존재·규모 / 과잉제거 탐지 / 라벨==내용 일치 / 테스트 green) 전부 통과분만 자동 배포, 베이스라인 대비 악화 시 자동 revert, 크론 충돌은 루프 동안 비활성화 후 재활성화.

### 3.3 반복된 지시 패턴 (사용자 쪽)

번호 매긴 다중 질문(1, 1-1, 1-2…)을 한 번에 던지고 같은 번호로 답변받기 · 큰 방향 전환 전에는 "코드 작업은 하지 말고 계획부터, 승인 나면 진행" → 승인 후 "중간에 멈추지 말고 끝까지" · 결정 사항은 한 번에 하나씩 객관식으로 확인한 뒤에만 공식 계획 문서 작성(200줄짜리 영어 계획 문서 금지) · 실행 전 요약표 의무화 · 항상 plan mode로 시작하고 **영구 진행 문서를 만들지 않음**(stale 방지) · "세션 하나 = 산출물 하나" · **재현성 시험**("이 스킬만 읽은 새 세션이 같은 형식으로 채울 수 있는가. 채울 수 없으면 스킬이 부족한 것이지 세션이 부족한 것이 아니다") · 스킬은 기본 동작이 아니라 **옵트인** · 비용 게이트(N=10→100→전체 스모크 사다리) · 판정자를 하나만 믿지 않기 · effort/model을 작업 성격별로 전환 · 판단용 미니 UI는 앱을 만들지 않고 아티팩트로 즉석 생성 · `CLAUDE.md` ↔ `AGENTS.md` 동일 본문 미러링으로 두 CLI 병행(`@` import 한 줄 관용구는 2026-07부터 이미 사용).

### 3.4 텍스트 규범의 한계 — 실측 2건

강제 수준이 이미 **A(서버 결정론 툴, 기계적 강제) / B(verbatim 스킬, 규범 강제) / C(서버가 모델 페이로드 재작성)** 3계층으로 자체 분류돼 있고, 스킬은 B다. 그리고 B가 무시된 실측 사례가 둘이다.

1. 코드 주석 원문: *"house-rules norm alone was verified live to be ignored by the model, so the intent is FORCED through the required `resultOutput` field ... and enforced here on the server."* — 텍스트 규범이 안 지켜져 **스키마 필수 필드로 승격**됐다.
2. 규칙 파일은 **모델만** 구속하는데 자동 정리는 **호스트 소유 훅**이라 그것을 무시했고, "자동정리 금지"라고 쓴 사용자의 배치를 서버가 되돌리는 사고가 났다. 텍스트 규범이 모델도 사람도 아닌 **호스트 자신의 코드**에조차 안 먹힌 사례다.

B를 C로 올리는 안(스킬 이름 + 파라미터만 받아 서버가 canonical 소스를 주입)은 작성 시점에 **이미 논의됐으나 미착수(이연)**로 남아 있다. 덧붙여 선언과 실사용의 괴리도 실측됐다 — "mandatory"라고 적은 툴이 11세션 중 1회 호출, 무거운 승인 카드 2회 vs 가벼운 질문 카드 12회, 유일하게 트리거 문장이 **없는** 스킬이 15회 중 4회로 가장 많이 읽혔고 트리거 문장이 있는 6개는 한 번도 안 읽혔다(표본이 11세션으로 작다는 단서 포함). 인덱스 140자 절단이 13개 중 5개의 문장을 중간에서 자른다.

### 3.5 하네스가 항상 이득은 아니다

자체 하네스가 baseline(순정 CLI + MCP)보다 우월하다는 결론에 이르지 못했다. 사용자 발언이 남아 있다: *"일단 이번 실험에서도 하네스가 없는 버전이 시각적으로는 더 우수하다고 판단되네. 자율성과 퀄리티는 비례할 수 밖에 없는건가?"* role/mode 추상화를 만들었다가 폐기했고, 적응형 모델 라우팅도 만들었다가 수동 고정으로 되돌렸으며, 버전업에서 오히려 신뢰성이 후퇴한 기록(비커밋률 17.4% → 29.6%)도 있다. 다만 **품질 게이트를 어떻게 설계할지는 실물이 있다** — 고정 과제 + 외부 성공판정 기준 + 의도적 버그 주입 후 자가수리 검증까지 갖춘 벤치마크 하니스 문서, 그리고 §3.2의 자율 루프 안전모델이다.

### 3.6 배포·버전·인벤토리의 공백

- **버전 관리가 어디에도 없다.** 배포 스크립트(51줄)는 `filecmp` 동일성 검사만 하고 버전 비교를 안 한다. "스킬이 바뀌면 이미 뿌린 사본을 어떻게 갱신하나"에 대한 답이 조사 전체에 없다. 마켓플레이스 경로만 `version` + `gitCommitSha` 고정 개념을 갖고 있다.
- **마켓플레이스 설치 = 저장소 전체 clone.** 제3자 마켓플레이스는 플러그인 본체 외에 벤치마크·테스트·문서까지 통째로 내려받는다.
- **로컬 경로 플러그인 설치의 재현성이 불명**하다(어떤 영속 레지스트리에도 안 남는다).
- **동기화 세대 미정리** — 계정/조직을 바꿔 쓴 흔적이 비활성 세대 3세트로 쌓여 있다(자동 청소 없음). 비슷한 캐시를 설계하면 세대 GC를 처음부터 넣어야 한다는 반면교사.
- **자산 인벤토리 자체가 없다.** 흩어진 스킬/에이전트 자산이 로컬 6곳 이상 + GitHub 19개 저장소 + 전역 설정 3계층(직접 만든 스킬 / 마켓플레이스 설치본 / 계정 동기화 내장본)에서 발견됐다. 그중 하나는 버전관리가 없고, 하나는 커밋 0인 빈 저장소이며, 하나는 동기화 장치 없는 완전 중복 두 벌이고, 하나는 설치 흔적이 사라졌다.
- **"사용자가 스스로 도구를 만드는" 흐름의 선례가 다르다.** 과거에 도구가 만들어진 방식은 (a) 사용자가 성공한 코드를 붙여주고 에이전트가 정리 (b) 에이전트가 자기 조사 노트에서 "수확"해 파생 (c) 실패 로그를 근거로 쿡북을 채점해 고침 (d) 반복 지적 3회 → 메모리 고정 — **넷 다 사후 정리**이지 사전 생성이 아니다.
- **"사무소 동료에게 준다"의 유일한 실물이 텍스트 체크리스트 한 장**(온보딩 파일 31줄, 소프트웨어·계정·AI 도구 카테고리)이고 그마저 자격증명이 평문이다. 사무소 공용 자산으로 확인된 다른 것은 엑셀 서식·인허가 원표 같은 **문서**이지 에이전트 도구가 아니다.
- **옵트인 기능이 한 번도 안 켜졌다** — 개발자 피드백 스킬의 로그 파일이 애초에 생성된 적이 없다.

## 5. 현재 VIDE와의 관계

**PRD 사실.** PRD §12.3은 개발자가 제공하는 작은 확장의 **등록·실행·비활성화**(FR-13, MVP 지원 범위)를 약속하고, 확장이 프로젝트 문맥·입력·허용 도구와 권한·진행·결과·실패를 공통 기반과 연결해야 하며 "빈 슬롯이나 manifest만 있는 것을 완료로 보지 않는다"고 적는다. FR-21 전문 자동화 스킬(법규·구조·사이트·도면·개요·전문 일람표)은 **후속 확장**이고, 첫 전문 스킬의 종류와 개발 순서는 OQ-07의 후속 항목이다. PRD §14는 **공개 마켓·결제·임의 비신뢰 코드 실행을 첫 출시에서 제외**한다. 용어집에는 Plug-in(도구·코드·필요한 UI를 등록하는 확장 단위), Extension(스킬·플러그인의 통칭), Skill(재사용하는 업무 절차·지침)이 정의돼 있다. AC-26이 "작은 확장 등록·실행·실패·비활성화, 임의 권한 확대 없음"을 수용 시나리오로 둔다.

## 6. 사용자 확인 목록

1. **(J-00)** jig의 "공유"는 누구 사이인가 — 본인의 여러 프로젝트 사이 / 사무소 동료 / 외부 사용자 중 어디까지이며, 첫 버전에서 **받는 쪽과 주는 쪽 중 어느 방향을 먼저** 여는가? 받는 쪽은 실운영 경험이 있고 주는 쪽(업로드 받기·검수·승인·버전 갱신·신뢰 표시)만 선례가 0이다.
2. **(J-00)** 스킬 형식을 표준 `SKILL.md`와 호환시킬 것인가, 이전 IDE처럼 자체 경량 인덱스 + 온디맨드 읽기로 갈 것인가? 둘 다 만들어 봤고, 이전 IDE는 `SKILL.md`를 알면서 안 썼다(상시 컨텍스트 절약이 이유). 두 형식을 동시에 읽는 브리지는 어디에도 없다.
3. **(J-00)** "스킬이 바뀌면 이미 배포된 사본을 어떻게 갱신하나"를 jig가 책임질 범위인가, 아니면 "IDE가 직접 서빙하니 버전 문제 자체가 없다"로 가는가?
4. **(J-00)** jig 스킬의 강제 수준은 어디까지인가 — 규범(모델이 읽고 따르길 기대)인가, 실행기가 페이로드를 검증·재작성하는 수준인가? 자체 기록이 "규범만으로는 모델도 호스트도 무시한 사례가 있다"이고 승격안은 미착수다.
5. **(J-00)** 흩어진 기존 자산을 흡수 대상으로 보는가, 형식만 참고할 대상으로 보는가? 흡수라면 먼저 정리가 필요하고(가장 잘 만든 세트는 `.git`조차 없음), 서드파티 포크 계열의 라이선스 준수 여부가 미확인이다.
6. **(J-01)** 사이트 모델링을 **Rhino/GH 안에서 완결**할 것인가, **Node 파이프라인이 만든 데이터를 Rhino로 내보내는** 방식인가? 전자는 로컬 폴더 하나가 유일 원본이고 후자는 비공개 저장소에 있다.
7. **(J-01)** 자체 GH MCP 브리지(Wireify)는 jig와 어떤 관계인가 — 그 위에 얹히는가, 흡수·대체하는가, 아예 안 쓰고 "사람이 붙여넣기" 폴백만 남기는가? GH 캔버스 자동 배선이 전부 여기에 물려 있다.

## 7. 결론

1. **재사용 가능한 자산이 예상보다 많고, 대부분 사용자 계정 안에만 있다.** J-01·J-03·J-04는 2~3세대에 걸쳐 실제 대지에 적용된 코드가 있고, J-05와 J-09도 보충 조사에서 실동 코드가 새로 드러났다. 다만 J-03·J-04 계열은 비공개 저장소, J-01의 가장 잘 패키징된 세트는 버전관리 밖 로컬 폴더, J-09의 최신 스킬은 공개본에 없는 로컬 전용이다 — **이식은 "공개 코드 가져오기"가 아니라 비공개·비버전관리 자산 반입의 문제다.**
2. **선례가 진짜로 없는 것은 셋뿐이다** — 회의록 전 구간(J-08의 앞단), "노드 방식 렌더 자동화"(J-06), 그리고 jig의 **주는 쪽**(업로드 받기·검수·승인·버전 갱신·신뢰 표시). 나머지는 신규 개발이 아니라 재패키징·통합 문제다.
3. **반복된 실패 유형이 하나로 수렴한다 — "에러 없이 틀린 결과".** 그리고 그것을 실제로 막은 것은 문서 규범이 아니라 결정론 코드와 exit 1 게이트였다. 텍스트 규범이 모델에게도 호스트 자신에게도 무시된 실측 사례가 각각 하나씩 있다.
4. **기능 설명과 과거 경험 사이의 간극이 기능마다 다른 종류다.** J-05는 "관리"가 통째로 미경험이고, J-02는 Figma 왕복과 정본 위치 결정이며, J-07은 사용자가 이미 한 번 내린 반대 방향 판단이고, J-08은 형식 원본 자체의 부재다. 이 간극들은 조사로 메울 수 없고 사용자 결정이 필요하다.
5. **오케스트레이션·게이트·승인의 최소 설계는 이미 실물이 있다** — `pipeline`/`parallel`/`agent(schema)` 위의 4단계 검증 골격, dry-run→확인→적용, ask-back + CAS, 객관 게이트 통과분만 자동 배포와 악화 시 revert. jig가 이것들을 제공한다면 발명이 아니라 재현이다.

**다음 문서(PLAN 또는 SPEC)를 쓰기 전에 필요한 것.** ① §6의 확인 목록 중 최소한 1~5(jig 자체의 형식·강제 수준·배포 범위·버전·자산 흡수 여부)에 대한 사용자 결정 — 이것이 정해지지 않으면 어느 기능도 확장 계약을 쓸 수 없다. ② FR-13이 요구하는 "작은 확장 하나"의 대상 선정과 그 확장이 쓸 공통 입력·권한·진행·결과 계약(OQ-07). ③ 미확인으로 남은 두 구역의 확인 — 사이트 모델링 확장 계획 본문과 대응 워크플로 4종(J-01), 한 프로젝트의 대형 세션 6개를 회의·협의 키워드로 재검색(J-08). ④ 이식 후보 자산의 라이선스·소유권 정리(서드파티 포크 계보, 사무소 고유 데이터를 배포본에 넣을지 사용자별 로컬로 뺄지).
