RESEARCH-06 — 프로젝트 지식 DB(온톨로지)

00 / 목적과 범위

0.1 사용자 요청(2026-09-28)

메일·첨부파일(PDF·PPTX·CAD·Rhino 등)·회의록을 올리면 정보를 조합해 어느 회사(누가) 무슨 말을 했는지, 프로젝트의 주요 쟁점, 진행 경과를 파악해 DB로 정리한다. 이를 바탕으로 질문에 바로 답하고, 도면·모델 크리틱과 판단을 돕는 일종의 온톨로지를 만든다. 시각화 여부와 위치는 실무 효용을 따져 정한다. 이번 단계는 파악과 계획이며 구현은 하지 않는다.

0.2 이 문서가 하는 일과 안 하는 일

현재 제품 약속·코드와의 관계, 기능의 층 구분, 데이터 구조 초안, 형식별 수집 방법, 활용·시각화 판단, 위험과 사용자 결정 항목을 정리한다. 제품 범위 확정은 PRD(C-02 제안), 동작 계약은 후속 SPEC, 구현 순서는 PLAN-08이 소유한다. 실제 프로젝트 자료로 추출 품질을 측정하지 않았으므로 품질 수치는 제시하지 않는다.

01 / 이미 있는 약속·자산과의 관계

새 개념처럼 보이지만 PRD가 이미 뼈대를 약속하고 있다. 빠진 것은 외부 자료의 수집과 정리다.

기존 기준 내용 이 요청과의 관계
PRD §6.2 근거·조건: “회의록·스케치·자료 위치, 적용 범위, 채택 여부” 회의록·자료를 근거로 대상에 연결하는 요구가 이미 있다. 수집·정리 방법은 없다
PRD §6.3 원본에서 읽음 / 계산 / 사용자 확정 / AI 추정 구분, 추정의 자동 사실 승격 금지 온톨로지의 모든 진술에 그대로 적용해야 하는 핵심 규칙
PRD §6.4 “이 부분을 유지하는 근거는?”, “이 관계는 사실인가 추정인가” 질의응답의 목표 질문과 같다
PRD §6.5 전체 대화·회의록을 매 요청에 반복 입력하지 않음 검색·도구 기반 조회 구조가 필요하다는 뜻
FR-09·SPEC-03.4 값의 출처(원본/계산/사용자/AI)와 역할(사실/가정/필수조건/참고), 근거↔대상 양방향 조회 데이터 모델의 기준축. 새 모델은 이 축을 확장한다
FR-18·AC-30 AI 전송·공개 범위 확인·제외 메일·계약 자료를 AI에 보내는 범위 동의가 필수
FR-21 법규·구조·도면 등 전문 스킬은 후속 확장 도면·모델 크리틱은 이쪽에 가깝다
ADR-010 첫 출시는 로컬 전용 지식 DB도 로컬 저장이 기본. 웹 공유는 별도 결정
RESEARCH-04 J-08 회의록 기능: 과거 형식·코드 없음, 회의 자료는 민감정보와 분리 불가, “열 수 없는 파일”로 취급돼 옴, 결정 이력 재구성이 어려웠던 실제 피해 필요성과 위험을 동시에 보여주는 선례

코드 자산은 다음과 같다.

  • 저장: 로컬 SQLite(node:sqlite, 3.51). FTS5 trigram 전문 검색이 추가 의존성 없이 동작해 한국어 부분 문자열 검색이 된다(2026-09-28 확인).
  • 첨부: 현재 요청 첨부는 TXT·MD·CSV·JSON, 파일당 50,000바이트, 요청 본문에 그대로 포함된다(SPEC-01). 프로젝트 단위 자료함은 없다.
  • AI 실행: 구독 CLI(Claude Code·Codex)가 VIDE MCP 도구만 쓰는 구조(ARCH-01 §2·3). 지식 조회는 같은 방식의 읽기 전용 도구로 붙이면 기존 권한 경계를 유지한다.
  • 도면·모델: ZWCAD 연결 Sync가 문자·레이어·해치·xref를, Rhino Sync가 레이어·객체명·속성(user text)을 이미 읽는다. CAD/Rhino 첨부의 텍스트 정보 추출에 재사용할 수 있다.
  • 수량: 기본 집계(FR-22)가 면적·길이를 계산한다. 크리틱에서 AI가 숫자를 추측하지 않게 하는 근거가 된다.

02 / 기능을 네 층으로 나눈다

층 하는 일 AI 필요 먼저 쓸모가 생기는 시점
① 수집 파일·메일을 원본 그대로 보관하고 텍스트·메타데이터를 뽑는다(보낸 사람·날짜·페이지·슬라이드) 대부분 불필요 자료가 한곳에 모이고 원문 검색이 되는 순간
② 정리 원문에서 “누가·언제·무엇을(요구/결정/의견/질문/일정)”을 진술로 뽑고 사람·회사·공간·요소에 연결 필요(근거 구간 필수) 브리핑·타임라인·쟁점 표
③ 활용 질의응답(인용 포함), 모델 요청 시 관련 조건 제안, 도면·모델 크리틱, 변경 영향 확인 필요 실무 판단 보조
④ 표시 목록·표·타임라인·객체의 근거 표시, (선택) 관계 그래프 불필요 ②와 함께

①만으로도 “그 메일 어디 있었지”, “구조 협의에서 기둥 간격 얘기가 언제 나왔지”에 답할 수 있다. ②③은 ①의 원문 근거를 전제로 해야 환각을 통제할 수 있다. 따라서 수집 → 원문 검색 → 구조화 → AI 활용 순서가 맞다.

03 / 데이터 구조(온톨로지) 초안

그래프 DB나 RDF를 도입하지 않고 SQLite의 관계 테이블로 시작한다. 건축 프로젝트의 질문 대부분은 “대상·주체·시점·상태로 거르고 원문을 인용”하는 형태여서 관계형 + 전문 검색으로 충분하고, 기존 저장·백업·마이그레이션 체계(T-023)를 그대로 쓸 수 있다.

3.1 개념

개념 예 핵심 속성
Source(자료) 메일, PDF, PPTX, 회의록, DWG, 3DM 원본 해시, 형식, 받은/작성 시각, 보낸 사람·받는 사람, 원본 보관 위치, AI 전송 허용 여부
Excerpt(근거 구간) PDF 3쪽 두 번째 문단, 메일 본문 5–8행, 슬라이드 7, 도면의 문자 객체 Source, 위치(쪽·슬라이드·행·CAD handle), 원문 텍스트
Party(주체) 발주처 한빛건설, 구조사무소, 김OO 소장 조직/사람, 역할(발주처·설계·구조·설비·시공·인허가), 별칭

3.2 진술에 반드시 둘 축(PRD §6.3과 일치)

  • 출처 구분: 원문에서 읽음(원문 인용과 일치) / AI 추정(요약·해석) / 사용자 확정. AI 추정은 사용자가 확정하기 전까지 사실로 표시하지 않는다.
  • 역할: 필수조건 / 결정 / 요청 / 의견·제안 / 질문 / 참고 사실.
  • 상태와 시간: 제안됨 → 합의됨 → 대체됨(더 최신 결정이 덮음) / 철회. “대체됨”은 이전 진술을 지우지 않고 연결한다. 모순이 보이면 자동 판정하지 않고 쟁점으로 올린다.
  • 모델 연결: 진술·쟁점을 Rhino/CAD 객체(핀과 같은 식별 기준)에 연결할 수 있다. 객체가 삭제·재생성되면 연결 끊김을 표시하고 가까운 객체에 자동 재연결하지 않는다(AC-21과 같은 원칙).

3.3 기존 기록과의 연결

요청 입력의 “참고 자료” 첨부를 Source 참조로 바꾸고, AI 작업 결과·검토본이 사용한 진술을 기록하면 SPEC-03.4의 “근거에서 대상으로, 대상에서 근거로” 조회가 외부 자료까지 확장된다.

04 / 수집 방법

4.1 들어오는 경로

경로 장점 부담 판단
자료함에 파일 끌어 놓기 사용자가 범위를 직접 통제, 구현 단순 매번 수동 1단계 기본
프로젝트 폴더 지정·감시 기존 폴더 구조 그대로 사용, 새 파일 자동 수집 민감 파일까지 들어올 위험, 제외 규칙 필요 1단계에 “제외 목록 + 수집 전 확인”과 함께
메일 파일(.eml/.msg) 내보내기 메일 헤더(보낸 사람·날짜·스레드)가 정확 사용자가 내보내야 함 1단계
메일 계정 직접 연결(Outlook·Gmail) 자동·완전 계정 인증, 범위 제어, 개인 메일 혼입 사용 패턴 확인 뒤 결정(OQ)

4.2 형식별 추출

형식 추출 방법 비고
EML 헤더·본문·첨부 분리(표준 MIME) 스레드·인용 부분 중복 제거 필요
MSG(Outlook) 별도 파서 필요 사무소 메일 환경 확인 필요
PDF 텍스트 레이어 추출, 쪽 번호 유지 스캔 PDF는 OCR 또는 AI 이미지 판독 필요
PPTX·DOCX·XLSX ZIP 안 XML에서 텍스트·슬라이드·표 추출 이미지 속 글자는 제외 또는 AI 판독

3DM Rhino worker의 레이어·객체명·user text 모델 크리틱 입력과 공유
이미지·스케치 AI 이미지 판독(선택) 전송 동의 대상
녹음 STT 없음(J-08) 1단계 제외. 회의록 텍스트부터 받는다

결정적 파서로 뽑을 수 있는 것은 AI를 쓰지 않는다. 같은 해시의 자료는 다시 처리하지 않는다.

05 / 정리(구조화) 방법

  • 추출 단위: Source를 근거 구간 단위로 나누고, AI가 각 구간에서 진술 후보를 JSON으로 뽑는다. 진술마다 근거 구간 ID와 원문 인용 문자열을 필수로 하고, 인용이 원문과 일치하지 않으면 버린다(RESEARCH-04의 “인용-원문 문자열 대조” 선례).
  • 주체·대상 정규화: 같은 회사·사람의 다른 표기(“한빛”, “한빛건설(주)”)를 별칭으로 묶되, 확신이 없으면 후보로만 두고 사용자가 합친다.
  • 검토 큐: 새 진술은 “AI 추정”으로 들어오고, 사용자가 확정·수정·기각한다. 결정·필수조건처럼 판단에 영향이 큰 종류만 확정을 요구하고, 의견·참고는 자동 목록화에 그친다.
  • 증분 처리: 새 자료가 들어오면 관련 쟁점에 연결하고, 이전 결정을 대체할 가능성이 있으면 “대체 후보”로 표시한다. 자동으로 대체 확정하지 않는다.
  • 실행 경로: 기존 구독 CLI 실행을 도구 없는 추출 작업으로 재사용한다. 비용·시간은 자료량에 비례하므로 진행률·중단·재개(FR-15·16)를 적용한다.

06 / 활용

활용 방식 필수 조건
질의응답 AI가 읽기 전용 도구(검색·진술 조회·타임라인·대상별 근거)로 찾아 답한다 답의 문장마다 근거 인용. 근거가 없으면 “자료에 없음”
요청 문맥 제안 모델 수정 요청 시 대상·키워드에 걸리는 필수조건·결정을 칩으로 제안 자동 첨부가 아니라 제안. 사용자가 고른다(FR-08)
도면·모델 크리틱 확정된 요구·결정과 현재 모델·도면을 대조. 치수·면적은 계산 도구로, 시각 판단은 화면 캡처로 결과는 “AI 추정” 쟁점으로 객체에 연결. 법규 판단은 FR-21 범위
변경 영향 “이 결정을 바꾸면?” → 연결된 대상·진술·과거 작업 목록 연결된 것만 말하고, 연결이 없으면 모른다고 표시
브리핑 프로젝트 첫 화면 요약: 주체, 열린 쟁점, 최근 결정, 다가오는 일정 요약 문장마다 근거 링크

크리틱은 가치가 크지만 품질 편차도 가장 크다. 확정된 요구·결정이 쌓인 뒤에야 의미 있는 대조가 되므로 가장 뒤 단계에 둔다.

07 / 시각화 판단

관계 그래프(노드-링크) 화면은 보기에는 좋지만 실무 질문에 직접 답하지 못한다. 노드가 수백 개를 넘으면 읽기 어렵고, 설계자가 실제로 찾는 것은 “이 대상에 걸린 조건”, “이 쟁점의 최신 결정”, “누가 언제 말했나”다. 그래서 다음 순서를 권한다.

  1. 채팅 답변의 인용: 가장 자주 쓰는 경로. 인용을 누르면 원문 구간이 열린다.
  2. Inspector의 근거 표시: 객체를 고르면 연결된 요구·결정·쟁점이 나온다. 기존 “관계” 탭의 확장이다.
  3. 프로젝트 정보 탭(왼쪽 레일 새 탭): 브리핑 카드, 쟁점 표(상태·최신 결정·근거), 타임라인(날짜별 자료·결정), 주체 목록, 자료함.
  4. 검토 큐: AI가 뽑은 진술을 확정·수정·기각하는 목록.
  5. (선택) 관계 그래프: 한 쟁점이나 한 주체를 중심으로 1–2단계만 보여주는 국소 그래프. 전체 그래프는 만들지 않는다.

1–4는 실무 효용이 분명하고, 5는 사용 데이터가 쌓인 뒤 필요할 때 추가한다.

09 / 사용자 결정이 필요한 항목

  1. 제품 범위: 이 기능을 후보 기능(C-02)으로 둘지, MVP 이후 확장으로 둘지, 현재 개발과 병행할지.
  2. 자료 입력 경로: 끌어 놓기·폴더 감시·메일 파일 중 무엇부터. 메일 환경(Outlook/Gmail, .msg 여부).
  3. AI 전송 기본값: 수집한 자료를 AI 정리에 보내는 것을 자료별로 매번 확인할지, 프로젝트 단위로 허용할지.
  4. 확정 부담: 사용자가 확정해야 하는 진술 종류(결정·필수조건만 / 전부).
  5. 표본 자료: 품질 측정에 쓸 실제 프로젝트 자료 1세트(사본). 어떤 프로젝트를 쓸 수 있는지.
  6. 공유: 지식 DB를 웹 공유(팀·협력사)에 포함할지. 기본은 제외를 권한다.
  7. 크리틱 범위: 첫 크리틱을 “요구·결정 대비 모델 대조”로 한정할지, 도면 표현(표기·치수 누락)까지 볼지.
