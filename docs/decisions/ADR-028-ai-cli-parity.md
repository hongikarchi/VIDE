# VIDE 안의 AI CLI를 터미널에 가깝게

## 결정

2026-10-02 사용자 결정. **승인 범위:** 결정 1~5의 방향은 사용자가 정했다(인용). 각 결정의 구체 값(키, 상한, 기본값, 도구 이름)은 이를 구현하기 위한 구체화이며 동작 정본은 [SPEC-02](../specs/SPEC-02-execution-candidates.md).19의 3·5, 물리 계약은 [ARCH-01](../architecture/ARCH-01-system.md) §2 「대화 세션의 CLI 실행」·「AI 실행 인자」, 작업은 [PLAN-24](../plans/PLAN-24-ai-conversations.md) T-104·T-105, 실측은 [SPIKE-2026-10-02-claude-persistent-process](../tdd/SPIKE-2026-10-02-claude-persistent-process.md)다.

1. **Claude도 대화마다 프로세스 하나.** "Claude도 대화마다 프로세스 하나를 띄워 두고 턴을 입력 스트림으로 넣는 방식으로 바꾸자." 대화(세션)의 첫 턴에 `claude -p --input-format stream-json`을 띄우고, 턴마다 사용자 메시지 하나를 표준 입력에 넣는다. 턴은 그 턴의 `result`로 끝난다(그 턴이 시작한 하위 에이전트가 모두 보고한 뒤의 마지막 `result`). 프로세스를 띄울 때 정해지는 것 — 실행 파일, 기본 로그인 계정, 모델, effort, 덧붙인 지시 묶음, MCP 서버와 도구, 내장 도구, 계획·자동, 질문 도구, 구조화 출력 스키마 — 가 프로세스의 열쇠이고, 다음 턴의 열쇠가 다르면 그 프로세스를 끝내고 같은 세션을 `--resume`으로 잇는 새 프로세스를 띄운다. 쉬는 프로세스는 10분 뒤, 엔진을 닫으면 끝낸다(Windows는 지금처럼 `taskkill /T`). 턴 중단은 CLI에 중단 요청(`interrupt`)을 보내고 곧 끝나지 않으면 프로세스를 끝낸다(다음 턴은 `--resume`). 턴 중에 프로세스가 죽으면 지금과 같은 실패 처리다. 단발 실행(대화 밖)은 지금처럼 실행마다 프로세스 하나다. Codex는 이미 `codex app-server`로 대화마다 프로세스 하나다(ADR-026 4, T-075). 환경 변수 `VIDE_CLAUDE_PERSISTENT=0`이면 턴마다 프로세스 하나로 돌아간다.
2. **출력은 전체 상한 대신 한 줄 상한.** "전체 상한을 없애고 한 줄 크기만 제한"(합의). 한 실행의 표준 출력 전체 1 MB 상한을 없애고, 이벤트 한 줄(stream-json 이벤트·JSON-RPC 메시지 하나)이 16 MB를 넘을 때만 `OUTPUT_TOO_LARGE`로 멈춘다. Codex app-server의 한 줄 상한(8 MB)도 같은 16 MB로 맞추고, 한 덩어리에 여러 줄이 와도 줄마다 잰다.
3. **세션 길이 기본값을 모델 문맥 수준으로.** "기본값을 모델 문맥 한도 수준으로 올리자." 새 세션 제안(SPEC-02.19의 5 '대화가 길어짐')의 기본값을 12턴·누적 입력 150k 토큰에서 **100턴·800k 토큰**으로 올린다. 설정값의 범위(2~200턴, 10k~2M 토큰)와 사용자가 저장한 값은 그대로다.
4. **하위 에이전트와 할 일 목록.** "서브에이전트와 TodoWrite은 있어야지." Claude의 대화 턴·호스트(모델링) 턴·jig 만들기 턴에 하위 에이전트(`Task`, 호출 이름 `Agent`)와 할 일 목록 도구(옛 판 `TodoWrite`, 2.1.28x의 `TaskCreate`·`TaskGet`·`TaskList`·`TaskUpdate`)를 준다. 하위 에이전트는 그 턴의 `--tools`·`--allowedTools`·`--restricted`를 그대로 따르며(셸·파일 쓰기·다른 MCP 없음), 그 호출 이벤트도 같은 검사를 받는다. 검토 jig와 단발 실행에는 주지 않는다. VIDE 연결(MCP)이 없는 턴에는 도구를 하나도 주지 않는 지금 규칙이 그대로다.
5. **웹 검색.** "Claude는 WebSearch·WebFetch, Codex는 web_search를 켜자." 4와 같은 턴에서 Claude는 `WebSearch`·`WebFetch`, Codex는 `web_search="live"`를 쓴다. 설정 → AI 「AI 웹 검색」(기본 켬, `<data>/web-settings.json`)으로 끌 수 있다. 계획 모드 턴도 받는다(문서를 바꾸지 않는다). 턴 규칙은 웹 내용을 자료로만 다루고 출처를 밝히며 프로젝트 자료·파일 내용·토큰을 웹 도구로 보내지 말라고 적는다.

## 대체하는 것

- [RESEARCH-11](../research/RESEARCH-11-ai-parity.md) §3의 '격리는 유지한다'는 위 4·5의 도구만큼 좁아진다. 공급자 skill·plugin·전역 MCP·개인 설정은 계속 끈다(`--safe-mode`/`--restricted`, `--strict-mcp-config`, `--setting-sources ""`, Codex `--ignore-user-config`·`--disable` 목록 그대로). 셸·파일 쓰기(만들기 턴의 초안 폴더 밖)·다른 MCP 서버는 계속 없다.
- [ADR-021](../decisions/ADR-021-conversation-sessions.md)·ARCH-01 §2의 '턴 하나 = CLI 실행 하나'는 Claude 대화 턴에서 '대화 하나 = 프로세스 하나(열쇠가 바뀌면 이어 받는 새 프로세스)'가 된다. 턴마다 권한을 새로 주고 회수하는 SPEC-02.19의 3은 그대로다.

## 맥락

- [RESEARCH-11](../research/RESEARCH-11-ai-parity.md)과 [SPIKE-2026-09-30-ai-parity-ab](../tdd/SPIKE-2026-09-30-ai-parity-ab.md): VIDE 안의 AI는 터미널 Claude Code와 같은 요청에서 성공 수는 같았으나 시간이 2~4배였다. 원인의 하나가 턴마다 CLI를 새로 띄우는 비용(프로세스 기동·로그인·MCP 연결, 실측 약 0.7초 + 세션 재적재)이다. 프로세스를 남기면 둘째 턴은 7 ms 안에 시작했다(SPIKE-2026-10-02).
- 터미널에서는 하위 에이전트로 일을 나누고 할 일 목록으로 긴 작업을 추적하며 웹에서 자료를 찾는다. VIDE에서 이것들이 막혀 있어 같은 요청에서 덜 해냈다.
- 1 MB 전체 상한은 긴 모델링 턴(조회 결과·생각 요약이 많은 턴)을 중간에 끊었다. 메모리를 지키는 데 필요한 것은 한 줄을 쌓아 두는 버퍼의 상한이다.

## 선택지

| 질문 | 안 | 판단 |
|---|---|---|
| 프로세스를 남길 단위 | 턴마다 / 대화마다 / 엔진 하나 | 대화마다. 사용자 결정 1. 한 대화에는 진행 중 턴이 하나라(SPEC-02.19의 4) 프로세스를 나눠 쓰지 않는다 |
| 턴마다 달라지는 MCP 토큰 | 턴마다 새 프로세스 / 프로세스 고유 토큰을 그 턴의 토큰으로 잇기 | 잇기. 프로세스는 시작 때 받은 토큰을 쓰고, 엔진이 턴 동안만 그 토큰을 그 턴의 범위로 대응시킨다(`agent-relay.ts`). 턴 사이에는 아무 범위도 아니다(401) |
| 하위 에이전트의 배경 실행 | 끄기(환경 변수) / 보고까지 기다리기 | 기다리기. 끄는 방법은 실측하지 않았고, 기다리면 판과 무관하게 맞다 |
| 할 일 목록 이름 | `TodoWrite`만 / 새 Task* 도구까지 | 둘 다. 2.1.287은 Task*만 있다(SPIKE) |
| 웹 기본값 | 끔 / 켬 | 켬. 사용자 결정 5. 설정으로 끈다 |

## 결과

- 좋아지는 것: 둘째 턴부터 시작 지연이 사라지고, 긴 턴이 출력 상한에 끊기지 않으며, 긴 대화가 새 세션 제안에 덜 끊긴다. AI가 일을 나누고 웹 자료를 찾는다.
- 위험과 대응: 남은 프로세스가 메모리를 쓴다(쉬면 10분 뒤 끝냄, 엔진 종료 때 끝냄). 계정이 바뀌면 열쇠가 달라 다음 턴에 새로 띄운다(SPEC-02.18의 3). 중단 요청을 CLI가 따르지 않으면 프로세스를 끝내고 이어 받는다. 웹으로 자료가 새지 않도록 규칙 문장을 둔다(모델 지시이며 기술적 차단은 아니다). 하위 에이전트가 VIDE MCP 도구를 쓰는지와 중단 요청의 실제 동작은 실제 CLI로 확인하지 않았다(SPIKE 한계).
