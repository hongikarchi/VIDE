# ADR-018 · 프로젝트 지식은 쌓기만 하는 기록으로 저장하고, 지식만 팀이 함께 쌓는다

**상태: 초안. 사용자 결정 전이며 구현 근거가 아니다.** PRD C-02(첨삭 R-74)가 채택될 때 함께 결정한다. 조사와 비교는 [RESEARCH-06](../research/RESEARCH-06-project-knowledge.md), 단계는 [PLAN-08](../plans/PLAN-08-project-knowledge.md)을 따른다.

## 1. 결정할 것

1. 협의가 계속 바뀌고 기하 판단이 섞인 프로젝트 지식을 어떤 구조로 기록하는가.
2. 로컬 저장 엔진은 무엇인가.
3. 여러 팀원이 함께 자료를 쌓는 것(공동 축적)을 허용하는가. 허용한다면 PRD §14의 “프로젝트별 한 로컬 작업환경이 호스트 제어·원본 반영, 여러 PC 공동 제어는 후속” 원칙과 어떻게 구분하는가.
4. 팀 공용 원본을 어디에 두는가. 원본 자료(회사 서버)는 어떻게 다루는가.

## 2. 제안

### 2.1 기록 구조

- 근거 원문은 고치지 않는다.
- 진술·확정·대체·관측은 고유 ID·작성자·기록 시각을 가진 사건으로 쌓기만 한다.
- 진술은 유효 시간과 기록 시간의 두 시간축을 가진다.
- 대상·관계는 BOT·IFC 어휘를 빌린 속성 그래프(노드·연결 표)로 둔다.
- 기하는 형상 대신 모델 시점과 연결된 계산 관측으로 기록하고, 요구는 구조화된 조건으로도 저장한다.

### 2.2 로컬 엔진

각 PC는 기존 SQLite(FTS5·R*Tree·JSON)를 쓴다. 그래프 DB·RDF·시간 DB·벡터 DB는 도입하지 않고, 부족함이 측정될 때 다시 검토한다.

### 2.3 공동 축적 예외

지식 기록(자료 등록·진술·확정)은 같은 프로젝트의 여러 PC가 함께 쓴다. **호스트 제어와 원본 반영은 기존대로 한 작업환경만** 한다(AC-37 유지). 지식 공동 축적은 호스트 공동 제어가 아니다.

### 2.4 팀 공용 원본과 동기화

팀 공용 원본은 사건을 모으는 중앙 저장소다. 각 PC는 로컬 사본과 사건 단위로 동기화한다. AI 정리·질문은 각자 PC의 구독 CLI로 하고, 서버 쪽 AI 실행은 두지 않는다. 동기화 방식은 저장소와 분리한다.

### 2.5 원본 자료

원본은 회사 서버에 그대로 둔다. VIDE는 복사·업로드하지 않고 위치 참조·내용 해시·추출 텍스트·근거 구간만 저장한다. 자료마다 공개 범위와 AI 전송 허용을 둔다.

## 3. 팀 공용 원본 위치 — 사용자 결정 필요

| 선택지 | 맞는 조건 | 대가 |
|---|---|---|
| A. 사내 팀 서버(회사 서버·NAS의 VIDE 팀 서비스 + DB) | 사내 서버를 운영할 수 있고 외부 저장이 부담될 때 | 운영(설치·업데이트·백업), 사외 접속은 VPN |
| B. Cloudflare D1 + R2(기존 공유 기반) | 파생 데이터(진술·인용)의 외부 저장이 허용되고 운영 부담을 줄이려 할 때 | 외부 저장, DB당 10GB, 동기화 직접 구현 |
| C. Supabase(PostgreSQL, 서울) | 서버 쪽 공간·벡터 검색과 행 단위 권한이 필요할 때 | 공유 기반 이중화, 업체 추가 |

에이전트 제안: **회사 정책 확인 전에는 A를 기본 가정으로 설계하고, 동기화를 저장소와 분리해 B로도 옮길 수 있게 한다.** 원본이 이미 회사 서버에 있고 팀원이 사내망에서 일한다는 조건에 가장 맞기 때문이다. 다만 AI 정리 단계에서 원문이 외부 AI 공급자로 가므로, “외부 저장 금지”와 “외부 AI 처리 허용”은 따로 확인해야 한다.

## 4. 결과와 한계

- 공동 축적의 충돌은 덮어쓰기 대신 나란한 판단으로 남아, 사람이 쟁점으로 정리한다.
- 폴더 권한을 자동으로 따라가지 않는다. 제한 자료의 진술이 공용 원본으로 퍼지지 않도록 자료별 공개 범위를 사람이 정한다.
- 여러 사람이 같은 SQLite 파일을 공유 폴더에서 직접 쓰는 방식은 채택하지 않는다.
- 이 결정은 C-02 채택과 역할·공개 범위 결정 없이 확정할 수 없다.
