# ADR-004 · 모델 뷰·표시 갱신 전략

## 1. 배경

VIDE는 호스트 뷰포트와 IDE 자체 뷰를 함께 사용할 수 있어야 한다. 자체 뷰는 호스트가 없어도 모델·후보·검토본·웹 공유 상태를 보고 핀·스케치를 연결하기 위한 표시 표면이다. 이때 서로 다른 세 문제를 구분해야 한다.

1. **객체 식별** — 호스트와 IDE에서 가리킨 대상이 같은 설계 대상을 뜻하는가.
2. **시점·선택 동기화** — 호스트의 카메라나 선택 상태를 IDE가 자동으로 따라갈 것인가.
3. **모델 표시 갱신** — 호스트의 현재 모델 상태를 언제 IDE 표시 데이터로 가져올 것인가.

기존 0.2~0.3 문서는 1과 2를 구분했지만 모델 표시 갱신을 `push` 중심으로 적어, 자동 갱신 전체를 MVP 약속으로 읽거나 반대로 갱신 기능이 전혀 없는 것으로 읽힐 여지가 있었다. 2026-09-19 사용자 결정으로 세 경계를 다시 정리한다.

## 2. 용어

| 용어 | 이 결정에서의 의미 | 첫 출시 |
|---|---|---|
| Sync | 사용자가 지정한 호스트·문서의 현재 지원 상태를 한 번 읽어 IDE 표시 데이터를 갱신 | 포함 |
| Live Sync | 호스트의 변경을 지속적으로 감지해 IDE 표시를 자동 갱신 | 후속 목표 |
| Camera Sync | 호스트와 IDE의 카메라 시점을 자동으로 따라가게 함 | 제품 목표에서 제외 |
| 선택 상태 자동 동기화 | 한 뷰의 현재 선택을 다른 뷰가 계속 따라감 | 첫 출시에서 요구하지 않음 |

이 용어의 UI 이름은 Design/SPEC에서 달라질 수 있으나 행동 의미는 유지한다.

## 3. 결정

### 3.1 객체 식별은 공유하고 뷰는 독립적으로 본다

호스트 뷰포트와 IDE 자체 뷰의 선택 상태·카메라 시점을 자동으로 맞추지 않는다. 사용자는 어느 쪽에서든 대상을 가리킬 수 있고, 확인 가능한 범위에서는 같은 객체·설계 대상으로 요청에 연결한다. `지금 Rhino에서 선택한 대상 가져오기`처럼 사용자가 명시적으로 현재 선택을 읽는 행동은 허용한다.

Camera Sync는 현재 제품 목표에 포함하지 않는다. 발표자 따라보기 역시 별도 기능으로 취급한다.

### 3.2 첫 출시는 수동 Sync를 제공한다

첫 출시는 사용자가 지정한 호스트·문서의 현재 지원 상태를 한 번 읽어 IDE 표시 데이터를 갱신하는 **Sync**를 제공한다.

Sync는 다음과 구분한다.

- 후보를 원본에 반영하는 행동
- 다른 호스트의 원본을 변경하는 행동
- 네이티브 파일 저장
- 웹 공개 범위의 승인 또는 공유 발행
- 과거 검토본의 내용을 최신 상태로 바꾸는 행동

사용자는 마지막으로 Sync한 호스트·문서·기준과 갱신 결과를 확인할 수 있어야 한다. Sync 전의 IDE 표시가 현재 호스트와 다를 수 있으면 이를 최신으로 단정하지 않는다. 지원 데이터·오류·부분 갱신·재시도·노후화 규칙은 SPEC에서 정한다.

### 3.3 Live Sync는 후속 목표다

호스트 변경을 지속적으로 감지해 IDE 표시를 자동으로 갱신하는 Live Sync는 후속 개발 목표로 둔다. Live Sync는 **호스트 → IDE 표시 데이터의 자동 갱신**을 뜻하며, Rhino와 ZWCAD의 원본을 요청 없이 서로 바꾸는 양방향 모델 동기화와 다르다.

Live Sync가 없는 첫 출시에서도 AI 작업의 진행·개입 상태와 VIDE가 만든 검토 가능한 중간 후보는 실제 상태에 근거해 표시해야 한다. 수동 Sync를 채택했다는 이유로 진행 상태를 숨기거나 오래된 AI 결과가 사람의 직접 수정을 덮어쓸 수 있게 해서는 안 된다.

### 3.4 웹 공유는 별도의 갱신 경계다

로컬 IDE에 모델 상태가 반영되는 것과 웹 공유에 발행되는 것은 다른 상태다. 사용자가 호스트를 직접 수정한 경우, 첫 출시에서는 Sync 등으로 IDE가 그 상태를 확인한 뒤 허용된 공유 범위의 갱신 대상으로 사용할 수 있다. Sync 완료가 자동으로 공개 범위를 넓히거나 웹 발행을 승인하지 않는다.

과거 검토본은 저장 당시의 상태를 유지한다.

## 4. 근거

- 건축 작업에서는 호스트 뷰포트와 IDE를 오가며 서로 다른 시점으로 보는 일이 자연스럽다. 카메라를 계속 맞추는 비용과 혼란을 기본 기능으로 가져올 필요가 없다.
- 반면 IDE가 호스트의 현재 상태를 필요할 때 다시 읽을 수 없으면 표시가 오래된 상태인지 사용자가 판단하기 어렵다. MVP에는 명시적인 수동 Sync가 필요하다.
- Live Sync는 편의와 즉시성을 높이지만 변경 감지·연속 갱신·성능·오류 복구의 추가 계약이 필요하다. 플랫폼 기본 흐름을 먼저 검증한 뒤 확장한다.
- Sync를 원본 반영·저장·웹 공개와 분리하면 버튼 하나가 여러 권한과 상태를 동시에 바꾸는 혼동을 피할 수 있다.

## 5. 문서 적용

- PRD §8.2: 선택·카메라 자동 동기화는 요구하지 않고, 필요한 호스트 상태는 Sync로 IDE 표시를 갱신한다고 적는다.
- PRD §12.2·§13·§14.2·§15: 수동 Sync를 MVP 능력과 수용 기준으로 연결한다. Live Sync는 후속 목표, Camera Sync는 제외로 구분한다.
- PRD §12.5: 호스트 직접 수정은 IDE에서 확인된 뒤 공유 갱신에 사용할 수 있다고 구분한다.
- Design §03·§11~§13: `push` 기본 전제를 제거하고 마지막 Sync 기준·수동 갱신 행동·오래된 표시를 표현한다.
- 호스트별 Sync 지원 상태·표시용 형상·좌표·단위는 OQ-03과 관련 SPEC에서 선언한다.

## 6. SPEC·PLAN에 남기는 것

이 ADR은 갱신 기능의 제품 범위만 정한다. 다음은 이후 문서가 소유한다.

- SPEC: Sync 대상·지원 데이터, 시작/완료/부분 실패/연결 유실, 오래된 표시 판정, 후보·직접 수정과의 관계, 웹 공유에 넘길 수 있는 상태
- PLAN: 변경 감지 방식, 호출·전송 프로토콜, 표시용 형상 추출, 캐시·저장, 렌더러, 성능·재시도 구현

성과 미달에 따른 자동 범위 축소는 두지 않는다. 측정 결과는 ADR-012에 따라 사용자의 재결정 자료로 사용한다.
