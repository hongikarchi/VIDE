# ADR-004 · 모델 뷰 전략 — 객체 식별 공유, 뷰 연동 없음

## 1. 배경

Design §03의 중앙 '3D/평면/도면/비교'는 IDE 자체 뷰어를 전제하지만 어느 문서도 그 범위를 선언하지 않았다(Design R-39, PRD R-11/Codex R-31, 제안 OQ-11). 자체 뷰어는 호스트별 표시용 형상 추출·좌표 매핑·선택 동기화·렌더러·픽킹·대형 모델 처리를 뜻해 1인 개발에서 가장 큰 단일 비용 항목이다. 제품 형태(독립 IDE vs 호스트 내장 패널 등, PRD R-49)도 이 결정과 묶여 있다. 0.1은 양방향 동기화(C안)를 골랐으나, 2026-09-17 순차 결정 대화에서 개념을 바꿔 0.2로 개정했다(제품 형태·뷰 전략, OQ-11 종결).

## 2. 선택지

| 안 | 내용 | 트레이드오프 |
|---|---|---|
| A | 호스트 뷰포트 + IDE 동반 패널(자체 뷰 없음) | 가장 싸다. 호스트 없이는 아무것도 볼 수 없고 웹 검토와 뷰어를 공유할 수 없음 |
| B | IDE 자체 뷰어만 | 호스트 부재 열람·웹 공유 가능. 사실상 뷰어 제품 하나를 더 만드는 일 |
| C | 둘 다 + 양방향 동기화 | 사용자는 어디서든 보고 가리킬 수 있음. A+B의 비용에 동기화 계약이 추가됨 |
| D | 둘 다 두되 연동 없음 — 객체 식별만 공유, 자체 뷰는 보기·핀·스케치, 갱신은 호스트 push | 어느 쪽에서 가리켰든 같은 객체로 요청에 들어감. 동기화 계약이 없어 C보다 싸고, 자체 뷰는 요청·체크포인트 시점 기준이라 실시간이 아님 |

## 3. 결정

**D. 객체 식별을 공유하고 뷰는 연동하지 않는다.** 호스트 뷰포트와 IDE 자체 뷰를 서로 맞추지(선택·카메라 동기화) 않는다. 자체 뷰는 보기·핀·스케치용이며 갱신은 호스트 push가 기본이다. (2026-09-17 개정 — 0.1의 C안을 대체한다.)

- 사용자는 어느 쪽에서든 가리킬 수 있고, 어느 쪽에서 가리켰든 같은 객체로 요청에 들어간다("지금 Rhino에서 선택한 것 가져오기"면 충분하다).
- 첫 출시: 자체 뷰에서 보기·핀·스케치. 표시 형상은 요청·체크포인트 시점 기준이고, 갱신은 호스트에서 밀어 넣는(push) 방식이 기본이다. 자동 갱신은 약속하지 않는다(있으면 좋음).
- 어댑터 계약에 지금부터 포함: 객체 식별, 현재 선택 읽기(요청 시 호스트→IDE), 표시용 형상 추출(Rhino 메시, ZWCAD 2D 엔티티), 좌표계·단위. 선택 이벤트 왕복과 카메라 상태 동기화는 계약에서 뺀다.
- 후보(ADR-003)는 호스트 문서 안에 있으므로 호스트 뷰포트에서는 즉시 보이고, IDE 자체 뷰에는 원본과 구분되는 후보의 표시용 형상으로 그린다. 분리·표시 방식은 ADR-003 0.2에 따라 SPEC·PLAN에서 정한다.
- 제품 형태는 **로컬 설치형**이다(PRD §1.3): UI·로컬 서비스·호스트 애드인이 한 PC에서 동작한다. 화면을 브라우저 탭으로 띄울지 데스크톱 창으로 감쌀지는 기술 선택이라 PLAN이 정한다. 웹 작업 공간의 열람·탐색·의견 작성은 첫 출시 범위이고(ADR-010, PRD §1.3·§12.5), 웹에서의 AI 실행 시작·개입·원본 반영 승인은 제외한다(PRD §14.4). 근거: 여러 호스트를 같은 프로젝트에서 다루고 호스트 없이도 후보·기록을 열람하려면 호스트 밖의 앱이 필요하다.

> **[검토 · codex · R-01 · 높음]** **추가 지적.** **양방향 동기화의 최소 계약.** 자체 뷰와 호스트 뷰를 함께 제공한다는 사용자 선택을 기준으로 삼는다. 다만 선택·카메라라는 이름만으로 호스트별 동일 표현이나 완전한 동기화를 보장할 수는 없다. 제안: Rhino 3D와 ZWCAD 2D에서 지원할 투영·뷰·단위, 선택 대상 매핑, 대응할 수 없는 카메라/객체의 표시, 갱신 지연 허용 범위를 선언한다. 왕복 이벤트의 출처·순서와 되울림 방지, 문서 종료/재열기 뒤 오래된 이벤트 배제도 확인해야 한다. ADR-009의 단일 활성 대상과 동기화 대상을 일치시키고, 오프라인 표시용 기록은 현재 호스트 상태와 구분한다. 상세 프로토콜·렌더러 선정은 PLAN의 몫이다.

## 4. 근거

소유자의 사용 방식은 호스트 뷰포트와 IDE 창을 오가며 가리키는 것이다. 요청에 필요한 것은 '같은 객체'라는 식별뿐이고, 두 뷰의 선택·카메라를 맞추는 동기화 계약(왕복 이벤트·되울림 방지·지연 허용)은 1인 개발에서 비용이 크다. 웹 작업 공간이 첫 출시에 포함되므로(ADR-010 0.2, PRD §12.5) 자체 뷰의 표시용 형상·객체 식별을 웹 열람과 함께 쓸 근거는 남는다. 다만 그것은 두 뷰의 선택·카메라를 맞추는 동기화 계약과 별개이므로 이 결정(뷰 연동 없음)은 바뀌지 않는다.

## 5. 결과 — 적용 시 바꿀 문장

- PRD §8.2: "가리키기는 호스트 뷰포트에서든 IDE 자체 뷰에서든 가능하고 같은 객체로 인식된다. 두 뷰의 선택·카메라를 서로 맞추는 것은 약속하지 않는다." §5·§8·§12에 동기화를 약속하는 문장이 있으면 같은 취지로 고친다. §14.2 포함에 "자체 뷰의 보기·핀·스케치(표시 형상은 요청·체크포인트 시점 기준, 호스트 push 갱신)", 제외에 "뷰 동기화(선택·카메라)·자동 실시간 갱신". §1.3에 제품 형태 근거 2~3문장("독립 Windows IDE" → "로컬 설치형"), §0 요약표 '제품 형태' 행도 같은 표현. PRD 0.6 §18에는 OQ-11 행이 없고, 선택·카메라 동기화 제외만 유지된다고 적혀 있다.
- PRD §14.1은 표가 아닌 서술이므로, 호스트별 최소 능력(표시 형상 추출·객체 식별·좌표 변환·push 갱신 방식)은 호스트 지원표·연계 SPEC(OQ-03)에서 명시한다.
- Design §03: "자체 뷰는 보기·핀·스케치용이며 호스트 뷰포트와 선택·카메라를 맞추지 않는다. 표시 형상은 요청·체크포인트 시점 기준(호스트 push 갱신)." §04·§05·§08의 "호스트 뷰포트에서 할 때 / IDE 뷰에서 할 때" 구분은 두 진입점으로 유지.
- 가이드 §06 스파이크 순서 ③(표시 기준): Rhino 메시 추출 + 현재 선택 읽기 + ZWCAD 2D 렌더 최소 실험. 선택 양방향 동기화는 대상에서 뺀다.

## 6. 축소 조건 (alpha 판정 관문, ADR-006)

없음 — 목표는 ADR-012(두 기준선 대비 개선, 판정 관문 아님)다. 0.1의 축소 조건(자체 뷰를 C-02로 내리고 A안으로 축소, 웹 뷰어 재정의)은 철회했다. 목표 미달은 자동 축소가 아니라 사용자의 재결정 시점이며, 판정 절차와 시점은 PLAN §6·§9가 정한다.

<!-- codex-review:start -->

> **[검토 · codex · R-02 · 높음]** **추가 지적.** **비교 시간의 범위와 축소 판단.** 자체 뷰 구축 시간이 그 뷰를 포함하는 첫 호스트 슬라이스 전체보다 오래 걸리는지 비교하면 부분과 전체의 기준이 겹친다. 의도한 기준이 뷰를 제외한 슬라이스 예상 시간이라면 이를 명시해야 한다. 제안: 뷰 실험의 별도 노력 상한·최소 표시/선택 성공 기준을 먼저 정하고 실제 결과로 계속/보완/범위 재결정을 한다. 텍스트 대비 대상 오인이 줄지 않았다는 사실 하나로 호스트 부재 열람·후보 비교·웹 표시 가치까지 부정할 수도 없다. 축소는 사용자가 그 조건까지 수락한 경우에 적용하며, 시험 미완료와 실패를 구분한다.
