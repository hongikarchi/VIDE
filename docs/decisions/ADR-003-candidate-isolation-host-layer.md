# ADR-003 · 후보 격리 원칙 — 호스트 안 격리 영역

## 1. 배경

PRD §5·§11.2는 "원본과 분리된, 호스트에서 편집 가능한 실제 후보"를 약속하지만 실현 수단이 없었다. Codex R-42와 Claude R-46은 격리 수단이 호스트마다 다르면 '후보'의 공통 의미가 흔들린다고 지적했고, 호스트별 보장 수준(L1 IDE 측 변경 집합 / L2 호스트 안 격리 영역 / L3 별도 문서)을 선언하는 안을 제안했다(제안 OQ-10). ADR-001로 Revit이 빠지면서 트랜잭션 제약이 사라져 단일 원칙이 가능해졌다.

## 2. 선택지

| 안 | 내용 | 트레이드오프 |
|---|---|---|
| A | 호스트 안 격리 영역(전용 레이어·그룹)으로 통일 | 실제 형상·호스트 도구 재편집·뷰포트 표시가 모두 됨. 원본 객체 무변경을 호스트별로 검수해야 함 |
| B | 별도 호스트 문서(사본)에만 존재 | 원본 문서 절대 무변경. 반영이 문서 간 복사가 되어 참조·속성 유지가 어렵고 두 문서를 오가야 함 |
| C | 호스트별 수준 허용(L1~L3) | 유연하지만 SPEC-00과 UI가 복잡해짐. Revit 추가 시에만 필요할 가능성 |

## 3. 결정

**A. 후보는 원본 문서 안의 격리 영역(전용 레이어 또는 그룹)에 실제 형상으로 존재한다.** Rhino·ZWCAD 모두 같은 원칙이다.

- 수용 기준: **후보를 폐기하면 원본 객체·파일은 무변경**(AC-17·AC-24 보강). 원본 객체는 후보가 채택되어 원본 반영을 확인하기 전까지 수정되지 않는다.
- 후보는 호스트 기본 도구로 재편집할 수 있고, 반영은 격리 영역의 형상을 원본 레이어로 옮기거나 원본 객체를 교체하는 동작으로 정의한다(세부는 SPEC-00-common 2차와 hosts/ 지원표).
- Revit을 추가하는 시점에 C안(수준 선언)으로 확장할지 재검토한다.

<!-- codex-review:start -->

> **[검토 · codex · R-01 · 높음]** **추가 지적.** **기존 객체 보존과 문서 무변경.** 같은 문서의 전용 레이어/그룹에 실제 후보를 만드는 선택과 원본 파일 무변경 보장은 분리해야 한다. [RhinoCommon ObjectTable](https://developer.rhino3d.com/api/rhinocommon/rhino.docobjects.tables.objecttable)은 객체 추가·변환 등을 문서의 객체 테이블 작업으로 제공한다. 이 사실로부터 같은 문서의 후보도 문서 내용의 일부라는 결론은 가능하지만, 레이어 분리만으로 파일 바이트·저장·공유 속성까지 보존된다는 결론은 나오지 않는다. 제안 문구: 후보 조작은 사전에 선언한 기존 객체·속성·관계를 바꾸지 않으며, 후보 영역 때문에 발생하는 문서 변경과 저장/자동 저장 정책을 별도로 정의한다. 폐기는 자기 후보만 제거하고 사용자가 그동안 수정한 원본을 되돌리지 않는다. 후보 생성→호스트 재편집→폐기뿐 아니라 후보가 남은 저장/재열기·공유 정의·동시 수동 편집도 확인한다. Revit 제외만으로 이 보장이 증명되었다고 쓰지 않는다.

## 4. 근거

두 호스트 모두 레이어 기반 격리가 가능하고, 후보가 호스트 안에 있으면 호스트 뷰포트에서 바로 보이며(ADR-004) 호스트 없이 후보를 보존할 필요가 줄어든다.

## 5. 결과 — 적용 시 바꿀 문장

- PRD §5 '후보' 행에 격리 원칙 한 문장, §11.2 탐색 행, AC-17·AC-24에 "후보 폐기 뒤 원본 무변경" 시험, §18에 OQ-10 행(이 ADR 링크).
- SPEC-00-common: 후보 상태(생성·수정·폐기·채택·반영)와 격리 영역 명명 규칙. hosts/rhino.md·hosts/zwcad.md: 격리 영역 구현 방식과 제한.
- Design §08: '기준이 바뀐 후보'(Codex R-34) 표현은 격리 영역 안 후보와 현재 원본의 차이로 정의.

<!-- codex-review:start -->

> **[검토 · codex · R-02 · 높음]** **추가 지적.** **반영의 대상과 부분 실패.** 후보를 원본 레이어로 이동하는 것은 새 객체 추가일 수 있고 기존 객체 교체는 ID·연결 관계·참조를 바꿀 수 있어, 두 동작을 하나의 반영 의미로 취급하면 늦은 결과와 이력 추적이 흔들린다. 제안: 생성/수정/삭제 대상, 후보와 원본의 대응, 유지할 속성·참조, 기준 버전 확인, 반영 일부 실패·결과 불명의 복구를 최소 계약에 포함한다. 반영 확인 뒤 저장 실패는 쓰기 재실행과 분리하고, 재시도는 이미 적용된 변경을 중복 생성하지 않아야 한다. 레이어 명명 규칙보다 이 의미를 먼저 SPEC-00과 각 호스트 지원표에 연결할 것을 권한다.

## 6. 재검토 조건

첫 호스트 후보/원본 경계 스파이크(가이드 R-39 순서 ②)에서 "폐기 뒤 원본 무변경"을 보장할 수 없는 경우가 나오면 B안 또는 C안으로 돌아간다.

## 부록 · Codex 검토 요약 (2026-09-17)

후보를 같은 문서에 두는 A안 자체를 거부하지 않는다. 다만 이를 원본 문서·파일 절대 무변경이나 트랜잭션 격리로 표현하는 것은 보장이 과하다. 기존 객체 보존과 반영·저장 의미를 구분한 뒤 호스트별로 실증해야 한다.

이번 검토는 사용자 수락이나 본문 반영을 뜻하지 않는다. 기존 스레드는 같은 ID로 갱신하고, 새 지적은 별도 ID를 부여한다. 철회 기록은 상대 참조가 정리될 때까지 남긴다.

### 결정이 필요한 사항

원본으로 보호하는 대상이 기존 객체·관계인지, 문서 전체와 저장 파일까지인지 먼저 명시한다. 후자까지 요구한다면 같은 문서 방식으로 가능한지 실증하고 대안을 비교한다. 반영의 대상 대응·부분 실패 복구도 함께 결정한다.
