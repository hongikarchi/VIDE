# 도메인 서비스 분리와 VIDE 연동

## 결정

2026-10-07 사용자 메모와 선택이며, 저장소 나누기는 2026-10-08에 정했다.

1. **서비스는 VIDE와 분리해 만들되, 별도 저장소는 cLAWde 하나다.** 2026-10-07 사용자: "각각의 서비스로 만들어놓고, vide에서는 그것들을 가져다가 쓰는 방식으로", "개별적인 기능의 디테일한 사항들은 각각의 repo에서 구현되도록". 2026-10-08 사용자가 "repo로 분리하는 것과 우리 프로그램 안에서 그냥 폴더 나눠서 관리하는 것 중에 뭐가 더 효율적이고, 좋을까?"라고 묻고 "cLAWde만 별도 비공개 저장소로 만들자"로 정했다. 대상 서비스는 다음과 같다.
   - **cLAWde**: 법규검토, 인허가, 질의 정보. 지식 구조(온톨로지)를 계속 쌓는다. 별도 비공개 저장소 `hongikarchi/cLAWde`에서 만든다(로컬 작업본 `C:\Users\user\Desktop\cLAWde-service`).
   - **ArchiDB**: 회의록, 협의, 메일을 DB로 만들고 보고서를 쓴다.
   - **Site Modeling**: 대지 형상과 정보를 함께 모은다.
   - **Structure Analysis**: 구조검토.
   - ArchiDB·Site Modeling·Structure Analysis는 VIDE 저장소 안에서 경계가 분명한 폴더로 관리한다. 필요하면 계정 사이트(`src/sharing`)처럼 따로 배포하는 서비스로 둘 수 있다.
   - cLAWde만 떼는 이유: VIDE 저장소는 공개인데 cLAWde는 법령 DB·판정 레코드·사용자가 보낸 프로젝트 정보와 법제처 인증값을 다룬다. 자료가 크고, 배포 주기와 웹 사이트가 따로이며, VIDE와는 HTTP 계약으로만 연결된다.
   - 다른 서비스는 다른 제품이 쓰게 되거나, 비공개 자료가 들어오거나, 실행 환경이 달라지면 별도 저장소로 나눌지 다시 본다.
   - 옛 비공개 저장소 `CLAWDE`(RESEARCH-04 S-01)는 GitHub 저장소 이름이 대소문자를 가리지 않으므로 `hongikarchi/CLAWDE-legacy`로 이름을 바꿨다.
2. **VIDE는 IDE로 남는다.** 사용자: "vide는 기본적으로 ide의 개념".
   - 서비스 결과를 프로젝트에 맞게 jig로 추가하거나 개조해 쓴다. 사용자: "가져다 쓰면서 해당 프로젝트에 맞게 jig의 방식으로 추가/개조할 수 있도록".
   - 서비스의 세부 기능은 VIDE 코어(IDE·엔진)에 섞지 않는다. VIDE 저장소 안에 둔 서비스도 자기 폴더와 연동 계약 뒤에 둔다.
3. **DB는 공유할 수 있게 한다.** 사용자: "DB는 공유할 수 있으면 좋을 듯".
   - VIDE가 서비스 DB를 읽는다.
   - VIDE에서 쌓은 프로젝트 정보를 서비스로 되돌려 보낼 수 있다. 사용자: "vide에 추가한 정보들이 역으로 clawde로 넘어갈 수도 있으면 좋겠다".
   - 되돌려 보내는 것은 사용자가 항목을 확인한 뒤에만 한다(PRD §6.3의 출처 구분, SPEC-08 공유 범위).
4. **이번에는 연동 계약만 쓴다.** 사용자가 고른 범위는 'ADR과 연동 계약만'이다. 서비스 코드와 VIDE의 연결 코드는 만들지 않는다.

## 맥락

- 구조 분석은 이미 VIDE 안의 jig(FR-23, ADR-019)다. 앞으로 Structure Analysis 서비스가 생기면 같은 계약으로 옮길지 정한다(OQ-16).
- 과거 CLAWDE 저장소(RESEARCH-04 S-01, 지금 `hongikarchi/CLAWDE-legacy`)는 J-01~J-04(사이트 모델링·분석·법규) 후보의 출처다.
- VIDE의 프로젝트 자료(C-02)와 계정 사이트(ADR-037)는 이미 팀 공유 층을 가진다. ArchiDB와 겹치는 부분은 OQ-16에서 정한다.

## 결과

- 물리 계약(서비스 주소, 인증, 응답 형식, 캐시, 역전송 요청)은 [ARCH-01](../architecture/ARCH-01-system.md) §「외부 도메인 서비스」가 소유한다.
- jig는 서비스를 `service.<name>` 능력으로 선언해 쓴다(ARCH-03의 예약 능력). 실행 방식은 서비스를 처음 연결할 때 SPEC-07에 정한다.
- 다음 두 결정은 OQ로 남긴다.
  - 서비스 DB를 공유하는 방식(직접 읽기, API, 사본 동기화): OQ-16
  - 역전송 확인의 단위(항목별, 묶음별): OQ-17
- 규모검토, 법규 Q&A, 패널링 같은 세부 흐름은 [RESEARCH-16](../research/RESEARCH-16-domain-services-roadmap.md)에 정리한다. 해당 서비스가 정본을 갖는다(cLAWde는 별도 저장소, 나머지는 VIDE 저장소 안의 서비스 폴더).
