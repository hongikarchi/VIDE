# 작업 폴더와 서버 연결

## 맥락

- 지금 VIDE는 프로젝트 폴더를 여러 개 등록하고 실제 경로(UNC 포함)를 기억하지만(SPEC-01.13), **사용자 폴더에는 아무것도 쓰지 않는다**. VIDE가 만든 모든 것은 `%LOCALAPPDATA%\VIDE`에 있다([ARCH-01](../architecture/ARCH-01-system.md) 「데이터 위치」). 그래서 폴더만 보고는 무엇이 있었는지 알 수 없고, 폴더만 복제해서는 재현되지 않는다.
- 사용자는 규모검토를 VIDE 밖의 작업 폴더(`논현동 164/7-3 규모검토`)에서 하고 있고, 그 폴더에는 역할별 경로와 정본 위치를 적은 `project.config.json`, 사람·AI 공용 진입문, 프로젝트 로컬 git이 있다([RESEARCH-17](../research/RESEARCH-17-workspace-and-records.md) §3).
- 회사의 정본은 NAS 서버 폴더(`\\Lifethings\Lifethings_02\PROJECTS\2026 Project\…`)이고 앞으로도 그 구조로 간다. 폴더 구조는 **회사마다, 사람마다 다르다**. NAS는 느려서 Rhino는 로컬에서 작업하고, CAD는 xref로 묶여 있어 서버 파일이 고쳐지는 것이 맞다. 사용자는 AI가 서버 파일을 바로 고치는 것을 아직 신뢰하지 않는다(2026-10-15).
- 파일들은 서로 이어져 있다(xref, Rhino↔CAD Sync 쌍, jig 입력과 결과, 데이터와 보고서). 지금 탐색기는 이름 목록이라 요청 하나가 어느 파일에 미치는지 보이지 않는다.
- 게시는 이미 둘로 나뉘어 있다: VIDE 공유 사이트(D1·R2, [ADR-037](ADR-037-team-shared-project-layer.md))와 사용자가 직접 올리는 Cloudflare Worker.

## 결정

2026-10-15 사용자 채팅 결정이다(같은 날 두 번 고쳤다: 서버 역할 매핑 → 대화로 기억, 파일 지도 추가). 세부 분석은 RESEARCH-17 §4~§5, 작업은 [PLAN-52](../plans/PLAN-52-workspace-folders.md)가 소유한다.

1. **역할 세 곳.** 작업 폴더(로컬)가 **정본**, 공유 사이트는 **게시본**, VIDE PC 데이터는 **캐시·개인 것**이다. GitHub은 장소가 아니라 작업 폴더의 **이력**이다. 게시본은 폴더에서 다시 게시하면 덮인다.
2. **어느 폴더를 연결할지는 지금처럼 설정에서 미리 정한다.** SPEC-01.13의 프로젝트 폴더(로컬·NAS·UNC)를 그대로 쓴다. 이 ADR은 등록 방식을 바꾸지 않는다.
3. **로컬 트리는 VIDE가 만들되 템플릿이다.** 새 프로젝트는 'VS Code 폴더 열기'처럼 폴더로 만들고, VIDE가 `project.config.json`·`README.md`·`AGENTS.md`와 기본 트리 `01_운영 / 02_자료 / 03_모델 / 04_도면 / 05_검토 / 06_산출물 / 07_검토본 / 08_레퍼런스 / 09_도구 / 10_아카이브`를 만든다(기능 → 폴더 표는 RESEARCH-17 §5). 이 이름·번호는 **설정 파일의 기본값**이며 회사·개인이 바꿔 쓴다. 코드는 이름을 알지 못하고 역할만 안다. 새 역할은 11부터 뒤에 붙인다.
4. **정본은 폴더 이름이 아니라 역할 경로다.** `project.config.json`의 역할 경로(운영·자료·모델·도면·검토·산출물·검토본·레퍼런스·도구·아카이브)와 정본 위치가 기준이다. 3의 트리는 그 역할을 채우는 한 가지 모양일 뿐이다.
5. **VIDE가 로컬 작업 폴더에 쓴다.** 매니페스트, jig 결과(검토용 HTML·데이터), 보고용 산출물, 일지·회의록·할 일의 파일 사본, 프로젝트 jig의 README를 역할 경로에 사람이 읽는 형태로 쓴다. DB·인덱스·대화 원문·키는 지금처럼 PC 데이터에 둔다. ARCH-01 「데이터 위치」 표에 '로컬 작업 폴더' 열을 더하고 이 ADR을 역링크한다. 폴더(+git)만 있으면 VIDE가 프로젝트를 다시 만들고 DB를 다시 짓는다.
6. **연결한 서버 폴더에 VIDE는 구조를 씌우지 않는다.** 폴더를 만들거나 이름을 바꾸지 않고, 어떤 규약도 요구하지 않는다. 대신 폴더를 연결하면 AI가 **이미 있는 구조를 읽어 대화로 제안**한다("도면은 `…\03_도면`, 보고서는 `…\05_보고서`로 보이는데 맞나요?"). 사람이 채팅에서 확인하거나 고치면 그 결과를 프로젝트에 **기억**한다. `project.config.json`의 `server` 블록은 이 기억이지 규약이 아니며, 뒤에 "앞으로 보고서는 여기에"라고 말하면 기억이 바뀐다. 로컬 결과를 서버로 보낼 때 VIDE는 기억한 자리를 제안하고, 기억이 없을 때만 묻는다. 읽기(원본 자료·레퍼런스·도면)는 서버에서 바로 하고 인덱스만 로컬에 둔다.
7. **Rhino 3dm은 로컬 체크아웃.** 작업할 3dm을 로컬 모델 폴더로 가져오고 서버에는 '작업 중(누가·언제)' 표시를 남긴다(사이트로 팀원도 본다). AI는 로컬 사본에만 쓴다. **[서버에 반영]**은 사람이 누를 때만 로컬 → 서버로 복사하며, 반영 전에 바뀐 객체 목록과 Sync 어긋남을 보여주고, 서버의 이전 판은 `아카이브/<날짜>/`에 자동 보관한다. 반영 위치는 6의 기억을 따른다.
8. **CAD dwg는 서버에서 직접 작업한다.** xref는 서버 경로를 읽는다. AI 수정은 1차 보호 규칙 — 요청 단위 되돌리기, 그날 첫 수정 전 로컬 자동 사본, 호스트 안 rev cloud 표시 — 아래에서만 하고, 설정으로 dwg도 로컬 체크아웃(7과 같은 흐름)으로 바꿀 수 있다. 어느 쪽을 기본으로 굳힐지와 파일 종류별 '바로 서버 쓰기' 허용은 OQ-18이다.
9. **파일 지도.** 탐색기는 로컬과 연결한 서버의 파일을 **노드**로, 파일 사이 관계를 **선**으로 그린다 — xref, Rhino↔CAD Sync 쌍, jig 입력 → 결과, 데이터 → 보고서, 로컬 체크아웃 ↔ 서버 원본, 참조 이미지 → 요청. 파일 사건(Sync·체크아웃·반영·jig 실행)은 **시간축**에 놓인다. 파일을 고르거나 요청이 어떤 파일을 대상으로 잡으면 **영향받는 파일이 켜진다**. 1차 범위는 관계 + 영향 미리보기 + 시간축이다(사용자 결정). 노드·선·시간축 차트 부품은 [PLAN-53](../plans/PLAN-53-project-records.md)의 기록 모델과 공유하며, 뒤에 기록(결정·근거)이 파일 노드에 붙는다.
10. **게시본.** 보고용 산출물은 로컬 산출물 폴더에 쓴 뒤 VIDE 공유 사이트 또는 사용자의 Cloudflare 계정으로 게시한다(C-11). 서버에 두는 것은 [서버에 반영]으로 한다.
11. **git.** 작업 폴더는 프로젝트 로컬 git을 쓸 수 있고 텍스트(매니페스트·정의·md·html·JSON)만 추적하며 바이너리는 제외한다. GitHub 원격은 사용자 계정으로 연결한다(C-11). NAS가 없는 사람끼리는 GitHub으로 폴더를 맞춘다.

## 대안과 기각 이유

| 대안 | 기각 이유 |
|---|---|
| 지금처럼 VIDE 데이터만 쓰고 폴더에는 쓰지 않는다 | 폴더만 보고 작업을 알 수 없고 재현이 내보내기에 의존한다. 사용자가 원한 "사람이 관리할 수 있고 AI도 읽기 쉬운" 폴더가 되지 않는다 |
| 규모검토 폴더(00~90)를 그대로 기본 트리로 | 엔진 코드가 프로젝트 안에 있고, 3dm과 dwg가 한 폴더에 섞여 서버/로컬 규칙을 나눌 수 없으며, 산출물과 배포 설정이 섞인다(RESEARCH-17 §3) |
| 로컬 트리 이름을 코드에 고정 | 회사마다 사람마다 다르다. 역할만 코드가 알고 이름은 설정이 안다 |
| 서버 폴더를 VIDE 트리로 재구성 | 회사 서버 구조는 다른 도구와 사람이 공유하는 것이라 VIDE가 바꿀 수 없다 |
| 서버 폴더에 역할 매핑을 필수로 요구(첫 초안 0.1) | 회사마다 구조가 달라 결국 VIDE의 틀을 씌우게 된다. 구조는 AI가 읽어 대화로 기억하면 되고, 매핑 화면은 필요 없다 |
| 모든 파일을 로컬 체크아웃 | dwg는 xref로 서버에 묶여 있어 로컬 사본이 참조를 깨뜨리거나 두 판을 만든다. 사용자도 "CAD는 서버에서"를 택했다 |
| 모든 파일에 AI가 서버 직접 쓰기 | 사용자가 아직 신뢰하지 않는다. 3dm은 느린 NAS 때문에도 로컬이 맞다 |
| 탐색기는 이름 목록으로 두고 관계는 Sync jig 안에서만 | 요청을 쓰는 순간 영향 범위가 보이지 않는다. 사용자는 아티팩트처럼 관계·영향·시간을 한 화면에서 보길 원했다 |
| 폴더 번호 00·10·20 | 역할이 매니페스트로 고정되므로 끼워 넣을 빈 번호가 필요 없다. 사용자 선택은 01~09 |

## 결과

- **PRD:** C-10(작업 폴더·서버 연결·CLI 진입점), C-11(산출물 등급·외부 계정) 후보, OQ-18 미결. 파일 지도는 C-10 안의 항목으로 적는다. §14 범위는 바꾸지 않는다.
- **SPEC-01.13** 보완: 작업 폴더 만들기·매니페스트·서버 구조 읽기와 기억·체크아웃/반영/'작업 중'·아카이브·파일 지도의 관계 종류와 영향 규칙. **SPEC-10**: 일지·회의록의 파일 사본. **SPEC-05**: [서버에 반영] 전 어긋남 보기.
- **ARCH-01** 「데이터 위치」: 로컬 작업 폴더 열 추가, 매니페스트 스키마(`project.config.json`은 `architecture-workspace/1`과 호환, `server` 블록은 기억) 소유.
- **PLAN-52**가 구현 순서·검증을 소유한다. 0.1의 '서버 매핑 UI' 티켓은 '연결 시 구조 읽기 → 제안 대화 → 기억 저장'으로 바꾸고, '파일 지도'(관계·영향·시간축) 티켓을 새로 둔다. 차트 부품은 PLAN-53과 나눠 쓴다. 기존 프로젝트의 이전(폴더 없는 프로젝트에 폴더 붙이기)은 PLAN-52가 정한다.
- 이 결정은 [ADR-030](ADR-030-link-id-in-document.md)(연결 ID는 문서 안)과 [ADR-037](ADR-037-team-shared-project-layer.md)(사이트는 가공 지식의 원본)을 바꾸지 않는다. 사이트에 올라가는 노트·할 일·일지는 그대로 사이트가 원본이고, 폴더의 파일은 그 **사본**이다.

## 미결

- **OQ-18:** 서버 원본(dwg·xref)에 AI가 직접 쓰는 것을 기본으로 둘지, 8의 보호 규칙이 충분한지, 파일 종류별(운영·검토·산출물) '바로 서버 쓰기' 허용. 작업 폴더를 1차로 써 본 뒤 결정한다.
- 체크아웃 충돌(두 사람이 같은 3dm을 가져감)의 규칙은 '작업 중' 표시와 반영 때 경고로 시작하고, 잠금은 두지 않는다. 바꿀 필요가 보이면 이 ADR을 갱신한다.
- 서버 구조 읽기가 틀린 제안을 할 때의 정정 방법은 채팅 한 문장으로 충분한지 PLAN-52 1차 사용에서 본다.
