ADR-004 · 모델 뷰 전략 — 객체 식별 공유, 뷰 연동 없음

초록 추가·교체 제안빨강 삭제·교체 대상CLAUDE: 파란 상자 · CODEX: 보라 상자

검토자 필터는 코멘트·부록만 바꿉니다. ‘인라인 제안 미리보기’는 코멘트의 대안까지 합친 최종본이 아닙니다. 보기 전환은 MD 수정·수락·승인을 하지 않습니다.

01 / 배경

Design §03의 중앙 '3D/평면/도면/비교'는 IDE 자체 뷰어를 전제하지만 어느 문서도 그 범위를 선언하지 않았다(Design R-39, PRD R-11/Codex R-31, 제안 OQ-11). 자체 뷰어는 호스트별 표시용 형상 추출·좌표 매핑·선택 동기화·렌더러·픽킹·대형 모델 처리를 뜻해 1인 개발에서 가장 큰 단일 비용 항목이다. 제품 형태(독립 IDE vs 호스트 내장 패널 등, PRD R-49)도 이 결정과 묶여 있다. 0.1은 양방향 동기화(C안)를 골랐으나, 2026-09-17 순차 결정 대화에서 개념을 바꿔 0.2로 개정했다(제품 형태·뷰 전략, OQ-11 종결).

02 / 선택지

안 내용 트레이드오프
A 호스트 뷰포트 + IDE 동반 패널(자체 뷰 없음) 가장 싸다. 호스트 없이는 아무것도 볼 수 없고 웹 검토와 뷰어를 공유할 수 없음
B IDE 자체 뷰어만 호스트 부재 열람·웹 공유 가능. 사실상 뷰어 제품 하나를 더 만드는 일
C 둘 다 + 양방향 동기화 사용자는 어디서든 보고 가리킬 수 있음. A+B의 비용에 동기화 계약이 추가됨
D 둘 다 두되 연동 없음 — 객체 식별만 공유, 자체 뷰는 보기·핀·스케치, 갱신은 호스트 push 어느 쪽에서 가리켰든 같은 객체로 요청에 들어감. 동기화 계약이 없어 C보다 싸고, 자체 뷰는 요청·체크포인트 시점 기준이라 실시간이 아님

03 / 결정

D. 객체 식별을 공유하고 뷰는 연동하지 않는다. 호스트 뷰포트와 IDE 자체 뷰를 서로 맞추지(선택·카메라 동기화) 않는다. 자체 뷰는 보기·핀·스케치용이며 갱신은 호스트 push가 기본이다. (2026-09-17 개정 — 0.1의 C안을 대체한다.)

  • 사용자는 어느 쪽에서든 가리킬 수 있고, 어느 쪽에서 가리켰든 같은 객체로 요청에 들어간다("지금 Rhino에서 선택한 것 가져오기"면 충분하다).
  • 첫 출시: 자체 뷰에서 보기·핀·스케치. 표시 형상은 요청·체크포인트 시점 기준이고, 갱신은 호스트에서 밀어 넣는(push) 방식이 기본이다. 자동 갱신은 약속하지 않는다(있으면 좋음).
  • 어댑터 계약에 지금부터 포함: 객체 식별, 현재 선택 읽기(요청 시 호스트→IDE), 표시용 형상 추출(Rhino 메시, ZWCAD 2D 엔티티), 좌표계·단위. 선택 이벤트 왕복과 카메라 상태 동기화는 계약에서 뺀다.
  • 후보(ADR-003)는 호스트 안에 있으므로 호스트 뷰포트에서는 즉시 보이고, IDE 자체 뷰에는 격리 영역의 표시용 형상으로 그린다.
  • 제품 형태는 로컬 설치형이다(PRD §1.1): UI·로컬 서비스·호스트 애드인이 한 PC에서 동작한다. 화면을 브라우저 탭으로 띄울지 데스크톱 창으로 감쌀지는 기술 선택이라 PLAN이 정한다. 원격 접속은 같은 서비스에 중계를 붙이는 확장 경로다(ADR-010). 근거: 여러 호스트를 같은 프로젝트에서 다루고 호스트 없이도 후보·기록을 열람하려면 호스트 밖의 앱이 필요하다.

codexR-01높음 추가 지적. 양방향 동기화의 최소 계약. 자체 뷰와 호스트 뷰를 함께 제공한다는 사용자 선택을 기준으로 삼는다. 다만 선택·카메라라는 이름만으로 호스트별 동일 표현이나 완전한 동기화를 보장할 수는 없다. 제안: Rhino 3D와 ZWCAD 2D에서 지원할 투영·뷰·단위, 선택 대상 매핑, 대응할 수 없는 카메라/객체의 표시, 갱신 지연 허용 범위를 선언한다. 왕복 이벤트의 출처·순서와 되울림 방지, 문서 종료/재열기 뒤 오래된 이벤트 배제도 확인해야 한다. ADR-009의 단일 활성 대상과 동기화 대상을 일치시키고, 오프라인 표시용 기록은 현재 호스트 상태와 구분한다. 상세 프로토콜·렌더러 선정은 PLAN의 몫이다.

04 / 근거

소유자의 사용 방식은 호스트 뷰포트와 IDE 창을 오가며 가리키는 것이다. 요청에 필요한 것은 '같은 객체'라는 식별뿐이고, 두 뷰의 선택·카메라를 맞추는 동기화 계약(왕복 이벤트·되울림 방지·지연 허용)은 1인 개발에서 비용이 크다. 웹 검토(ADR-007)가 후속 확장으로 옮겨져(ADR-010) 자체 뷰어를 웹 뷰어와 공유할 근거도 사라졌다.

05 / 결과 — 적용 시 바꿀 문장

  • PRD §8.2: "가리키기는 호스트 뷰포트에서든 IDE 자체 뷰에서든 가능하고 같은 객체로 인식된다. 두 뷰의 선택·카메라를 서로 맞추는 것은 약속하지 않는다." §5·§8·§12에 동기화를 약속하는 문장이 있으면 같은 취지로 고친다. §14.2 포함에 "자체 뷰의 보기·핀·스케치(표시 형상은 요청·체크포인트 시점 기준, 호스트 push 갱신)", 제외에 "뷰 동기화(선택·카메라)·자동 실시간 갱신". §1.1에 제품 형태 근거 2~3문장("독립 Windows IDE" → "로컬 설치형"), §0 요약표 '주 사용 환경' 행도 같은 표현. §18 '결정 초안'의 OQ-11 구절을 "ADR-004 개정으로 종결"로.
  • PRD §14.1 '요구할 능력' 열에 호스트별 최소 능력(표시 형상 추출·객체 식별·좌표 변환·push 갱신 방식)을 명시.
  • Design §03: "자체 뷰는 보기·핀·스케치용이며 호스트 뷰포트와 선택·카메라를 맞추지 않는다. 표시 형상은 요청·체크포인트 시점 기준(호스트 push 갱신)." §04·§05·§08의 "호스트 뷰포트에서 할 때 / IDE 뷰에서 할 때" 구분은 두 진입점으로 유지.
  • 가이드 §06 스파이크 순서 ③(표시 기준): Rhino 메시 추출 + 현재 선택 읽기 + ZWCAD 2D 렌더 최소 실험. 선택 양방향 동기화는 대상에서 뺀다.

06 / 축소 조건 (alpha 판정 관문, ADR-006)

없음 — 목표는 ADR-012(두 기준선 대비 개선, 판정 관문 아님)다. 0.1의 축소 조건(자체 뷰를 C-02로 내리고 A안으로 축소, 웹 뷰어 재정의)은 철회했다. 목표 미달은 자동 축소가 아니라 사용자의 재결정 시점이며, 판정 절차와 시점은 PLAN §6·§9가 정한다.

codexR-02높음 추가 지적. 비교 시간의 범위와 축소 판단. 자체 뷰 구축 시간이 그 뷰를 포함하는 첫 호스트 슬라이스 전체보다 오래 걸리는지 비교하면 부분과 전체의 기준이 겹친다. 의도한 기준이 뷰를 제외한 슬라이스 예상 시간이라면 이를 명시해야 한다. 제안: 뷰 실험의 별도 노력 상한·최소 표시/선택 성공 기준을 먼저 정하고 실제 결과로 계속/보완/범위 재결정을 한다. 텍스트 대비 대상 오인이 줄지 않았다는 사실 하나로 호스트 부재 열람·후보 비교·웹 표시 가치까지 부정할 수도 없다. 축소는 사용자가 그 조건까지 수락한 경우에 적용하며, 시험 미완료와 실패를 구분한다.

07 / 출처

PRD R-11·R-49, Codex R-31, Design R-39·R-42. 2026-09-17 brainstorming Q&A. 0.2 개정: 2026-09-17 순차 결정 대화(제품 형태·뷰 전략, OQ-11 종결).

07 / 부록 · Codex 검토 요약 (2026-09-17)

양방향 뷰 선택은 존중한다. 확정 전 필요한 것은 지원 능력의 경계와 검증 가능한 축소 기준이며, 모든 대안을 처음부터 다시 비교하는 절차는 아니다.

이번 검토는 사용자 수락이나 본문 반영을 뜻하지 않는다. 기존 스레드는 같은 ID로 갱신하고, 새 지적은 별도 ID를 부여한다. 철회 기록은 상대 참조가 정리될 때까지 남긴다.
