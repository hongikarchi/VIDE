Three.js 유지와 뷰포트 경계 정리

00 / 결정

사용자의 조사·실험·선정 위임에 따라 2026-09-22 Three.js 0.186.0 유지를 구현 기준으로 채택한다. 범용 엔진 비교뿐 아니라 Speckle·xeokit의 코드와 실제 로컬 로딩·객체 갱신·CSP까지 조사한 판단이다. 웹/서버의 확정 스택은 ADR-016을 따른다. 현재 검증 경로인 WebGLRenderer를 사용하고 WebGPU·다른 엔진·React Three Fiber를 동시에 추가하지 않는다. 엔진 교체 자체는 개발 목표가 아니다.

01 / 근거

PLAN-01 §9의 후보 조사와 실험 결과를 근거로 한다. Three.js와 Babylon.js 모두 기본 선택·평면·단면 검사를 통과했고, 실측 성능은 항목별로 엇갈렸다. 기존 입력·객체 연결·배포 경로를 버리고 옮길 만큼의 이점은 확인되지 않았다. Three.js의 보급 지표와 기존 코드 활용도 유지보수 판단에 반영하되 사용자 수나 성능 보증으로 해석하지 않는다.

Speckle과 xeokit은 계정/외부 서버 없이 로컬 메시 로딩·ID 유지·리소스 재생성을 실제 통과했다. Speckle의 측정/단면/BVH, xeokit의 주석/단면/측정은 직접 개발량을 줄일 수 있다. 다만 원 입력 보존·빈번한 위상 변경·고유 UX 연결에는 어댑터와 갱신 전략이 필요하다. Speckle의 고정 Three 버전·로더 보완·신규 데이터 전환, xeokit의 CSP UI·배포 조건도 관리 비용이다. 현재 제품의 편집 입력 경로에 비해 도입 이득이 충분히 입증되지 않아 유지한다. 이들이 느리거나 로컬 사용이 불가능하다는 판단은 아니다. 세부 비교는 PLAN-01 §9.2가 소유한다.

02 / 구현 방향·완료 조건

React는 UI, Three 어댑터는 캔버스·카메라·GPU 자원·포인터 해석을 소유한다. 모델/문서 참조·원점/단위·스케치 점열은 엔진 밖 DTO로 유지한다. 버텍스 업로드 전 지역 원점으로 이동하며 원래 좌표를 보존한다. 전체 교체 대신 객체별 변경을 반영하고, 객체 수가 큰 장면에서는 배칭/인스턴싱과 객체 ID 대응을 함께 검증한다. 선택 병목이 측정되면 BVH 등 가속을 검토한다. 엔진 유지가 기존 viewport.mjs의 전체 재생성 구조 유지 승인은 아니다.

PLAN §3.3의 5단계는 엔진 교체 대신 TypeScript 어댑터·React 수명 통합과 기존 기능 회귀를 수행한다. 스냅·단면·대형 모델·context loss·실제 브라우저 검수는 해당 기능을 지원 완료로 표시하기 전 수행한다. 이번 결정은 제한된 실험에 근거한 구현 기준이며 모든 T-015 수용 조건 통과나 MVP 완료 선언이 아니다.

검증된 목표 장면에서 메모리/응답성이 요구를 충족하지 못하고 국소 최적화로 해결되지 않거나, 필수 기능의 구현 비용이 대안보다 명확히 커지는 증거가 생기면 재검토한다. 막연한 미래 교체를 위해 모든 엔진을 동시에 감싸는 범용 추상화를 만들지 않는다.
