# 결정 브리프 (`docs/briefs/`)

사용자가 그때그때 **보고 판단할 내용**(분석 결과, 보고, 결정할 항목)을 한 장짜리 HTML로 둔다. 아티팩트는 열기 번거로우므로 파일을 더블클릭해서 본다(2026-10-19 사용자 지시). 이 폴더는 AI.md §4 "저장소에는 MD만 둔다"의 **유일한 예외**이며, 여기 HTML은 생성물이 아니라 원본이다. 렌더러(`tools/docs`)는 이 폴더의 HTML을 건드리지 않는다.

결정의 **정본은 PRD·ADR·SPEC·PLAN**이다. 브리프는 결정을 받기 위한 안내문이고, 답이 나오면 정본에 반영한다.

## 양식 원칙 — 쉽고, 짧고, 보자마자 결정

1. **한 문서 = 한 번에 결정할 묶음.** 결정 항목은 최대 6개. 넘으면 문서를 나눈다.
2. **맨 위 세 줄.** 제목 · 날짜와 상태와 근거 문서 · "왜 지금 정해야 하나" 한 문장.
3. **결정 항목 하나의 구성.** 질문 한 문장 → 선택지 2~4개(추천을 맨 앞에 두고 '추천' 표시) → 추천 이유 한 줄 → 틀렸을 때의 비용 한 줄. 그 밖의 근거는 '더 보기'에 접고 정본 문서로 링크한다.
4. **글자 수.** 질문 40자, 선택지 이름 12자 + 설명 40자, 이유 60자 안. 표는 3열 이하. 코드·식별자·숫자는 꼭 필요한 것만.
5. **조작.** 선택지를 누르면 표시되고 [추천 전부]로 한 번에 고를 수 있다. [답장 복사]가 "D1 ③ / D2 ① / 메모: …" 문장을 만든다. 사용자는 그 문장을 채팅에 붙이기만 하면 된다.
6. **파일.** `_template.html`을 복사해 만든다. 공통 스타일은 `_base.css` 하나를 상대 경로로 링크하고 문서별 추가 CSS·JS만 안에 둔다. 외부 의존(CDN·웹폰트) 없음. 흰 바탕 하나(어두운 테마 없음), 인쇄/PDF 가능. 이름은 `YYYY-MM-DD-<slug>.html`(ASCII kebab). 만들면 `index.html` 목록 맨 위에 한 줄 추가한다.
7. **보고용도 같은 꼴.** 결정 항목 대신 '결과 카드'(한 줄 결론 + 상태 색 통과·주의·실패 + 더 보기)를 쓴다. 긴 분석은 RESEARCH/VERIFY에 쓰고 브리프에는 결론만 옮긴다.
8. **수명.** 답이 오면 정본(PRD·ADR·SPEC·PLAN)에 반영하고 **브리프는 지운다**(2026-10-19 사용자 지시 "필요 없는 HTML은 삭제"). 다른 브리프가 대신하게 된 것도 지운다. 답과 이력은 Git과 정본에 남는다. 남는 것은 답을 기다리는 브리프와 아직 쓰는 실제 화면 스토리보드뿐이며 `index.html`도 맞춘다.
9. **넣지 않는 것.** 비밀값, 사람 이름, 사용자 원본 파일명, 보고서 전문, 아티팩트를 대신하는 긴 서술.
10. **실제 화면처럼.** 상자 와이어프레임을 쓰지 않는다(2026-10-19 사용자 지시). 이미 있는 화면은 캡처, 아직 없는 요소는 실제 UI 안에 그 자리의 카드를 기존 컴포넌트 CSS로 끼워 넣고 캡처해 '합성'이라 표시한다. 둘 다 안 될 때만 점선 '화면 없음' 표식.
11. **보고서 스타일**(2026-10-19 사용자 지시 "이런 스타일로 보고서를"). 결론이 곧 제목(h1 두 줄까지) · 숫자가 결론을 바꿀 때만 큰 숫자 줄(`.stat-row`) · 번호 섹션 머리(`01 / …`) · 가는 선으로 나누고 둥근 카드·색 배지 없음 · 강조색은 코랄 하나 · 질문은 질문→선택지→이유→틀리면 한 묶음(`.qs`) · 보고는 `.cf` 카드(한 줄 결론 + 상태 칩 통과·주의·실패)와 근거 표(`.ev`).
12. **정보량**(2026-10-19 사용자 지시 "정보가 너무 쓸데없이 많다"). 참고 보고서가 기준: 본문 글자 3,000자 안, 섹션 4~6개, 섹션 하나 = 주장 하나(h2 한 줄) + 그림이나 숫자 하나. 항목이 많은 목록(기능·결함·화면)은 ID·이름·상태만 한 줄로 두고 항목별 설명·의심·캡처·태그 설명을 두지 않는다. 캡처는 결정이 그 화면에 달린 곳에만 둔다. 비유·배경 설명·조작법 안내는 쓰지 않는다. 더 알아야 할 것은 정본 문서 링크 하나로 대신한다.

## 구성

- `index.html` — 브리프 목록(최신이 위). 상태: 결정 대기 · 검토 대기(스토리보드) · 보고. 결정됨·대체됨 브리프는 지운다(원칙 8).
- `_base.css` — 모든 브리프가 상대 경로로 링크하는 공통 스타일(원칙 6·11).
- `_template.html` — 복사해 쓰는 틀. 결정 항목(`<li class="d">`)·결과 카드(`.cf`)·근거 표(`.ev`) 예가 하나씩 있다.
- `_storyboard-template.html` — 스토리보드 브리프 틀(아래 절).
- `assets/<slug>/` — 스토리보드 캡처 이미지.
- `YYYY-MM-DD-<slug>.html` — 브리프 본문.

## 에이전트가 만들 때

사용자가 "브리프로", "보고 판단하게", "결정할 것 정리해 줘"라고 하면 이 양식으로 만든다. 만든 뒤 채팅에는 파일 경로와 결정 항목 ID 목록만 적는다. 답을 받으면 정본 문서에 반영하고 브리프 상태를 갱신한다.

## 스토리보드 브리프

**목적.** 기능을 다 만들고 빌드해 써 보기 전에, 전체 흐름과 기능 구성을 화면 단위로 보고 넣을지·뺄지·고칠지를 정한다. 글로 된 PRD·SPEC 대신 보는 검토용 보기이며 **정본이 아니다**. 정본은 SPEC(동작)·Design(표현)이다.

**두 종류.**

- 아직 안 만든 기능 → **합성 캡처**. 실제 UI의 그 자리에 기존 컴포넌트 CSS로 카드를 끼워 넣고 찍는다(`<img class="shot">`, 머리나 카드 태그에 '합성' 표시). 합성도 안 되면 점선 '화면 없음' 표식(`<div class="frame missing">`)만 둔다. 상자 와이어프레임은 쓰지 않는다(원칙 10).
- 이미 만든 기능 → **실제 화면 캡처**(`<img class="shot">`). 목업을 새로 그리지 않는다(2026-10-01 "목업 말고 실제 UI" 원칙).
- 화면 체계 자체를 새로 설계할 때(2026-10-19 "실제 기능이 붙기 전에 목업 프론트를 보고 싶다") → **살아 있는 HTML 목업**. `assets/<slug>/`에 공통 `app.css`·`app.js`·`_shell.html`과 장별 HTML을 두고, 스토리보드는 `figure.shot` 안에 `<div class="live"><iframe …>`로 그 화면을 그대로 끼운다(1440×900을 폭에 맞춰 축소, [새 창 ↗] 링크). 목업도 실제 제품처럼 보이게 만들고(레퍼런스: collectui 등 캡처해 토큰을 정함), 회색 상자 와이어프레임은 쓰지 않는다. 작은 그림 띠용 썸네일은 `assets/<slug>/thumbs/NN.png`. 목업은 제품 코드가 아니며 구도가 정해지면 Design·SPEC에 옮기고 목업 폴더는 지운다.

**카드 하나 = 한 단계.** `_storyboard-template.html`을 복사한다. 카드는 8장 이하(넘으면 흐름을 나눈다). 왼쪽 그림(`.stick` 안 `figure.shot[data-s]`)과 오른쪽 단계(`.step[data-s]`)가 같은 번호끼리 짝이며, [이전]/[다음]·← →·아래 작은 그림 띠로 넘긴다. 단계 구성:

1. 제목 한 줄과 ID(`S1`…, `.step`의 `data-id`)
2. 그림(짝인 `figure.shot`): 실제 화면 캡처 또는 합성 캡처(16:10). 없으면 점선 '화면 없음'
3. `사용자` 하는 것 한 줄 · `화면` 보여주는 것 한 줄
4. `근거 SPEC-NN.m` — SPEC 항목 ID **하나**
5. (선택) 결정 — `.step` 안 `<div class="decide" data-id="D1">`, 결정 브리프의 선택지와 같은 꼴
6. 피드백 줄: 단계마다 `.step`의 `data-choices` 단추(기본 `좋음,수정`, 필요하면 `좋음,수정,빼기`) + 한 줄 메모.

합성 캡처가 들어간 문서는 머리(`meta`)에 "실제 화면 캡처 · 끼운 카드 n장은 실제 UI에 합성"처럼 적는다.

**피드백 복사 형식.** 바닥의 [피드백 복사]가 `S1 좋음 / S3 수정: 메모 / D1 ③ / 메모: …`을 만든다. 카드 단추는 카드마다 하나만 켜지고 다시 누르면 꺼진다. 전체 메모만 적으면 `메모: …`로 시작한다. 사용자는 이 문장을 채팅에 붙인다.

**한 장형**(예: `2026-10-19-vide-one-page.html`). 결론 제목 → 숫자 줄 → 핵심 흐름 캡처 3장(`.story`) → 겹별 기능 목록 → 질문 → 근거 표. 기능은 한 줄(`F01`… ID·이름·상태)이고 앞의 네모를 켜면 빼기다(원칙 12: 기능별 설명·캡처 없음). 상태 네 가지: `써봄`(실제로 써 봄) · `일부`(일부만 동작) · `미검증`(만들었으나 실사용 확인 전) · `계획만`(문서만 있음). 겹마다 상태 막대와 '써봄 n / 전체', 숫자 줄의 '빼기' 개수는 켤 때마다 갱신된다. 캡처 위 태그: `AI 응답 주입`(AI를 부르지 않고 결과 상태를 넣어 찍음) · `합성` · `대체`(가까운 화면). 복사 형식은 `Q1 ① / 빼기: F12 F28 / 메모: …`(없으면 `없음`).

**캡처 도구** `tools/briefs/capture.mjs`. 개발 엔진을 임의 포트·임시 데이터 폴더로 띄우고(설치 엔진 47821·47831 금지, 합성 자료만), 단계 JSON을 넘긴다. 끝나면 엔진을 종료한다.

```text
node tools/briefs/capture.mjs --token <임시데이터>/launch.json --out docs/briefs/assets/<slug> --steps steps.json
steps.json: [{"name":"01-compose","path":"/","actions":[{"type":"textarea","text":"기둥 색을 바꿔 줘"}]}]
```

1280×800·밝은 테마·Edge(Playwright `msedge`)로 찍고, 상태 막대의 계정 이메일은 늘 가린다. 더 가릴 요소는 단계의 `mask`, 일부만 찍을 때는 `clip`(선택자).

**이미지.** `docs/briefs/assets/<slug>/`에 PNG, 장당 300 KB 이하, 폭 1280 이하. 사람 이름·이메일·사용자 원본 파일명·실제 프로젝트 이름이 보이면 쓰지 않는다.

**순서.** 피드백을 받으면 ① SPEC·Design(필요하면 PRD 첨삭)에 반영 → ② 스토리보드를 다시 만든다(같은 파일 갱신, 상태 '결정됨' 또는 새 날짜 판). 스토리보드만 고치고 정본을 두지 않는 일은 없다.

**파일 이름.** `YYYY-MM-DD-storyboard-<slug>.html`. 만들면 `index.html` 맨 위에 한 줄(상태 '검토 대기').
