01 / FLOW

자료 → 조건·결정 → 작업 → 검토. 기록은 늘.

Kiro의 spec 흐름을 건축에 옮긴 것. 모델·도면 수정은 '작업' 단계의 산출 하나다.

  • 0시작두 길 — 바로 하기 / 설계 세우기
  • 1자료폴더·메일·회의록·법규·대지를 읽어 사실로. 사람이 확정
  • 2조건 · 결정 · 작업requirements · design · tasks의 건축판
  • 3작업① 바로 적용 + 되돌리기 ② 아티팩트에서 보고 [반영]
  • 4검토 · 보고법규·구조·수량·검토본 비교 → 수정 작업으로
  • 늘기록결정·실행·검토본 그래프. 자료가 바뀌면 영향 표시

02 / SCREENS

화면 8장, 한 프로젝트의 하루.

왼쪽 화면은 살아 있는 목업이다. 탭·토글·표 행을 눌러 볼 수 있고, 오른쪽 위 ‹ › 로 다음 장으로 간다. 어두운 테마가 기본, 해 아이콘으로 밝게.

화면 안 글자가 작으면 [새 창 ↗]으로 연다. 그림 위 ‹ ›와 ← → 키로 넘긴다.

01

시작 — 두 길

사용자 프로젝트를 고르거나, 새 프로젝트를 「바로 하기」 또는 「설계 세우기」로 연다.

화면 두 길 카드와 최근 프로젝트. 셸은 이미 완성형(레일 · 탐색기 · 가운데 · 에이전트).

Kiro의 Vibe / Spec · ADR-045
02

자료 읽기 → 사실 DB

사용자 "폴더랑 메일 읽어서 조건 정리해 줘".

화면 가운데에 사실 표(문장 · 출처 칩 · 확정/미확정/오염). 에이전트는 모순 하나를 묻는다. 확정된 사실만 다음 턴부터 AI에 들어간다.

자료 작업공간(SCR-19) · steering에 해당
03

조건 · 결정 · 작업

사용자 결정 문서를 본다. 회의록이 새로 들어와 조건 2개가 바뀌었다.

화면 결정 카드마다 근거 칩과 영향 작업. 바뀐 조건은 경고 줄. 작업 탭은 체크리스트이고 [열기]가 작업 화면으로 간다.

requirements · design · tasks의 건축판 · hooks
04

속도 ① 바로 적용

사용자 Rhino에서 기둥을 고르고 "이 기둥 600 동쪽으로". 선택은 입력창 안 칩으로만 보인다.

화면 결과는 한 줄(모델 1 · 객체 1 변경 · 검토 · 되돌리기). 가운데에는 전/후 비교가 열린다. 도면 반영은 물어본다.

뷰포트 위 '1개 선택 · 요청 고정' 띠는 없다. 직접 적용 결정(2026-09-30) · SPEC-02.13
05

속도 ② 검토 후 반영 — 구조 검토안

사용자 "기둥 배치 구조 검토해 줘".

화면 가운데에 평면 겹침 + 스팬 표. 12 m 초과 1곳과 제안 기둥. [반영]을 눌러야 Rhino에 들어가고 결정에 기록된다.

도구(jig) = 저장해 둔 아티팩트 · S-06
06

DB × 3D 연동

사용자 "실별 면적이랑 모델 맞는지 보여 줘". 표 행을 누르면 모델의 실이 켜진다.

화면 표와 등각 모델이 한 아티팩트. 불일치 2곳. 표 기준/모델 기준 중 고르면 호스트에 반영된다.

성수동 사례의 DB 보기를 모델과 묶은 것. 자료 → 호스트 행동 API
07

기록 그래프

사용자 레일의 「기록」을 연다.

화면 결정 ● 실행 ○ 검토본 ◆ 이 한 줄기, 대안은 가지. 노드를 누르면 그 시점의 모델·문서를 본다.

Source Control 자리 · 기록 타임라인(F27)
08

검토본 비교 · 보고

사용자 "10/12 검토본이랑 비교해서 중간 보고 만들어 줘".

화면 A/B 두 장과 바뀐 점, 보고서 미리보기, 외부 의견 2건 → 수정 작업. 폴더에 쓰는 일은 '확인 필요' 카드 한 곳에서만 묻는다.

보고서 등급(SCR-40) · 확인은 한곳(Kiro Focus Mode)
03 / QUESTIONS

구도와 셸만 정하면 된다.

화면 세부는 단계별 좋음·수정으로.

  • Q1가운데 = 아티팩트 창, 두 속도(바로 적용 / 검토 후 반영). 이 구도로 갑니까?

    이유호스트가 못 보여 주는 것만 가운데에 두니 뷰어·채팅·대시보드가 한 자리로 정리된다.

    틀리면아티팩트 API(데이터·모델·호스트 행동)를 먼저 만드는 순서가 바뀐다.

  • Q2셸은 무엇으로 만듭니까?

    이유엔진은 같으니 셸 선택은 조작감의 문제다. 실제로 써 봐야 갈린다. PLAN-51이 미룬 MCP 기준선과 같은 실험이다.

    틀리면UI를 한 번 더 갈아엎는다.

  • Q3첫 번째로 진짜 만들 아티팩트는?

    이유①이 아티팩트 API의 세 가지를 한 번에 검증한다.

    틀리면첫 아티팩트가 API 한 축만 검증해 두 번째에서 다시 설계한다.
