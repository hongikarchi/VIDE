AI.md — 에이전트 공통 규약 (형식)

폴더·문서·AI 작업 규약

버전 0.18 · 2026-09-28 · 소유: user

이 파일은 이 저장소에서 일하는 모든 에이전트(Claude Code, Codex, Gemini CLI 등)와 사람이 공유하는 형식 규약이다. 문서별 판단 기준과 진입 경로, 폴더·파일·ID·상태·첨삭·생성물의 공통 규칙을 정한다. 제품이 무엇인지·범위·요구는 docs/PRD.md가 정하고, 작업 절차는 DEVELOPMENT_GUIDE.md가 정한다. 가이드 전체를 매번 읽을 필요는 없지만 현재 단계에 해당하는 절은 따른다. 이 파일은 기술 스택·화면·기능 범위를 결정하지 않는다.

01 / 읽는 순서와 권위

  1. AI.md (이 파일)
  2. docs/PRD.md — 제품 결정의 기준. 범위·요구·수용 기준·미정 항목(OQ)은 여기서만 바뀐다.
  3. DEVELOPMENT_GUIDE.md §01·§12 — 문서별 판단 기준과 다음 개발 세션의 실행 규약. 현재 티켓·증거·다음 행동은 docs/plans/PLAN.md §6.5가 소유한다.
  4. 개발 작업은 PLAN §6.5에서 현재 티켓을 찾고, docs/specs/README.md → SPEC-00 → 해당 기능/호스트 SPEC을 읽는다. UI 작업은 Design.md의 해당 SCR을, 기술 계약은 docs/architecture/ARCH-01-system.md, 구현·검증은 해당 작업 PLAN을 함께 읽는다. 전체 절차는 가이드 §12를 따른다.

권위는 주제별로 구분한다. 형식·산출물 위치는 이 파일, 제품 범위·FR·AC·OQ는 PRD, 동작 의미는 SPEC, 시각·상호작용 표현은 Design, 기술 구조·물리 계약은 ARCH, 구현 순서·검증 계획은 PLAN, 작업 절차는 가이드가 소유한다. 하위 문서는 제품 요구를 덮어쓰지 않는다. 충돌은 해당 원본 문서에서 해소한다. 문서 안의 <ins>/<del>/검토 인용 블록은 제안이지 확정이 아니다.

문장의 소속은 다음 다섯 규칙으로 정한다(층 분리 규칙).

  1. 소속 판별: 제품 목표·범위·사용자에게 한 약속은 PRD, 그 약속을 구체화하는 기능 동작·논리 계약은 SPEC, 디자인 DNA·배치·색·타이포·컴포넌트·상호작용 표현은 Design, 기술 구조·스택·물리 계약은 ARCH, 구현 순서·작업·검사 방법은 PLAN·TEST에 쓴다. 조사 사실·대안 비교는 RESEARCH, 선택 근거는 ADR, 실측은 SPIKE·VERIFY에 쓴다. 작업 운영 절차는 개발 가이드가 소유한다.
  2. 의미와 구현의 경계: 상태·정보 항목의 의미, 허용 동작·권한·실패 결과는 SPEC이 소유한다. DB 열·타입·인덱스, API 필드명·직렬화·전송 형식은 ARCH가 소유한다. 예를 들어 대상 문서를 고정해야 한다는 동작은 SPEC, 이를 전달하는 요청 스키마는 ARCH, 화면의 대상 배지·배치는 Design이다. 필드나 상태 이름이 있다는 이유만으로 소속을 정하지 않는다. PRD에는 제품 약속과 세부 정본 참조를 둔다.
  3. 첫 출시 한정: PRD §0~§13은 제품 전체를 말하고 '첫 출시·MVP·아직 미정'이라는 말을 쓰지 않는다. 넣고 빼는 판단은 §13 범위 태그와 §14에만 적으며, 태그는 개념 절의 약속을 좁힐 뿐 새 약속을 만들거나 다시 정의하지 않는다. SPEC·PLAN은 §14가 고른 범위에 대해서만 쓴다.
  4. 정본 하나: 한 약속은 한 절이 소유하고, 다른 절·요약표·위험 목록은 절 번호나 FR/AC ID로 가리킨다. 같은 뜻을 다른 문장으로 다시 쓰지 않으며, 두 절이 서로를 인용하는 순환을 만들지 않는다.
  5. 미정은 OQ 행 하나: 본문에 "아직 정해지지 않았다"를 쓰지 않고 OQ ID를 붙인다. 결정의 시점·방법·작업 순서는 OQ 행과 가이드가, 결정 자체는 사용자가 소유한다. 기술적 한계(ID 변동 등)는 PRD가 아니라 SPEC 호스트 지원표나 SPIKE 기록에 적는다.

문서 렌더러는 제품 PLAN과 독립적으로 개발한다. 기술 실험은 대응하는 SPIKE-* 기록에 질문·코드 위치·종료 조건을, 목업은 VERIFY-* 기록에 범위·기준 SPEC/Design·코드 위치를 남긴다. 제품 PLAN 이전에도 가능하나 제품 지원 완료로 집계하지 않는다. 제품 코드로 채택할 때는 PLAN의 작업에 연결한다. 실험 기록은 계획과 실제 실행 결과를 구분한다.

03 / 파일 이름 규칙

  • 고정 이름(바꾸지 않음): AI.md CLAUDE.md AGENTS.md Design.md DEVELOPMENT_GUIDE.md docs/PRD.md docs/plans/PLAN.md docs/tdd/TEST_PLAN.md
  • 번호 접두: SPEC-NN-<slug>.md ARCH-NN-<slug>.md PLAN-NN-<slug>.md RESEARCH-NN-<slug>.md ADR-NNN-<slug>.md. NN은 0을 채운다. 한 번 부여한 번호는 재사용·재부여하지 않는다(폐기 시 status: superseded).
  • 날짜 접두: SPIKE-YYYY-MM-DD-<slug>.md VERIFY-YYYY-MM-DD-<scope>.md
  • <slug>와 폴더 이름은 ASCII 소문자 kebab-case. 한국어는 본문에만 쓴다. 공백 금지.
  • 호스트 파일: docs/specs/hosts/<host>.md, <host> ∈ rhino, revit, autocad, zwcad.
  • 고유 기준 문서의 복제본을 다른 폴더에 두지 않는다. 폴더별 README.md와 도구의 필수 파일명은 허용하며 전체 경로로 구분한다. 외부 도구가 요구하는 이름·기존 루트 이름은 소문자 규칙의 예외다.

04 / md / html 짝

  • .md만 원본이다. 같은 폴더·같은 basename의 .html과 루트 index.html은 tools/docs/build.mjs가 만드는 생성물이며 손으로 편집하지 않는다. 생성물 머리에는 GENERATED FILE 주석이 있다.
  • 재생성: npm --prefix tools/docs run build (최초 1회 npm --prefix tools/docs install). 사람이 편집할 때는 run watch, 확인만 하려면 run check(오래됐으면 exit 1).
  • 자동 재생성: Claude Code가 .md를 Edit/Write 하면 .claude/settings.json의 PostToolUse 훅이 재생성한다. git commit 때는 .githooks/pre-commit이 재생성하고 바뀐 HTML을 커밋에 넣는다.
  • pre-commit은 빌드 입력(*.md, tools/docs)의 미스테이징·미추적 파일이 있으면 중단한다. 재생성 후에도 미스테이징·미추적 HTML이 남으면 중단하고 확인·스테이징을 안내한다. 미리 생성해 둔 HTML도 커밋에서 빠지지 않도록 검사한다. 실제 커밋은 사용자 지시가 있을 때만 수행한다.
  • 새 문서는 docs/specs/ docs/architecture/ docs/plans/ docs/research/ docs/tdd/ docs/decisions/에 두면 자동 탐색된다. 상단 탭·설명은 tools/docs/docs.config.json에서 정한다.
  • MD를 고친 에이전트는 HTML을 직접 건드리지 않는다. 훅이 실패하면 위 명령으로 재생성한다.

05 / 검토·첨삭 표기

검토 의견은 문서 안에 직접 표기한다. 별도 리뷰 파일을 만들지 않는다. 검토자는 여럿일 수 있고(Claude, Codex 등) 같은 문서 안에서 스레드로 대화한다.

  • 본문 수정 제안: <del>기존 문구</del><ins>제안 문구</ins>. 추가만이면 <ins>…</ins>, 삭제만이면 <del>…</del>. 표 셀 안에서도 같되 제안 문구에 |를 넣지 않는다. 다른 검토자의 ins/del을 중첩해 고치지 않는다.
  • 코멘트: 대상 문단(또는 표) 바로 아래 한 줄 띄우고 인용 블록으로 쓴다. 지적 하나 = 인용 블록 하나. > **[검토 · <agent> · R-NN · 높음|중간|낮음]** 문제. 제안: … R-NN은 문서별 일련번호이며 검토자 사이에 공유한다. 새 번호는 해당 문서의 기존 최대값 다음이고(해소로 삭제된 번호는 Git 이력에서 확인), 한 라운드(한 검토자의 갱신 커밋)에는 한 검토자만 번호를 부여한다. 부여한 번호는 재사용하지 않는다.
  • 검토자 블록: 각 검토자는 자기 코멘트를 <!-- <agent>-review:start --> … <!-- <agent>-review:end -->로 감싼다. 다른 검토자의 블록과 부록은 수정·삭제하지 않는다.
  • 스레드: 같은 문단에 대한 답변은 상대 블록 아래에 둔다. 갱신한 코멘트는 스레드 끝으로 옮긴다(최신 발언이 마지막). 답변은 라벨 뒤에 **답변 · [<Agent> R-MM](#review-R-MM) · 유지|수정|철회|동의|부분 동의|이견.**으로 시작하고, 본문은 이전 판을 읽지 않아도 되게 자기완결형으로 다시 쓴다.
  • 철회: 지적을 거두면 코멘트를 한 줄 stub로 줄인다 — **철회 · [<Agent> R-MM](#review-R-MM).** 이유. <Agent> 정리 후 이 줄 삭제. 상대가 자기 답변을 닫은 뒤 정리 커밋에서 둘 다 지운다.
  • 부록: 검토 진행 중에는 문서 맨 끝에 검토자당 하나 ## 부록 · <Agent> 검토 요약 (YYYY-MM-DD). 라운드마다 자기 부록을 교체하고 최신 부록이 뒤에 오게 한다. 구성: 총평, 스레드 표(위치 | 자기 ID | 상대 ID | 판단 | 상태), 신규 지적 표, 결정이 필요한 질문, 다음 단계. 표 안에서는 굵은 라벨 대신 링크형 [R-NN](#review-R-NN)만 쓴다.
  • 심각도: 높음 = 다음 문서(SPEC/PLAN)를 막거나 독자를 오도함 · 중간 = 확정 전에 수정 · 낮음 = 다듬기. 갱신 때 심각도는 바꿀 수 있고 ID는 바꾸지 않는다.
  • 해소는 사용자만 한다. 검토·재검토·비교 요청에서 에이전트는 원문과 상대 제안을 보존하고 표기만 추가한다. 동의 판단과 HTML 미리보기는 확정이 아니다. 사용자가 항목이나 범위를 명시해 수락하면 <del>…</del>를 지우고 <ins> 태그만 벗기고 관련 코멘트와 부록 행을 지운다. 거부는 반대로 한다. 사용자가 결정을 말로 내린 항목(예: 제품명)은 본문에 반영하고 해당 코멘트를 철회로 닫는다. 검토 표기가 남아 있는 문서는 status를 approved로 올리지 않는다. 설명용 코드 예제의 태그는 미해결 검토로 세지 않는다.
  • 위임 해소: 사용자가 "합의 항목은 적용하고 이견·확인 항목만 남기라"처럼 범위를 정해 해소를 맡기면, 에이전트는 양측 판단이 일치한 스레드만 본문에 반영하고 그 스레드의 코멘트(양측 블록)를 지운다. 제품 결정(범위·호스트·배포·제품 형태 등)이 걸린 항목은 양측이 동의해도 남기고 관련 ADR을 표시한다. 미해결 항목이 있으면 검토자별 부록을 ## 부록 · 검토 현황 (YYYY-MM-DD) 하나로 합쳐 남은 항목과 필요한 결정만 적는다. 모두 해소되면 검토 부록도 제거한다. 이전 검토와 처리 이력은 Git 이력에 남긴다.
  • 해소 후 정리: 확정된 규칙·결정은 해당 본문에 반영하고, 해소된 코멘트·답변·적용 항목 표·과거 인계 메모는 제거한다. 중요한 결정의 근거는 해당 ADR을 참조한다. AI.md에는 현재 공통 지침만 유지하고 개발 위임·작업 절차는 가이드 §12, 진행 현황은 PLAN §6.5를 참조한다. 미해결 항목은 오래됐다는 이유만으로 삭제하지 않는다.
  • HTML에서는 tools/docs/review.css가 ins를 초록, del을 빨강 취소선, 검토 인용 블록을 검토자별 색(Claude 파랑·Codex 보라) 상자로 그리고, 부록 절·목차의 건수 배지와 검토자 필터를 표시한다. 상단 '첨삭' 메뉴의 원문만·인라인 제안 미리보기는 표시만 바꾸며 코멘트의 대안을 합치지 않는다. 표기 자체는 VS Code 미리보기·GitHub에서도 추가 처리 없이 보인다.

06 / 문서 상태 헤더

PRD·Design·가이드 및 docs/ 아래의 작성 문서에는 맨 위에 YAML front matter를 둔다. AI.md·에이전트 진입 파일·외부 도구의 필수 문서·생성물은 예외다.

YAML
---
id: SPEC-02            # 고정 이름 문서는 PRD / DESIGN / GUIDE / PLAN / TEST
title: 공간 입력 (핀·스케치·코멘트)
status: draft          # draft | review | approved | superseded
version: 0.2
updated: 2026-09-17
owner: user            # 사람 이름 또는 agent:claude 등
related: [FR-05, FR-06, AC-01, OQ-03]
---

상태는 헤더에만 적는다. 색인(README)은 상태를 복사하지 않고 링크만 둔다.

draft는 작성 중, review는 검토 가능한 초안, approved는 명시된 범위의 합의된 기준, superseded는 대체된 문서다. 상태를 단순한 크기 순서로 비교하지 않는다. approved는 구현·시험 완료나 모든 OQ 해결을 뜻하지 않는다. 미결 OQ는 영향받는 작업을 제한하며, 사용자 승인 또는 명시적 위임 범위 안에서만 기준을 확정한다. 문서 의미가 바뀌면 version·updated를 갱신하고, 기존 승인 범위를 바꾸는 미합의 변경은 review로 돌린다.

색인은 INDEX-SPECS, 호스트 문서는 HOST-RHINO 등, 실험·검수 문서는 확장자를 뺀 파일명을 id로 쓴다. 제목·관련 ID는 실제 내용에 맞춘다.

T·SCR·SPEC 세부 항목 번호도 한 번 부여하면 재사용하지 않는다. 참조·실행·개입·적용·저장 상태를 어떻게 나눌지와 그 논리적 의미는 SPEC이, 저장·API의 물리 필드와 전송 형식은 ARCH가 소유한다. 이 파일은 소유 관계만 정한다. 제품 안의 Task와 개발 티켓 T-NNN은 별개다.

08 / 에이전트 규칙

현재 문서 역할·개발 재개 절차는 가이드 §01·§12를 따른다. 현재 티켓에 필요한 조건만 확인하고 후속 기능의 미결로 독립 작업까지 차단하지 않는다.

  • 산출물은 §2의 폴더에만 쓴다. 다음 병렬 문서는 만들지 않는다: MVP_SCOPE.md TECH_DESIGN.md NOTES.md SUMMARY.md, 승인된 ARCH 외의 병렬 아키텍처 정본, 루트의 요약·보고 파일, docs/superpowers/**.
  • PRD의 범위·요구를 바꾸는 미합의 제안은 §5 첨삭 코멘트 또는 ADR 초안으로 낸다. 사용자가 수락 항목이나 범위를 명시해 반영을 위임했으면 그 범위의 수정만 확정하고 근거·변경 내용을 보고한다. 검토·재검토 요청 자체는 위임이 아니다. 미정인 호스트·출시 범위 같은 제품 선택까지 임의로 확정하지 않는다.
  • 빈 자리표시 문서를 만들지 않는다(.gitkeep은 예외).
  • 제품 구현은 사용자의 개발 지시 범위 안에서, PLAN.md가 review 또는 approved이고 해당 티켓이 가이드 §05의 시작 조건을 충족할 때 진행한다. 지시의 적용과 자율 진행 범위는 가이드 §12를 따른다. 합의 전 조건이 첨삭 제안으로만 남아 있으면 해당 구현을 시작하지 않는다. 현재 개발 위임은 가이드 §12와 이후 사용자 지시를 따른다. 현재 티켓에 필요한 미합의 제품 결정·계약이나 환경이 부족하면 그 의존성만 확인하고 독립 작업을 계속한다. 문서 정리 요청은 구현 개시 지시로 해석하지 않는다. 문서 도구·한정된 실험·임시 목업은 §2의 별도 위치를 사용한다.
  • HTML을 손으로 편집하지 않는다. 렌더러 코드(tools/docs/)를 바꿀 때는 이 규약과 어긋나지 않게 한다. AI.md는 사용자 지시 없이 수정하지 않는다(제안은 첨삭으로).
  • 본문은 한국어, 파일명·ID·코드 식별자는 ASCII. UI 문자열·시험 데이터·주석은 내용에 필요한 한국어를 사용할 수 있다. 텍스트는 UTF-8, 줄바꿈은 LF로 저장한다. 기존 문서를 번역하지 않는다.
  • 기존 작업·동시 변경·추적되지 않은 파일은 덮어쓰지 않는다. 비밀키·인증정보·비공개 프로젝트 원본을 저장소나 검수 증거에 넣지 않는다.
  • 에이전트는 사용자의 원본 문서를 호스트(Rhino·ZWCAD 등)로 직접 열지 않는다. 호스트 시험은 .vide/ 아래의 사본이나 합성 문서로 하고, 에이전트가 띄운 호스트는 시험 뒤 종료한다. 에이전트 셸(특히 샌드박스)에서 실행한 호스트는 그 권한을 물려받아 사용자 폴더에 저장하지 못할 수 있으므로 사용자의 실무 창으로 넘기지 않는다. 사용자가 작업할 호스트 창은 사용자가 직접 실행한다.
  • 커밋·push는 사용자가 요청할 때만 한다.
  • 작업 결과·남은 조건·증거·다음 행동은 PLAN §6.5에 갱신한다. 세션 요약은 채팅으로 내고 별도 인계 문서를 자동 생성하지 않는다. 재개·검증·완료 판단은 가이드 §12를 따른다.

구현 착수의 판단 기준 — PRD → SPEC → PLAN

개발 지시는 구현 권한을 주지만 판단 기준을 생략하는 권한은 아니다. 제품 코드를 수정하기 전에 PRD의 요구/목표 → SPEC의 동작·실패 규칙 → PLAN의 변경·검증 항목 → 구현·검증 증거의 연결을 확인한다. 채팅에서 떠올린 방법이나 에이전트의 기억만으로 구현을 시작하지 않는다.

  1. 현재 기준 확인: 해당 작업이 충족할 PRD의 FR/AC 또는 범위 절, 적용할 SPEC 항목, 실행할 PLAN의 티켓/작업 절을 찾는다. 기존 코드·지원표·VERIFY를 대조해 이미 완료한 일과 남은 일을 구분한다. 관련 부분을 읽는 것으로 충분하며 전체 문서를 매번 다시 읽거나 다시 쓰지 않는다.
  2. 누락은 소유 문서에서 먼저 보완: 제품 목표·범위가 바뀌면 PRD 결정이 먼저이고, 허용 동작·입력/출력 의미·권한·실패/복구가 달라지거나 비어 있으면 SPEC을 먼저 보완한다. 기술 구조·스택·물리 계약은 ARCH, 변경 대상·순서·선행 조건·시험·완료 기준은 PLAN에 적는다. PLAN만으로 새 제품 동작을 정하거나 코드 구현 뒤 문서를 끼워 맞추지 않는다.
  3. 실행 가능한 PLAN: 현재 작업에는 최소한 목적/기준 참조, 구체 변경 범위, 선행 조건·미결/외부 조건, 정상·실패 검증 방법, 완료 판단이 있어야 한다. 기존 PLAN에 이 항목이 충분하면 그대로 진행한다. 부족하면 해당 작업 PLAN을 먼저 갱신하고, 마스터 PLAN에는 현재 작업 링크·상태만 둔다. 별도 계획 파일이나 상세 작업 일지를 무조건 추가하지 않는다.
  4. 가벼운 변경과 기반 작업: 기존 SPEC을 만족시키는 작은 버그 수정·리팩터링은 기존 티켓에 변경·검증 항목을 보완하는 것으로 충분하다. Git/CI/포맷 등 개발 기반은 관련 PLAN·ARCH와 완료 기준으로 추적하며 가짜 FR이나 SPEC을 만들지 않는다. UI 변경은 해당 Design 기준도 확인한다. 원인 파악을 위한 읽기·진단은 계획 보완 전에 할 수 있고, 불확실성을 검증할 실험은 §2의 SPIKE 절차를 따른다.
  5. 기준이 부족하면 해당 구현만 보류: 중요한 제품 결정·동작 계약이 미합의이면 영향받는 구현을 추측으로 진행하지 않는다. 필요한 결정과 선택지를 구체화하고 독립 작업은 계속한다. 이미 승인·위임된 범위의 기술 구체화와 계획 보완에는 반복 승인을 요구하지 않는다. 채팅의 새 지시는 기존 문서와 대조하고 영향을 받는 정본에 반영한 뒤 의존 구현을 진행한다.
  6. 진행 중에도 같은 기준 적용: 작업 범위·접근 방법이 달라지면 영향받는 SPEC/ARCH/PLAN을 먼저 갱신한다. 시험 통과는 실제 적용 기준에 대해서만 보고하고 계획·구현·검증 완료를 구분한다. 기준 연결 없이 수정한 사실을 발견하면 후속 구현을 멈춰 기준과 변경분을 대조하고 계획을 보완한다. 이미 작성된 코드를 정당화하려고 요구를 바꾸지 않는다.

착수 보고는 적용할 티켓/계획과 이번 완료 기준을 짧게 알리는 것으로 충분하다. 보고나 문서 갱신 자체를 작업 종료·승인 대기 사유로 삼지 않고, 기준이 갖춰지면 구현·검증·다음 준비된 작업으로 이어간다.

실행 우선 — 작동하는 결과부터 확인

사용자가 요청한 핵심 흐름을 실제 환경에서 빠르게 작동시킨 뒤, 확인된 문제를 바탕으로 수정·최적화한다. 완전한 설계·범용화·성능 최적화를 먼저 끝내야 구현할 수 있다는 순서를 만들지 않는다.

  1. 현재 목표에 필요한 만큼만 계획한다: 기존 PRD·SPEC·PLAN을 기준으로 가장 짧은 구현·확인 경로를 택한다. 부족한 기준은 해당 작업에 필요한 부분만 보완한다. 문서 전면 재작성, 추가 조사, 새로운 승인 절차를 관성적으로 끼워 넣지 않는다.
  2. 완료 조건을 임의로 늘리지 않는다: 사용자가 요청하지 않은 완전성 검사, 전송·표시 상한, 모든 객체·예외의 지원, 향후 확장성 등을 현재 결과의 선행 조건으로 추가하지 않는다. 실제 오류나 필수 플랫폼 제약 때문에 필요한 처리는 그 문제를 해결하는 최소 범위로 한정한다.
  3. 핵심 흐름을 먼저 끝까지 연결한다: 예를 들어 Rhino 객체 표시 요청은 연결 → 실제 객체 조회 → localhost 뷰포트 표시부터 확인한다. 편집용 사본의 검증이나 저장·복원 완결을 단순 조회·표시의 선행 조건으로 삼지 않는다. 실제 적용·저장에 필요한 검증은 그 동작을 수행할 때 적용한다.
  4. 최적화는 관찰한 문제에 맞춘다: 작동 확인 뒤 로딩 시간·메모리·렌더링·지원 범위의 실제 문제를 측정하고 개선한다. 추측으로 제한·추상화·규칙을 늘리거나 같은 검사를 반복해 시간과 토큰을 낭비하지 않는다. 현재 접근이 핵심 결과를 계속 막으면 검사를 덧붙이기 전에 더 단순한 경로를 검토한다.
  5. 빠르게 만들되 결과를 정확히 말한다: 사용자 원본·비밀정보 보호, 권한 경계, 실제 변경·저장의 필수 검증은 유지한다. 작은 자동 검증과 실제 화면·호스트 확인으로 요청한 흐름을 확인하며, 목업·부분 표시·미지원 항목을 전체 성공으로 보고하지 않는다. 독립적으로 작동하는 부분은 제공하고 남은 문제는 구분해 알린다.

중간 보고와 계속 실행

개발을 위임받으면 중간 보고·질문 답변·개별 티켓 완료·테스트 통과·커밋을 턴 종료 사유로 삼지 않는다. 중간 보고는 진행 메시지로 전달하고 같은 턴에서 다음 도구 호출과 준비된 티켓을 계속 수행한다. 전체 위임 범위의 완료 또는 실제 중단 조건은 개발 가이드 §12의 「턴 종료 조건」으로 판단한다. 응답을 끝낸 뒤에도 개발이 백그라운드에서 계속된다고 말하지 않는다.

코드와 작업 파일 정리

  • 파일·함수·컴포넌트는 책임과 변경 이유에 따라 나눈다. 화면·업무 규칙·저장·외부 연동이 한 파일에 섞이거나 독립 시험이 어려워지면 관련 작업에서 분리한다. 줄 수를 맞추기 위한 과도한 파일 분할·추상화·빈 폴더는 만들지 않는다. 구체 구조는 ARCH가 소유한다.
  • 새 파일을 만들기 전에 기존 위치와 재사용 가능성을 확인한다. 루트에 일회성 스크립트·로그·백업 복사본을 쌓지 않는다. 재사용할 실험 코드는 §2의 위치에, 일회성 산출물은 용도가 구분된 임시 디렉터리에 둔다. 캐시·로그·빌드 결과의 경로와 제외 규칙을 명시하며, .gitignore만 추가하고 무제한 누적시키지 않는다.
  • 티켓을 마칠 때 변경·새 파일 목록을 확인하고, 자신이 만든 불필요한 임시 파일·디버그 출력·폐기 코드를 정리한다. 미사용 코드·의존성·파일은 동적 로딩·설정·문서 참조와 재현 필요성을 확인한 뒤 제거하고 관련 검증을 수행한다. 정리를 이유로 무관한 대규모 재구성을 하지 않는다.
  • 출처·용도가 불명확한 파일, 다른 작업자의 변경, 사용자 데이터는 임의 삭제하지 않는다. 추적되지 않거나 오래됐다는 이유만으로 정크로 판단하지 않는다. 삭제·이동 전 실제 대상 경로와 범위를 확인하고, 저장소 전체를 일괄 청소하는 명령은 사용하지 않는다.
  • 문서와 짝인 HTML, 필요한 잠금 파일·마이그레이션·시험 자료, 문서에서 참조하는 검증 증거는 유지한다. 임시 산출물을 증거로 채택하면 필요한 부분만 정해진 위치에 보존하고 참조를 갱신한다.

09 / 플러그인·스킬 경로 덮어쓰기

  • superpowers brainstorming이 쓰는 설계 문서 → 기능 동작이면 docs/specs/SPEC-NN-<slug>.md, 기술 구조면 docs/architecture/ARCH-NN-<slug>.md. docs/superpowers/는 만들지 않는다.
  • superpowers writing-plans → docs/plans/PLAN-NN-<slug>.md. 마스터는 PLAN.md이고 목차는 DEVELOPMENT_GUIDE.md §05를 따른다.
  • 스펙 "커밋" 단계는 사용자가 요청할 때만 실행한다.
  • 문서 작성·검토·첨삭·재배치 작업은 brainstorming 게이트 대상이 아니다. 제품 코드 작성 시 필요한 절차는 이미 합의된 SPEC·PLAN과 현재 사용 가능한 스킬을 기준으로 적용한다. 미설치 플러그인 실행이나 이미 합의한 설계의 반복 승인을 전제하지 않는다.
  • 다른 플러그인이 기본 경로를 가지면 같은 원칙으로 §2에 맞춘다.

10 / CLAUDE.md · AGENTS.md

  • CLAUDE.md는 @AI.md 한 줄이다(Claude Code가 이 파일을 인라인한다).
  • AGENTS.md는 "AI.md를 먼저 읽고 따르라"는 안내문이다(Codex 등은 @ import를 지원하지 않고, Windows에서 심볼릭 링크는 피한다).
  • 두 파일에 다른 규칙을 적지 않는다. Gemini CLI가 필요하면 GEMINI.md에 @./AI.md 한 줄을 둔다.

11 / AI.md를 고치는 때

문서별 권위·진입 경로 또는 공통 형식·에이전트 규칙이 바뀔 때 사용자 지시 범위 안에서 고친다. 개별 기능·화면·기술 선택·진행 현황의 변경은 해당 정본에 기록하고 이 파일에 복제하지 않는다. 수정 권한·승인 조건 자체를 넓히는 변경은 일반 문서 정리 위임으로 확정하지 않고 별도 제안한다. 고칠 때 맨 위의 버전·날짜를 올린다.

실행 계획의 수명

마스터 PLAN에는 단계·의존성·작업 링크·현재 상태·전체 완료 기준만 유지한다. 작업 계획은 해당 작업의 변경 범위·선행 조건·검증·완료 기준을 소유한다. 기술 계약은 ARCH, 조사 원문은 RESEARCH, 선택은 ADR, 실제 결과는 VERIFY/SPIKE로 연결하며 마스터에 복제하지 않는다. 완료 시 기존 상태를 갱신하고 새 이력 절을 계속 추가하지 않는다. 이전 문서 ID는 재사용하지 않으며 이전 안내는 짧게 유지한다.
